# Требования к новому коду и выкату: масштабирование и обновления без простоя

2026-10-14 · Маус · **требования, которые Томас просил обязательно предусмотреть при
проектировании** (решение 2026-10-14). Не архитектура и не план реализации: это
ограничения на то, как писать и выкатывать новый код, чтобы позже не переделывать.
Связано: [mvp-readiness-map.md](mvp-readiness-map.md) (двери),
[stage-2-architecture-clean-sheet.md](stage-2-architecture-clean-sheet.md) (принцип P8:
горизонтальное масштабирование не требование Stage 2, но существующее не ломаем).

## 1. Что такое масштабирование и что в нём копируется

- **Вертикальное:** сервер мощнее. Просто, но предел и один «ящик».
- **Горизонтальное:** **несколько копий приложения** за балансировщиком; лишние гасятся, когда
  нагрузка спала.
- **Копируется только слой приложения.** **База данных не копируется:** все копии работают с
  одной общей базой (и общими Redis, очередью, хранилищем файлов). Именно база обычно
  становится узким местом, а не приложение.
- Новый сервер на каждую копию не обязателен: чаще это несколько копий на одной-двух машинах.
- Для закрытой группы (около 10 проектов) масштабирование **не требуется**. Задача — не
  закрыть дорогу.

## 2. Семь правил для нового кода

| #   | Правило                                                                                             | Зачем                                               | Как проверять                                                               |
| --- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------- |
| 1   | **Нет состояния в памяти процесса,** кроме ограниченных кэшей с источником правды в общем хранилище | иначе вторая копия «не знает», что сделала первая   | запуск двух копий; сценарий, меняющий состояние в одной и читающий в другой |
| 2   | **Фоновые задачи безопасны при двух копиях** (блокировка строк, идемпотентность)                    | без этого дубли рассылок и двойная работа           | две копии одновременно; проверка отсутствия дублей                          |
| 3   | **Файлы в объектном хранилище,** не на диске сервера                                                | копия на другой машине не видит чужой диск          | загрузка через одну копию, чтение через другую                              |
| 4   | **Настройки и секреты из окружения,** не вшиты в сборку                                             | один образ для любой среды                          | сборка одним артефактом и запуск с разными настройками                      |
| 5   | **Аккуратное завершение:** копия доделывает запросы и только потом гаснет                           | иначе обрыв запросов при обновлении                 | перезапуск под нагрузкой: ноль оборванных запросов                          |
| 6   | **Проверки «жив» и «готов»** для балансировщика                                                     | не пускать трафик на копию, которая ещё запускается | остановка зависимости; копия сообщает «не готова»                           |
| 7   | **Изменения базы только добавлением** (см. раздел 3)                                                | старая и новая версия живут на одной схеме          | миграция при работающей старой версии                                       |

## 3. Обновления без перерыва

Идея: **новая версия поднимается рядом со старой, трафик переключается, когда она готова.**

1. **Минимум две копии ядра** за балансировщиком (nginx у нас уже есть). Обновление по одной
   (rolling) или переключение разом (blue-green).
2. **Миграции базы в три шага:** (а) добавить новое, старый код продолжает работать;
   (б) перенести данные; (в) убрать старое отдельным обновлением. «Только вперёд» у нас уже
   принято и хорошо ложится, но **каждая миграция пишется так, чтобы старая и новая версия
   кода работали на одной схеме.** Опасные шаги (удаление) — отдельно и с резервной копией.
3. **Совместимость API на период перехода:** у человека может быть открыта вкладка со старым
   интерфейсом; старые запросы должны работать ещё какое-то время.
4. **Интерфейс отдаётся статикой с версионированными файлами,** чтобы браузер не держал старое.
5. **Флаги функций:** новое выкатывается выключенным и включается отдельно (механизм флагов
   у нас есть).
6. **Откат:** вернуть прежнюю версию кода; возможно, потому что схема менялась только добавлением.
7. **Сессии не привязаны к копии:** вход через внешний провайдер, токены; ничего не теряется
   при смене копии.

## 4. Как это у нас сейчас (читал код и скрипт выката; запуска двух копий не было)

| Что                                               | Состояние                                                                                                                              |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Рассылка событий и вебхуки                        | **безопасны при двух копиях:** `FOR UPDATE SKIP LOCKED`                                                                                |
| Ограничители входа                                | в Redis (общие)                                                                                                                        |
| Корректное завершение                             | есть обработка `SIGTERM` и закрытие подключений                                                                                        |
| Проверка живости                                  | есть контроллер здоровья                                                                                                               |
| Кэш прав в памяти (рубеж действительности сессий) | короткий, источник правды в базе, задержка названа числом: допустимо                                                                   |
| Фоновые таймеры внутри процесса                   | три (события, вебхуки, обслуживание партиций): блокировки есть у первых двух; у обслуживания партиций — операция по смыслу повторяемая |
| **Ядро не в контейнере**                          | в Docker только инфраструктура (база, Redis, очередь, хранилище, nginx, вход); ядро — служба сервера, **Dockerfile нет**               |
| **Выкат**                                         | резервная копия базы, сборка на сервере, **перезапуск службы — простой на секунды**, затем проверка маршрутов                          |

## 5. Ступени (предложение)

| Когда                               | Что                                                                                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Сейчас** (закрытая группа)        | один сервер; перезапуск на секунды с предупреждением; резервные копии и **проверенное восстановление**; новый код — по семи правилам |
| **Когда простой станет неприемлем** | ядро в контейнер (один Dockerfile), две копии за nginx, обновление по одной; без оркестратора                                        |
| **Когда реальная нагрузка**         | автомасштабирование: управляемая платформа контейнеров или Kubernetes; управляемая база с репликами                                  |

При модели «один человек + агенты» **Kubernetes не брать, пока нет настоящей нужды:** это
отдельная работа. Предпочитать управляемые сервисы, дешёвые по вниманию.

## 6. Что решить Томасу

1. Принять семь правил как **требования к новому коду Stage 2**.
2. **Целевой простой для закрытой группы:** допустимы секунды при обновлении с
   предупреждением или нужно «без перерыва» уже сейчас.
3. **Когда контейнеризировать ядро** (условие, а не дата): например, при первом требовании
   «обновления без простоя» или при переносе на новый сервер.

## 7. Чего не проверено

- Две копии ядра не запускались; нагрузочных измерений нет; оценки по чтению кода.
- Поведение фоновых таймеров при двух копиях проверено только по описанию блокировок.
- Стоимость и пределы конкретных управляемых платформ не исследовались.
- Совместимость старого интерфейса с новым API при обновлении — требует отдельного теста
  в сценариях приёмки.
