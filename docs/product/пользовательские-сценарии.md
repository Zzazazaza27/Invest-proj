# Пользовательские сценарии

Не ТЗ, а список сценариев для совместной проработки: по ним проходят руками и
фиксируют, что именно пользователь должен видеть и уметь на каждом шаге. Из
этого собирается продуктовый бэклог.

Зачем отдельно от прогонов. В репозитории сотни проверок, и почти все отвечают
на вопрос «правильно ли отвечает сервер». Ни одна не отвечает на вопрос
«понимает ли человек, что делать дальше» — даже браузерные `render-check-*`
смотрят, что элемент отрисовался, а не что путь через экраны связен. Первый же
живой проход кабинета основателя это подтвердил: заявку можно подать пустой, а
кабинет пускал к себе чужую роль — при полностью зелёных прогонах.

Источник — постановка владельца, перенесена без правок. Ход проработки и
находки идут в `TODO.md`.

Это не ТЗ, а список пользовательских сценариев для совместной проработки. Предлагаю по ним пройтись и по ходу фиксировать, что именно должен видеть и уметь пользователь на каждом шаге. Из этого уже соберём нормальный продуктовый backlog/ТЗ.

1. **Новый основатель с нуля.**
   Заходит на витрину → понимает, что это вообще такое → регистрируется именно как founder → принимает обязательные согласия → попадает в свой кабинет → создаёт первый проект → заполняет его → загружает материалы → понимает, что делать дальше → запускает AI-анализ/скоринг → видит результат → исправляет проект → понимает, как довести его до публикации.
   У founder-интерфейса уже есть отдельные страницы проектов, проекта, материалов, биллинга и публичных согласий — значит, именно связность между ними сейчас и надо проверять.

2. **Основатель хочет реально опубликоваться.**
   Создал проект → указал сумму привлечения → система предложила/потребовала тариф → оформил подписку → прошёл KYC или понял, почему не может идти дальше → отправил проект → получил статус → увидел, что именно блокирует публикацию.
   Тут особенно важно проверить не «endpoint работает», а чтобы пользователь **никогда не оказывался в тупике без объяснения следующего действия**.

3. **Новый инвестор.**
   Витрина → регистрация как investor → verification → подписка → каталог → фильтрация/поиск → карточка проекта → интерес/предложение → дальнейшее действие.
   У инвестора уже явно существуют страницы `Catalog`, `Verification`, `Subscription`, `Offers`, `Billing`.
   Вот их надо пройти как один фильм, а не пять отдельных экранов.

4. **Founder ↔ Investor — первый настоящий cross-role сценарий.**
   Это я бы вообще считал главным тестом проекта.
   Founder создаёт и публикует проект → Investor реально видит его в каталоге → открывает → проявляет интерес/создаёт предложение → Founder получает это событие → понимает, что произошло и что делать дальше.
   Если эта цепочка ощущается цельной — у вас уже есть продукт. Если разваливается — все 444 теста можно пока положить на полку.

5. **Эксперт.**
   Админ/система назначает эксперта → эксперт логинится → видит назначение → получает ровно те материалы, которые должен видеть → заявляет конфликт или начинает review → выставляет оценки/заключение → Founder видит результат и понимает, что с ним делать.
   Особенно проверить отрицательные ветки: конфликт интересов, пропущенные поля, возврат на доработку.

6. **Админ как оператор платформы.**
   Не «посмотреть красивую админку», а прожить рабочий день: новый пользователь → KYC queue → новый проект → модерация → назначение эксперта → тариф/подписка → зависший кейс → ручное вмешательство.
   Вопрос простой: **может ли один реальный оператор понять состояние системы и исправить проблему без API-console?**

7. **Юрлицо / KYB.**
   Founder или investor говорит «я действую от компании» → заводит юрлицо → вводит ИНН/данные → запускает KYB → видит статус → после проверки получает доступ к соответствующему сценарию. README говорит, что это уже вынесено в кабинеты.
   Здесь я бы особенно смотрел на понятность языка — там легко сделать юридический интерфейс, который понимает только автор базы.

8. **Деньги и отключённые функции.**
   У вас платёжный провайдер ещё не подключён, и README прямо говорит, что `billing.payments.enabled` выключен, а маршрут должен честно сообщать `feature_disabled`.
   Надо пройти руками: пользователь нажимает «оплатить» → что он видит? Не технический `503`, а нормальное продуктовое состояние вроде «Оплата пока недоступна / мы сообщим». То же касается регулируемого инвестиционного контура, который выключен до юридического гейта.

9. **Восстановление доступа.**
   Забыл пароль → запросил письмо → получил ссылку → поменял пароль → старые сессии умерли → новый вход работает.
   Пока почтового транспорта нет, проверить ещё и то, как интерфейс объясняет невозможность отправки, потому что backend специально не притворяется, что письмо ушло.

10. **Дурак-пользователь.**
    Это очень важно. Не заполняет обязательное, жмёт два раза, обновляет страницу посреди процесса, идёт назад, открывает URL напрямую, пытается зайти не в свой кабинет, грузит не тот файл, слишком большой файл, повторно создаёт действие.
    Ваш backend, судя по всему, уже сильно защищён. Теперь надо проверить, **не выглядит ли эта защищённость для пользователя как “ничего не произошло”**.

В целом, простое правило тестирования каждого сценария:

**На каждом экране пользователь должен понимать три вещи:**
**где я → что сейчас происходит → что я могу/должен сделать дальше.**

Если хотя бы одного ответа нет — это новая задача для разработки
