# Этап 5.9 — монетизация: что сделано, что структурно, что выключено, чего нет

Сводка на 2026-09-19 (этап 5.9.6). Назначение документа — одно: чтобы можно
было честно ответить, что сегодня работает, а что только выглядит
работающим. Текущее состояние продукта целиком — в
`руководство-по-продукту.md`; история — в `журнал-изменений.md`.

**Два разных расчёта, которые нельзя смешивать.** В этапе 5.9 их два, и они
не связаны ни входом, ни правилами:

1. **стоимость запуска раунда** — разовая плата основателя за запуск
   конкретного раунда: пакет по диапазону суммы запроса плюс докупленные
   услуги (`computeRoundQuote`);
2. **вознаграждение платформы** — комиссия с КАЖДОГО подтверждённого транша
   по договору: общая ставка и её распределение между сторонами
   (`billing.confirm_tranche`).

Первое платит основатель до привлечения; второе возникает, когда деньги
фактически поступили. Ни один порог, ни одна настройка уведомлений на эти
расчёты не влияет.

## 2. Реализовано структурно (API и БД есть, интерфейса нет)

Схема, правила целостности и проверки существуют; сценарий нельзя пройти в
браузере.

- **Покупка запуска раунда**: таблицы `billing.round_purchases` и
  `round_purchase_items` со снимком условий и денежной базой позиций. Записей
  никто не создаёт — ни API, ни экрана (см. §5).
- **Функциональные полномочия сотрудника**: каталог и выдача есть, работают
  через API (`/v1/admin/capabilities/...`); экрана с галочками нет.
- **Назначение на сопровождение сделок**: API есть
  (`/v1/admin/capabilities/deal-support`), экрана нет.
- **Уведомления команде по порогу**: см. §3 — события записываются, внешней
  доставки нет.
- **Возможности инвестора для его кабинета**: `GET /v1/me/plan-capabilities`
  отвечает, что доступно и почему; кабинет инвестора этим пока не
  пользуется.

## 3. Выключено до продуктового решения

Механизм есть, но включать его нельзя, и запрет стоит в базе, а не в
договорённости.

| Что                                        | Почему выключено                                                            | Что снимет запрет                                      |
| ------------------------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------ |
| Продажа пакетов запуска раунда             | `paidPackages.enabled` = false в условиях страны                            | решения из §5                                          |
| Бесплатная граница привлечения             | база учёта не определена; включённая настройка даёт отказ (fail-closed)     | решение «по раунду или накопительно»                   |
| Зачёт оплаченных услуг в комиссию          | правило зачёта не утверждено; запись зачёта запрещена триггером             | правило (получатель, покрытие, распределение, остаток) |
| Платные ограничения возможностей инвестора | матрица бесплатного и платного не утверждена; `is_enforced` включить нельзя | матрица                                                |
| Приём платежей                             | провайдера нет; `POST /v1/billing/payments` отвечает «функция выключена»    | решение о провайдере и моменте оплаты                  |
| Контур сделок                              | выключен флагом `investments.instrument.loan`                               | отдельное решение владельца                            |

**Уведомления команде — отдельно и точно.** События **записываются**:
открытие раунда с суммой не ниже порога создаёт запись
`comms.operator_notifications` с получателями из настройки, один раз на
событие. **Внешняя доставка не реализована и не включена:** письма никуда не
уходят, транспорт фиксируется в самой записи (локально `none`). Называть это
«отправкой уведомлений» нельзя — это журнал событий, который прочитает
администратор.

**Что порог НЕ делает.** Он не влияет ни на стоимость запуска раунда, ни на
вознаграждение с траншей — это разные расчёты, и порог не входит ни в один
из них. Он не меняет доступ и не делает участие оператора обязательным:
`manualReviewRequired` — отдельная настройка.

## 4. Не реализовано вовсе

- **Оформление покупки**: выбор пакета и услуг основателем, создание
  покупки, счёт, подтверждение оплаты — ни API, ни экрана.
- **Выполнение оплаченных услуг**: в каталоге у услуги есть признак «услуга
  реализована в продукте», но состояния «эта услуга по этой покупке
  выполнена» нет — ни поля, ни процесса.
- **Гейт открытия раунда по оплате**: сегодня платный режим просто
  отказывает («оплата запуска ещё не реализована»); проверки «покупка
  оплачена — открывай» нет.
- **Возврат начисленного при возврате транша автоматически**: сознательно
  нет — см. §6, это ручная процедура по решению владельца.
- **Кабинет инвестора по возможностям тарифа**: список возможностей есть,
  интерфейс их не показывает.
- **Экраны для отложенного**: выдача полномочий галочками, назначение
  сопровождения, распределение экспертных заданий.

## 5. Что осталось до сквозного сценария

Сценарий: **выбрать пакет → оформить покупку → подтвердить тестовую оплату →
выполнить условия → открыть раунд.**

Отсутствующие шаги, по порядку:

1. **Выбор пакета основателем сохраняется.** Сейчас выбор живёт только в
   параметрах запроса расчёта и нигде не хранится. Нужно место для
   незавершённого выбора (черновик покупки) или создание покупки сразу.
2. **Создание покупки** — сервис и API: снимок условий, позиции, сумма из
   `computeRoundQuote`, а не из тела запроса. Структуры готовы (M095).
3. **Счёт и тестовое подтверждение оплаты.** Счета (`billing.invoices`)
   существуют; приёма платежей нет и не будет до решения о провайдере.
   Нужен путь «администратор отмечает счёт оплаченным» — тот же, что уже
   используется для подписок, — и перевод покупки в `paid`.
4. **Отметка выполнения услуг по покупке.** Нужно состояние на позиции
   покупки: запланировано / выполнено / не выполнено, с автором и датой.
5. **Гейт открытия.** `assertCommercialConditions` должен пропускать раунд,
   когда для него есть оплаченная покупка, покрывающая требуемый пакет, — и
   отказывать иначе. Сейчас платный режим отказывает всегда.
6. **Экран покупки в кабинете** и её состояние в карточке раунда.

**Решения, без которых эти шаги действительно нельзя закончить** (остальное —
настройки, которые задаются в админке и разработку не блокируют):

- **Момент оплаты**: до открытия раунда или после; можно ли открыть раунд с
  неоплаченной покупкой. Без этого шаг 5 не формулируется.
- **Границы оплаченного раунда**: срок действия покупки, что происходит при
  паузе и возобновлении, при увеличении суммы с переходом в другой диапазон
  (доплата, пересчёт, ничего). Без этого шаги 2 и 5 не закончить.
- **Что считать доступным улучшением пакета**: сейчас работает временная
  техническая проверка «состав включает весь состав требуемого»; для покупки
  нужен утверждённый способ (явные альтернативы в админке).
- **Возврат покупки**: возможен ли возврат оплаты запуска и на каких
  условиях. Нужен до включения продаж, не раньше.

**Не блокируют:** конкретные цены пакетов, ставки вознаграждения и состав
услуг — это настройки, которые задаются в админке версиями и меняются без
релиза.

## 6. Возвраты и корректировки: что уже решено

Чтобы не перечислять это как открытый вопрос.

**Согласовано и реализовано** (решение владельца 2026-09-19):

- возврат по траншу фиксируется ВРУЧНУЮ как запись о состоявшемся событии:
  сумма, валюта, дата, основание, подтверждение, автор. Платформа денег не
  перечисляет;
- возвраты частичные, в сумме не больше подтверждённого транша; повторная
  отправка не создаёт дубликат; исходный транш сохраняется; ошибочная запись
  аннулируется с основанием;
- возврат инвестиции сам по себе комиссию НЕ отменяет;
- корректировка вознаграждения — отдельная запись, и уменьшение начисления
  отличается от фактического возврата уже уплаченного;
- обсуждение возврата, фиксация факта и корректировка комиссии — три разных
  полномочия.

**Что осталось решить именно по возвратам** (конкретно, а не «возвраты
траншей вообще»):

- **обязан ли оператор оформлять уменьшение начисления** при возврате
  транша, и в каких случаях: всегда, при полном возврате, по усмотрению;
- **сопровождается ли возврат уплаченной комиссии реальным перечислением** —
  сейчас это только запись о факте;
- **возврат оплаты запуска раунда** (не транша) — см. §5.
