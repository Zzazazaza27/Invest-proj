### Осознанно отложено (решения Томаса 2026-10-12)

Это **не незавершённые ошибки переноса**, а вопросы, которые решаются позже.

1. **Перевод тестового сервера на новый репозиторий — отложен до реального
   проектирования и развёртывания Stage 2.** Тестовый сервер сейчас в
   работе практически не нужен и не трогается: он по-прежнему смотрит в
   старый репозиторий. При возврате к теме отдельно решается **топология
   окружений**: станет ли существующий сервер production; остаётся ли он UAT;
   появится ли отдельный production-сервер; либо UAT и production будут
   изолированно работать на одной машине. Тогда же: ключ развёртывания только
   для чтения в новом репозитории (команды — раздел 7), сверка `deploy.mjs`
   (`git fetch origin main` теперь указывает на новый `origin`), ротация
   секретов (раздел 6).
2. **Защита `main` не настраивается: GitHub Pro сейчас не покупается.**
   Branch protection и rulesets недоступны для приватного репозитория на
   бесплатном аккаунте (GitHub: «Upgrade to GitHub Pro or make this repository
   public»). Сейчас `main` без серверной защиты: CI и секрет-скан запускаются
   на push, но не блокируют слияние и прямую отправку. **Открытый вопрос:** при
   проектировании автономной разработки вернуться к server-side protection,
   обязательным проверкам, прямой отправке в `main` и правам агентов. Если
   выбранная архитектура потребует полноценной защиты приватного `main` —
   рассматривается GitHub Pro.

## 10. После проверки: локальные remotes

```bash
git remote rename origin legacy
git remote rename stage2 origin
git branch -u origin/main main
git remote set-url --push legacy DISABLED   # legacy только для чтения
```

Старый `origin` остаётся **доступным для `fetch`**, но отправка в него
блокируется. Архивировать или закрыть сам старый репозиторий может только его
владелец (`artem141414`): Томас может об этом попросить, но не сделать.

**Безопасный вариант для старого адреса (рекомендация):** оставить его
локально под именем `legacy` с заблокированной отправкой. Он ничего не стоит
и даёт возможность сверить хэши и быстро вернуться; удалить можно в любой
момент командой `git remote remove legacy`, ничего не теряя в новом
репозитории. Удалять сразу не стоит: пока сервер и привычные команды не
переведены на новый адрес, `legacy` страхует от ошибок.

## 11. Порядок и откат

1. Подтверждения (раздел 8).
2. Создать пустой репозиторий (внешнее действие, нужно слово Томаса).
3. Отправить `main` и четыре тега (`pre-stage-2`, три `stand-*`).
4. Проверка: хэши, ручной CI, секрет-скан.
5. Настроить Actions, защиту `main`, ключ развёртывания.
6. Сервер: сменить адрес `origin`, пробный выкат `npm run deploy -- --dry-run`.
7. Переименовать remotes (раздел 10).
8. Ротация секретов (раздел 6).
9. Через ~2 недели спокойной работы — решить судьбу старого репозитория.

**Откат на любом шаге:** старый репозиторий не меняется, поэтому можно
вернуться к нему простым `git remote` без потерь. Опасных шагов нет. После
отправки проверяются: совпадение хэшей коммитов (`git ls-remote`), наличие
`main` и четырёх тегов, зелёный ручной запуск CI на новом репозитории.
