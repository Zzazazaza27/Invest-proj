# Stage 2 Architecture — clean-sheet proposal

2026-10-12 · Маус · по постановке Томаса и Тэнка (идея 093) и поправкам Томаса.
**Статус: предложение для обсуждения. Ничего не реализуется.**

Построено из текущей продуктовой постановки, а не из старых ADR. ADR-001…008
и документы-основания (`Architect*.md`, `Database_Launch.md`) написаны
предыдущим исполнителем до принятия проекта Томасом, под другую постановку
(регулируемый оператор, сделка в центре, команда разработки). Они **не
ограничения** для Stage 2: используются только в разделе 8 как справка для
понимания существующего кода. Прежний файл
[stage-2-adr-provenance-milestones.md](stage-2-adr-provenance-milestones.md)
— рабочие заметки; «метки» ADR в нём не являются решениями.

Порядок документа: постановка → требования → архитектура с чистого листа →
сравнение с существующей реализацией.

## 1. Продуктовые инварианты

Что должно оставаться истинным, как бы ни менялась реализация.

1. **Центр — проект и его жизнь**, а не сделка. Инвестиция — один из видов
   взаимодействия вокруг проекта. Проект существует и без неё.
2. **Любой проект.** От вышивки до проекта на миллион: никакая обязательная
   сумма, стадия или отрасль не определяет, «настоящий» ли это проект (082).
3. **Четыре стороны вокруг проекта:** основатель, инвестор, партнёр,
   наблюдатель. Один человек в разных проектах — в разных ролях.
4. **Цикл:** проект → история и состояние → внимание → участие →
   потребность/запрос → отклик → взаимодействие → результат/событие →
   изменение состояния проекта → следующий цикл.
5. **Платформа — инфраструктура и доверительный слой.** Ценность создают
   участники. Платформа может сама создавать автоматическую ценность (анализ,
   подбор, проверки), но **рост ценности не должен требовать пропорционального
   роста человеческого внимания** операторов.
6. **Честность происхождения.** Показанное людям не выдаётся за больше, чем
   оно есть: «сообщено человеком» ≠ «зафиксировано платформой».
7. **Долговременная история проекта** — вехи, а не обязательный постинг.
   Ленты и мелкие обновления — позже, если использование покажет нужду.
8. **Настоящих платежей нет** (оператор не выбран, оплата тестовая).
9. **Не только Россия:** Россия — место старта, а не потолок.
10. **Эксплуатируется одним человеком и агентами;** критические решения —
    человек.
11. **Минимальная достаточность.** Сущности появляются, когда возникает
    реальная продуктовая необходимость; Stage 2 нужен, чтобы выяснить, какие
    из них фундаментальны.

## 2. Минимальные архитектурные принципы

Каждый — следствие инварианта; указано, какого.

| #   | Принцип                                                                                                                                                                                            | Из чего следует  |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| P1  | **Проект — самостоятельная сущность** без обязательных инвестиционных, денежных или тарифных полей. Всё инвестиционное — отдельное, привязанное к проекту                                          | 1, 2, 8          |
| P2  | **Роль принадлежит участию в проекте**, а не учётной записи. У человека одна учётная запись и много участий в разных ролях                                                                         | 3                |
| P3  | **Что показывается людям как история — только дописывается.** Исправление — новая запись со ссылкой на прежнюю, не правка                                                                          | 6, 7             |
| P4  | **У каждого действия есть действующий и его тип** (человек, агент, система, интеграция)                                                                                                            | 10, 6            |
| P5  | **Event, milestone и provenance — разные вещи** (раздел 4)                                                                                                                                         | 6, 7             |
| P6  | **Автоматически рассчитанное помечено как рассчитанное.** Подбор, анализ, оценки — производный слой над фактами: пересчитываемый, версионный, никогда не подменяющий факт                          | 5, 6             |
| P7  | **Один основной тип хранилища на старте** (реляционная база; гибкая часть — JSONB-поля), **одно приложение со строгими границами модулей**; вынос части — когда нагрузка это докажет, а не заранее | 10, 11           |
| P8  | **Экземпляры приложения без состояния:** сессии, кэши и блокировки — вне процесса; фоновые задачи не дублируются при нескольких копиях; файлы — вне базы                                           | 10, «массовость» |
| P9  | **Один типизированный внешний интерфейс (API)**; интерфейсы заменяемы, правила не живут во фронтенде                                                                                               | 10, 11           |
| P10 | **Эксплуатация воспроизводима командой:** выкат, откат, резервирование, диагностика — без ручных шагов; агентам — узкие права, журнал, выключатель                                                 | 10               |

## 3. Минимальная модель сущностей для первого dogfooding

Вопрос не «какую полную модель мира можно придумать», а «чего достаточно,
чтобы ~10 реальных проектов начали жить внутри системы и мы увидели
настоящее использование». Всё ниже — **рабочая гипотеза**.

| Сущность          | Что это                                                                                                                   | Статус                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **Person**        | человек: вход, минимальный профиль                                                                                        | нужна                                                                                                         |
| **Project**       | название, суть, по желанию стадия и страна, видимость; **без суммы и тарифа**                                             | нужна                                                                                                         |
| **Participation** | человек в проекте: роль (основатель, участник команды…), состояние (приглашён / принял / вышел), период                   | нужна                                                                                                         |
| **Request**       | проект сообщает, что ему нужно: свободный тип и текст, статус                                                             | нужна                                                                                                         |
| **Response**      | отклик на запрос: кто, что предлагает, статус                                                                             | нужна                                                                                                         |
| **Event**         | что произошло: действующий (с типом), субъект, вид, время, подробности. Дописывается; служит и журналом, и сырьём для вех | нужна                                                                                                         |
| **Milestone**     | существенное изменение истории проекта (раздел 4)                                                                         | нужна                                                                                                         |
| **Feedback**      | «не смог / неудобно / хочу» в один клик                                                                                   | нужна (возможно, на готовом механизме обращений)                                                              |
| **Notification**  | уведомление в кабинете о событии, касающемся человека                                                                     | нужна как доставка, не как предметная сущность                                                                |
| Follow (подписка) | человек следит за проектом                                                                                                | **гипотеза**: проверяем, нужен ли наблюдатель как отдельная сторона. Реализуется простейше                    |
| Organization      | компания/фонд как участник                                                                                                | **гипотеза**: на старте — название текстом; сущность появится, если люди захотят действовать «от организации» |
| Confirmation      | подтверждение факта другим источником                                                                                     | **не создаётся** (см. ниже)                                                                                   |

Не входят: ресурс, инвестиционная деятельность, программа партнёра, платное
предложение, баллы и кредиты, рейтинг и репутация.

**Нужна ли пустая таблица Confirmation: нет.** Веха будет иметь неизменный
идентификатор, а исправления только дописываются. Значит, подтверждение можно
добавить позже **новой таблицей, ссылающейся на веху**, без переделки уже
накопленных данных. Пустая таблица была бы заготовкой под ненаблюдаемую
модель. Условие, при котором дверь закроется: если вехи начнут изменяться на
месте или потеряют стабильный идентификатор — поэтому эти два свойства
фиксируются как принцип (P3), а не как таблица.

## 4. Actor / Event / Milestone / Provenance

| Понятие        | Отвечает на вопрос                                         | Свойства                                                                                                                                      |
| -------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Actor**      | кто действовал                                             | тип (человек / агент / система / интеграция) + идентификатор. Список типов открыт                                                             |
| **Event**      | что произошло                                              | действующий, субъект, вид события, время, подробности. Только дописывается. Ориентирован на точность и наблюдаемость, не на показ             |
| **Milestone**  | что существенно изменилось в истории или состоянии проекта | отобрано для показа людям; свои заголовок, описание, видимость, «когда произошло». **Не равно событию**; может быть итогом нескольких событий |
| **Provenance** | откуда известно                                            | кто сообщил, источник, на каком основании, когда произошло, когда записано                                                                    |

**Provenance на старте — два происхождения:**

- **сообщено человеком** (действующий — человек; основание — необязательная
  ссылка или текст);
- **зафиксировано действием платформы** (действующий — система; основание —
  ссылки на события, из которых это выведено).

**Не каждое событие — веха.** Примеры по Томасу:

| Что произошло                                              | Событие | Веха      |
| ---------------------------------------------------------- | ------- | --------- |
| на запрос пришёл отклик                                    | да      | нет       |
| обновлена презентация                                      | да      | нет       |
| участник присоединился к проекту                           | да      | кандидат  |
| запрос закрыт реальным результатом                         | да      | кандидат  |
| первый клиент, запуск, новый рынок, начало/закрытие раунда | да      | кандидаты |

**Одна веха — из нескольких событий.** Цепочка «создан запрос → получены
отклики → выбран человек → человек принял приглашение» даёт **одну** веху
«К проекту присоединился разработчик», с основанием в виде ссылок на эти
события. Веха — не красивая обёртка журнала действий.

**Как возникают вехи в первом L2 (предположение):**

- платформа имеет **короткий список правил в коде** («приглашение принято» →
  веха «присоединился», «запрос закрыт с выбранным откликом» → веха) — три-
  четыре правила, не каталог и не настраиваемая система;
- человек добавляет веху вручную (запуск, первый клиент и т. п.);
- какие вехи реально считаются значимыми — **покажет dogfooding**; вид вехи —
  открытое поле, а не фиксированный список.

**Откуда видна история подписчику:** лента «что изменилось» — представление
над вехами (и ответами на запросы), а не отдельная лента постов.

## 5. Дешёвые двери, которые стоит оставить сейчас

Критерий: стоит копейки сейчас и дорого, если закрыть. Каждая — с ценой отказа.

| Дверь                                                             | Что значит                                                     | Цена, если закрыть                                                   |
| ----------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| Идентификаторы без общего счётчика (UUIDv7)                       | записи создаются независимо, без пересечений                   | менять ключи в живой базе                                            |
| Тип действующего в каждом Event                                   | человек / агент / система                                      | не отличить действия агентов от человеческих в истории               |
| Event и Milestone только дописываются; исправление — новая запись | история не переписывается                                      | потеря честности истории; невозможность позже добавить подтверждения |
| «Когда произошло» отдельно от «когда записано»                    | человек может указать дату события; время записи ставит сервер | перерасчёт исторических данных                                       |
| Роль на участии в проекте                                         | один человек — разные роли в разных проектах                   | перепроектирование кабинетов и доступа                               |
| Открытые «вид» и «тип» (текст + JSONB)                            | новые вехи и запросы без миграции                              | миграция на каждый новый вид                                         |
| Страна, язык, валюта — поля, а не константы                       | не только Россия                                               | массовая правка кода и данных                                        |
| Приложение без состояния в процессе                               | запуск нескольких копий                                        | переписывание хранения сессий и фоновых задач                        |
| Файлы вне базы                                                    | рост без раздувания базы                                       | перенос файлов позже                                                 |

**Двери, которые я проверил и отклонил:** пустая таблица подтверждений;
цели и согласия внутри provenance (другая ось, P12); сегментирование базы;
отдельный поиск; подготовленные ленты. Все они добавляются позже без
болезненной переделки, если принципы P3–P8 соблюдены.

## 6. Что мы сознательно не проектируем

- L1: «sensorium», «actuation», универсальный граф, главный автономный
  агент, машинная модель состояния рынка.
- Внутренняя валюта, журнал баллов и кредитов, глобальный рынок ресурсов.
- Системы доверия: веса источников, репутация, рейтинг, реестр «кто вправе
  подтверждать», очереди верификации.
- Социальная лента, посты, лайки, мелкие обновления.
- Подбор, рекомендации, поиск связей как функции (они придут как
  автоматическая ценность, когда будут данные).
- Платные предложения, программы партнёров, кабинеты партнёра и наблюдателя
  как отдельные приложения.
- Рассылки наружу, микросервисы, вторая база данных, инфраструктура под
  миллиард.
- Юридический контур данных: цели обработки, согласия, права использования
  (P12) — отдельно, когда определены данные и способы использования.
- Агентная дорожка — отдельный документ; здесь только требование P10 и
  тип действующего.

## 7. Гипотезы, которые проверяет использование

| #   | Гипотеза                                                                                      | Что наблюдаем                                                                   |
| --- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| H1  | Люди возвращаются, когда что-то изменилось в проектах, которые им важны                       | что вернуло; что было без напоминаний                                           |
| H2  | У проекта появляется полезная история **без** регулярных постов                               | какие вехи возникли сами, какие вносили вручную                                 |
| H3  | Системные вехи полезны, а не шум                                                              | какие вехи читают и которым возвращаются                                        |
| H4  | Запросы и отклики порождают настоящие взаимодействия, в том числе **между разными проектами** | сколько откликов привело к участию/работе                                       |
| H5  | Наблюдатель — отдельная сторона с отдельной ценностью                                         | кто просто следит и что хочет видеть                                            |
| H6  | Нужна ли организация как сущность                                                             | пытаются ли действовать «от организации»                                        |
| H7  | Ссылкой на проект делятся наружу                                                              | кого участники сами хотят позвать                                               |
| H8  | Что остаётся в Telegram и таблицах                                                            | где люди уходят и почему                                                        |
| H9  | Что люди пытаются зафиксировать вручную                                                       | кандидаты на новые виды вех                                                     |
| H10 | **Сколько внимания владельца уходит на группу**                                               | время и обращения на единицу пользы — собственная метрика платформенной дорожки |

Фиксируем (без порогов): что пытался сделать человек; зачем вернулся или не
вернулся; что происходило без напоминаний; куда уходил; какие взаимодействия
возникли между проектами; кого хотели позвать; какие вехи возникли сами;
что пытались зафиксировать вручную. Сырые счётчики собираются, но
статистическая достоверность на группе из десяти знакомых людей не
изображается.

## 8. Сравнение с существующей реализацией

**Метод.** Один проход по схеме базы (147 миграций), модулям ядра и
приложениям; код построчно не читался. Старые ADR используются только как
справка: что и почему устроено так. Размер для масштаба: ядро ≈ 37 800 строк,
крупнейшие модули — `lab` (проекты, заявки, раунды) 6 900, `billing` 4 500,
`identity` 2 900, `ai` 2 700. Приложения: `admin` ≈ 17 500 строк, `lab`
≈ 7 600, `console` ≈ 3 700.

### 8.1. Подходит как есть (используется в Stage 2)

| -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |

### 8.2. Не мешает — оставить без изменений

`billing` (подписки, счета, комиссии), `investments` (договоры, транши,
номинальный счёт), `kyc`, `scoring` и `ai` (скоринг заявки, паспорта),
`experts`, `seasons`, `intelligence` (заморожены), `integration`
(вебхуки). Это отдельные контуры; они не затрагивают первые девять пунктов
Stage 2, если **не просачиваются в интерфейс и модель нового проекта**.
Выключаются флагами. Условие, при котором «не мешает» перестанет быть
верным: общий проект тянет за собой их обязательные поля (см. 8.3).

### 8.3. Реально конфликтует со Stage 2

### 8.4. Остальное, что стоит помнить

- В схеме есть `kyc.business_entities` и `entity_members` (организации для
  проверки) и `identity.consents` (согласия). Они не заменяют Organization и
  не определяют будущий контур данных (P12), но это готовые фрагменты, если
  понадобятся.
- Из пяти заготовок для первого L2 (девяти пунктов) полностью «с нуля»
  требуются: **Participation, Request/Response, Milestone, Event как
  продуктовая лента, вход «проект без денег»**; остальное — расширение
  существующего.

### 8.5. Решение, которое нужно принять первым

C1 — главный конфликт. Варианты, **без выбора**:

- **A. Новая сущность проекта для Stage 2**, а нынешний `lab.projects`
  остаётся «инвестиционной заявкой», связанной с проектом. Плюс: старый
  контур не трогается, чистое начало. Минус: две сущности «проект» на время,
  связь между ними.
- **B. Ослабить нынешний `lab.projects`** следующими миграциями (сумма
  необязательна, валюта и стадия свободнее, статус заявки — в отдельное
  место). Плюс: одна сущность. Минус: тянет весь инвестиционный код
  (6 900 строк `lab`) на проверку и правку; миграции только вперёд.

Предварительная склонность Мауса: **A**, потому что это следует из «заявка
становится одним из видов запроса проекта» и не требует переписывать то, что
работает. Но выбор — после обсуждения.
