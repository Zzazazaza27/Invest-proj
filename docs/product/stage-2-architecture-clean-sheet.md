# Stage 2 Architecture — clean-sheet proposal (v2)

2026-10-12 · Маус · по постановке Томаса и Тэнка (идея 093) и решениям Томаса.
**Статус: рабочий исследовательский документ, не утверждённая архитектура.**
Решение Томаса 2026-10-12: предложенная здесь **продуктовая модель** (сущности,
вехи, Follow, запросы и отклики, контуры) **не утверждена**; проектирование
бизнес-логики Stage 2 остановлено. Ценны найденные **факты о существующем
коде** (раздел 9) и **технические выводы**; всё остальное — гипотезы. Решения
Томаса из раздела 0 (независимый репозиторий, вариант A для проекта, три
контура как рабочая рамка) остаются как направление, но детальная модель
ждёт отдельного решения.

Построено из текущей продуктовой постановки, а не из старых ADR. ADR-001…008
и документы-основания (`Architect*.md`, `Database_Launch.md`) написаны

ограничения** для Stage 2 и используются только как историческая справка в
разделе 9.

Порядок: постановка → требования → архитектура с чистого листа → сравнение с
существующей реализацией. Соседние документы:
[stage-2-adr-provenance-milestones.md](stage-2-adr-provenance-milestones.md)
(рабочие заметки, не рамка),

## 1. Продуктовые инварианты

1. **Центр — проект и его жизнь**, а не сделка. Инвестиция — один из видов
   взаимодействия вокруг проекта. Проект существует и без неё.
2. **Любой проект.** От вышивки до проекта на миллион: никакая обязательная
   сумма, стадия или отрасль не определяют, «настоящий» ли это проект (082).
3. **Четыре стороны вокруг проекта:** основатель, инвестор, партнёр,
   наблюдатель. Один человек в разных проектах — в разных ролях.
4. **Цикл:** проект → история и состояние → внимание → участие →
   потребность/запрос → отклик → взаимодействие → результат/событие →
   изменение состояния проекта → следующий цикл.
5. **Платформа — инфраструктура и доверительный слой.** Ценность создают
   участники. Платформа может сама создавать автоматическую ценность (анализ,
   подбор, проверки), но **рост ценности не должен требовать пропорционального
   роста человеческого внимания** операторов.
6. **Честность происхождения.** Показанное людям не выдаётся за большее, чем
   оно есть: «сообщено человеком» ≠ «зафиксировано платформой».
7. **Долговременная история проекта** — вехи, а не обязательный постинг.
   Ленты и мелкие обновления — позже, если использование покажет нужду.
8. **Настоящих платежей нет** (оператор не выбран, оплата тестовая).
9. **Не только Россия:** Россия — место старта, а не потолок.
10. **Эксплуатируется одним человеком и агентами;** критические решения —
    человек.
11. **Минимальная достаточность.** Сущности появляются, когда возникает
    реальная продуктовая необходимость; Stage 2 нужен, чтобы выяснить, какие
    из них фундаментальны.

## 3. Минимальная модель сущностей для первого dogfooding

Вопрос не «какую полную модель мира можно придумать», а «чего достаточно,
чтобы ~10 реальных проектов начали жить внутри системы и мы увидели
настоящее использование». Всё ниже — **рабочая гипотеза.**

| Сущность              | Что это                                                                                                                                | Статус                                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Person**            | человек: вход, минимальный профиль (на основе существующей учётной записи)                                                             | нужна                                                                                                                |
| **Project**           | каноническая сущность проекта: название, суть, по желанию стадия и страна, видимость. **Без суммы и тарифа**                           | нужна                                                                                                                |
| **Participation**     | человек в проекте: роль, состояние (приглашён / принял / вышел), период. Создатель проекта получает участие «основатель» автоматически | нужна                                                                                                                |
| **Request**           | проект сообщает, что ему нужно: свободный тип и текст, статус                                                                          | нужна                                                                                                                |
| **Response**          | отклик на запрос: кто, что предлагает, статус                                                                                          | нужна                                                                                                                |
| **DomainEvent**       | что произошло в предметной области (участие принято, запрос закрыт…)                                                                   | нужна                                                                                                                |
| **Milestone**         | существенное изменение истории проекта, для человека (раздел 4)                                                                        | нужна                                                                                                                |
| **Follow**            | `Person → follows → Project`. Никакого кабинета наблюдателя, алгоритмической ленты и рекомендаций                                      | **входит** (нужна для проверки H1, H3, H5)                                                                           |
| **Feedback**          | «не смог / неудобно / хочу» в один клик                                                                                                | нужна (возможно, на готовом механизме обращений)                                                                     |
| **Notification**      | уведомление в кабинете                                                                                                                 | нужна как доставка                                                                                                   |
| Organization          | компания/фонд как участник                                                                                                             | **откладывается** до первого случая, когда человек захочет действовать от имени организации; пока — название текстом |
| Confirmation          | подтверждение факта другим источником                                                                                                  | **не создаётся**                                                                                                     |
| InvestmentApplication | существующая сущность инвестиционного контура (сейчас `lab.projects`), связанная с Project                                             | legacy, не часть Stage 2 Core                                                                                        |

Не входят: ресурс, программа партнёра, платное предложение, баллы и кредиты,
рейтинг и репутация, кабинеты наблюдателя и партнёра.

**Про `Confirmation`:** веха получит стабильный идентификатор, а смысловые
правки оставляют видимый след (P3). Поэтому подтверждение можно добавить
позже **новой таблицей, ссылающейся на веху**, без переделки накопленного.
Пустая таблица была бы заготовкой под ненаблюдаемую модель.

**Про Project и инвестиции:** `InvestmentApplication → Project` — явная связь,
направленная из legacy в Core. Project о заявке ничего не знает (P0).

## 4. AuditEvent / DomainEvent / Milestone / Actor / Provenance

| Понятие         | Отвечает на вопрос                                                  | Для кого и зачем                                           | Свойства                                                                                                                                        |
| --------------- | ------------------------------------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Actor**       | кто действовал                                                      | везде                                                      | тип (человек / агент / система / интеграция) + идентификатор. Список типов открыт                                                               |
| **AuditEvent**  | кто что сделал в системе                                            | безопасность, диагностика, наблюдаемость, разбор поведения | технический, полный, неизменяемый; не предназначен для показа людям. Это существующий `audit.events`                                            |
| **DomainEvent** | что произошло в предметной области (с проектом, участием, запросом) | сырьё для вех и уведомлений                                | предметный смысл, не техническая подробность. **Новое понятие**: существующая таблица журнала им не считается, даже если на неё можно сослаться |
| **Milestone**   | что существенно изменилось в истории или состоянии проекта          | люди (владелец, команда, подписчики, инвесторы)            | отобрана для показа; свои заголовок, описание, видимость, «когда произошло»; **не равна событию**, может быть итогом нескольких событий         |
| **Provenance**  | откуда известно                                                     | честность показанного                                      | кто сообщил, источник, на каком основании, когда произошло и когда записано                                                                     |

Между слоями допустимы ссылки (веха может указывать на DomainEvent, DomainEvent
— на AuditEvent как на основание), но по смыслу это разные вещи, и один слой
не подменяет другой.

**Provenance на старте — два происхождения:**

- **сообщено человеком** (действующий — человек; основание — необязательная
  ссылка или текст);
- **зафиксировано действием платформы** (действующий — система; основание —
  ссылки на события, из которых это выведено).

**Не каждое событие — веха:**

| Что произошло                                              | DomainEvent | Milestone |
| ---------------------------------------------------------- | ----------- | --------- |
| на запрос пришёл отклик                                    | да          | нет       |
| обновлена презентация                                      | да          | нет       |
| участник присоединился к проекту                           | да          | кандидат  |
| запрос закрыт реальным результатом                         | да          | кандидат  |
| первый клиент, запуск, новый рынок, начало/закрытие раунда | да          | кандидаты |

**Одна веха — из нескольких событий:** «создан запрос → получены отклики →
выбран человек → человек принял приглашение» даёт **одну** веху «К проекту
присоединился разработчик», основание — ссылки на эти события. Веха — не
красивая обёртка журнала действий.

**Как вехи возникают в первом L2 (предположение):** короткий список правил в
коде (три-четыре: «приглашение принято», «запрос закрыт с выбранным откликом»,
«проект создан»…); плюс вехи, которые человек вносит вручную. Каталога типов
вех нет: вид — открытое поле, а что люди считают значимым, покажет
dogfooding.

**Неизменность и правка (P3).** Различаем:

| Что меняется                                             | Как                                                            |
| -------------------------------------------------------- | -------------------------------------------------------------- |
| опечатка, формулировка, оформление, порядок слов         | правится свободно                                              |
| то, **что произошло**, или **когда**, или кто участвовал | правится, но остаётся видимый след (кто и когда изменил смысл) |
| веха, оказавшаяся ошибочной                              | отзывается с отметкой, а не пропадает молча                    |

Исторические записи AuditEvent не переписываются вовсе — это другая задача
(безопасность), и это уже так.

## 5. Дешёвые двери, которые стоит оставить сейчас

| Дверь                                                         | Что значит                                                 | Цена, если закрыть                                    |
| ------------------------------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------- |
| Тип действующего в AuditEvent и DomainEvent                   | человек / агент / система                                  | не отличить действия агентов от человеческих          |
| «Когда произошло» отдельно от «когда записано»                | человек указывает дату события; время записи ставит сервер | перерасчёт исторических данных                        |
| Стабильный идентификатор вехи и видимый след смысловых правок | подтверждение и аудит можно добавить позже                 | потеря доверия к истории; невозможность подтверждений |
| Роль на участии в проекте                                     | один человек — разные роли в разных проектах               | перепроектирование кабинетов и доступа                |
| Открытые «вид» и «тип» (текст + JSONB)                        | новые вехи и запросы без миграции                          | миграция на каждый новый вид                          |
| Страна, язык, валюта — поля в новых таблицах                  | не только Россия                                           | массовая правка кода и данных                         |
| Идентификаторы UUIDv7 в новых таблицах (уже так в проекте)    | без общего счётчика                                        | менять ключи в живой базе                             |
| Файлы вне базы (уже так)                                      | рост без раздувания базы                                   | перенос файлов позже                                  |

**Проверил и отклонил:** пустая таблица подтверждений; цели и согласия внутри
provenance (другая ось, P12); сегментирование базы; отдельный поиск;
подготовленные ленты; **специальная перестройка под несколько копий
приложения** (решение 8).

## 6. Что мы сознательно не проектируем

- L1: «sensorium», «actuation», универсальный граф, главный автономный
  агент, машинная модель состояния рынка.
- Внутренняя валюта, журнал баллов и кредитов, глобальный рынок ресурсов.
- Системы доверия: веса источников, репутация, рейтинг, реестр «кто вправе
  подтверждать», очереди верификации.
- Социальная лента, посты, лайки, мелкие обновления; алгоритмическая лента и
  рекомендации для Follow.
- Подбор, рекомендации, поиск связей как функции (придут как автоматическая
  ценность, когда будут данные).
- Платные предложения, программы партнёров, кабинеты партнёра и наблюдателя.
- Organization как сущность (до первого реального случая).
- Объявление InvestmentApplication видом Request (до практики).
- Рассылки наружу, микросервисы, вторая база данных, инфраструктура под
  миллиард, перестройка под несколько копий приложения.
- Юридический контур данных: цели обработки, согласия, права использования
  (P12).
- Агентная дорожка — отдельный документ.

## 7. Гипотезы, которые проверяет использование

| #   | Гипотеза                                                                            | Что наблюдаем                                   |

| H1  | Люди возвращаются, когда что-то изменилось в проектах, которые им важны (Follow)    | что вернуло; что было без напоминаний           |
| H2  | У проекта появляется полезная история **без** регулярных постов                     | какие вехи возникли сами, какие вносили вручную |
| H3  | Системные вехи полезны, а не шум                                                    | какие вехи читают и по каким возвращаются       |
| H4  | Запросы и отклики порождают взаимодействия, в том числе **между разными проектами** | сколько откликов привело к участию/работе       |
| H5  | Наблюдатель — отдельная сторона с отдельной ценностью (Follow)                      | кто просто следит и что хочет видеть            |
| H6  | Нужна ли организация как сущность                                                   | пытаются ли действовать «от организации»        |
| H7  | Ссылкой на проект делятся наружу                                                    | кого участники сами хотят позвать               |
| H8  | Что остаётся в Telegram и таблицах                                                  | где люди уходят и почему                        |
| H9  | Что люди пытаются зафиксировать вручную                                             | кандидаты на новые виды вех                     |
| H10 | **Сколько внимания владельца уходит на группу**                                     | время и обращения на единицу пользы             |

Фиксируем (без порогов): что пытался сделать человек; зачем вернулся или не
вернулся; что происходило без напоминаний; куда уходил; какие взаимодействия
возникли между проектами; кого хотели позвать; какие вехи возникли сами; что
пытались зафиксировать вручную. Сырые счётчики собираются, но статистическая
достоверность на группе из десяти знакомых людей не изображается.

## 8. Три контура

**Правило зависимости:** Stage 2 Core → Shared Infrastructure ← Legacy
Investment. Legacy может ссылаться на Core (на `Project`). **Core на Legacy не
ссылается ни таблицей, ни кодом.** Legacy не удаляем ради чистоты; не
используем ради экономии, если он искажает новую модель.

```
        ┌────────────────────────────┐        ┌────────────────────────────┐
        │  Stage 2 Core  (НОВОЕ)     │        │  Legacy Investment         │
        │  Project, Participation,   │◄───────│  (СУЩЕСТВУЕТ, сохраняем)   │
        │  Request/Response,         │  явная │  заявки, раунды, листинг,  │
        │  DomainEvent, Milestone,   │  связь │  тарифы, инвестиции, KYC,  │
        │  Follow, Feedback          │  только│  скоринг, эксперты         │
        └──────────────┬─────────────┘  сюда  └──────────────┬─────────────┘
                       │ использует                          │ использует
                       ▼                                     ▼
        ┌──────────────────────────────────────────────────────────────────┐
        │  Shared Infrastructure  (СУЩЕСТВУЕТ, используем)                 │
        └──────────────────────────────────────────────────────────────────┘
```

Core → Legacy: **запрещено.** Legacy → Core: только через явную связь с
`Project`. Граница проверяется автоматически (идея: правило импортов в линтере
по образцу уже существующего запрета «фронтенд не импортирует бэкенд»).

### Карта модулей (по результатам одного прохода по схеме и модулям)

| Контур                    | Что входит                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage 2 Core** (новое)  | Project, Participation, Request, Response, DomainEvent, Milestone, Follow; новый фронтенд Stage 2 (страница проекта, история, запросы, «что нового»); новая схема БД; правила создания вех                                                                                                                                                                                                                |
| **Shared Infrastructure** | `identity` (вход, учётные записи, роли, согласия, аватары); `audit.*` (AuditEvent, outbox); `comms` (уведомления, обращения → Feedback); `storage` и медиа; `content.*` (языки, тексты); флаги функций; роли БД, построчный доступ, миграции вперёд; пакеты `contracts`, `api-client`, `ui`, `cabinet`; приложения `auth`, `admin`, `console`, `web-public`, `staff`; CI, стенд, наборы проверок, выкатка |
| **Legacy Investment**     | `lab` (заявка, раунды, каталог, доступ к материалам, избранное инвестора), `billing`, `investments`, `kyc`, `scoring`, `ai` (разбор заявки), `experts`, приложения `lab`, `investor`, `expert`. Заморожены и без влияния на Stage 2: `seasons`, `intelligence`                                                                                                                                            |
| **Проверить на границе**  | `integration` (исходящие вебхуки): скорее Shared; `identity.investor_profiles` и `kyc.business_entities`: лежат внутри Shared-схем, но по смыслу Legacy — Core их не использует; `lab.project_favorites`: зачаток Follow, но привязан к legacy-проекту — Follow строится заново на `Project`                                                                                                              |

## 9. Сравнение с существующей реализацией

**Метод.** Один проход по схеме базы (147 миграций), модулям ядра и
приложениям; код построчно не читался. Старые ADR — только справка: что и
почему устроено так. Масштаб: ядро ≈ 37 800 строк; крупнейшие модули — `lab`
6 900, `billing` 4 500, `identity` 2 900, `ai` 2 700.

### 9.1. Подходит как есть (Shared Infrastructure)

| Что есть                                                                              | Для чего в Stage 2                                            |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `identity` — пользователи, внешние входы, роли, согласия                              | Person; вход                                                  |
| `audit.events` — журнал: действующий (id и текстовая роль), субъект, вид, подробности | **AuditEvent**; добавить тип действующего; не DomainEvent     |
| `audit.outbox_events`, `audit.agent_runs`                                             | доставка событий; зачаток записи действий агентов             |
| `comms.notifications`, настройки                                                      | уведомления в кабинете                                        |
| `comms.support_tickets`                                                               | Feedback (проверить достаточность)                            |
| `lab.project_media`, модуль хранения                                                  | файлы и видео проекта (потребуется привязка к новому Project) |

| `feature_flags`                                                                       | включение функций для группы                                  |
| UUIDv7, роли БД, построчный доступ, миграции вперёд, стенд, проверки, `packages/*`    | основа                                                        |

### 9.2. Не мешает — оставить без изменений (Legacy)

`billing`, `investments`, `kyc`, `scoring`, `ai`, `experts`, `seasons`,
`intelligence`, приложения `lab`, `investor`, `expert`. Условие, при котором
«не мешает» перестанет быть верным: новый Project начнёт зависеть от их
обязательных полей — это запрещено P0.
