# Мультироли, кабинеты, организации: как это решают другие

2026-10-13 · Маус · исследование по первичным источникам (два прохода: продукты и
технические модели прав). Контекст: обсуждение Томас – Маус – Тэнк, идея 073
(`ideas.md`). **Выводов за Томаса нет; решения остаются за ним.** Часть справок
(Upwork, Fiverr, Republic) отдаёт 403 — там факты из поисковой выдачи, это помечено.

## 1. Рабочая модель, которую проверяли

Четыре разных вопроса: кто вошёл (один аккаунт); чем сейчас занимается (кабинет,
сам по себе прав не даёт); как связан с конкретным проектом/организацией (участие и
права); от чьего имени действует (лично или от организации).

## 3. Что повторяется у многих

1. **Один человек — один аккаунт, жёстко.** Слияния аккаунтов разных ролей у Airbnb и
   Upwork нет; решается запретом второго аккаунта. У Republic объединён только вход.
2. **Режим — переключатель инструментов; права от него не зависят** (Airbnb, GitHub).
3. **Организация — отдельная сущность, человек связан с ней ролью** (Eventbrite, Stripe,
   GitHub, LinkedIn, Wefunder). Права определяет связь «человек — организация».
4. **Гейт ставят на чувствительное действие, не на выдачу кабинета** (Kickstarter,
   Wefunder, Upwork).
5. **«От имени» выбирают в момент действия** (Wefunder: лично или через организацию при
   инвестиции) и **в профиле остаётся личное имя** уполномоченного лица.
6. **Гость — отдельный урезанный статус с ограничением по объекту и сроку** (Slack,
   Notion, Google Drive, GitHub).
7. **Для групп организаций — надстройка** (Stripe organization, Slack Connect).
8. **Публичная история видна в профиле и не даёт права действовать** (Kickstarter).
9. Предупреждение Stripe: несколько ролей в одном месте **складываются**, возможны
   конфликты — сложение прав надо делать явным.

## 4. Технические модели прав

- **Три семейства:** по ролям (RBAC), по атрибутам (ABAC), по отношениям (ReBAC; Google
  Zanzibar, 2019; открытые OpenFGA и SpiceDB; язык политик Cedar от AWS). Наш случай
  («права следуют из связи человек–проект») — ближе к отношениям, но с малой глубиной
  наследования.
- **Главная ошибка** (она же главный риск для нас): роль висит на аккаунте («он
  инвестор»), а не на связи с объектом. В нашем коде сейчас именно так (роли на
  аккаунте).
- **Самая частая реальная уязвимость:** подстановка чужого идентификатора объекта без
  проверки «может ли этот человек именно с этим объектом» (OWASP API1:2023,
  broken object level authorization). Нужны тесты авторизации.
- **Для малой команды на PostgreSQL** (варианты от простого к сложному, **без выбора**):
  1. таблица участий + проверка в коде + журнал;
  2. то же + построчная защита (RLS) как второй рубеж (контекст задаётся на транзакцию,
     роль приложения без обхода RLS; подзапросы к таблице участий в политиках дают
     гонки, нужны осторожность и тесты);
  3. одна функция/представление «эффективный доступ» как единственное место расчёта;
  4. внешний движок политик в процессе (Cedar) при множестве условий;
  5. отдельный сервис отношений (OpenFGA/SpiceDB) — для нескольких сервисов и глубоких
     графов; для ~10 проектов, по источникам, не оправдан, но полезно держать форму данных
     совместимой (субъект – отношение – объект).
- **Keycloak (он у нас):** в версии 26 есть «Organizations» (членство, приглашения,
  claim `organization` в токене, выбор организации при входе). Ролей **внутри** организации
  в документации не найдено; организационные группы в его политиках не используются;
  делегирование (`act`) в 26.8 — preview по блогу. **Вывод для архитектуры:** Keycloak отвечает на
  «кто вошёл» (и, по желанию, подсказывает активную организацию); права считаются по
  нашей базе. Активную организацию из токена надо **перепроверять** по базе (иначе устаревший
  токен после выхода человека).
- **«От имени»:** общий приём — в журнале три поля: **кто** (человек), **от чьего имени**
  (организация), **через что** (интерфейс или агент). Это то же, что `sub`/`act` в
  RFC 8693, но реализуется и без OAuth-обмена.
- **Жизненный цикл участия:** приглашение — отдельная запись до принятия;
  «заявка → решение» отдельное состояние; участие с началом и концом (мягкое завершение),
  история остаётся при потере прав. Готовой «канонической» спецификации нет.
- **Агенты (ИИ):** OWASP LLM06:2025 «Excessive Agency» совпадает с идеей «права по
  объекту»: агент — отдельный субъект, права — пересечение прав человека и агента (как у
  GitHub Apps), проверка прав в нижестоящей системе, а не суждением модели.
- **Ловушки:** «кабинет открыт = права получены»; активная организация из токена без
  проверки по базе; `SET` без `LOCAL` на пуле соединений; журнал без «от чьего имени» и
  «через что»; смешение истории участия с правами; опора на preview-функции Keycloak.

## 5. Что это значит для нашей модели (наблюдения, не решения)

| Находка                                                  | Подтверждает / уточняет                                                                                     |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| один аккаунт на человека; слияний нет                    | подтверждает основу                                                                                         |
| режим не добавляет прав                                  | подтверждает формулировку Тэнка                                                                             |
| гейт на действие, а не на кабинет                        | подтверждает мой вариант «открывать кабинет свободно, чувствительное — по статусу»                          |
| «от имени» выбирается при действии; личное имя в профиле | **уточняет**: «Организация» — не пункт переключателя кабинетов, а выбор при действии (+ три поля в журнале) |
| гость — на объект и срок                                 | соответствует «особым допускам» на закрытые документы                                                       |
| история ≠ права                                          | подтверждает                                                                                                |
| права на аккаунте — главная ошибка                       | **задевает текущий код** (роли на аккаунте); для Stage 2 нужна связь «человек–объект»                       |
| для ниши инвестиций прецедентов почти нет                | свои правила несовместимости ролей и конфликтов интересов придётся писать сами                              |
