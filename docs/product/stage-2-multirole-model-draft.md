# Мультироли, кабинеты, организации — модель на проверку (черновик)

2026-10-14 · Маус · по итогам обсуждения Томас – Тэнк – Маус. **Это не утверждённая
архитектура и не схема БД.** Задача: понятная модель понятий и связей, проверка на
сценариях, мобильные переходы, граница первой версии, открытые решения, сравнение с
текущим кодом. Дополнение Томаса: передача прав (продажа бизнеса, наследство), «фейковое
ООО», приближённый список подводных камней, и кто всё это разбирает при модели «один
человек + агенты». Исходные материалы: [multirole-precedents.md](multirole-precedents.md),
идея 073 в `ideas.md`.

## 1. Принципы, зафиксированные Томасом (без изменений)

1. Один личный аккаунт; после регистрации по почте — базовые возможности наблюдателя.
2. Основатель и инвестор — **подключаемые роли с разными кабинетами**; кабинет не равен
   аккаунту, копии профиля и дублированию проектов.
3. Четыре разных понятия: **аккаунт** (кто вошёл); **роль и кабинет** (чем пользуется);
   **отношение и доступ к объекту** (что разрешено в проекте или организации);
   **представительство** (лично или от организации).
4. Переключение кабинета прав не меняет. Выбор кабинета и выбор «лично / от организации» —
   разные вещи; «от чьего имени» не спрашиваем перед каждым действием.
5. Организация — отдельная сущность; создание организации не обязательно для создания
   проекта; создатель карточки — её первоначальный администратор, это **не доказательство
   юридических полномочий**.
6. Простые права, проверяемые сервером; без конструктора ролей и политик; иерархию
   должностей не строим.
7. Не превращать потенциальные возможности в обязательный объём первой версии.

## 2. Компактная модель

### Понятия (8)

| #   | Понятие                       | Что это                                                                                                                             | Кому принадлежит                                     |
| --- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 1   | **Человек**                   | один личный аккаунт                                                                                                                 | сам                                                  |
| 2   | **Кабинет**                   | набор инструментов для вида деятельности (личное пространство, основатель, инвестор); есть «по умолчанию»; сам по себе прав не даёт | включается человеку                                  |
| 3   | **Проект**                    | то, вокруг чего всё построено                                                                                                       | **ровно одному владельцу:** человеку или организации |
| 4   | **Организация**               | отдельная сторона (компания, фонд, акселератор), не отдельный логин                                                                 | у неё есть администратор (в первой версии один)      |
| 5   | **Связь человека с объектом** | как человек связан с проектом или организацией и что ему там разрешено                                                              | у связи есть начало, состояние, конец                |
| 6   | **Представительство**         | в чьё имя совершено существенное действие (лично / организация)                                                                     | записывается при действии                            |
| 7   | **Допуск к сведениям**        | кому открыты закрытые блоки проекта                                                                                                 | выдаёт управляющий проектом                          |
| 8   | **Видимость блока**           | что в проекте для всех, что закрыто                                                                                                 | настраивает управляющий, с разумными умолчаниями     |

### Связи

```
Человек ──(один аккаунт)── кабинеты: Личное · Основатель · Инвестор (подключаются)
   │
   ├─ владелец/управляющий ──────────────► Проект (личный)
   ├─ администратор ──► Организация ─(владеет)──► Проект организации
   ├─ участник (принято) ────────────────► Проект / Организация   [история, без прав управления]
   └─ получатель допуска (человек ИЛИ организация) ──► блоки закрытых сведений проекта

Действие над проектом: «кто совершил» (человек) + «от чьего имени» (лично / организация)
```

**Что намеренно не ввожу:** иерархию подразделений, должности, конструктор ролей,
поведенческие ступени доверия, общую «летопись» организации.

### Три различия, которые Томас просил держать

| Различие                                | Как выражается в модели                                                                                                                 |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| отклик ≠ принятое участие               | отклик — запрос; участие возникает только после принятия владельцем                                                                     |
| заявление ≠ подтверждённое событие      | у каждого заявленного факта (в том числе «я представляю организацию X») видно: заявлено человеком или подтверждено платформой/проверкой |
| исторический вклад ≠ действующий доступ | участник остаётся в истории после потери права редактировать                                                                            |

## 3. Проверка на мобильных сценариях

Схемы переходов (экран → экран). Проверка критерия: **нет обязательной цепочки «роль →
организация → полномочие → проект» перед действием**.

### С1. Регистрация → просмотр → сохранение проекта

```
[Старт: почта] → [Код/ссылка из письма] → [Публичный каталог] → [Страница проекта: публичные блоки]
        → [Сохранить] → [Личное: сохранённое]
```

- Цепочки нет. Кабинет один (Личное), переключателя не видно.
- **Вопросы:** что видит наблюдатель на месте закрытых блоков (замок без объяснения или
  «запросить доступ»); «сохранить» = личный список, **не подписка и не уведомления**
  (иначе наблюдатель не узнает об изменениях — это сознательный выбор первой версии).

### С2. Личный проект → обновление

```
[Личное] → [Создать проект: название, суть] → [Страница проекта (вид владельца)]
        → [Обновить: описание / веха] → [Публичная страница обновлена]
```

- Кабинет основателя **появляется как следствие действия** (создал проект), а не отдельным
  шагом подключения. «Лично или от организации» не спрашивается, если у человека нет
  организаций (по умолчанию лично).
- Цепочки нет. **Открытое решение Q1:** это и есть «условие открытия кабинета основателя».

### С3. Проект компании → управление

```
[Создать проект] → «Лично или от организации?»(только если организации есть или выбрана)
   → [Создать организацию: название; реквизиты по желанию] → [Проект создан от организации]
   → [Кабинет основателя → Проекты → проект]
```

- Организация создаётся **по ходу**, не обязательным шагом: для компании нужен один
  дополнительный выбор. Создатель — администратор организации и управляющий проектом.
- **Противоречие:** администратор организации и управляющий проектом — одно лицо, пока нет
  делегирования; при его утрате организация «осиротеет» (раздел 6).
- Метка на странице: **«организация заявлена, не подтверждена»** до проверки.

### С4. Инвестор лично и от фонда → запрос материалов

```
[Кабинет инвестора: сохранённое, критерии] → [Страница проекта] → [Запросить материалы]
   → «От кого: лично / Фонд X» (если организации есть; по умолчанию — как в прошлый раз)
   → [Запрос отправлен: виден статус]
Владелец: [Входящий запрос: «Иван (от Фонда X, не подтверждён)»]
   → [Дать допуск: человеку или организации; какие блоки; срок?]
```

- Цепочки нет; выбор «от кого» один и только когда возможны разные авторы.
- **Противоречия и решения:** получатель допуска человек или организация (Q6); что значит
  «статус инвестора» (Q2); обязателен ли срок (Томас: не утверждено).

### С5. Один человек — основатель и инвестор → переключение

```
[Шапка/нижняя панель: Личное · Основатель · Инвестор] → переключение на лету; «по умолчанию»
```

- Переключатель показывается, **только если кабинетов два и более** (иначе скрыт).
- **Противоречие/правило:** человек, открывший **свой же проект** из кабинета инвестора, не
  должен получать «инвесторский» вид; показывать «это ваш проект — открыть как владельца».
  Правило в коде: нельзя запрашивать допуск к собственному проекту и оценивать его как внешний.
- Действующий контекст (кабинет, и если применимо — «от имени») виден плашкой.

### Принципы мобильного интерфейса (из сценариев)

1. Переключатель кабинетов — только при ≥2 кабинетах.
2. «Лично / от организации» — выбор в момент действия, только когда авторы возможны разные.
3. Плашка действующего контекста, где контекст неоднозначен.
4. Состояние запроса и допуска всегда видно (не «ушло в никуда»).
5. **Текущее состояние кода:** адаптивной вёрстки почти нет (`@media` всего в нескольких
   файлах: 3 в `packages/ui`, по 1 в `lab` и `admin`, 0 в `investor`); `viewport` в
   страницах есть. Мобильная проверка потребует отдельной работы.

### 4.2. «Фейковое ООО» и самозванство

| Угроза                                                                             | Чем опасно                           | Мера (минимум)                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Человек создаёт карточку организации без юрлица и «ведёт деятельность»             | накопление ложного доверия           | **три разных уровня:** «заявлена» → «юрлицо существует (реестр)» → «представитель уполномочен»; бейдж «подтверждена» только после проверки; видно «создана N дней назад»                                     |

| Один человек — несколько личностей и организаций (обход блокировок)                | накрутка, конфликт интересов         | один аккаунт на человека; при блокировке — не создавать новые (поддержка вручную); привязка статусных ролей к подтверждённому лицу                                                                           |
| Перепродажа статусных аккаунтов (прецедент Gojek)                                  | подмена подтверждённого лица         | запрет передачи аккаунта; смена подтверждённого лица — как новая проверка                                                                                                                                    |
| Конфликт интересов (основатель-инвестор, оценка своего проекта)                    | искажение                            | правила в коде (раздел 3, С5)                                                                                                                                                                                |
| Бывший сотрудник продолжает «представлять» организацию                             | ущерб                                | отзыв полномочий действует немедленно; в журнале «кто» + «от имени кого»                                                                                                                                     |

### 4.3. Приближённый общий список подводных камней

1. Организация «осиротела» (единственный администратор исчез).
2. Спор двух людей о том, кто представляет организацию.
3. Публикация личных данных сотрудников и их удаление по требованию при сохранении
   рабочих данных организации (согласия, 152-ФЗ).
4. Несовершеннолетние и недееспособные (вопрос в юридический список).
5. Ответственность за публикуемые заявления (что платформа не подтверждает).
6. Блокировка **роли** без блокировки аккаунта (в коде есть отзыв роли отдельно от
   блокировки аккаунта — см. раздел 7).
7. Историческое имя автора после ухода человека или переименования организации.
8. Параллельные проекты одного человека в разных организациях (конфликт интересов).
9. Совместное участие ≠ совместное управление (Томас): участие в истории без права править.
10. Мобильный интерфейс не должен показывать все роли и полномочия сразу.

## 5. Кто всё это обрабатывает при «одна компания — один человек — агенты»

Ручной разбор проверок организаций, жалоб, споров о владении, наследства и «фейков» —
самое дорогое по **вниманию единственного человека**. Поэтому принципы:

1. **Платформа не арбитр правовых споров о юрлицах.** Уровень «подтверждена» выдаётся
   только по проверяемым внешним источникам (реестр юрлиц, документ), а не по суждению
   оператора. Нет подтверждения — нет и обещания.
2. **«Заявлено / подтверждено»** снимает необходимость решать, «кто прав»: показываем
   честно, что подтверждено.
3. **Гейт на действие, а не на вход:** проверка нужна только перед чувствительным
   (допуск к закрытым сведениям, действие от имени организации перед инвесторами).
4. **Агенты готовят карточку, человек решает спорное:** агент собирает данные реестра,
   сходство названий, историю заявлений и формирует очередь решений; человек видит только
   пограничные случаи и несёт ответственность (граница автономии — в
   `ai-dev-environment-architecture.md`).
5. **Жалоба → автоматическая осторожная мера** (временно снять публичные заявления
   «от имени организации»), затем ручной разбор; без пересмотра каждого случая вручную.
6. **В первой версии объём малый** (около 10 человек): всё допустимо вручную и редко;
   метрика внимания владельца (гипотеза H10 в clean-sheet) покажет, когда нужна автоматизация.
7. **Юридическая часть** (наследство, продажа, ответственность, несовершеннолетние)
   вынесена в список вопросов Вики: до публичного запуска, не блокирует закрытую фазу.

## 6. Граница первой версии (предложение)

**Входит (минимум для закрытой группы):**

- один аккаунт, регистрация по почте, наблюдатель (публичный каталог и страницы, «сохранить»);
- кабинет основателя (включается созданием проекта), личные проекты;
- организация как **карточка с одним администратором**; проект личный или организации;
- видимость блоков проекта: **публично / закрыто**; допуск именным людям (получатель — человек);
- метка «заявлено / подтверждено» на организации (реестровая проверка — позже);
- участие в проекте как запись **в истории** (добавляет владелец, принимает человек), **без прав управления**;
- переключение кабинетов при ≥2 кабинетах.

**Остаётся возможным в модели, но не строится:** приглашения и управление сотрудниками;
несколько администраторов; несколько проектов одной организации и несколько организаций
одного человека; кабинет инвестора как новый инструмент (в старом контуре он есть);
допуски организациям; «видимость для инвесторов»; срок и журнал допусков; передача
владения; перенос личного проекта в проект компании; летопись участия и организации;
приостановка роли; уведомления, подписки, комментарии.

## 7. Сравнение с текущим кодом (проверено чтением схемы)

| Что в модели       | Что есть сейчас                                                                                                                                                                                                                   | Оценка                                                                                                                                                            |

## 8. Противоречия и острые места записки

1. **Команда на «Пятом элементе» (088) против «один управляющий и без приглашений»:**
   проект «Пятый элемент» ведёт команда, а в первой версии у проекта один управляющий. Как
   показать команду? Выход: **участие как запись в истории** (добавляет владелец, принимает
   человек), без управления. Это не «приглашения и роли», а минимальная форма и она
   нужна уже в закрытой фазе.
2. **«Администратор организации» не равен «владелец юрлица», но он единственный:** при его
   утрате организация без управляющего. Нужен путь восстановления (по документам), иначе
   «сиротские» организации.
3. **Организация-карточка против юрлица в коде:** сейчас организации существуют только как
   проверяемые юрлица (KYB). Нужно развести «организацию» и «подтверждение юрлица».
4. **«Видимость для инвесторов»** требует статуса инвестора, а он открыт (Q2): в первой
   версии либо не предлагать, либо оставить только «публично / закрыто + именной допуск».
5. **«Сохранить проект»** без подписок: личный список, но без уведомлений; нужно сказать
   пользователю, что уведомлений нет.
6. **Кабинет основателя «подключаемый» и «появляется созданием проекта»:** это и есть ответ
   на условие подключения; нужно подтвердить.
7. **Данные организации не исчезают при уходе сотрудника,** но у человека есть право на
   удаление: нужна политика (что остаётся: рабочие записи без личных данных).
8. **Совместное участие ≠ совместное управление** противоречит желанию «показать команду»,
   если не развести историю и права (пункт 1).
