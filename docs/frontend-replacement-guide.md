# Руководство: как заменить фронтенд

Документ отвечает на один вопрос: **что нужно сделать, чтобы выбросить любой
фронтенд (или все сразу) и написать новый, не трогая бэкенд.** Ответ: почти
ничего. Ниже — точный перечень.

---

## 1. Что такое «фронтенд» в этом репозитории

Пять независимых приложений. Каждое — отдельный workspace со своим
`package.json`, своей сборкой и своим статическим деплоем:

```
apps/web-public   apps/lab   apps/investor   apps/expert   apps/admin
```

Ни одно из них не является частью серверного рантайма. Бэкенд (`apps/core`) не
рендерит HTML, не отдаёт шаблоны, не импортирует React и не знает, чем занят
фронтенд.

## 2. Единственный шов

```
фронтенд ──HTTP──► https://api.5espace.test/v1 ──► apps/core
             ▲
             └── @fifth/api-client (типы из @fifth/contracts)
```

Разрешённые зависимости фронтенда на монорепо:

| Пакет               | Что даёт                                      | Обязателен?                               |
| ------------------- | --------------------------------------------- | ----------------------------------------- |
| `@fifth/contracts`  | zod-схемы запросов/ответов, типы, коды ошибок | нет — можно сгенерировать свои из OpenAPI |
| `@fifth/api-client` | типизированный клиент на `fetch`, без React   | нет — можно писать запросы руками         |
| `@fifth/ui`         | дизайн-токены и примитивы                     | нет                                       |

**Всё три — опциональны.** Обязателен только HTTP-контракт `/v1`.

Запрещённые зависимости (ошибка сборки, не замечание ревью):

- любой импорт из `apps/core` или `database`;
- драйверы `pg`, `ioredis`, `nats`, `bullmq`;
- прямой доступ к БД, очередям, S3 и шине событий.

Проверяется в двух местах: правило ESLint `no-restricted-imports`
(`eslint.config.js`) и SAST-правило `unicorn-frontend-must-not-touch-db`
(`.semgrep/guardian.yml`). Оба — блокирующие гейты CI.

## 3. Замена одного портала

```bash
rm -rf apps/investor          # портал исчез
npm run build                 # остальное собирается — проверяется в CI
```

Далее:

1. Создать новый `apps/investor` на любом стеке (Next.js, Nuxt, SvelteKit,
   Remix, Astro, нативный мобильный клиент, десктоп).
2. Указать базовый URL API: `VITE_API_BASE_URL` (или свой аналог) →
   `https://api.5espace.test/v1`.
3. Добавить Origin нового фронта в `CORS_ALLOWED_ORIGINS` бэкенда.
4. Если workspace называется иначе — поправить массив `workspaces` в корневом
   `package.json`.

**Изменений в бэкенде: одна переменная окружения.** Ни строки кода.

## 4. Замена всех фронтендов сразу

```bash
rm -rf apps/web-public apps/lab apps/investor apps/expert apps/admin
```

`apps/core`, `database`, `packages/contracts`, `apps/ai-gateway` продолжают
собираться и проходить тесты. Бэкенд остаётся полноценным продуктом с
документированным API — на нём можно построить что угодно.

## 5. Контракт, на который опирается новый фронт

- **OpenAPI 3.1:** `GET /v1/openapi.json` — генерируется из тех же zod-схем,
  что валидируют запросы на сервере, поэтому не расходится с реальностью.
- **Ошибки:** RFC 9457 (`application/problem+json`) с полями `type`, `title`,
  `status`, `detail`, `instance`, `traceId`.
- **Пагинация:** keyset (`cursor`, `limit`), не offset.
- **Идемпотентность:** заголовок `Idempotency-Key` обязателен на всех
  денежных и регулируемых POST.
- **Версия данных:** `data_version` в ответах для оптимистичной блокировки.

## 6. Аутентификация: два поддерживаемых режима

| Режим  | Кому                          | Как                                                                                                                                                                    |
| ------ | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cookie | Веб-фронтенды                 | `__Host-ul_session` — httpOnly, `Secure`, `SameSite=Strict`. Плюс double-submit CSRF-токен в заголовке `X-CSRF-Token` для небезопасных методов. Токен недоступен из JS |
| Bearer | Мобильные и сторонние клиенты | OAuth 2.1 Authorization Code + PKCE напрямую к IdP `https://id.5espace.test`, затем `Authorization: Bearer <access_token>`                                             |

> **Статус этого режима.** Ветка Bearer/OIDC **НЕ проверена против реального
> IdP end-to-end**: ядро принимает и валидирует JWT (issuer, audience,
> алгоритмы, JWKS с таймаутом), но обмен кода на сессию в самом ядре не
> реализован — это CRITICAL внешнего аудита, открытый пункт `TODO.md`.
> С Ф45 в локальном контуре есть realm Keycloak (клиент, роли, PKCE S256) —
> инфраструктура для такой проверки, но не сама проверка. Интегратору стоит
> закладывать время на верификацию этого пути.

Оба валидируются одним и тем же кодом на сервере. Новый фронт выбирает любой.

## 7. Что фронтенд НЕ должен реализовывать

Ни одна из этих проверок не является контролем, если сделана только в UI. Все
они продублированы на сервере и там — источник правды:

- блокирующий акцепт `platform_rules` / `tos` / `pdn` / `commission_terms`
  перед активацией аккаунта;
- резолв тарифа основателя по `investment_ask`;
- допуск инвестора к полной карточке (активная подписка + KYC);
- лимиты, запрет self-deal и аффилированных сделок;
- подтверждение первого транша и начисление вознаграждения ОИП;
- любые переходы статусов договора.

Фронтенд может дублировать их для UX — но убрав дубль, он ничего не сломает в
безопасности.

## 8. Чек-лист приёмки нового фронтенда

- [ ] Не импортирует ничего из `apps/core` и `database` (`npm run lint` зелёный)
- [ ] Все запросы идут через `/v1`, ни одного прямого обращения к инфраструктуре
- [ ] Токен не хранится в `localStorage` / `sessionStorage`
- [ ] Небезопасные методы шлют `X-CSRF-Token`
- [ ] Денежные операции шлют `Idempotency-Key`
- [ ] Тарифы и вознаграждение ОИП видны без авторизации (принцип радикальной
      прозрачности, `docs/architecture/Architect_Launch.md` §5.4)
- [ ] Ошибки RFC 9457 отображаются пользователю без утечки внутренних деталей
- [ ] Origin добавлен в `CORS_ALLOWED_ORIGINS`
