## Замеры (20 000 проектов одного сезона)

| Запрос                              | До индекса | После M031 | Бюджет  |
| ----------------------------------- | ---------- | ---------- | ------- |
| каталог: первая страница            | 15.5 мс    | 0.0 мс     | 200 мс  |
| каталог: страница по курсору (5000) | 10.4 мс    | 0.0 мс     | 200 мс  |
| каталог: полнотекстовый поиск       | 13.7 мс    | 0.0 мс     | 200 мс  |
| каталог: фильтр по сумме и стадии   | 4.0 мс     | 0.1 мс     | 200 мс  |
| отбор: проекты сезона на этапе      | 2.9 мс     | 2.9 мс     | 200 мс  |
| реестр договоров: страница          | 0.0 мс     | 0.1 мс     | 200 мс  |
| `REFRESH MV CONCURRENTLY` рейтинга  | 763 мс     | 784 мс     | 5000 мс |

Замер сам по себе дал находку: каталог шёл `Seq Scan` + сортировкой всего
отобранного набора — существующий `projects_catalog (listing_status,
taxonomy_id, listed_at DESC)` для запроса без фильтра по направлению не
подходит. M031 добавил частичный индекс под фактический ключевой набор
`(listed_at DESC, id DESC)`; после него план — `Index Scan`.

Оговорки, которые нельзя опускать:

- «Отбор проектов сезона на этапе» остался `Seq Scan`: в синтетике весь сезон —
  это вся таблица, и планировщик прав. На реальном распределении данных индекс
  `projects_season_status` будет выбираться; этого замер НЕ доказывает.
- Замер однопользовательский. Поведение под параллельной нагрузкой и на
  200 000+ проектов не проверялось.
