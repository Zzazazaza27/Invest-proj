# Ф58 — развёртывание внутреннего стенда на ВПС 193.233.217.210

Дата: 2026-08-21. Режим: BROWNFIELD, развёртывание существующего контура на новой машине.
Решение владельца по контуру: **внутренний стенд** — наружу не публикуется, доступ по SSH-туннелю, реальные ПДн не загружаются.

---

## Scope

**Машина.** Ubuntu 24.04.1 LTS, 4 vCPU / 7.8 ГБ / 119 ГБ, до начала работ — чистая (только sshd).

**Установлено:** Docker 29.7.2 + Compose v5.5.0, Node v22.23.2, npm 10.9.8, git 2.43.0, Python 3.12.3 (venv шлюза), ufw, chromium для браузерных прогонов.

**Развёрнуто в `/opt/unicorn-launch`:** рабочее дерево репозитория без `.git`, `node_modules`, `dist`, логов, `.env` и `.ssh`. Секреты стенда сгенерированы **на самой машине** и локальный `.env` на сервер не копировался.

**Контур:** postgres 16 · redis 7.4 · nats 2.10 (JetStream, стрим `LAUNCH`) · minio (бакет `unicorn-launch`, учётки `unicorn_app` и `unicorn_archive`) · nginx как единая точка входа · ядро (systemd `unicorn-core`) · AI-шлюз (systemd `unicorn-ai-gateway`).

**Файлы репозитория, изменённые в этой сессии:** `scripts/smoke-ai.mjs` (кроссплатформенный `stopGateway`, см. finding 4).

### По finding 7

Ужесточение (`PasswordAuthentication no`, `PermitRootLogin prohibit-password`) подготовлено, но **не применено**: владелец сообщил, что работа идёт вдвоём и появятся новые SSH-ключи коллег. С закрытым парольным входом новый ключ нельзя добавить «с нуля» — только через уже имеющийся доступ или консоль хостера. Это осознанный компромисс, а не упущение; решение за владельцем.

Отдельно зафиксировано: ключ `rebel_diesel` (SHA256:hemLwUW…) был дописан в `/root/.ssh/authorized_keys` в 13:30:23 из сессии, вошедшей по root-паролю с 95.67.208.8. Владелец подтвердил: это ключ коллеги, доступ легитимный.

## Периметр

Наружу открыт **единственный порт 22**. Проверено `curl` снаружи по 80, 443, 4300, 5433, 6380, 8100, 9000, 9001, 4222, 8222 — соединение не устанавливается ни по одному; на 22 отвечает баннер `SSH-2.0-OpenSSH_9.6p`.

Вся инфраструктура (postgres, redis, nats, minio, nginx) слушает `127.0.0.1` — это свойство `infra/docker-compose.yml`, а не firewall. Ядро на `0.0.0.0:4300` закрыто ufw.

```
ufw: default deny incoming / allow outgoing
  22/tcp                ALLOW  Anywhere
  4300/tcp              ALLOW  172.16.0.0/12   # nginx-контейнер -> ядро на хосте
```

**Отдельно отмечено:** проверка портов через `/dev/tcp` из Git Bash на Windows дала ложное «ОТКРЫТ СНАРУЖИ» сразу по пяти закрытым портам. Закрытость периметра подтверждена `curl` и `ss -tlnp` на самой машине; `/dev/tcp` в этом окружении использовать нельзя.

## Доступ

Публичного адреса у стенда нет. Доступ — SSH-туннель:

```
ssh -i .ssh/SERG -o UserKnownHostsFile=.ssh/known_hosts -o IdentitiesOnly=yes \
    -L 8080:127.0.0.1:80 root@193.233.217.210
```

Затем `http://127.0.0.1:8080/` — витрина, `/lab/`, `/investor/`, `/expert/`, `/admin/`, `/login/`, `/console/`. Фронтенды ходят в API по относительному `/v1/`, поэтому запросы остаются same-origin и номер локального порта роли не играет.

Учётные записи стенда заведены `dev-stand.mjs`: `stand-founder`, `stand-investor`, `stand-expert`, `stand-admin`, `stand-organizer`; пароль — в `DEV_TEST_USER_PASSWORD` на сервере.

## Ограничения — что НЕ проверялось

- **TLS и домен отсутствуют.** Стенд внутренний, `__Host-` cookie и Secure-флаги в этом контуре не проверялись.
- **Реальные ПДн не загружались** и загружаться в этот контур не должны: `KMS_MODE=local`, KEK лежат в `.env` на той же машине, внешнего KMS/Vault нет.
- **Keycloak не поднимался** — стенд работает на `AUTH_MODE=local`; профиль `idp` не запускался.
- **Пентест периметра не проводился** — статическая проверка и `curl` его не заменяют (условие гейта A, `docs/architecture/Architect_Launch.md` §7).
- **PITR и восстановление на точку во времени** не проверялись — свойство production-инфраструктуры.
- **Нагрузочное тестирование** не гонялось; SLO по этому стенду не заявляются.
- **Object Lock и SSE-KMS** в MinIO не включены — свойства боевого хранилища, как и было записано в `TODO.md`.
- Отчёт статический в части кода: прогоны подтверждают поведение контура, но не заменяют аудит исходников.

## Перезагрузка

Автозапуск проверен **фактическим `systemctl reboot`**, а не только `systemctl is-enabled`: «включено в автозапуск» и «поднимается само» — разные утверждения.

После возврата машины (`up 0 minutes`), без единого ручного действия:

- `unicorn-core`, `unicorn-ai-gateway`, `docker`, `ufw` — все `active`;
- пять контейнеров `Up 33 seconds (healthy)`: web, redis, postgres, nats, minio;
- слушают: `127.0.0.1:80` (nginx), `127.0.0.1:8100` (шлюз), `0.0.0.0:4300` (ядро);
- `GET /v1/health` → `{"service":"unicorn-launch-core","status":"ok","checks":{"database":"ok"}}`;
- все семь разделов за единой точкой входа отвечают 200: `/`, `/lab/`, `/investor/`, `/expert/`, `/admin/`, `/login/`, `/console/`.

Порядок запуска выдержан за счёт `Requires=docker.service` и запаса попыток (`StartLimitBurst=10`): ядро не падает окончательно, если postgres ещё не готов.

## Техдолг и рекомендации

1. **Закрыть findings 1–3 в репозитории.** Правки на стенде живут только в `/opt/unicorn-launch/.env`; следующий, кто развернёт контур с нуля из `.env.example`, наступит на те же три грабли.
2. **Прогон «чистая копия → работающий стенд»** — единственное, что закроет этот класс долга насовсем. Гейт `gate:roles-env` его не ловит: он сверяет имена переменных с CI, а не имя роли внутри URL и не факт запуска.
3. **Решить вопрос парольного входа** (finding 7) — как именно добавляются ключи новых участников.
4. Production-контур (Terraform/Helm) по-прежнему не написан; этот стенд его не заменяет и заменять не должен.
