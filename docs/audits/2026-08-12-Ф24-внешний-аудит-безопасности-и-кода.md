## 2. Закрыто в этой фазе

### 2.1. SEC-07 — классификатор адресов пропускал часть внутренних сетей

**Подтверждено воспроизведением** против скомпилированного кода до правки —
пять обходов из пяти:

```
FAIL fe90::1          ожидалось block, факт allow
FAIL febf::1          ожидалось block, факт allow
FAIL ::ffff:7f00:1    ожидалось block, факт allow
FAIL 224.0.0.1        ожидалось block, факт allow
FAIL 198.18.0.1       ожидалось block, факт allow
OK   93.184.216.34    ожидалось allow, факт allow   ← контроль
```

Причина одна на все пять: сравнивались строковые ПРЕФИКСЫ. `startsWith('fe80')`
покрывает литерал, а не сеть `fe80::/10` — то есть первые десять бит; разбор
IPv4-mapped ловил только точечную форму, а не шестнадцатеричную; multicast и
benchmark-сетей в списке не было вовсе.

**Исправлено:** новый `apps/core/src/events/ip-classifier.ts` приводит адрес к
каноническим байтам и сравнивает с диапазонами по длине префикса. Форма записи
перестала иметь значение: сокращённая, развёрнутая, с зоной, IPv4-mapped, NAT64
и 6to4 сводятся к одному числу. Неразобранный адрес считается запрещённым.

**Вторая половина находки — slow-drip.** `req.setTimeout` — таймаут
БЕЗДЕЙСТВИЯ: получатель, отдающий по байту чуть чаще, чем раз в `timeoutMs`, не
срабатывает по нему никогда. Добавлен абсолютный предельный срок. Отдельно:
превышение предела тела раньше лишь ПЕРЕСТАВАЛО СОХРАНЯТЬ данные, продолжая их
принимать, — теперь соединение обрывается.

**Гейт проверен на падение:** на прежнем поведении 3 теста из 62 падают.

### 2.2. SEC-08 — приостановка сервисного аккаунта не отзывала выданные токены

Прежний код документировал это как открытый долг: приостановка и ротация
секрета закрывали только выдачу НОВЫХ токенов, уже выданный жил до часа.

**Исправлено:** рубеж токенов аккаунта (`token_epoch`, M042) — тот же приём, что
у пользовательских сессий. Рубеж кладётся в токен при выдаче и сверяется на
каждом запросе через `ServiceAccountStateService` (снимок на 5 с, fail-closed).
Приостановка, возобновление и ротация секрета рубеж увеличивают.

**Живой прогон** `scripts/probe-service-token-epoch.mjs` — 9/9, **проверен на
падение**: со снятой проверкой приостановленный аккаунт продолжает отвечать
`HTTP 200` по старому токену (3 провала из 9).

### 2.3. SEC-06 — аренда доставки допускала повторный внешний эффект

**Подтверждено арифметикой:** до `OUTBOX_BATCH_SIZE` (по умолчанию 50) строк
получали ОДНУ аренду в 60 секунд, а отправлялись последовательно. К концу пачки
аренда истекала, другой экземпляр забирал те же строки и слал вебхук второй раз
— с настоящим побочным эффектом у получателя.

**Исправлено:** аренда продлевается перед КАЖДОЙ доставкой с ограждением по
владельцу (`locked_by`); потерявший аренду не отправляет. Итог доставки
пишется только держателем аренды. Срок аренды больше не константа — он выводится
из предельной длительности одной доставки.

### 2.4. SEC-11 — потолок частоты по адресу мог заблокировать навсегда

`INCR` и `EXPIRE` были двумя операциями. Обрыв между ними оставляет ключ БЕЗ
СРОКА: он не истекает никогда, счётчик растёт, живой пользователь получает 429
бессрочно.

**Исправлено:** одна атомарная Lua-операция, которая ещё и лечит уже
осиротевшие ключи. **Прогон** `scripts/probe-ip-ceiling-ttl.mjs` — 8/8,
**проверен на падение**: на прежней схеме осиротевший ключ остаётся с `TTL -1`.

### 2.5. SEC-05 — брокер в production принимал подключение без аутентификации

Проверялся только префикс `tls://`; `NATS_USER`/`NATS_PASSWORD` имели пустые
значения по умолчанию. TLS шифрует канал, но не проверяет публикующего.

**Исправлено:** конфигурация production требует учётные данные брокера; учётные
данные внутри адреса запрещены (тот же запрет, что для БД и Redis).

### 2.6. SEC-13 — карты исходников в сборке пяти интерфейсов

`sourcemap: true` в пяти `vite.config.ts`. Шага, вырезающего `.map` перед
выкладкой, нет — значит карты раздавались бы вместе с артефактом.
**Исправлено:** `false` во всех пяти.

### 2.7. SEC-15 — `x-request-id` принимался без проверки

Заголовок попадал в структурированный журнал, поля трассировки и контекст
аудита без ограничения формата и длины. Управляющий символ в нём — подделка
строки лога чужими руками.

**Исправлено:** принимается только 8–64 безопасных ASCII-символа, иначе
подставляется свой. Дополнительно найдено и закрыто **четыре места**, читавших
сырой заголовок в обход проверки.

### 2.8. SEC-16 — поле `ip_hash` не содержало адреса

В колонку с именем `ip_hash` писался хеш `traceId`. Утечки нет, неверен смысл:
запись о согласии — юридическое доказательство, и поле читается проверяющим как
«с какого адреса дано согласие».

**Исправлено (M043):** честное имя `request_trace_hash` + комментарий, прямо
говорящий, чем это значение НЕ является. Перенесено 5091 согласие, значения
совпадают побайтно; триггер неизменяемости снят на одну операцию и восстановлен
(проверено: `tgenabled = 'O'`).

### 2.9. SEC-18 — незакреплённые звенья цепочки сборки

**Исправлено:** `gitleaks:latest`, образ semgrep и образы служб CI закреплены
ДАЙДЖЕСТАМИ; `pip-audit` и `pytest` — версиями.

### 2.10. CODE-18 — сборка на чистой копии не проходила проверку типов

**Воспроизведено:** после удаления `packages/ui/dist` и `npm run build:packages`
проверка типов падает — `Cannot find module '@unicorn/ui'`. `build:packages`
собирал только `contracts` и `api-client`, а пять интерфейсов импортируют `ui`
через `dist/`.

**Исправлено:** `packages/ui` добавлен в `build:packages`. После правки проверка
типов на том же чистом состоянии проходит.

## 7. Ограничения

- **Предел тела и абсолютный срок доставки проверены юнит-тестами, а не живым
  прогоном.** Причина названа прямо: `postPinned` по построению отказывается
  соединяться с любым локальным адресом, поэтому поднять медленного получателя
  на той же машине нельзя, не ослабив сам классификатор. Логика чтения вынесена
  отдельной функцией и проверяется потоком напрямую — это та же функция, которую
  вызывает доставка, а не её пересказ.
- **Ограждение аренды доставки проверено арифметикой и чтением, а не двумя
  живыми экземплярами со медленным получателем** — по той же причине.
- Конкурентность проверялась на одной машине и одном экземпляре ядра.
- Статический анализ не заменяет pen-test и разбор поведения под нагрузкой.
