## Фаза 6.3 — сервер: действия над учётной записью

**Scope:**

- `database/migrations/M123_user_account_status.sql` — причина, автор и время
  смены состояния; три события журнала;
- `database/migrations/M124_user_status_columns_grant.sql` — права на новые
  колонки (см. находку ниже);
- `packages/contracts/src/domain/admin-users.ts` — действие вместо статуса;
- `apps/core/src/admin/users.service.ts` — `changeStatus`, `updateProfile`;
- `apps/core/src/admin/users.controller.ts` — два маршрута `PATCH`;
- `scripts/check-admin-users-api.mjs` — разделы [8] и [9].

**Решения, которые стоит назвать:**

1. **Нового статуса нет.** Блокировка — это существующий `status='suspended'`,
   который уже проверяется при входе. Добавлены только причина, автор и время.
2. **Передаётся действие, а не желаемый статус.** Снятие блокировки
   возвращает человека в `active` ТОЛЬКО при полном наборе акцептов, иначе в
   `pending_consents`. Иначе блокировка-разблокировка стала бы способом
   активировать аккаунт в обход инварианта M002.
3. **Блокировка закрывает живые сессии** сдвигом рубежа (M035), а не только
   будущие входы.
4. **Причина обязательна на уровне БД** (`CHECK`), а не только в схеме входа.

**Гейт Шагов 2–3:**

| Проверка                   | Результат                                 | Доказательство                                                 |
| -------------------------- | ----------------------------------------- | -------------------------------------------------------------- |
| Валидация                  | причина 3–500, лишнее поле отвергается    | прогон: пустая причина 400, `status` в теле правки профиля 400 |
| AuthZ                      | только `admin`; себя заблокировать нельзя | прогон: HTTP 403 на себе                                       |

**Ограничения:**

- Защита «последний администратор» вживую не воспроизводилась: поодиночке её

  блокирующих друг друга одновременно. Для воспроизведения нужен параллельный
  прогон с двумя сессиями; проверка оставлена как второй замок и описана в
  коде.
- Разблокировка тоже сдвигает рубеж сессий. Это сознательно: у
  заблокированного действующих токенов остаться не должно.

## Фаза 6.4 — сервер: свой профиль (имя, аватар, пароль)

**Scope:**

- `database/migrations/M125_user_avatars_and_password_change.sql` — таблица
  аватаров с RLS и грант `UPDATE (password_hash)`, обещанный комментарием
  M056; три события журнала;
- `packages/contracts/src/domain/profile.ts` (+ экспорт);
- `apps/core/src/identity/profile.service.ts`, `profile.controller.ts`;
- `apps/core/src/app.module.ts`;
- `scripts/check-profile-api.mjs` (новая проверка);
- `README.md` — четыре строки в таблице маршрутов.

**Решения:**

1. **Смена пароля прекращает ВСЕ сессии, включая текущую.** Выпускать новый
   токен взамен нельзя: в рабочем контуре токены выдаёт внешний поставщик
   входа (ADR-003), и поведение разошлось бы между контурами. Ответ прямо
   говорит `sessionsClosed: true` — клиент обязан увести человека на вход.
2. **Счётчик неудач проверяется до argon2.** Иначе подбор текущего пароля
   оплачивается процессором сервера. Ключ — по учётной записи, а не по
   контакту: здесь мы уже знаем, кто пришёл.
3. **Аватар идёт тем же конвейером, что изображения проекта** (M119):
   формат определяется разбором, пределы по пикселям и байтам, варианты
   пересобираются (EXIF с координатами съёмки не переживает пересборку),
   байты отдаёт маршрут ядра, бакет остаётся приватным.
4. **Все маршруты `/me` адресуют только себя** — идентификатор из сессии.
   Проверять владение нечего: чужой профиль этим путём не адресуется.

**Гейт Шагов 2–3:**

| Проверка               | Результат                                                             | Доказательство                                           |

| Валидация              | правила пароля те же, что при регистрации; лишние поля отвергаются    | прогон: слабый пароль 400, `status`/`roles` в теле 400   |
