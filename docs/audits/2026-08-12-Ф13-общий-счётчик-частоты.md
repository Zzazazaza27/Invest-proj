## 2. Что сделано и зачем

Счётчики ограничения частоты жили в памяти процесса. Это не ограничение
частоты, а его видимость: два экземпляра ядра считают свои запросы независимо,
поэтому фактически разрешённая частота умножается на их число, а перезапуск
обнуляет счётчики целиком.

Счётчик переведён в Redis. Отдельно решены три вопроса, каждый — с явной
стороной размена:

1. **Поведение при отказе счётчика.** Плагин по умолчанию пропускает запрос
   мимо лимита (`skipOnError: true`). Для класса auth это то, чего добивается
   атакующий: уронить счётчик и получить неограниченный перебор. Выбрано
   `skipOnError: false` — отказ вместо снятия защиты.
2. **Учётные данные.** Пароль внутри URL попадает в логи подключения и тексты
   ошибок; вынесен в `REDIS_PASSWORD`, адрес с `@` отвергается конфигурацией в
   любом режиме.
3. **Транспорт.** В production обязателен `rediss://` с проверкой цепочки и
   непустым паролем — те же требования, что уже действуют для БД и брокера.

### Отказ счётчика воспроизведён

```
docker stop unicorn-redis  → GET /v1/health = HTTP 500 (generic problem+json)
docker start unicorn-redis → GET /v1/health = HTTP 200
```

То есть недоступный счётчик действительно означает отказ, а не тихий пропуск
мимо лимита, и после возврата счётчика обслуживание восстанавливается само.
Наружу при отказе уходит generic-ошибка без деталей зависимости.

### Отрицательный контроль

Тот же сценарий на двух экземплярах с пустым `REDIS_URL` (поведение до
исправления):

```
на A лимит сработал: true HTTP 429
B после исчерпания A: HTTP 401 — СЧЁТЧИК НЕ ОБЩИЙ (поведение до исправления)
```

То есть прогон действительно различает исправленное и неисправленное
состояние, а не зелёный по построению.

## 5. CODE-AUDIT (Шаг 2)

- **Внешний вызов:** у команд счётчика есть таймаут (`commandTimeout`),
  очередь офлайн-команд выключена, повторы ограничены — зависший Redis не
  держит запрос пользователя.
- **TLS:** проверка цепочки включена явно; отключения проверки нет нигде.
- **Секреты:** пароль не попадает ни в адрес, ни в логи; в репозитории только
  локальный плейсхолдер.
- **Аутентификация инфраструктуры:** в production подключение без пароля не
  проходит валидацию конфигурации.
- **Зависимости:** `ioredis@5.11.1`, MIT, версия закреплена точно; выбрана
  ветка 5.x — именно против неё тестируется `@fastify/rate-limit` v10;
  `npm audit` — 0 уязвимостей.
- **Fail-closed:** отказ счётчика приводит к отказу в обслуживании, а не к
  снятию ограничения.
