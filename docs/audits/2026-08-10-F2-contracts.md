## 4. Решения фазы, влияющие на безопасность

1. **Деньги — строка, не `number`.** IEEE-754 не представляет `0.1` точно.
   Арифметика идёт в копейках через `bigint` (`toMinorUnits`/`fromMinorUnits`);
   тест проверяет, что 10% и 5% от 1 000 000 ₽ считаются точно.
2. **Тариф резолвит сервер.** В `CreateSubscriptionRequest` основателя нет
   поля `planId` — только `projectId`. Подставить чужой, более дешёвый тариф
   технически невозможно, а не «запрещено правилами».
3. **Принятие предложения требует явного `acknowledgedFeeDisclosure: true`.**
   Литеральный тип: `false` не проходит валидацию. Пользователь не может
   заключить регулируемую сделку, не подтвердив, что видел последствие —
   начисление от полной суммы договора однократно.
4. **Оценка без источников не является валидной.** `sources` в `Score` и
   `MentorAnswer` — непустой массив по контракту.
5. **SSRF-фильтр внешних ссылок** в самой схеме: отвергаются `http://`,
   loopback, приватные диапазоны и адрес метаданных облака. Семь негативных
   тестов.
6. **Ответ, не прошедший схему, — ошибка.** Клиент не отдаёт в UI данные,
   разошедшиеся с контрактом: рассинхрон версий обнаруживается сразу.
7. **Повтор только для GET.** POST мог примениться частично; повторять его без
   ключа идемпотентности — способ создать вторую сделку.
8. **Токен не хранится в JS.** Веб-режим — httpOnly-cookie + double-submit
   CSRF; мобильный — Bearer из OAuth PKCE. Проверено тестами: `credentials`,
   `X-CSRF-Token` только на небезопасных методах, `Authorization` только в
   bearer-режиме.

## 5. Ограничения

1. **OpenAPI-документ ещё не генерируется** — `GET /v1/openapi.json` появится
   вместе с core (Ф3). До этого руководство по замене фронтенда ссылается на
   эндпоинт, которого пока нет; в TODO это отражено.
2. **Клиент не проверялся против живого сервера** — сервера нет. Все 16 тестов
   работают на моке транспорта; интеграционная проверка — в Ф3 и Ф11.
3. **Проверка границы выполнена для одного приложения** (`apps/web-public`):
   остальные четыре появятся в Ф10. Скрипт перебирает все существующие, поэтому
   расширится сам.
4. **Живая проверка HTTP-заголовков** по-прежнему не выполнялась.

## 7. Рекомендации

1. Позитивный контроль (F-30) стоит применять ко всем гейтам, а не только к
   этому: гейт, который не умеет падать, ничего не проверяет. Прямое
   подтверждение правила `RULES.md` о позитивном контроле в каждом механизме.
2. Любое новое поле контракта, влияющее на деньги или доступ, должно иметь
   негативный тест до реализации на сервере.
