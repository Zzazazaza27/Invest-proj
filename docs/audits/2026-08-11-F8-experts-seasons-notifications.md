### Разбор двух HIGH

**1. ON CONFLICT против RLS.** Воспроизведено прямым прогоном под ролью
`app_backend`: тот же INSERT без `ON CONFLICT` для чужого `user_id` проходит, с
`ON CONFLICT` — падает `42501 new row violates row-level security policy`.
Проверены три гипотезы: (а) политика INSERT отсутствует — опровергнута
(`notifications_enqueue`, `WITH CHECK true`, роль `app_backend`, подтверждено
`pg_policies`); (б) роль не состоит в группе — опровергнута
(`pg_has_role → true`); (в) `ON CONFLICT` добавляет проверку SELECT-политики —
**подтверждена** воспроизведением на трёх вариантах запроса.

Ослаблять `notifications_own` нельзя: это дало бы API право читать чужие ленты
уведомлений. Дедупликация оставлена на уникальном индексе, а повтор ловится
через `SAVEPOINT` + `ROLLBACK TO SAVEPOINT` по коду `23505` — без savepoint
ошибка обрывала бы всю доменную транзакцию. Проверка до/после: было — HTTP 500
и 0 строк в очереди; стало — HTTP 201 и ровно 1 строка на назначение.

**2. Доступ рецензента к проекту.** Найдено живым прогоном: `POST
/v1/experts/assignments/:id/decision` отвечал 404 при корректном назначении,
потому что запрос джойнит `lab.projects`, а политика M004 эксперта не
перечисляет. Исправлено ОТДЕЛЬНОЙ permissive-политикой (складываются по ИЛИ),
чтобы не переписывать существующую логику доступа. Доступ выдаётся не роли
`expert` вообще, а конкретному эксперту на конкретный проект и только при
статусе назначения `assigned`/`accepted`/`completed`. Позитивный контроль в
тестах: назначенный видит (1 строка), отказавшийся — не видит (0 строк).

## 4. Аудит §3.1 — прикладная безопасность

- **Вход:** все тела и параметры через `parseOrThrow` (строгие схемы, неизвестные
  поля отвергаются). Проверено тестом: посторонний `expertId` в теле рецензии → 400.
- **AuthN/AuthZ:** каждый новый маршрут объявляет роль явно; guard глобальный.
  Разведение проверено живьём: эксперт не назначает (403), не читает сводку
  рецензий (403), не пересчитывает рейтинг (403), не разрешает свой конфликт (403).
- **IDOR:** ни один маршрут уведомлений не принимает `userId` из запроса — только
  из контекста. Живьём: чужое устройство не отзывается (404), чужие уведомления
  не видны (0 строк), рецензия по чужому назначению — 404 (не 403: разница между
  «нет прав» и «нет объекта» была бы оракулом состава рецензентов).
- **Конкурентность:** лимит золотых билетов держит триггер под
  `pg_advisory_xact_lock`, а не проверка в приложении; уникальный индекс
  `assignments_active_uq` не даёт продублировать активное назначение.
- **Секреты:** push-токен не возвращается наружу (проверено живьём); ноль
  секретов в новом коде (SAST + ручной просмотр).
- **Наружу — generic:** ошибки БД переводятся в доменные; сообщение драйвера в
  ответ не попадает.
- **SECURITY DEFINER:** `seasons.refresh_rating()` проверяет роль внутри себя;
  права отозваны у PUBLIC, выданы только `app_backend`. Позитивный контроль:
  вызов без роли организатора → исключение `admin or organizer` (тест);
  прямой `REFRESH MATERIALIZED VIEW` из-под роли приложения → отказ (тест).
- **Зависимости:** новых пакетов не добавлено.
