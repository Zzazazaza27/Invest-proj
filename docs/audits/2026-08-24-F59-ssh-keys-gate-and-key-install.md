### По findings 1–2

Обе версии дефекта — один и тот же класс: **признак «похоже на ключ» был слабее,
чем материал ключа**. Сначала признаком был маркер, потом маркер плюс «сколько-то
base64-символов». Устойчивый признак — закрывающий `-----END` и тело из целых
строк чистого base64; на исходном коде и на прозе он не срабатывает, потому что
там строки содержат пробелы и знаки препинания.

Дефект 2 показателен тем, что **был внесён починкой дефекта 1 и пойман только
повторным прогоном**: после правки в объекты сессии попал новый чекпоинт с самим
исправленным скриптом — и гейт немедленно покраснел на себе. Статическая вычитка
фикса этого не показала.

### По findings 5

Сверка вынесена на `paramiko.Transport`, потому что `SSHClient.connect`
отправляет пароль внутри одного вызова — между рукопожатием и аутентификацией
там некуда вставить проверку. Теперь при расхождении отпечатка соединение
рвётся **до** передачи пароля.

Проверено против живого стенда:

- неверный ожидаемый отпечаток → `ОШИБКА: отпечаток хоста не совпал … Пароль НЕ передан`;
- верный → `[хост] ssh-ed25519 SHA256:mhxr0uUeP1pwYJDPL/He7tVcqO3G45r+bxkJ7F5gT8I — совпал с ожидаемым`, дальше штатный отказ по заведомо неверному паролю.

Отпечаток снят независимо `ssh-keyscan` + `ssh-keygen -lf` и совпал с тем, что
показывает скрипт.

## Решение владельца: парольный вход root остаётся открытым

Finding 7 из Ф58 переведён в **ACCEPTED** (решение 2026-08-24). Контур тестовый;
ужесточение `PasswordAuthentication no` / `PermitRootLogin prohibit-password`
не применяется, потому что работа идёт вдвоём и участник должен уметь завести
свой ключ, не имея доступа.

Риск назван честно и не переписан задним числом: `auth.log` показывает 32
неудачные попытки с шести адресов, перебор идёт постоянно. Риск ограничен
свойствами **этого** контура — наружу открыт единственный порт 22, реальные ПДн
не грузятся, `KMS_MODE=local`. Условие принятия: как только контур перестаёт быть
тестовым или в него попадают реальные данные, решение недействительно. На
production не распространяется.

Следствие: `ssh-key-install.py` перестал быть блокирующим — он писался как ответ
на «как завести ключ при закрытом пароле». Остаётся как процедура: сервер
переустанавливают, и установка должна быть повторяемой, а не ручной.

## Ограничения — что НЕ проверялось

- **Полный путь `ssh-key-install.py` не прогонялся**: он требует пароля root,
  которого в этой сессии не было. Проверены валидация входа (4 негативных
  контроля), обе ветки сверки отпечатка против живого сервера и отказ по
  паролю. **Фактическая запись в `authorized_keys` и шаг 3 (вход по ключу) в
  этой сессии не выполнялись** — они подтверждены только прогоном Ф58, до правок
  этой фазы.
- Ветка `--password-file` не прогонялась (прогонялась `SSH_ROOT_PASSWORD`).
- Ключ с парольной фразой: обработка добавлена, но живым ключом с фразой не
  проверялась — у SERG её нет.
- Гонка «чтение → запись `authorized_keys`»: файл перезаписывается целиком, и
  ключ, добавленный кем-то между чтением и записью, будет потерян. Для двоих
  участников риск принят; атомарная правка — отдельная работа.
- `gate:ssh-keys` в CI **на живом прогоне GitHub Actions не наблюдался** —
  проверен локально. Работа выбрана по `fetch-depth: 0`; без полной истории
  проверка объектов видела бы один коммит.
- Полный `npm run gate` не гонялся: требует поднятой инфраструктуры и `.env`.
  Прогнаны точечно `gate:ssh-keys`, `eslint`, `prettier`, `py_compile`.

## Техдолг

1. **Прогнать `ssh-key-install.py` целиком** при следующей установке ключа —
   включая `--expect-host-key` в штатном режиме. Сейчас доказана только та часть,
   что не требует пароля.
2. **Атомарная правка `authorized_keys`** (временный файл + rename) — закрывает
   потерю чужого ключа при одновременной записи.
3. **Поставить парольную фразу на SERG** (🟢 из Ф58) — после этого проверить
   ветку `PasswordRequiredException` фактом.
4. Убедиться на первом же прогоне CI, что шаг гейта отработал на полной истории.
