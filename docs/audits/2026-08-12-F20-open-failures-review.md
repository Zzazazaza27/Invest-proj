## 1. Падение 1: рендер кабинета основателя — **ПРИЧИНА НАЙДЕНА, ЗАКРЫТО**

### Воспроизведение

Последовательные прогоны не воспроизводили: 14 подряд зелёных. Воспроизвёл
**параллельный** запуск — два одновременных прогона дали падение 1 из 2.

### Гипотезы и что с ними стало

| Гипотеза                    | Проверка                                                               | Итог                         |
| --------------------------- | ---------------------------------------------------------------------- | ---------------------------- |
| Исчерпано ведро класса auth | Прогон падает с явным «регистрация: HTTP 429», а не таймаутом локатора | **отвергнута**               |
| Холодный preview-сервер     | Перезапуск сервера + немедленный прогон                                | **отвергнута** — прошёл      |
| Нагрузка/конкуренция        | Два одновременных прогона                                              | **подтверждена как условие** |

### Причинная цепь

Диагностика, добавленная в прогон, назвала причину в момент падения:

```
последние вызовы API: … | GET /v1/taxonomy → 200 | POST /v1/projects → 400
ошибки консоли: Failed to load resource: … 400 (Bad Request)
```

`CreateProjectForm` инициализирует `taxonomyId` пустой строкой и заполняет её
только после ответа справочника. Под нагрузкой прогон успевал нажать «Создать»
раньше ответа — сервер отвергал запрос с 400, форма оставалась открытой, и
ожидаемый элемент карточки не появлялся никогда.

### Исправление — с двух сторон

1. **Продукт:** кнопка «Создать» неактивна, пока справочник не загружен, и
   причина названа словами под кнопкой. Отправка, ведущая только к отказу, не
   должна быть нажимаемой.
2. **Прогон:** ждёт появления пункта в списке направлений, а не времени.

### Проверка до и после

|       | Результат                                    |
| ----- | -------------------------------------------- |
| До    | 2 одновременных прогона → 1 падение          |
| После | 3 одновременных → 3/3; 4 одновременных → 4/4 |

## 2. Падение 2: зонд уборки брошенных загрузок — **НЕ ВОСПРОИЗВЕДЕНО, OPEN**

### Что известно из исходного случая

Оборвался за ~1 с после шести успешных проверок, не напечатав ни строки
причины, с ненулевым кодом возврата. Аудит не записывал ни код, ни сигнал —
поэтому различить «упал сам» и «был убит» невозможно даже задним числом.

### Попытки воспроизведения — ~20 прогонов в пяти условиях

| Условие                                                                             | Результат |
| ----------------------------------------------------------------------------------- | --------- |
| Одиночный прогон                                                                    | 5/5 чисто |
| Тем же способом, каким запускает аудит (`spawnSync`, `shell:true`, то же окружение) | чисто     |
| Парой после зонда отзыва токена (порядок как в аудите)                              | чисто     |
| Под нагрузкой трёх параллельных браузерных прогонов                                 | чисто     |
| Двумя копиями одновременно (конкуренция за порт 4304)                               | обе 14/14 |

### Что сделано вместо догадки

1. **Аудит печатает `status`/`signal`/`error`** упавшего прогона. Проверено
   подстановкой скрипта, который печатает две успешные строки и выходит с кодом
   3: аудит называет `завершение: status=3 signal=—`.
2. **Зонды падают с объяснением**, если поднятый ими экземпляр умер или порт
   занят чужим процессом. Проверено: с `CORE_JANITOR_PORT=4300` (занят рабочим
   ядром) зонд печатает «ЭКЗЕМПЛЯР ОБСЛУЖИВАНИЯ ЗАВЕРШИЛСЯ САМ» и падает. До
   этого он дожидался health **от чужого процесса** и объявлял проверку
   пройденной — ложное зелёное, найденное по ходу расследования.

Статус остаётся **OPEN**: причина не установлена, а объявлять её найденной без
доказательства — то же самое, что закрыть находку словами.
