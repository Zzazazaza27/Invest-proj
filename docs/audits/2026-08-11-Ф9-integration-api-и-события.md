### Разбор двух HIGH

**1. Молчаливый успех фонового старта.** Симптом: правки не влияют на поведение
вообще. Проверены три гипотезы: (а) ошибка в коде guard — опровергнута чтением
и типами; (б) кеш сборки — опровергнут пересборкой; (в) отвечает другой
процесс — **подтверждена** через `netstat -ano`: порт 4300 держал pid прежнего
запуска, а в `core.log` были записи от него же. Исправлено в самом инструменте:
занятый порт теперь отказ, а не пустая строка успеха. Проверка до/после: было —
25 FAIL при корректном коде; стало — 50 OK на той же сборке.

**2. Чужая схема аутентификации.** Глобальный guard включён намеренно
(deny by default), и `@Public()` его не выключает при наличии заголовка
`Authorization`: он пытается верифицировать токен и падает. Введена явная
пометка `@ServiceAuth()` — «маршрут проверяет другой guard». Это не ослабление:
маршрут по-прежнему закрыт, просто проверку выполняет `IntegrationGuard`,
который требует токен сервисного клиента и объявленный скоуп.

## 4. Аудит §3.1 — прикладная безопасность

- **Вход:** все тела и параметры через `parseOrThrow`; курсоры пагинации
  проверяются по форме и отвергаются при подделке (юнит-тесты).
- **AuthN/AuthZ:** маршрут Integration API без `@Scope(...)` guard отклоняет —
  незаявленное право не выдаётся. Проверено живьём: скоуп `show:read` не
  открывает паспорт (403), сессия администратора не открывает Integration API
  (401), подделанная подпись токена — 401.
- **Секреты:** секрет клиента и секрет подписи вебхука выдаются один раз;
  в БД лежат Argon2id-хеш и шифртекст соответственно (проверено прогоном).
  Сравнение секретов — Argon2 verify и `timingSafeEqual`, обычного `===` нет
  (SAST-правило проекта).
- **Оракулы:** неизвестный `client_id` и неверный секрет отвечают одинаково;
  проверка идёт против фиктивного хеша, чтобы время ответа не выдавало список
  клиентов.
- **Конкурентность:** очередь разбирается через `FOR UPDATE SKIP LOCKED`;
  снятие роли администратора берёт advisory-лок ДО подсчёта, иначе две
  одновременные операции сняли бы последних двух.
- **Идемпотентность:** регистрация внешнего листинга идемпотентна по паре
  (система, внешний id); публикация дедуплицируется `msgID` на стороне стрима.
- **ПДн:** ни один ответ Integration API не содержит идентификаторов людей —
  проверено регулярным поиском по фактическим ответам в прогоне.
- **Внешние вызовы:** таймаут на каждой доставке; редиректы запрещены
  (`redirect: 'error'`), тело ответа получателя в логи не пишется.
- **Зависимости:** добавлен `nats@2.29.3` с закреплённой версией, `npm audit`
  чист.

## 5. Аудит §3.2 — сетевая безопасность

Прогон `scripts/network-audit.mjs`: 13 проверок, 0 находок.

Фаза изменила сетевой периметр в двух местах, и оба проверены отдельно:

1. **Исходящие соединения появились впервые** — доставка вебхуков ходит на
   адреса, заданные внешней системой. Барьеров три: схема запроса (только
   https, без учётных данных в URL), CHECK в БД и проверка резолва **перед
   каждой доставкой**. Последнее закрывает DNS rebinding, от которого проверка
   при регистрации не защищает вовсе. Живьём отвергнуты: http, `localhost`,
   `10.0.0.5`, `169.254.169.254`, `127.0.0.1`, `[::1]`, адрес с учётными
   данными. Юнит-тестами закрыты границы диапазонов, CGNAT, ULA, link-local и
   IPv4-mapped IPv6 (`::ffff:127.0.0.1`).
2. **Новый публичный маршрут выдачи токена** отнесён к классу лимита `auth`
   (30/мин) — тот же класс, что и вход человека: это проверка секрета, и
   перебор по ней ограничивается так же жёстко.

Подключение к NATS — на loopback, с аутентификацией по паролю, вынесенному из
URL. Порты фаза не открывала.

## 6. Ограничения — что НЕ проверено вживую

- **Секрет-скан** `gitleaks` локально не установлен: только CI.
- **Реальная интеграция с Capital:** события забирает собственный тестовый
  потребитель. Сквозной сценарий с внешней системой не проверялся.
- **mTLS:** заголовок от терминирующего прокси; прокси в локальном контуре нет,
  поэтому в dev проверка отпечатка выключена. В production пустое имя заголовка
  не проходит валидацию конфигурации — приложение не стартует.
- **Успешная доставка вебхука по реальному адресу:** проверены постановка в
  очередь, учёт неудачи и отложенный ретрай; сама успешная доставка требует
  внешнего HTTPS-приёмника, а доставка на loopback запрещена по построению.
- **Ротация KEK домена вебхуков** не прогонялась.
- **Инвариант «последний администратор»:** в базе прогона 53 действующих
  администратора (наследие прошлых прогонов), поэтому ветка отказа не
  воспроизведена живьём — закрыта логикой с advisory-локом и проверена на
  разжаловании второго администратора.
