# SESSION AUDIT REPORT — Ф25: редакция секретов в чекпоинтах Entire

Дата: 2026-08-12
Ветка: `main`
Предыдущая фаза: Ф24 (обработка внешнего аудита)

## 1. Что делалось

Инцидент 2026-08-12 (зафиксирован в коммите `aa82c05`): ветка
`entire/checkpoints/v1` унесла в git-объекты проекта ключевой материал
`KEK_KYC_DOCUMENTS`, `KEK_PASSPORT_SENSITIVE`, `KEK_NOMINAL_ACCOUNT_EVIDENCE`.
Тогда объекты вычистили, а Entire выключили флагом `enabled=false` — то есть
причину не устранили, а отключили функциональность.

Задача фазы: настроить редакцию секретов, доказать замером, что она работает,
и только после этого включить Entire обратно.

Порядок соблюдён: редакция → проверка → включение.

## 2. Расследование: почему встроенный детектор пропустил ключи

Встроенный конвейер Entire (Betterleaks + собственные слои) описан в
[docs.entire.io/security](https://docs.entire.io/security) и состоит из пяти
проходов. Существенны два:

- **энтропийный** — строки от 10 символов с энтропией Шеннона выше 4.5;
- **ограниченный по имени** — присваивания, где имя входит в список известных
  учётных имён: `DB_PASSWORD`, `PGPASSWORD`, `MYSQL_PWD`, `REDIS_PASSWORD`,
  `MONGO_PASSWORD`, `MONGODB_PASSWORD`.

`KEK_*` в этот список не входит. Проверка на стенде (см. §3) показала, что
44-символьные base64-ключи всё же перехватываются энтропийным проходом —
а вот значения длиной 24 символа и короче не перехватываются ничем:
энтропия 24-символьной base64url-строки ≈ 4.3, ниже порога 4.5.

Отсюда фактическая граница встроенной защиты: **секрет короче ~30 символов,
чьё имя не входит в список из шести, не редактируется**. В `.env` проекта под
это описание попадают `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `NATS_PASSWORD`,
`MINIO_ROOT_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`, `S3_SECRET_ACCESS_KEY`,
`OIDC_CLIENT_SECRET`, `DB_ROLE_PASSWORD_APP_*`.

Оговорка: воспроизвести исходную утечку именно `KEK_*` замером не удалось —
на стенде 44-символьные ключи редактируются. Вероятная причина расхождения —
иная форма попадания значения в транскрипт (не проверялось). Вывод фазы от
этого не меняется: правила добавлены и на `KEK_*` тоже.

## 3. Стенд и замер

Стенд: чистый git-репозиторий, `entire enable`, синтетический транскрипт
Claude Code с подставными секретами формы реальных, импорт через
`entire import claude-code --path`, затем сверка **всех** git-объектов с
эталоном значений. Реальные секреты на стенд не выносились.

Секреты размещены в четырёх местах транскрипта: `tool_result.content`,
`toolUseResult.file.content`, тексте ответа ассистента, `tool_use.input.command`.

| Прогон | Конфигурация | Утекло значений |
|---|---|---|
| A | только встроенный детектор | **2 из 8** — `POSTGRES_PASSWORD` (24), `OIDC_CLIENT_SECRET` (9) |
| B | + `project-secrets.yaml` | **1 из 8** — `POSTGRES_PASSWORD`, процитированный в тексте |
| C | + `local/env-values.yaml` | **0 из 8** |

Прогон B локализовал класс, который правилами на имена закрыть нельзя:
присваивание `POSTGRES_PASSWORD=…` пак закрыл (имя перестало встречаться в
объектах вовсе), но в тексте ответа — «пароль базы `<значение>`» — якоря-имени
нет, а 24 символа не дотягивают до порога энтропии. Обобщённое правило на
строку такой длины выжгло бы обычные идентификаторы. Закрывается только
точным совпадением значения — отсюда локальный пак.

Прогон C подтвердил заодно, что Entire загружает паки из
`.entire/redactors/local/`.

## 4. `gitleaks` даёт ложный зелёный на этом классе

На прогоне A, где `POSTGRES_PASSWORD` и `OIDC_CLIENT_SECRET` фактически лежали
в git-объектах, `gitleaks detect` вернул **0**. Сигнатурный сканер ищет
узнаваемые формы и связку «ключевое слово рядом со значением»; секрет,
процитированный в свободном тексте, под них не подходит.

Следствие: критерий «после сессии `gitleaks` чист» не является доказательством
отсутствия утечки ключевого материала. Введён зонд
`scripts/probe-secret-leak.mjs` — побайтовая сверка объектов репозитория со
значениями из `.env`. Гейт проверен на падение: на прогоне A возвращает 1 и
называет ровно те два значения, на прогоне C — 0.

| `scripts/build-local-redactors.mjs` | генерирует `.entire/redactors/local/env-values.yaml` из `.env`; отказывается писать, если каталог перестал игнорироваться git |
| `scripts/probe-secret-leak.mjs` | сверка объектов репозитория с `.env`; значения секретов не печатает |
| `.secret-leak-allow.json` | принятые осознанно значения, с причиной и планом снятия |
| `.entire/settings.json` | `enabled: true` |
| `.entire/.gitignore` | снято недействующее правило `checkpoints/`, записан разбор инцидента |

Правило `checkpoints/` снято намеренно: данные чекпоинтов живут в git-ССЫЛКЕ,
а не в рабочем каталоге, `.gitignore` на ссылки не влияет, каталог
`.entire/checkpoints/` не создаётся вообще. Правило выглядело защитой, ничего
не защищая; единственным реальным ограничителем был выключенный `enabled`.

## 8. Ограничения

- Исходная утечка `KEK_*` замером не воспроизведена (§2); правила добавлены
  по форме и по имени, но конкретный путь попадания не установлен.
- Зонд сверяет объекты только с текущим `.env`. Секреты, ротированные ранее,
  он не ищет — их значений у него нет.
- Локальный пак редактирует значения на момент генерации. После ротации
  обязателен `npm run secrets:redactors`, иначе новые значения уйдут в
  транскрипт открытыми. Автоматической проверки этой рассинхронизации нет.
- Проверка выполнена на импорте транскрипта (`entire import claude-code`).
  Путь «живая сессия → shadow-ветка → condense» отличается механикой записи;
  редакция по документации применяется на обоих, но отдельным замером на живой
  сессии это в фазе не подтверждалось.
- Статический разбор не заменяет пентест.
