## 1. Что делалось

Инцидент 2026-08-12 (зафиксирован в коммите `aa82c05`): ветка
`entire/checkpoints/v1` унесла в git-объекты проекта ключевой материал
`KEK_KYC_DOCUMENTS`, `KEK_PASSPORT_SENSITIVE`, `KEK_NOMINAL_ACCOUNT_EVIDENCE`.
Тогда объекты вычистили, а Entire выключили флагом `enabled=false` — то есть
причину не устранили, а отключили функциональность.

Задача фазы: настроить редакцию секретов, доказать замером, что она работает,
и только после этого включить Entire обратно.

Порядок соблюдён: редакция → проверка → включение.

## 2. Расследование: почему встроенный детектор пропустил ключи

Встроенный конвейер Entire (Betterleaks + собственные слои) описан в
[docs.entire.io/security](https://docs.entire.io/security) и состоит из пяти
проходов. Существенны два:

- **энтропийный** — строки от 10 символов с энтропией Шеннона выше 4.5;
- **ограниченный по имени** — присваивания, где имя входит в список известных
  учётных имён: `DB_PASSWORD`, `PGPASSWORD`, `MYSQL_PWD`, `REDIS_PASSWORD`,
  `MONGO_PASSWORD`, `MONGODB_PASSWORD`.

`KEK_*` в этот список не входит. Проверка на стенде (см. §3) показала, что
44-символьные base64-ключи всё же перехватываются энтропийным проходом —
а вот значения длиной 24 символа и короче не перехватываются ничем:
энтропия 24-символьной base64url-строки ≈ 4.3, ниже порога 4.5.

Отсюда фактическая граница встроенной защиты: **секрет короче ~30 символов,
чьё имя не входит в список из шести, не редактируется**. В `.env` проекта под
это описание попадают `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `NATS_PASSWORD`,
`MINIO_ROOT_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`, `S3_SECRET_ACCESS_KEY`,
`OIDC_CLIENT_SECRET`, `DB_ROLE_PASSWORD_APP_*`.

Оговорка: воспроизвести исходную утечку именно `KEK_*` замером не удалось —
на стенде 44-символьные ключи редактируются. Вероятная причина расхождения —
иная форма попадания значения в транскрипт (не проверялось). Вывод фазы от
этого не меняется: правила добавлены и на `KEK_*` тоже.

## 3. Стенд и замер

Стенд: чистый git-репозиторий, `entire enable`, синтетический транскрипт
Claude Code с подставными секретами формы реальных, импорт через
`entire import claude-code --path`, затем сверка **всех** git-объектов с
эталоном значений. Реальные секреты на стенд не выносились.

Секреты размещены в четырёх местах транскрипта: `tool_result.content`,
`toolUseResult.file.content`, тексте ответа ассистента, `tool_use.input.command`.

| Прогон | Конфигурация | Утекло значений |
|---|---|---|
| A | только встроенный детектор | **2 из 8** — `POSTGRES_PASSWORD` (24), `OIDC_CLIENT_SECRET` (9) |
| B | + `project-secrets.yaml` | **1 из 8** — `POSTGRES_PASSWORD`, процитированный в тексте |
| C | + `local/env-values.yaml` | **0 из 8** |

Прогон B локализовал класс, который правилами на имена закрыть нельзя:
присваивание `POSTGRES_PASSWORD=…` пак закрыл (имя перестало встречаться в
объектах вовсе), но в тексте ответа — «пароль базы `<значение>`» — якоря-имени
нет, а 24 символа не дотягивают до порога энтропии. Обобщённое правило на
строку такой длины выжгло бы обычные идентификаторы. Закрывается только
точным совпадением значения — отсюда локальный пак.

Прогон C подтвердил заодно, что Entire загружает паки из
`.entire/redactors/local/`.

## 4. `gitleaks` даёт ложный зелёный на этом классе

На прогоне A, где `POSTGRES_PASSWORD` и `OIDC_CLIENT_SECRET` фактически лежали
в git-объектах, `gitleaks detect` вернул **0**. Сигнатурный сканер ищет
узнаваемые формы и связку «ключевое слово рядом со значением»; секрет,
процитированный в свободном тексте, под них не подходит.

Следствие: критерий «после сессии `gitleaks` чист» не является доказательством
отсутствия утечки ключевого материала. Введён зонд
`scripts/probe-secret-leak.mjs` — побайтовая сверка объектов репозитория со
значениями из `.env`. Гейт проверен на падение: на прогоне A возвращает 1 и
называет ровно те два значения, на прогоне C — 0.

## 8. Проверка на реальных данных

Стенд отвечает на вопрос «работает ли механика», но не на вопрос «работает ли
она на нашем транскрипте». Поэтому дополнительно:

Из 94 локальных транскриптов Claude Code по этому проекту **11 содержат
реальный ключевой материал**; худший — 29 из 31 различного значения (все
`DATABASE_URL_*`, ключи подписи, KEK). Именно он импортирован в ветку
чекпоинтов: `entire import claude-code --session 65f9afa8…`, 33 перехода.

Результат:

| Проверка | Значение |
|---|---|
| Объектов в репозитории после импорта | 1919 (было 1636) |
| Содержимое ветки чекпоинтов | 198 файлов, 555 МБ, 18 449 вхождений `REDACTED` |
| `probe:secret-leak` | 0 утечек |
| `gitleaks detect` | 0 находок, 98 коммитов, 572 МБ |

Объём содержимого и число замен важны: зелёный результат на пустой ветке
ничего бы не значил.

Попутно `gitleaks` дал 2 находки на **самом паке** — синтетические значения из
`samples` по построению выглядят как настоящие ключи и попали под правила
`unicorn-kek-material` и `generic-api-key`. Исправлено по конвенции проекта:
образцы сделаны самоописательными (`SAMPLE_NOT_A_REAL_KEY_VALUE`) вместо
расширения allowlist. Правила проекта требуют чистого base64 без подчёркиваний,
поэтому подчёркивание в образце снимает срабатывание, а собственные правила
пака его по-прежнему ловят: 31 самопроверка, 0 расхождений.

Живая сессия при этом чекпоинт не создала: Entire был выключен на её старте,
поэтому сессия не зарегистрирована. Захват начнётся со следующей сессии —
проверка выполнена импортом, что покрывает тот же путь редакции.

## 9. Ротация утёкших KEK

Вопрос владельца: «`KEK_PASSPORT_SENSITIVE` шифрует контакты пользователей,
простая замена их обнулит».

Разбор `apps/core/src/crypto/crypto.service.ts` показывает, что схема
**конвертная**: значение шифруется одноразовым DEK, а KEK шифрует только сам
DEK. Данные при ротации не перешифровываются — меняется лишь обёртка.
Опасение верно ровно для слепой подстановки нового значения в `.env` без
переобёртки: тогда старые `wrapped_dek` перестанут открываться.

Три утёкших ключа делятся на две группы:

| Ключ | Чем защищён | Стоимость ротации |
|---|---|---|
| `KEK_KYC_DOCUMENTS` | **ничем** — домен объявлен, обращений в коде 0 | замена значения в `.env` |
| `KEK_NOMINAL_ACCOUNT_EVIDENCE` | **ничем** — домен объявлен, обращений в коде 0 | замена значения в `.env` |
| `KEK_PASSPORT_SENSITIVE` | `identity.users`: `email_ciphertext`, `phone_ciphertext` через `contact_wrapped_dek` | переобёртка 1403 строк, данные не читаются |

Существенная деталь: blind index (`email_hmac`, `phone_hmac`) построен на
**другом** домене — `search_index`. Ротация `passport_sensitive` поиск не
ломает. Повезло: `KEK_SEARCH_INDEX` в утечку не попал, а его ротация как раз
дорогая — все индексы пришлось бы пересчитывать из открытых значений.

Написан `scripts/rotate-kek.mjs` (`npm run rotate:kek`). Проверен на живой базе:

| Проверка | Результат |
|---|---|
| Осмотр `passport_sensitive` | 1403 строки, текущий ключ открывает все обёртки, 1403 поля успешно расшифрованы |
| Ротация с откатом (`--test`) | переобёрнуто 1403; новым ключом открывается — да, старым отвергается — да; транзакция откачена |
| База после отката | не изменена (повторный осмотр проходит старым ключом) |
| Отказ для `search_index` | код 1, названа причина (HMAC-домен) |
| Отказ для `webhook_secrets` | код 1, названа причина (прямое шифрование, нужна перешифровка) |
| Неиспользуемый домен | код 1, сказано, что достаточно замены в `.env` |

Ротация **не выполнена**: она меняет `.env` и требует перезапуска ядра, то есть
затрагивает окружение владельца. Решение за владельцем; механика готова и
проверена.

## 10. Гейт на рассинхронизацию пака

Самый простой способ вернуть утечку — сменить секрет и забыть пересобрать
локальный пак: он продолжит редактировать прежние значения, а новые уйдут в
транскрипт открытыми. `probe:secret-leak` поймает это только постфактум, когда
утечка уже в объектах.

Добавлен `npm run gate:redactors` (`build-local-redactors.mjs --check`):
пересобирает пак в памяти и сверяет с файлом на диске, ничего не записывая.
Значения не печатает — при расхождении называет идентификаторы правил.

| Сценарий | Ожидание | Результат |
|---|---|---|
| Пак совпадает с `.env` | 0 | 0, «пак актуален: 34 правил» |
| Значения разошлись (ротация без пересборки) | 1 | 1, «состав правил тот же — разошлись сами значения» |
| Пак отсутствует | 1 | 1, «секреты из .env не редактируются в транскриптах» |

В общий `npm run gate` не включён: требует `.env`, которого в CI нет.

## 11. Ограничения

- Исходная утечка `KEK_*` замером не воспроизведена (§2); правила добавлены
  по форме и по имени, но конкретный путь попадания не установлен.
- Зонд сверяет объекты только с текущим `.env`. Секреты, ротированные ранее,
  он не ищет — их значений у него нет.
- Локальный пак редактирует значения на момент генерации. После ротации
  обязателен `npm run secrets:redactors`, иначе новые значения уйдут в
  транскрипт открытыми. Автоматической проверки этой рассинхронизации нет.
- Живой путь «сессия → shadow-ветка → condense» **подтверждён**: коммит
  `fa52107` создал 2 чекпоинта текущей сессии (ветка чекпоинтов 6 файлов /
  2.78 МБ, 213 замен `REDACTED`; shadow-ветка 370 файлов / 5.47 МБ),
  `probe:secret-leak` — 0 утечек. Оговорка: транскрипт этой сессии беден
  реальными значениями (они сознательно не печатались), поэтому основной вес
  доказательства несёт импорт реального транскрипта с 29 значениями (§8).
- Ротация утёкших KEK не выполнена (§9): она меняет `.env` и требует
  перезапуска ядра. Механика написана и проверена на живой базе с откатом.
- `scripts/rotate-kek.mjs` покрывает только конвертные домены. Перешифровка
  `webhook_secrets` и пересчёт blind index для `search_index` не реализованы —
  скрипт явно отказывается и называет причину.
- Карта «домен → таблица» в `rotate-kek.mjs` поддерживается вручную. Новый
  домен или новая колонка с обёрнутым DEK туда не попадут автоматически;
  автоматической сверки с вызовами `crypto.seal*` нет.
- Статический разбор не заменяет пентест.
