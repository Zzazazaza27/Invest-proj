> **Статус после 2.1-W05 (29.10.2026):** пакеты, раунды, оплата, разбор заявки ИИ, экспертиза и кабинет эксперта удалены из кода и базы (миграция M150). Маршрут сохранён как история; действующий маршрут приёмки собирает `node scripts/seed-acceptance.mjs` в `.local/приёмка.md`.

Что показать на локальном стенде, в каком порядке, и — главное — что при этом

2026-09-19 (этап 5.9.9).

Чистая переустановка стенда — в `clean-local-deployment.md`. Здесь
только запуск и проход.

## 1. Запуск локального стенда

**Одна команда:**

```bash
npm run stand:up
```

Она собирает приложения, поднимает контейнеры, накатывает миграции, создаёт
поток событий, запускает ядро и шлюз анализа, останавливает лишние
dev-серверы, включает единую точку входа и проверяет все маршруты. Повторный
запуск на работающем стенде безопасен: поднятое не трогается, недостающее
добавляется.

| Команда                          | Что делает                                         |
| -------------------------------- | -------------------------------------------------- |
| `npm run stand:up`               | поднять всё и проверить                            |
| `npm run stand:up -- --no-build` | то же без пересборки статики (быстрее)             |
| `npm run stand:status`           | что работает, что нет и почему                     |
| `npm run stand:down`             | остановить; **данные остаются** в томах Docker     |
| `npm run infra:reset`            | удалить данные — отдельная команда с другим именем |

## Основной адрес — http://127.0.0.1/

Один адрес без портов. Это не косметика: страница и API лежат на ОДНОМ origin,
поэтому сессионная cookie работает во всех кабинетах, изображения проектов не
упираются в политику встраивания, а список разрешённых origin в CORS вообще не
участвует.

| Что                | Адрес                      |
| ------------------ | -------------------------- |
| Витрина            | http://127.0.0.1/          |
| Вход и регистрация | http://127.0.0.1/login/    |
| Кабинет основателя | http://127.0.0.1/lab/      |
| Кабинет инвестора  | http://127.0.0.1/investor/ |
| Кабинет эксперта   | http://127.0.0.1/expert/   |
| Админка            | http://127.0.0.1/admin/    |
| Служебная консоль  | http://127.0.0.1/console/  |

Служебная консоль анониму отвечает **404**, администратору — открывается. Это
не поломка: её прячет роль, а не отдельный контур, и 403 подтверждал бы, что
она здесь есть.

**Учётные записи** — в `.local/приёмка.md` (каталог вне Git). Там два набора:
обстановка приёмки (`priem-*`, у каждого свой пароль) и демонстрационный
комплект (`demo-*`, пять проектов и девять ролей, пароль общий из `.env`).
Пересобрать файл: `node scripts/seed-acceptance.mjs`.

**Демонстрационный комплект грузится отдельно:**

```bash
node scripts/seed-demo.mjs load     # загрузить
node scripts/seed-demo.mjs status   # что сейчас загружено
```

Он не часть `stand:up` намеренно: это ДАННЫЕ, и подкладывать их при каждом
подъёме стенда значило бы воскрешать удалённое. Но `stand:status` теперь
проверяет его наличие — потому что однажды стенд отвечал «работает целиком»,
а входа под `demo-*` не было: базу пересоздали, комплект не перезалили, и
выглядело это как неверный пароль.

## Что работает под капотом

nginx раздаёт СОБРАННУЮ статику из каталогов `dist`, а не проксирует на
dev-серверы Vite: локальная раздача устроена ровно как боевая, и разница между
«работает у меня» и «работает на стенде» не прячется в прокси. Маршрут `/v1/`
проксируется на ядро, которое работает процессом на хосте.

Отсюда следствие: **после правок кода нужна пересборка**. `npm run stand:up`
делает её сам; `--no-build` — осознанный пропуск, когда код не менялся.

## Если нужны dev-серверы

Прямой запуск Vite (`npm run dev -w apps/lab` и т.п.) остаётся для разработки
интерфейса с горячей перезагрузкой. Но при поднятой единой точке входа это
ВТОРОЙ стенд из исходников: половина проверок пойдёт на :5175, половина на
единый адрес, и расхождение между собранным и исходным кодом обнаружится не
сразу. Поэтому `stand:up` их останавливает, а `stand:status` предупреждает,
если они снова появились.

Браузерные прогоны умеют ходить через единый адрес:

```bash
FIFTH_ENTRY=web node scripts/render-check-first-tier.mjs
```

Без переменной они идут по dev-портам — так проверяется другой режим, и оба
имеют право на существование.

## Грабли, которые эти команды закрывают

Ниже — то, на чём здесь спотыкались раньше. Сейчас за это отвечает `stand:up`,
но при ручном запуске частями всё возвращается.

- **`dev-core.mjs`, а не `node dist/main.js`.** Ядро не умеет читать `.env`
  само (и не должно: в production переменные приходят из хранилища секретов).
  Запуск напрямую падает на `DATABASE_URL: expected string, received undefined`.
- **`npm run dev -w apps/core` на Windows поднимает только компилятор.** В
  скрипте два процесса через `&`, и `cmd.exe` этого не понимает: TypeScript
  собирается, сервер — нет.
- **Остатки прошлых запусков.** Прерванный запуск оставляет живой
  watch-компилятор `tsc` или процесс `node --watch dist/main.js`, который порт
  не слушает. Оба выглядят как работающий сервис в списке процессов. Проверять
  по ПОРТУ, а не по имени — этим и занимается `stand:status`.
- **При работе с dev-серверами: после правок в `packages/*` их надо
  перезапускать с очисткой кеша Vite** (`node_modules/.vite`). Vite
  предварительно собирает зависимости и не замечает пересборку рабочего
  пакета: кабинет продолжает звать старый клиент API, метод «не существует»,
  запрос молча падает — и экран показывает прошлое состояние без единой ошибки
  в консоли. На едином адресе этой грабли нет вовсе: там раздаётся сборка.
- **Порты заданы в `scripts/lib/ports.mjs`**; проверки берут их оттуда же.

Для платежей в `.env` нужны три переменные (образец — в `.env.example`):

```
PAYMENTS_PROVIDER=test
PAYMENTS_MODE=test
PAYMENTS_WEBHOOK_SECRET=<не короче 32 символов>
```

Ключ живёт только в окружении. В базе и в репозитории его нет и быть не
должно.

## 2. Маршрут показа

Два кабинета, две роли. Удобнее в двух окнах браузера.

### Шаг 1. Администратор готовит предложение

Админка → **Пакеты раунда**.

1. Завести услуги и отметить их реализованными.
2. Создать версию пакета: цена, валюта, страна, диапазон суммы запроса.
3. При необходимости — назначить **допустимые замены**: расширенный пакет
   становится заменой требуемого только по явному назначению. Ни цена, ни
   совпадение состава заменой не делают; несовпадение состава показывается
   предупреждением, решение принимает человек.
4. Блок **Оператор платежей** на этой же странице показывает, что произойдёт
   при попытке оплатить: подключён тестовый адаптер, настоящие платежи не
   принимаются, подпись уведомлений проверяется.

### Шаг 2. Основатель выбирает и оформляет покупку

Кабинет → проект → экран раунда.

5. Сумма запроса определяет **требуемый** пакет. Экран называет его, показывает
   итог и валюту, объясняет расчёт словами.
6. Выбрать замену или докупить услугу. Выбор сохраняется и переживает
   перезагрузку страницы.
7. **Оформить покупку.** Сумма берётся из расчёта на сервере, а не из запроса;
   покупка хранит снимок условий. Повторное нажатие второй покупки не создаёт.

### Шаг 3. Оплата

8. **Перейти к оплате.** Создаётся платёж на серверную сумму, появляется адрес
   страницы оплаты.
9. Вернуться на экран раунда. Состояние — «ждём подтверждения оператора».
   Возврат со страницы оплаты ничего не подтверждает, и это видно.
10. Подтверждение приходит уведомлением оператора. Локально его посылает
    прогон `scripts/smoke-payments.mjs` — он подписывает уведомление тем же
    ключом и отправляет на `POST /v1/billing/payments/notify`.

Альтернатива для показа без скрипта: админка → **Покупки запуска** →
«подтвердить тестовую оплату». Это ручной путь оператора, он закрыт ролью,
флагом и окружением и помечает покупку тестовой навсегда.

### Шаг 3а. Разбор заявки (услуга платформы)

Если услуга в пакете помечена как исполняемая платформой (`ai_analysis`), в
кабинете появляется блок «Услуги, которые выполняет платформа».

10а. **Запустить разбор.** Прогон фиксирует версию заявки и отпечаток входа,
обращается к AI-шлюзу и сохраняет отчёт. Только после этого позиция
закрывается — отметить её руками нельзя.
10б. Экран говорит, ЧЕМ выполнен разбор. Сегодня — «по правилам, без языковой
модели»: ключа провайдера нет, и называть это полноценным ИИ-анализом
нельзя.
10в. Изменить заявку и обновить экран: отчёт остаётся, но помечается как
относящийся к прошлой версии.

**Что именно разбирается.** Ответы ПОДАННОЙ версии анкеты вместе с
формулировками вопросов и стадией; карточка проекта (название, подзаголовок,
описание, сумма запроса, валюта, отрасль, страна); ТИПЫ подтверждённых
материалов. Содержимое материалов и ссылки наружу не уходят. Черновик заявки в
разбор не берётся: отчёт привязан к версии, а черновик меняется в любую
секунду. Если заявка не подана, разбор идёт по карточке проекта — и отчёт так
и называется, «анализом версии заявки» его не зовут.

Услуга с обещанием ИИ-анализа до подключения модели не продаётся: пометить её
реализованной база не даёт.

Шлюз должен быть поднят: `node scripts/dev-ai-gateway.mjs` (венв ставится
один раз: `python -m venv apps/ai-gateway/.venv` и установка requirements).

### Шаг 4. Выполнение услуг

11. Админка → **Покупки запуска**: у каждой позиции своё состояние. Отметку
    «выполнено» ставит человек и обязательно с основанием.
12. Экран основателя по мере этого меняет текст: сперва «покупка не оплачена»,
    затем «услуги не выполнены: 3 из 3», затем «условия выполнены».

### Шаг 5. Открытие раунда

13. Основатель открывает раунд. До этого момента открытие отклоняется, и отказ
    называет причину словами.

### Шаг 6. Сотрудники платформы: полномочия и назначения

Админка → **Доступ**. Четыре раздела, и они отвечают на разные вопросы.

14. **Роли пользователя** — кем человек является (`expert`, `organizer`,
    `admin`). Роль сама по себе не открывает ни одного конкретного действия.
15. **Полномочия сотрудника** — что он вправе делать вообще. Каталог
    реализованных функций по разделам, выдача и отзыв галочкой с обязательным
    основанием. Нереализованное полномочие галочкой не ставится: база не даёт
    выдать обещание несуществующего действия.
16. **Назначение на оценку проекта** (`review`) — открывает рецензенту
    материалы проекта и право написать рецензию. Кнопка «Прекратить доступ»
    закрывает именно доступ и работает при любом состоянии работы, в том числе
    после сданной рецензии: рецензия и её авторство остаются, строка назначения
    тоже. Если рецензии ещё нет, назначение при этом закрывается. Вернуть
    доступ можно только новым назначением. Заявленный и не закрытый конфликт
    интересов выбранного эксперта показывается ДО назначения; отклоняет такое
    назначение всё равно сервер.
17. **Сопровождение сделок проекта** (`deal_support`) — область работы для
    денежных действий. Рецензентских материалов НЕ открывает. Прекращается той
    же кнопкой; уже сделанные записи о деньгах остаются — они о состоявшихся
    событиях.

Три условия нужны одновременно там, где так задумано: полномочие без
назначения не открывает конкретный объект (ответ — «не найдено»: сделка вне
области работы для сотрудника не существует), назначение без полномочия не даёт
трогать деньги (ответ — «недостаточно полномочий»). Ответы разные намеренно:
по ним видно, чего именно не хватает.

Эксперт не может выдать полномочие ни себе, ни другому: маршрут выдачи закрыт
ролью администратора.

**Что этот экран НЕ настраивает.** Каталог полномочий — четыре финансовых
действия, и это весь каталог. Заявки, публикация, комплаенс, поддержка,
тарифы, интеграции работают по ролевой модели: там решает роль целиком плюс,
где заведено, назначение на объект и предикат аудитории проекта.

## 3. Что происходит по-настоящему, а что изображается

Главный раздел документа. Показывать сценарий, не сказав этого, нельзя.

### Работает по-настоящему

| Что                                                              | Замечание                                              |
| ---------------------------------------------------------------- | ------------------------------------------------------ |
| Настройка услуг, пакетов, цен, диапазонов, замен, условий страны | версии неизменяемы, диапазоны в стране не пересекаются |
| Расчёт стоимости запуска раунда                                  | одно место расчёта, его спрашивают все три маршрута    |
| Оформление покупки со снимком условий                            | сумма серверная, повтор не дублирует                   |
| Создание платежа, разбор и проверка уведомления                  | подпись HMAC, повтор события не исполняется дважды     |
| Обработка неуспеха и отмены                                      | после них можно платить заново                         |
| Состояние выполнения услуг сотрудника                            | ставит человек с основанием                            |
| Разбор заявки как оплаченная услуга                              | считает шлюз; отметка только по сохранённому отчёту    |
| Допуск к открытию раунда                                         | одно место, причина называется словами                 |
| Начисление вознаграждения с подтверждённого транша               | по API, экрана нет                                     |
| Ручная фиксация возвратов и корректировок комиссии               | записи о состоявшихся событиях                         |

### Изображается тестовым сценарием

| Что                           | Чем именно изображается                                                   |
| ----------------------------- | ------------------------------------------------------------------------- |
| **Поступление денег**         | тестовый адаптер: платёж помечается `mode = test`, покупка — тестовой     |
| **Страница оплаты оператора** | адрес ведёт на заглушку ядра, настоящей платёжной формы нет               |
| **Уведомление оператора**     | шлёт прогон или ручное подтверждение администратора, а не внешняя система |

Тестовая покупка **не открывает платный раунд в рабочем окружении**: метку
проверяет сам допуск (M107), а бэкенд в production отказывает независимо от
настроек. Это не декоративная защита — именно она ловит запись, попавшую в
рабочую базу переносом дампа.

### Услуги пакета: что из них реально выполняется

Отметку «выполнено» ставит сотрудник вручную, и это честно для услуг, которые
сотрудник и выполняет: проверка комплектности документов, сверка реквизитов,
разбор с экспертом. **Подменять фиктивной отметкой работу ИИ-разбора или
экспертного заключения нельзя** — для первого прохода в пакет берутся только
услуги, выполнимые человеком. Признак «услуга реализована в продукте» в
каталоге отвечает на другой вопрос, чем «услуга выполнена по этой покупке», и
эти два состояния намеренно разведены.

### Отложено

| Что                                             | Состояние                                                                  |
| ----------------------------------------------- | -------------------------------------------------------------------------- |
| Настоящий оператор платежей                     | не выбран; ИП как конфигурация не утверждена                               |
| Счёт как документ                               | таблица есть, выпуска нет                                                  |
| Продление подписки и рекуррентные списания      | `auto_renew` есть и включить его нельзя                                    |
| Движение инвестиционных денег и комиссии        | отдельный процесс, через оператора услуг НЕ идёт                           |
| Возвраты оплаты услуг                           | автоматических возвратов нет; существующие записи — не команда перечислить |
| Ненулевой срок покупки, доплата при росте суммы | отложенные возможности, запуску не мешают                                  |

## 4. Прогоны, которые показывают то же самое без рук

```bash
node scripts/smoke-payments.mjs             # оплата: подпись, повторы, неуспех (43)
node scripts/smoke-service-execution.mjs    # исполнение услуги разбора (25)
node scripts/smoke-round-purchase.mjs       # покупка целиком
node scripts/render-check-round-purchase.mjs # тот же путь в браузере, две роли
node scripts/smoke-staff-capabilities.mjs   # полномочия и ручные записи (39)
node scripts/render-check-staff-access.mjs  # управление экспертами в браузере (26)
```

**Что прогонять после правок анализа.** `smoke-ai` и
`smoke-service-execution` — оба требуют поднятого шлюза. Это не формальность:
четыре проверки `smoke-ai` больше месяца показывали устаревшее поведение и
никто этого не видел, потому что запустить их было нечем — виртуальное
окружение шлюза на машине не создавалось. Теперь оба прогона начинаются с
проверки шлюза и падают с внятным сообщением вместо «анализ завершился
ошибкой».
