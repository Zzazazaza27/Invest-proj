# Полное восстановление рабочей среды на чистом узле

Работа № 5 раздела 01 (2.1.4, протокол по 2.5). Это же подтверждение переноса. Покупка новой
площадки и географическая независимость — отдельные условия.

**Состояние на 12.11.2026:** код и инструкция готовы. На площадке не запускались: создание
площадки и работа с настоящей копией prod — этап общей приёмки, по слову Томаса.

## Что лежит в комплекте

Комплект копий (`backup.mjs set`, на узле под root) берёт то, с чем узел работает сейчас, а
не файлы репозитория:

| Часть                 | Откуда                                                                                                       | Где в копиях                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| Compose               | метки запущенных контейнеров: файлы проекта, файл переменных, рабочий каталог; примонтированные с узла файлы | `sets/<id>/config/host`                              |
| Юниты                 | каждый локально установленный юнит: файл, drop-in, EnvironmentFile, состояние включения и работы             | то же                                                |
| Caddy                 | файл из `ExecStart` службы и всё, что он импортирует (файлы и шаблоны)                                       | то же                                                |
| Ссылки                | всё, на что взятые файлы ссылаются путём (`/etc`, `/opt`, `/usr/local`, …) — замыкание                       | то же                                                |
| Секреты               | по пути (`.env`, TLS, approle, `secrets/`, ключи) и по содержимому                                           | `sets/<id>/config/host-secrets.tar.gpg`, ключ Томаса |
| Образы                | каждый контейнер — по идентификатору образа (`docker save`)                                                  | `images/<id>.tar`, один раз на образ                 |
| Код                   | отслеживаемые файлы серверной копии в нынешнем виде                                                          | `code/<sha256>.tar.gz`, один раз на содержимое       |
| ОС, пакеты, владельцы | `os-release`, версии пакетов, учётные записи владельцев файлов                                               | `host.json`                                          |

Не берётся намеренно:

- **Static seal key** (`/etc/fifth-openbao/seal`) хранится в аварийном комплекте Томаса, а не
  рядом со снимком. Без верного ключа снимок не читается, в этом и защита.
- **`/run`** создают службы: секреты в `/run/fifth-secrets` выдаёт OpenBao Agent.
- **Данные** восстанавливаются своим путём: база (pgBackRest), файлы (rclone), OpenBao
  (снимок). Каталог копий и комплектов выпуска тоже не берётся.

Не взятое записано в `host.json` (`skipped`) с причиной. Без конфигурации узла комплект
восстанавливает данные, но в ограничениях пишется «конфигурации узла нет». Проверка съёма —
`node scripts/check-host-config.mjs`.

## Площадка WSL

Отдельный дистрибутив `fifth-restore` со своим systemd и своим Docker. Docker ноутбука не
используется. Команды выполняются в PowerShell на ноутбуке, в каталоге репозитория.

1. **Образ ОС.** Ubuntu 24.04 rootfs для WSL. Адрес и SHA-256 записываются в протокол.
   Скачивание — с согласия Томаса:

   ```bash
   node scripts/restore-site-wsl.mjs create --rootfs <файл .tar> --sha256 <hex> --source <адрес>
   ```

   В `wsl.conf` площадки: systemd, без дисков Windows, без запуска программ Windows, свой
   `/etc/hosts`.

2. **Подготовка.** Пакеты Ubuntu (`docker.io`, `docker-compose-v2`, `caddy`, `gnupg`, …) — это
   единственный выход наружу. Затем создаётся сетевое пространство `fifth` с одной петлёй, и
   Docker, containerd и Caddy переводятся в него (drop-in `NetworkNamespacePath`):

   ```bash
   node scripts/restore-site-wsl.mjs prepare
   ```

   Поэтому изоляция не зависит от того, делит ли WSL сеть с Docker Desktop.

3. **Назначения и изоляция — до восстановления.** Условия:
   - systemd работает как PID 1;
   - дисков и программ Windows нет;
   - идентификатор Docker отличается от Docker ноутбука, сокет свой;
   - Docker работает в пространстве `fifth`, где нет маршрута наружу и попытка выйти наружу не
     проходит;
   - Docker пуст.

   Любое невыполненное условие — отказ:

   ```bash
   node scripts/restore-site-wsl.mjs check
   ```

4. **Восстановление.** Перед ним `check` выполняется ещё раз. На площадку уходят:
   - скачанный комплект;
   - инструмент (`scripts/`);
   - ключи — в `/dev/shm`, после прогона удаляются.

   `node` берётся из образа ядра комплекта:

   ```bash
   node scripts/restore-site-wsl.mjs run --set <.local/backup-pull/<id>> --secret-key <файл> --passphrase-file <файл> --openbao-keys <emergency.gpg> --audit <выгрузка аудита prod> --coverage-ack <покрыто до>
   ```

5. **Удаление** — дистрибутив удаляется целиком, вместе с данными:

   ```bash
   node scripts/restore-site-wsl.mjs destroy
   ```

Память WSL общая с Docker Desktop (4 ГБ, `.wslconfig`): на время прогона стенд лучше
остановить (`npm run stand:down`).

## Порядок восстановления (`restore-full.mjs`)

1. **Условия.** Linux, root, systemd; Docker пуст; порты 80 и 443 свободны; выхода наружу нет;
   комплект сверен с описью.
2. **Ключи.** Комплект ключей и секретная часть открываются ключом Томаса. Расшифрованное
   остаётся в памяти.
3. **Файлы.** Учётные записи с прежними uid и gid. Код, открытая конфигурация (хеши сверяются)
   и секреты ложатся на прежние места с правами и владельцами.
4. **Образы.** Загружаются из комплекта, идентификатор сверяется. Каждая служба получает свой
   образ по идентификатору (`pull_policy: never`), поэтому ссылки `name@sha256` не скачиваются.
5. **Удержание — до первого запуска служб.** Удерживается:
   - ядро — с `CORE_RESTORE_HOLD`: ворота закрыты, отправщики почты и вебхуков стоят;
   - почта — `MAIL_TRANSPORT=none`;
   - имена сайтов — направлены на 127.0.0.1;
   - Caddy — работает с `local_certs`, без ACME;
   - оповещения Zabbix — выключены в восстановленной базе, до запуска его сервера;
   - таймеры — установлены, но не запущены.

   Файлы удержания — `/var/lib/fifth-restore/hold`. Caddy удерживается drop-in
   `zz-restore-hold.conf`.

6. **OpenBao.** Static seal key берётся из аварийного комплекта и кладётся на место. Затем
   инициализация, `snapshot-force` снимка комплекта, и OpenBao открывается сам.
7. **База.** pgBackRest восстанавливает её на LSN момента T; транзакция T проверяется.
8. **Файлы.** Agent выдаёт секреты, Garage настраивает установщик самой среды (`garage-init`
   из кода комплекта). Файлы расшифровываются в бакет, SHA-256 каждого сверяется.
9. **Службы.** Запускаются службы, работавшие на исходном узле. Под удержанием ядро не готово.
10. **Юниты и Caddy.** Запускаются активные службы-демоны. Службы с внешними последствиями
    (копии наружу, пульс, аудит, выпуск) удерживаются.
11. **Сверка и учёт удалений по 2.1.5** — `deletions-apply` apply, verify, open, по
    [deletions-after-restore.md](deletions-after-restore.md). Без выгрузки аудита (`--audit`) и
    `--coverage-ack` работа не разрешается: ворота остаются закрытыми, контрольные операции не
    выполняются.
12. **Снятие удержания ядра.** Почта, выход наружу, оповещения и таймеры остаются удержаны до
    решения о разрешении работы.
13. **Контрольные операции** через публичный вход: страница кабинета, вход и свой профиль,
    чтение восстановленного файла, контрольная запись (новый материал: загрузка, завершение,
    чтение байт в байт). Также проверяются свежие данные Zabbix, потоки NATS и закрытый выход
    наружу из ядра.

Протокол — `out/restore-full/<время>/protocol.md` и `protocol.json`. В нём:

- отметки UTC: начало испытания, начало восстановления, возврат обслуживания;
- этапы, проверки, удержанное, ограничения;
- ОС и пакеты площадки, внешние источники;
- проверка изоляции (`site-check.json`).

Возврат полного резервирования на одном узле не измеряется.

## Перед первым прогоном на копии prod (общая приёмка)

1. Выпустить на сервер код копий с этой работой (`backup.mjs`, `lib/host-config.mjs`) — по
   слову Томаса. Первый комплект после выпуска сохранит образы, это займёт время и место.
2. Внеочередной комплект: `fifth-test op prod-backup-set`. Проверить, что в его ограничениях
   нет «конфигурации узла нет».
3. Скачать его: `node scripts/backup.mjs pull`. Образы идут по SSH: это гигабайты.
4. Подготовить аварийный комплект OpenBao (`.local/keys-openbao`) и свежую вынесенную выгрузку
   аудита prod (`scripts/audit-offsite.mjs pull`).
5. Выполнить `create` → `prepare` → `check` → `run`, затем `destroy`.

Отладка сценария на настоящем узле ещё впереди: первый прогон почти наверняка найдёт
расхождения с фактической конфигурацией. Это часть приёмки, а не отдельная работа.
