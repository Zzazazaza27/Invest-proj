# Журналы без секретов в источнике — nginx и PostgreSQL (на согласование Томаса)

Отдельная короткая правка до W08b (блок 8, 8.4): прекратить запись секретов
и данных, не дожидаясь архиватора. Ветка `fix/log-secrets-at-source`.

## Что найдено на VPS (2026-11-02)

- nginx в контейнере `web`: формат `main` пишет строку запроса целиком —
  одноразовый токен подтверждения почты из query попадает в вывод контейнера.
  Журнал ошибок nginx пишет строку запроса и referer всегда, формат не
  настраивается.
- PostgreSQL: при ошибке клиентского запроса пишет значения в самом
  сообщении, в `DETAIL` и `CONTEXT`, параметр запроса и текст запроса
  (`STATEMENT`); медленные запросы (`log_min_duration_statement=500`) — текстом
  с литералами.

## Изменение

- `infra/nginx/default.conf`: журнал доступа `safe` — исходный путь без
  аргументов, без referer и заголовков, статус, время, `$upstream_status`;
  журнал ошибок — уровень `crit`.
- `infra/docker-compose.yml` (postgres): `log_min_messages=log` (ERROR и
  WARNING не пишутся), `log_min_error_statement=panic`,
  `log_error_verbosity=terse`, `log_min_duration_statement=-1`,
  `log_parameter_max_length=0`, `log_parameter_max_length_on_error=0`.

**Что теряется.** В журнале nginx — текст ошибок обращения к ядру (статус
502/504 и `upstream` остаются в журнале доступа). В журнале PostgreSQL —
ошибки клиентских запросов, включая deadlock и тексты медленных запросов:
код ошибки видит ядро (в его журнале — с W08b), счётчик deadlock —
`pg_stat_database`, медленные — числовая статистика `pg_stat_statements` по
`queryid` без текста SQL. Нормализация текста не гарантирует удаления всех
значений: текст запросов читается только как ограниченная служебная
диагностика и автоматически не выгружается (в том числе в W08b). Остаются: подключения, отключения, ожидания блокировок (без
подробностей), FATAL/PANIC, служебные сообщения сервера.

Искусственные значения `CANARY-…`; контроль — та же нагрузка при прежних
настройках.

| Источник   | Что подано                                                                                                                                                      | Прежние настройки                                                          | Новые |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ----- |
| nginx      | токен в query `/v1/auth/email/verify/status`, query страницы, referer с query, cookie, `Authorization`, POST 2 МБ с query (413 → журнал ошибок)                 | 6 вхождений (журнал доступа и ошибок)                                      | 0     |

## Применение на VPS — только после «ок» Томаса

Предусловие: ветка влита в `main` **отдельным выпуском** поверх кода,
стоящего на VPS (между ними — только эта правка), CI именно этого коммита —
`completed success`.

1. **До выкладки** записать в `/root/log-secrets-before.txt`: полный SHA
   выпуска на VPS (`git rev-parse HEAD` — это `<P>` для возврата) и команду
   postgres (`docker inspect unicorn-postgres --format '{{json .Config.Cmd}}'`).
   Затем выкладка (`npm run deploy`, с `PUBLIC_PIN`, пока DNS не восстановлен)
   — она обновляет файлы, но контейнеры не трогает.
2. nginx: `docker restart unicorn-web` (шаблон собирается при старте; перерыв —
   секунды). Проверка: запрос с искусственным токеном в query → в `docker
logs unicorn-web` его нет; `/`, `/login/`, `/v1/health` — 200.
3. PostgreSQL: `cd /opt/unicorn-launch && node scripts/infra.mjs up --no-deps
postgres` — пересоздание только этого контейнера (перезапуск базы,
   ~10 с; ядро переподключается). Проверка: `pg_settings` — шесть значений
   выше; `/ready` ядра — ready; архив журнала идёт (`backup.mjs check`);
   ошибка с искусственным значением во временной таблице → в `docker logs
unicorn-postgres` значения нет.
4. Zabbix: открытых проблем по ядру, базе и резервированию нет.

**Возврат (временный, до исправляющего выпуска).** Критерий: сайт, вход или
ядро не поднимаются после шага 2 или 3.

1. Рабочая копия VPS целиком на прежний выпуск: `git reset --hard <P>`, где
   `<P>` — полный SHA из `/root/log-secrets-before.txt` (шаг 1). Правка не
   меняет код приложений, поэтому собранные `dist` остаются верными.
2. Контейнеры — из этих же файлов: `docker restart unicorn-web`, затем
   `node scripts/infra.mjs up --no-deps postgres`. Проверка: `git status`
   чистый, `git rev-parse HEAD` = `<P>`, команда `postgres` в `docker inspect`
   совпадает с записанной в шаге 1, `/`, `/login/`, `/v1/health` — 200,
   `/ready` — ready.
3. Записать в инцидент и TODO: VPS временно на `<P>` (точный SHA), утечка
   журналов возобновилась. `main` при этом содержит правку — **следующая
   выкладка `main` без исправления запрещена**: исправляющий выпуск идёт
   отдельным коммитом с той же процедурой (шаги 1–4).

Итог возврата: файлы на диске, рабочая копия и контейнеры соответствуют
одному коммиту `<P>`; перезапуск любого контейнера не меняет настроек.

## Накопленная история

Уже записанный вывод контейнеров (`json-file`) и journald содержит такие
значения. Он сохраняется как чувствительный архив по плану W08b (ограниченный

гарантируется; примеры реальных значений в отчёты не выносятся.
