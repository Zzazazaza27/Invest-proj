# Раннбук: подключение почты

Что делать, чтобы платформа начала отправлять настоящие письма, и как это
проверить. Код для этого готов (Ф65) — не хватает решения по провайдеру и
учётных данных.

## Ограничение, из которого всё следует

С ВПС `193.233.217.210` **исходящие 25, 465 и 587 закрыты провайдером** ко всем
проверенным MX (проверено с самого сервера 2026-08-24 с позитивным контролем
`github.com:443`). Открыт **2525** и 443.

Значит своя доставка с этого сервера невозможна физически. Не «сложно» и не
«надо настроить» — пакет не уходит. Любой план, где приложение или локальный
exim отдают письмо напрямую принимающему серверу, обречён, и выяснится это на
первом же реальном письме.

**Рабочая схема одна: smarthost.** Письмо отдаётся почтовому провайдеру с
аутентификацией на 2525, дальше он доставляет его от своего имени, со своим
адресом и своей репутацией. Это же снимает вопрос PTR: приёмник смотрит
обратную запись того, кто с ним соединился, то есть релея, а не нашу.

## Текущее состояние домена

Проверяется одной командой:

```bash
node scripts/probe-mail-readiness.mjs --domain <домен> --ip 193.233.217.210 \
  --relay smtp.timeweb.ru:2525
```

Зонд спрашивает **публичные резолверы** (8.8.8.8, 1.1.1.1), а не системный:
системный DNS на машине разработчика отдавал пустоту там, где публичный
возвращает и MX, и SPF, — и зонд рапортовал «записей нет». `--resolver system`
возвращает прежнее поведение, если это нужно осознанно.

На 2026-08-25:

| Что                          | Состояние                                                               |
| ---------------------------- | ----------------------------------------------------------------------- |
| MX                           | `10 mx1.timeweb.ru`, `20 mx2.timeweb.ru` — почту домен принимает        |
| SPF                          | `v=spf1 include:_spf.timeweb.ru ~all` — есть и корректна                |
| DMARC                        | **нет** — крупные провайдеры складывают такую почту в спам              |
| DKIM                         | ключа нет ни для одного из частых селекторов; выдаёт релей              |
| PTR                          | нет; при smarthost не мешает, при своей отправке (`--direct`) блокирует |
| Релей `smtp.timeweb.ru:2525` | отвечает `220`, объявляет `STARTTLS` и `AUTH PLAIN LOGIN`               |

## Порядок подключения

1. **Завести служебный ящик у провайдера.** MX уже указывают на Timeweb —
   вероятнее всего ящик заводится там же. Альтернативы, у которых открыт 2525:
   Mailgun, SendGrid, Brevo. Адрес нужен технический (`no-reply@`, `support@`),
   не личная почта сотрудника: человек уходит, адрес остаётся.

2. **Опубликовать DMARC.** Начинать с режима наблюдения:

   ```
   _dmarc.<домен>.  TXT  "v=DMARC1; p=none; rua=mailto:postmaster@<домен>"
   ```

   Ужесточать до `p=quarantine` и `p=reject` после того, как отчёты покажут,
   что своя почта проходит.

3. **Включить DKIM у провайдера** и опубликовать выданную им запись
   `<селектор>._domainkey.<домен>`. Селектор задаёт провайдер.

4. **Заполнить `.env` стенда:**

   ```
   MAIL_TRANSPORT=smtp
   MAIL_SMTP_HOST=smtp.timeweb.ru
   MAIL_SMTP_PORT=2525
   MAIL_SMTP_SECURITY=starttls
   MAIL_SMTP_USER=<адрес ящика>
   MAIL_SMTP_PASSWORD=<пароль ящика>
   MAIL_FROM=<адрес ящика>
   SUPPORT_INBOX_EMAIL=<служебный ящик>
   NOTIFY_INBOX_ON_REGISTRATION=true
   ```

   Пароль живёт в `.env` стенда и в секретах CI — в репозиторий не попадает.
   Конфигурация отказывает на старте, если: релей не задан; имя без пароля;
   открытый канал к нелокальному адресу; в production — незашифрованный канал
   или релей без аутентификации.

5. **Перезапустить ядро** и прогнать проверку из следующего раздела.

## Полный тест доставки (задача ТЗ №2, пункты 1–5)

Три из пяти пунктов проверяются автоматически, два — глазами, потому что
«не попало в спам» может подтвердить только чужой почтовый сервис.

| Пункт ТЗ                                       | Как проверить                                                                                                                           |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Письмо со служебного ящика на внешний адрес | Зарегистрировать учётку на внешний адрес: письмо подтверждения уходит само                                                              |
| 2. Письмо на служебный ящик                    | Открыть обращение в поддержку в интерфейсе — копия падает на `SUPPORT_INBOX_EMAIL`                                                      |
| 3. Отправка приложением по SMTP                | `node scripts/smoke-mail-smtp.mjs` — 17 проверок; при реальном релее проходят и ветки STARTTLS и AUTH, не покрытые локальным приёмником |
| 4. Доставка в крупный внешний сервис           | Пункт 1 на адрес Gmail/Яндекса; смотреть заголовки письма: `spf=pass`, `dkim=pass`, `dmarc=pass`                                        |
| 5. Не попадает ли сразу в спам                 | Тот же ящик: папка «Входящие» против «Спам». Без DMARC и DKIM шанс спама высокий — поэтому шаги 2 и 3 идут до теста                     |

## Локальная проверка без провайдера

Прогон работает против приёмника на петле — учётные данные не нужны:

```bash
npm run infra:mail-up                 # mailpit: 127.0.0.1:1025, интерфейс :8025
npm run build -w apps/core
MAIL_TRANSPORT=smtp MAIL_SMTP_HOST=127.0.0.1 MAIL_SMTP_PORT=1025 \
  MAIL_SMTP_SECURITY=plain NOTIFY_INBOX_ON_REGISTRATION=true \
  node scripts/dev-core.mjs --detached
node scripts/smoke-mail-smtp.mjs      # 17 проверок
```

Открытый канал разрешён только к литералу петли и только без пароля — и
конфигурацией, и самим транспортом перед каждой отправкой. К любому другому
адресу такая настройка не запустится.

## Чего этот раннбук не закрывает

- **HestiaCP не установлена** (задача ТЗ №1). Её установщик занимает 80/443 и
  8080, а они заняты Caddy и `unicorn-web`; без `--force` установщик удаляет
  ufw или прерывается. Решение за владельцем.
- **Приём почты платформой** (IMAP, ящики сотрудников) — это функция
  провайдера или панели, а не приложения: платформа письма только отправляет.
