# Тестовые сессии и просмотр кабинета

Как пройти платформу от лица участника, как разобрать упавший прогон и как
убрать за собой. Здесь же — программный интерфейс для сценарных проверок и
условия, при которых механизм можно было бы включить на проде.

**Где работает.** Только в тестовом контуре. В production механизм выключен
кодом (`AccessContextService.isEnabled`), а не переменной окружения:
переменная `TESTING_SESSIONS_ENABLED` там ничего не включает и вызывает
ошибку конфигурации, чтобы забытое значение в боевом конфиге было заметно.

---

## 1. Владельцу: ручная проверка

### Начать сессию

Админка → **Проверка** → **Тестовые сессии** → ввести название →
«Начать сессию».

Система заводит трёх участников: основателя, эксперта и инвестора. Это
отдельные учётные записи, **паролей у них нет и не будет** — кабинет
открывается контекстом доступа, живущим внутри вашей административной сессии.

### Переключаться между участниками

В карточке сессии — «Открыть кабинет» у каждого участника и «Открыть витрину
как гость».

Кабинет открывается **в отдельной вкладке**. Админка в своей вкладке остаётся
админкой: личность подставляет заголовок, который шлёт только та вкладка.
Сверху видна плашка «Тестовая сессия · Основатель», в ней — «Вернуться в
админку» и «Завершить просмотр».

Переключение туда и обратно возвращает **того же** участника с его данными:
новый человек при каждом переключении не заводится.

### Вернуться к прогону позже

Раздел показывает все сессии: название, откуда (вручную или прогон),
состояние, итог проверки и последнюю активность. Состояние и итог — разные
столбцы: завершённая сессия бывает и успешной, и упавшей.

«Подробности» открывают карточку: участники, шаги прогона с ожидаемым и
фактическим результатом, перечень созданных записей.

### Завершить и продолжить

«Завершить» закрывает выданные кабинеты, но **данные оставляет** — за ними к
упавшему прогону и возвращаются. «Продолжить» снова делает сессию рабочей и
выдаёт новые контексты.

### Убрать данные

«Что уберёт очистка» показывает состав: сколько записей и что с ними будет.
Учётные записи и проекты **помечаются удалёнными**, а не стираются: акцепты
согласий неизменяемы и ссылаются на пользователя, а у проекта висят версии,
раунды и материалы.

Уборка ходит **по перечню созданного этой сессией**, а не по таблицам.
Общие справочники, подготовленное содержимое (словарь, ЧАВО, вопросы, тарифы)
и рабочие записи она не трогает по построению.

Повторная уборка безопасна. Если уборка упирается в связь, которую нельзя
разорвать, она останавливается и пишет причину в карточку — это разбирает
человек, каскадом такое не решают.

## 2. Владельцу: «Посмотреть кабинет» реального пользователя

Админка → **Пользователи** → в строке кнопка **«Кабинет»** (если кабинетов
несколько — список выбора). То же действие есть в карточке человека.

Это **другой режим**, не тестовая сессия:

- открывается кабинет РАБОЧЕГО пользователя для разбора обращения;
- режим **только для чтения**, и запрет держит сервер, а не интерфейс;
- плашка говорит «Просмотр от имени … · Только чтение»;
- данные человека **не становятся тестовыми** и под уборку не попадают;
- начало и завершение просмотра попадают в журнал с указанием и
  администратора, и пользователя.

Полномочие — `identity.user.view_as`. Оговорка, которую стоит знать:
в этой платформе **администратор проходит все полномочия неявно** (так
устроено с M097), поэтому полномочие ограничивает сотрудников с частичными
правами, а не администратора. Менять эту модель — отдельное решение.

## 3. Маусу: программный интерфейс

Модуль `scripts/lib/testing-session.mjs`. Образец — `scripts/scenario-round-review.mjs`.

```js
import { startSession } from './lib/testing-session.mjs';

const run = await startSession('Сценарий «заявка → эксперт»', {
  scenarioId: 'round-review',
  codeVersion: process.env.GIT_COMMIT ?? null,
});

const founder = run.as('founder'); // клиент от лица участника
const guest = await run.asGuest(); // неавторизованные запросы

const { status, json } = await founder.call('/v1/projects');
await run.step('кабинет открывается', status === 200, {
  actor: 'основатель',
  expected: 'HTTP 200',
  actual: `HTTP ${status}`,
});

const outcome = await run.finish(); // итог = успех, если шаги не падали
if (outcome.result === 'passed') await run.cleanup();
```

Правила, которые стоит соблюдать:

- **никаких своих учётных записей и паролей** — участники приходят от сервера;
- **упавший прогон не убирать**: его данные и есть материал разбора;
- **шаги — диагностика, не отчёт**: ожидаемое и фактическое, без секретов и
  персональных данных (длина ограничена схемой);
- объекты, созданные участником через обычные маршруты, числятся за сессией
  автоматически там, где это реализовано (сейчас — проекты); остальное
  добавляйте явно, иначе уборка его не заметит.

Одновременные прогоны изолированы друг от друга: у каждого свои участники и
свои контексты.

## 4. Что переведено на механизм и что осталось

**Переведено (написано на механизме):**

| Прогон                              | Что делает                                                  |
| ----------------------------------- | ----------------------------------------------------------- |
| `scripts/scenario-round-review.mjs` | связанный сценарий: основатель → эксперт → инвестор → гость |

**Осталось как было — и почему.** Полсотни проверок заводят себе людей через
`/v1/auth/register` и входят их паролями. Механически перевести их нельзя:
у участников сессии **пароля нет по построению**, и вход под ними не
предусмотрен. Перевод каждой — это замена её способа аутентификации, а не
правка строчки, и каждая требует своей проверки.

Порядок перевода (по убыванию пользы):

1. `render-check-staff-access.mjs` — оставляет в списке шесть записей за
   прогон, видно сразу;
2. `smoke-project-access.mjs`, `smoke-lab.mjs` — крупные сценарии без
   проверки самой авторизации;
3. остальные `render-check-*` и `smoke-*`, создающие людей.

**Не переводится никогда** (решение владельца): модульные проверки, линтеры и
сборки; проверки миграций и восстановления БД; разрушительные и нагрузочные
прогоны; проверки настоящей регистрации, входа и восстановления пароля.
Переключение участника без пароля обычный вход не проверяет — например
`smoke-favorites.mjs` специально проверяет выход и повторный вход, и на
механизм он не переводится.

## 5. Как это устроено (коротко)

**Контекст доступа — запись на сервере, а не второй токен.** Платформа
проверяет токен ИНИЦИАТОРА обычным порядком, затем видит заголовок
`X-Unicorn-Context` и подставляет действующего пользователя. Токен участнику
не выпускается — поэтому схема не упирается во внешнего поставщика входа.

Условия действительности контекста (все проверяются прогоном
`check:testing-sessions`):

- привязан к КОНКРЕТНОЙ административной сессии инициатора: из второго входа
  того же администратора не открывается, после выхода мёртв;
- негодный, чужой, просроченный или отозванный — **отказ**, а не возврат к
  административной личности;
- права инициатора и участника **не объединяются**: роли берутся только у
  того, от чьего лица идёт запрос;
- гость — это неавторизованный запрос, несмотря на административную cookie;
- CSRF не ослаблен ни созданием, ни использованием, ни завершением.

**Запрет изменений в режиме просмотра стоит в двух местах**: страж отклоняет
небезопасные методы, а `Database.transaction()` отказывает по признаку
контекста — запрет по методу неполон, потому что изменения бывают неявные
(отметка уведомления прочитанным происходит на чтении).

**Обязательный аудит при этом сохраняется**: у `AuditRepository` есть
отдельный путь `recordDuringView`, у которого НЕТ параметра-обработчика —
через него нельзя выполнить произвольный запрос, только добавить запись в
журнал. Запись отличает инициатора от того, от чьего лица шёл запрос.

**Картинки и файлы** в контекстной вкладке забираются тем же клиентом с
заголовком, а в разметку идёт ссылка на полученные байты (`ContextualImage`).
Иначе браузер запросил бы их сам — без заголовка, то есть от имени
администратора.

**Идентификатор контекста** приезжает в якоре адреса (`#ctx=…`): якорь не
уходит на сервер и не попадает в журналы доступа. Вкладка сразу перекладывает
его в своё состояние (`sessionStorage` — своё у каждой вкладки) и чистит
адрес.

## 6. Условия для включения на проде

Сегодня механизм на проде выключен решением, а не техническим препятствием.
Чтобы его включить, нужно закрыть следующее:

1. **Перечень разрешённых операций.** Сейчас в режиме просмотра разрешено
   любое чтение. На проде должен быть явный список того, что вообще можно
   смотреть, и того, что не показывается никогда.
2. **Доказанная полнота запрета изменений.** Двух рубежей достаточно для
   стенда; для прода нужна опись обработчиков с побочными эффектами и
   проверка каждого, а не общее правило.
3. **Видимость для владельца аккаунта.** Человек должен узнавать, что его
   кабинет смотрели: сейчас это есть только в журнале аудита.
4. **Отдельное полномочие, действующее и на администратора.** Текущая модель
   пропускает администратора через все полномочия неявно; на проде «смотреть
   чужой кабинет» должно выдаваться явно.
5. **Срок и объём.** Ограничение числа одновременных просмотров и более
   короткий срок жизни контекста, чем нынешние два часа.
6. **Тестовые сессии на проде — отдельно от просмотра.** Заведение
   участников в боевой базе означает записи, которых там быть не должно;
   решать это следует отдельным контуром, а не флагом (см. `TODO.md`).

```bash
npm run check:testing-sessions                                  # границы доверия (API)
UNICORN_ENTRY=web node scripts/render-check-testing-sessions.mjs # интерфейс и вкладки
node scripts/scenario-round-review.mjs                          # сценарий на механизме
node scripts/scenario-round-review.mjs --keep                   # не убирать за собой
```
