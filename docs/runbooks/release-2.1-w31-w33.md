## 3. Сборка и проверки до любой установки

1. Заморозка: рабочее дерево чистое, push одной пачкой; таблица раздела 2 пересчитана.
2. **Полный CI** (`gh workflow run ci.yml --ref main`) — сборка, проверки, подписанный
   комплект `2.1-bNNN.1`. «Зелёный» — только по просмотру фактического запуска для этого коммита.
3. **Прогон совместимости** (`compat.yml`, ручной запуск Томасом; прежняя `2.1-b132.1`, кандидат
   `2.1-bNNN.1`) — отдельная проверка схемы, не часть CI.
4. Приём отчёта на узле: `kit.mjs compat-put --build 2.1-bNNN.1 --dir <артефакты>` — только
   подписанный закреплённым ключом отчёт о той же паре.
   **Условие:** пока отчёт не принят, точка возврата — «НЕ проверена», возврат `--rollback` на
   b132 при новых миграциях установщик запретит. Без принятого отчёта на test-2 и prod не ставим;
   иначе — только решением Томаса.
5. Проверка на стенде до сборки: ответ ядра 504 с `outcome` проходит nginx web без подмены
   (`error_page 504` в `infra/nginx/default.conf` действует только на ошибки самого nginx,
   `proxy_intercept_errors` не включён). Контроль на test-1 — раздел 4.

## 5. Слоты ядра: включение и возврат

Не входит в «установить комплект»; выполняется внутри этапа среды после первого контроля.

**Включение.**

- Предварительно: среда на новом комплекте, контроль пройден; `env.mjs slots-state <среда>` —
  слоты выключены, состояние согласовано; порт 4400 свободен для служебного; окно с короткой
  остановкой согласовано (переход на слоты — разовый короткий перерыв).
- Команда: test-1, test-2 — `env.mjs slots-enable <среда>` (test-2 — `--pilot-confirm`);
  prod — `release.mjs slots-enable prod --actor … --approved-by …` (после отдельного решения).
- Ожидаемо: ядро пересоздано раньше web; web подключил маршрут и статику из файла; через
  nginx отвечает активный слот.
- Контроль: `slots-state` — `consistent: true`; 5 ответов подряд от активного слота; затем
  повторный контроль среды (раздел 4).
- Возврат режима: при неподтверждении через nginx — сам; вручную — `slots-disable`.

**Возврат на b132 из режима слотов — не обещаем, пока не проверен.** b132 не знает
`BACKGROUND_START`, разрешения фона и протокола управления слотами; отчёт совместимости
проверяет схему, а не это. Предполагаемый порядок:

1. `slots-disable <среда>` — среда возвращается к одному ядру на новом комплекте;
2. контроль;
3. возврат кода: `prod-env-release <среда> 2.1-b132.1 2.1-bNNN.1 --rollback`;
4. контроль на b132: готовность, вход, фон, `release.mjs verify`.

**Испытание на test-1** (часть этапа test-1, до test-2): выполнить этот порядок на настоящем
комплекте b132, затем вернуть test-1 на кандидат и снова включить слоты. Записать: что
делает b132 с файлом маршрута и разрешением фона, запускается ли его фон, нет ли двойного
фона во время перехода. Не прошло — возврат из слотов для test-2 и prod не планируется,
решение — Тэнк и Томас. Обычный `--rollback` прямо из режима слотов не используется.

## Дополнение (Тэнк 10.11, после `1238731`)

**Возврат конфигурации вместе с кодом.** Заморозка закрепляет кандидата, но не доказывает, что
его дополнения Compose и узловые шаги совместимы с b132. Состояние b132 целиком воспроизводимо
из Git: коммит `8c165d6` (дополнения Compose, `env.mjs`, `release.mjs`, `infra.mjs`, узловые
шаги). Возврат на b132 — это код **и** конфигурация:

1. `slots-disable <среда>` — инструментами кандидата (b132 слотов не знает);
2. контроль: одно ядро, маршрут web, служебные порты, фон один;
3. `fifth-test sync 8c165d6` — дополнения и шаги возвращаются к версиям b132;
4. возврат кода на b132 шагом среды (`--rollback`) уже инструментами b132;
5. контроль на b132: дополнения (сверка SHA-256 с `8c165d6`), маршрут web, служебные порты
   (4400 и порты среды), **нет двойного фона**, готовность, вход, `release.mjs verify`.

Весь путь «слоты → slots-disable → sync 8c165d6 → b132» — испытание этапа test-1 на настоящем
b132. Если не подтвердился — слоты на test-2 и prod не включаются; выпуск самого комплекта без
слотов рассматривается отдельно.

**Расхождение серверной копии с b132 — открытый эксплуатационный риск**, правило «не
пересоздавать» — временное ограничение, а не устранение. Различаем:

- `docker restart <контейнер>` — тот же контейнер с прежней конфигурацией: безопасно;
- пересоздание через Compose (`env.mjs start/update`, `infra.mjs up`, установщик) — конфигурация
  берётся из **текущих** файлов серверной копии: на b132 с копией `b741531`+ даёт новые
  дополнения на старых образах.

До первого изменения на сервере (11.11, после окна, только чтение): снимок фактической
конфигурации всех контейнеров test-1, test-2, prod — файлы Compose из метки
`com.docker.compose.project.config_files`, `config-hash`, образ, переменные без значений — в
учёт выпуска. Способ восстановления запущенной конфигурации b132 — `fifth-test sync 8c165d6`
и пересоздание той же среды её шагом.

**504 через прокси** — по чтению конфигураций проходит без подмены; фактическая проверка на
test-1 через Caddy и nginx с сохранением `outcome` и `traceId` — в контроле этапа test-1.
