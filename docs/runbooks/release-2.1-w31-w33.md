## 2. Сборка и проверки до любой установки

1. Заморозка: последний коммит кандидата, рабочее дерево чистое, push одной пачкой.
2. **Полный CI** (`gh workflow run ci.yml --ref main`) — сборка, все проверки, подписанный
   комплект `2.1-bNNN.1`. «Зелёный» — только по просмотру фактического запуска для этого
   коммита. Расход Actions ~15 мин (остаток ~200).
3. **Прогон совместимости** (`compat.yml`, ручной запуск Томасом с main; прежняя — `2.1-b132.1`,
   кандидат — `2.1-bNNN.1`) — **отдельная проверка**, не часть CI. Подписанный отчёт и подпись —
   артефакты.
4. Приём отчёта на узле: `kit.mjs compat-put --build 2.1-bNNN.1 --dir <артефакты>` — принимает
   только подписанный закреплённым ключом отчёт о той же паре.
   **Условие:** пока первый настоящий прогон совместимости не прошёл и отчёт не принят
   установщиком, точка возврата каждой установки — «НЕ проверена», возврат `--rollback` на
   b132 при новых миграциях установщик **запретит**. Решение «ставить с непроверенной точкой
   возврата» — только Томаса; по умолчанию — не ставить на test-2 и prod без принятого отчёта.

## 3. Установка комплекта — по средам

Для каждой среды: копия базы до изменений (шаг среды делает сам), `release.mjs install`,
отдельная итоговая сверка (`release.mjs verify`), затем контроль.

**Контроль после установки (каждая среда):** `/v1/ready` 200; вход тестовым участником;
контрольная операция мониторинга; фон ядра работает (`/jobs`), очереди (`/queues`) с новыми
полями; журналы ядра без ошибок за 10 мин; для test-2 — production-режим: TLS служб, Agent
OpenBao, шифрованный вход к хранилищу; для prod — Zabbix видит ядро, тревог нет.

| ------ | ----------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| test-1 | `fifth-test op prod-env-release test-1 2.1-bNNN.1 2.1-b132.1` + контроль + короткий p1-api 2/с 10 мин                   | Маус                     |
| test-2 | `fifth-test op prod-env-release test-2 2.1-bNNN.1 2.1-b132.1` + контроль (репетиция prod: production-режим, Agent, TLS) | Томас (команда от Мауса) |

prod одной командой) **в этом выпуске не используется**: test-2 — отдельный этап репетиции
(Тэнк 10.11). Применять её — после отдельного решения, когда репетиция сводится к
автоматическому контролю.

**Возврат по среде:** тем же шагом с `--rollback` на b132 — только при принятом отчёте
совместимости; иначе исправление вперёд. Данные: копия базы, снятая шагом среды.

## 4. Отдельный шаг: переход на слоты ядра

Не входит в «установить комплект». Выполняется после того, как комплект встал и контроль
прошёл, — отдельно в каждой среде, в том же порядке.

- **Предварительно:** среда на новом комплекте; `env.mjs slots-state <среда>` — слоты выключены,
  состояние согласовано; порт 4400 свободен для служебного; окно с короткой остановкой
  согласовано (переход на слоты — разовый короткий перерыв).
- **Команда:** test-1, test-2 — `env.mjs slots-enable <среда>` (test-2 — `--pilot-confirm`);
  prod — `release.mjs slots-enable prod --actor … --approved-by …`.
- **Ожидаемо:** ядро пересоздано раньше web, web подключил маршрут и статику из файла;
  через nginx отвечает активный слот.
- **Контроль:** `slots-state` — `consistent: true`; 5 ответов подряд от активного слота;
  контроль среды (раздел 3).
- **Возврат:** при неподтверждении через nginx — сам; вручную — `slots-disable`.
- **Решение о слотах для prod** — отдельно, после test-1 и test-2: раскладка prod на ноутбуке
  не испытывалась.

## 5. Отдельный шаг: Caddyfile из Git

Сейчас основной Caddyfile на сервере правится вручную; копия в Git — `infra/caddy/Caddyfile` с
подстановками `{$CADDY_AUTH_*}`. Серверного шага применения **ещё нет** — подготовить до
выпуска (Маус), выполнить отдельно (Томас: Caddy общий для всех сред).

- **Подготовка (Маус):** шаг `prod-caddy-apply.sh`: хеши паролей — из защищённого файла
  окружения службы Caddy (не из Git); `caddy validate` на итоговом файле; копия текущего
  `/etc/caddy/Caddyfile`; `caddy reload`.
- **Предварительно:** `node scripts/caddy-drift.mjs` — расхождения сервера и Git перечислены и
  объяснены; файл окружения с хешами есть; `caddy validate` проходит.
- **Ожидаемо:** prod, test-1, test-2, files отвечают как до шага (коды, basic_auth, заголовки,
  страница недоступности).
- **Контроль:** для каждого адреса — ответ без пароля 401, с паролем 200, `/v1/ready` через
  Caddy; `caddy-drift` — расхождений нет.
- **Возврат:** вернуть копию файла и `caddy reload`.
- Маршрут контролируемого получателя вебхука для test-1 **в этот шаг не входит**: отдельная
  работа после выпуска; отказ вебхука до неё — «не проверено».
