# Резервирование стенда (блок 7, 2.1-W07)

Механизмы копирования на имеющихся ресурсах. **Копии лежат на том же VPS** —
от потери сервера они не защищают. Внешнее хранилище, закупки и восстановление
без исходного VPS (приёмка 2.1.4) — после запуска MVP (блок 7, «Поэтапное
включение»). До тех пор временная мера — ручное скачивание комплекта на ноутбук.

## Что и как копируется

| Часть             | Как                                                                                                  | Когда                                       |
| ----------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| База              | pgBackRest в контейнере базы: полная, добавочная, `verify`                                           | ежедневно 03:15 UTC; полная — раз в 7 суток |
| Журнал базы (WAL) | `archive_command` → pgBackRest, асинхронно                                                           | непрерывно, `archive_timeout=60`            |
| Файлы             | rclone `copy --immutable` из бакета (учётка только для чтения) в шифрованный каталог                 | каждый час, в составе комплекта             |
| Ключи и секреты   | весь `.env`, зашифрованный открытым ключом gpg Томаса                                                | при изменении `.env`, в составе комплекта   |
| Конфигурация      | несекретные значения `.env`, compose, Caddy, юниты, коммит, образы, потоки NATS                      | в составе комплекта                         |
| Узел целиком      | действующая конфигурация узла, секреты на ключ Томаса, образы, код — [restore-full](restore-full.md) | в составе комплекта (работа № 5)            |

**Комплект на момент T** (`sets/<id>`, каждый час): метка копии базы, копии,
от которых она зависит, начало её журнала, LSN и txid на T, объекты бакета на
T с SHA-256 содержимого и путём версии в копии, отпечаток комплекта ключей,
конфигурация и **опись** — каждый файл, нужный для восстановления (копии базы,
каждый сегмент журнала от начала основы до T, зашифрованные файлы, комплект
ключей, конфигурация), с размером и SHA-256. Хеш каждого уже сохранённого
файла сверяется с **реестром исходных хешей** (`state/ledger.json`, запись при
первом READY): испорченный после сохранения файл не становится новым эталоном
и останавливает выдачу READY. Штатно переписываются только сводки
pgBackRest (`backup.info`, `archive.info`). `READY` появляется только если
вся цепочка журнала до T без разрывов, все копии-основы на месте и каждый файл
сошёлся с описью. Скачивание берёт только комплекты с `READY`.

**Снимок сводок pgBackRest.** `backup.info` и `archive.info` переписывает
каждая новая копия базы, поэтому у комплекта свой снимок
(`sets/<id>/meta`), снятый под блокировкой задания копии базы (комплект ждёт
её окончания до 50 минут). В опись входит снимок, а не общие файлы;
скачивание раскладывает его на штатные места. Прежний комплект
скачивается и после новых копий базы: `backup.mjs pull --set <id>`.
Реестр исходных хешей сохраняется до записи READY.

**Версия кода.** В `config.commit` — полный SHA; если git его не отдал —
`null` и причина в `config.commitError`, а в `limitations` — «версия кода не
записана». Данные такого комплекта восстанавливаются, но полным он не
считается: сигнал `set-meta`, отметка в выводе `set` и `pull`. Комплекты до
2026-11-02 включительно (до исправления) записаны с пустым коммитом; их файлы
целы (проверено расшифровкой 02.11), ограничение — только в версии кода.

**Версии объектов.** Готовые объекты (окончательные файлы, медиа) по 2.1.2 не
перезаписываются: копия хранит их по ключу, а изменение содержимого под
прежним ключом (сравнение MD5/времени источника, при любом размере)
останавливает комплект с причиной — прежняя копия не затирается. Временные
ключи форм загрузки (`…/upload`) изменяемые: каждая версия сохраняется своим
путём `mutable/<версия>/…`, прежние остаются для старых комплектов. После копирования MD5 копии
сверяется с MD5 версии из списка (без MD5 — версия источника после
копирования): если объект перезаписали между списком и чтением, только что
записанный путь удаляется и комплект не выдаётся — следующий запуск снимет
версию заново.

Ничего не удаляется: срок хранения не согласован (7.5). Ядро больше не стирает
файлы при замене аватара, логотипа и обложки; очистка — отдельно, по 3.3.

## Сигналы

`check` каждые 5 минут, по компонентам:

| Ключ                | Проблема, когда                                                                                                                         |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `disk`              | свободно меньше `BACKUP_DISK_WARN_PERCENT` или меньше запаса                                                                            |
| `wal`               | архиватор отказывает; отставание больше 3 сегментов; принятый журнал не дошёл до хранилища (сброс очереди — разрыв)                     |
| `wal-chain`         | в хранилище нет хотя бы одного сегмента от начала последней копии базы до последнего архивного — разрыв; проходит только с новой копией |
| `db-full`           | полной копии нет или она старше 8 суток                                                                                                 |
| `db-backup`         | любой копии базы нет или она старше 26 часов                                                                                            |
| `job-db`, `job-set` | последний запуск задания с ошибкой (текст ошибки — в сигнале)                                                                           |
| `set`               | пригодного комплекта нет 2,5 часа                                                                                                       |
| `set-meta`          | последний пригодный комплект неполный (`limitations` в каталоге): например, не записана версия кода — с причиной от git                 |
| `keys`              | нет открытого ключа получателя комплекта ключей                                                                                         |

Первое нарушение — сообщение в Telegram, повторы — без шума, возврат —
«восстановилось». Недоставленное сообщение остаётся в очереди и повторяется не
чаще раза в 15 минут, пока не дойдёт; после доставки не повторяется. Без `BACKUP_TELEGRAM_*` сигналы только в журнале
(`journalctl -u fifth-backup-check`), и `check` пишет «telegram: не настроен».
Наблюдатель стоит на том же VPS: потерю всего сервера он не заметит —
независимый пульс в W08.

**Место.** Задание не начинается, если после него свободного места останется
меньше запаса (`BACKUP_DISK_RESERVE_PERCENT`, не меньше
`BACKUP_DISK_RESERVE_MIN_GB`). Старые комплекты ради места не удаляются. Если
архив журнала не принимает (нет места), очередь pgBackRest ограничена
`archive-push-queue-max=2GiB`: база не остановится из-за заполненного
`pg_wal`, а разрыв архива поймает `wal`.

## Включение на сервере (отдельным согласованным действием)

1. Дамп: `node scripts/db-backup.mjs` или как при выпуске.
2. Код с W07 на сервере (`npm run deploy`).
3. `.env`: `BACKUP_DIR=/var/backups/fifth-element`,
   `BACKUP_PGBACKREST_DIR=/var/backups/fifth-element/pgbackrest`,
   `BACKUP_ARCHIVE_MODE=on`; затем `node scripts/backup.mjs init-secrets`.
4. Каталог: `install -d -m 0700 /var/backups/fifth-element`,
   `install -d -o 999 -g 999 -m 0750 /var/backups/fifth-element/pgbackrest`
   (999 — postgres в контейнере).
5. Открытый ключ Томаса → `/var/backups/fifth-element/recipient.asc`.
6. Образ базы и учётка копирования: `node scripts/infra.mjs build postgres`,
   `node scripts/infra.mjs up postgres minio-init --force-recreate` —
   **перезапуск базы, секунды простоя**.
7. `node scripts/backup.mjs db --full`, затем `set`, затем `check`.
8. Таймеры: `cp infra/systemd/fifth-backup-* /etc/systemd/system/`,
   `systemctl daemon-reload`,
   `systemctl enable --now fifth-backup-check.timer fifth-backup-set.timer fifth-backup-db.timer`.
9. Telegram — после бота: токен и chat id в `.env`, проверка доставки
   (временно сломать порог и увидеть сообщение). До этого Telegram не считается готовым.

Откат: `systemctl disable --now fifth-backup-*.timer`, `BACKUP_ARCHIVE_MODE=off`,
перезапуск базы. Каталог копий не удалять.

## Скачать на ноутбук и проверить

```
npm run backup:pull
npm run backup:restore-check -- --secret-key <закрытый ключ> --passphrase-file <фраза>
```

`pull` скачивает последний `READY`-комплект — ровно файлы описи — в `.local/backup-pull/<id>` и
пересчитывает SHA-256 каждого файла описи и цепочку журнала: подмена файла того же размера ловится здесь, без ключей. `restore-check` работает только со скачанным: открывает
комплект ключей, восстанавливает базу на T в своём контейнере, расшифровывает
файлы в чистый Garage со сверкой SHA-256, поднимает OpenBao из снимка на ключах аварийного
комплекта (`--openbao-keys`), запускает ядро без внешних адресов и без местных KEK
(почта none, вебхуки capture), проверяет шифрованные поля, вход и материалы.
Отчёт — `out/backup-restore/`. Это проверка механизма, не приёмка 2.1.4.

## Ключи Томаса

`node scripts/backup.mjs keys-init` создаёт пару gpg в `.local/backup-keys`:
`secret-key.asc` и `passphrase.txt` — в KeePassXC (вложение и пароль), затем
удалить с диска; `recipient.asc` — на сервер. Закрытого ключа на сервере нет:
комплект ключей сервером не открывается.

## Пока не входит

Static seal key OpenBao — намеренно вне комплекта (аварийный комплект Томаса); снимок
OpenBao и полная конфигурация узла в комплекте есть (работа № 5, [restore-full](restore-full.md)). Внешнее S3, HDD,
флешка — после MVP. Zabbix и независимый пульс — W08. Почасовая выгрузка аудита
по 2.1.5 — отдельно (аудит сейчас в копии базы).
