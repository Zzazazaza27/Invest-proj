# Учёт удалений после восстановления (2.1.5)

Согласовано Тэнком 09.11.2026, исправления по его замечаниям к `1a7ef69`. Проверка —
`CHK-DELETIONS-REPLAY`.

## Что уже есть до аварии

- **Ворота среды** (M167). При закрытых воротах ядро отвечает людям 503, `/v1/ready` —
  «не готов», а фоновые отправщики с внешними последствиями (почта, вебхуки) не работают.
  Закрыто, если выполнено хоть одно:
  - у процесса ядра задано удержание `CORE_RESTORE_HOLD` (метка восстановления);
  - строка ворот закрыта (`deletions-apply.mjs close`) или её нет;
  - отпечаток базы (кластер, линия времени WAL, oid) не тот, при котором ворота открыли.

  Отпечаток — дополнительная защита, а не доказательство восстановления: логическое
  восстановление в ту же базу его не меняет. Поэтому среду закрывают **явно**. Копии
  pg_dump снимаются без строки ворот (`--exclude-table-data=ops.restore_gate`).

- **Выгрузка аудита** — каждый час на сервере для рабочей среды и test-2
  (`fifth-audit-export@<среда>.timer`), роль `app_archive_user`. Это копия на том же
  сервере, независимой она не считается.
- **Вынос** — ноутбук Томаса (`scripts/audit-offsite.mjs pull`, задание
  `infra/laptop/audit-offsite-task.xml`), свой каталог и контрольная точка на каждую
  среду. Давность видна по сигналам `audit-export-<среда>` (> 2 ч) и
  `audit-offsite-<среда>` (> 3 ч). Два часа — цель при доступном ноутбуке, не гарантия.

## Порядок

1. **Закрыть до восстановления.** Остановить ядро среды; задать ему удержание
   `CORE_RESTORE_HOLD=<метка>`; если текущая база доступна —
   `node scripts/deletions-apply.mjs close --db <URL> --restore-id <метка>`.
2. **Источник событий** — по таблице постановки 2.1.5:
   - текущая база доступна — снять её копию и брать события из неё (`--source-db`);
   - текущая база потеряна — поднять в закрытой среде самое позднее состояние через
     pgBackRest и WAL (`--source-db`);
   - дополнительно или при потере всего — вынесенная выгрузка (`--source-export`, ключ
     Томаса для расшифровки, **`--checkpoint`** — контрольная точка получателя).
3. **Восстановить** рабочие данные (2.1.3 / 2.1.4) и сразу снова `close` по
   восстановленной базе. Ядро стартует только с удержанием.
4. **Применить**:

   ```bash
   node scripts/deletions-apply.mjs apply --db <URL владельца восстановленной базы> \
     --restore-id <метка> --source-export <каталог>/series \
     --checkpoint <каталог>/checkpoint.json \
     --secret-key <ключ Томаса> --passphrase-file <файл> --report <отчёт.json>
   ```

   Применяется итоговое состояние каждой идентичности после последнего общего звена
   цепочки. Повтор безопасен. «Закрыто» в отчёте — неоднозначные объекты: содержимое
   скрыто, выдачи сняты, а исключения (запреты) сохранены. Также «закрыто» — замены, чей
   новый файл недоступен (прежний скрыт, слот пуст). «Не воссоздано» — подписки и
   устройства, созданные после копии: их секреты в журнал не пишутся.

5. **Проверить**: `node scripts/deletions-apply.mjs verify …те же аргументы…`.
6. **Открыть** — только после проверки и с явным подтверждением конца покрытия:

   ```bash
   node scripts/deletions-apply.mjs open …те же аргументы… --coverage-ack <покрыто до>
   ```

   Ворота открываются для текущего отпечатка базы. Все сессии требуют нового входа:
   отзывы токенов после копии в ней не сохранились. Затем снять удержание
   `CORE_RESTORE_HOLD` и перезапустить ядро.

7. Зафиксировать отчёт и покрытие в инциденте. Неполный источник — инцидент; затронутые
   данные не открываются без проверки.

## Граница

Пакет делает только логическое удаление и учёт. Физическая очистка хранилища — процедура
3.3. Хранение комплектов копий — правило блока 7. Журнал и выгрузки автоматически не
очищаются: сроков ещё нет. Ни выгрузка, ни применение не удаляют объекты хранилища и
комплекты.

Смена кластера при крупном обновлении PostgreSQL и переключение на реплику тоже закрывают
ворота по отпечатку. Открытие — тем же шагом проверки.

Избранное в первом пакете не учитывается (ограничение, решение Тэнка 09.11).
