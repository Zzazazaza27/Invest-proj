# Наблюдение (блок 8, 2.1-W08a)

Zabbix 7.0 LTS на том же VPS, тревоги в личный Telegram, внешний пульс
Healthchecks.io. Это W08a — наблюдение и тревоги. **Блок 8 целиком этим не
закрыт:** журналы — W08b, внутренняя ITSM — W08c, общая приёмка — после них.

## Состав

| Часть                       | Где                                                                                                                     |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Zabbix server, веб, agent 2 | `infra/docker-compose.yml`, профиль `monitoring` (+ `monitoring-host` на VPS, `monitoring-local` на стенде)             |
| База Zabbix                 | отдельная база `zabbix` и роль `zabbix` (предел 30 соединений) в том же PostgreSQL — попадает в копии W07               |
| Наблюдение за PostgreSQL    | роль `zbx_monitor`: `pg_monitor` и CONNECT, без доступа к данным                                                        |
| Конфигурация                | `node scripts/monitoring.mjs configure` — узел, проверки, пороги, Telegram, повторы, хранение (идемпотентно)            |
| Контейнеры                  | `scripts/monitor-export.mjs` раз в минуту пишет файл; агент читает его, Docker socket ему не даётся                     |
| Пульс                       | `scripts/monitor-pulse.mjs` раз в минуту: отметка только при свежей работе Zabbix                                       |
| Ядро                        | служебный порт: `/live` (не завис), `/ready` (зависимости), `/jobs` (фоновые задачи), `/queues` (очереди, функция M152) |

Наружу не публикуется ничего: веб Zabbix — `127.0.0.1:8090`, приём от агента
— `127.0.0.1:10051`. На VPS веб открывается через ssh-туннель:
`ssh -L 8090:127.0.0.1:8090 root@<VPS>`, затем http://127.0.0.1:8090/.

## Что наблюдается и пороги

Пороги — таблица 8.2, собраны в `THRESHOLDS` в `scripts/monitoring.mjs`.

| Область            | Проверка                                                         | Проблема                                                                               |
| ------------------ | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Ядро               | `/live`                                                          | не живо; нет данных 3 мин — «неизвестно» (высокая)                                     |
| Ядро               | `/ready` — база, хранилище, Valkey, NATS, фон                    | зависимость fail три проверки подряд (высокая)                                         |

| Резервирование W07 | сигналы и свежесть проверки                                      | проверка не запускалась 15 мин; сами проблемы W07 — «информация» (W07 сообщает сам)    |
| Zabbix             | очередь проверок                                                 | больше 50 старше 10 минут                                                              |

**Готовность ядра.** `/ready` проверяет зависимости с ожиданием 2 с
(`READINESS_CHECK_TIMEOUT_MS`), ответ 200 — только без fail. Доступность
групп функций по блоку 4 (4.11) этим **не** закрыта.

**Появится только с журналами W08b:** анализ ошибок по журналам, доля 5xx,
ошибка при ответе 2xx, задержки запросов, ошибки интерфейса, OOM из журнала
ядра Linux.

## Тревоги

- Критическая и высокая — сразу, повтор раз в 30 минут, пока проблему не
  подтвердили в Zabbix («принято в работу»).
- Предупреждение и средняя — повтор раз в 4 часа до подтверждения.
- Информация — только в Zabbix, без сообщения.
- Восстановление — отдельным сообщением. Недоставку Zabbix повторяет до 5 раз.

Условия действий — строгое «И»: в режиме «И/ИЛИ» Zabbix объединяет условия
одного типа через ИЛИ (поймано испытанием: «Информация» уходила в Telegram).

## Пульс

Healthchecks.io, период 60 с, допуск 120 с. Отметка уходит, только если
контрольный элемент `agent.ping` в Zabbix свежий (до 180 с), — это читается
через API, то есть подтверждает и сервер, и базу Zabbix. Иначе — `/fail`:
сервис сообщает сразу. Внешние тревоги приходят от @HealthchecksBot.

| Испытание (локально, 01.11.2026) | Итог                                              |
| -------------------------------- | ------------------------------------------------- |
| ядро остановлено                 | пульс идёт; тревоги о ядре от Zabbix за ~3 мин    |
| сервер Zabbix остановлен         | отказ «контрольная отметка устарела» через ~3 мин |
| роль базы Zabbix без входа       | отказ сразу: «Error connecting to database»       |

## Ресурсы

Пределы контейнеров: сервер 512 МБ / 1 CPU, веб 256 МБ / 0,5, агент 128 МБ /
0,25. Замер на стенде: ~110 МБ памяти всего. Записей ~42 в минуту — около
1,8 млн за 30 дней, база Zabbix порядка 100–150 МБ сверх начальных ~70 МБ.
Почасовые сводки 24 месяца малы. Копии W07 растут на объём базы Zabbix и её
журнала изменений; срок хранения копий не согласован — рост учитывать.

## Включение на VPS (отдельным согласованным действием)

1. Дамп, `npm run deploy` с кодом W08a (миграция M152).
2. `.env`: `MONITOR_ENV=vps`, `ZABBIX_HOST_NAME=5e-vps`,
   `MONITOR_STATE_DIR=/var/lib/fifth-monitor`, пароли `ZABBIX_DB_PASSWORD`,
   `ZABBIX_MONITOR_DB_PASSWORD`, `ZABBIX_ADMIN_PASSWORD` (генерируются),
   позже `HEALTHCHECKS_PING_URL`.
3. `COMPOSE_PROFILES=monitoring,monitoring-host node scripts/infra.mjs up zabbix-db-init zabbix-server zabbix-web zabbix-agent2-host`.
4. Таймеры: `cp infra/systemd/fifth-monitor-* /etc/systemd/system/`,
   `systemctl daemon-reload`, `systemctl enable --now fifth-monitor-export.timer fifth-monitor-pulse.timer`.
5. `node scripts/monitoring.mjs configure`, затем `status --items` — все
   проверки с данными.
6. Пароль Admin — в KeePassXC Томаса. Пульс: аккаунт Healthchecks.io
   (Томас), адрес пинга — в `.env` и KeePassXC.
7. Проверка доставки на VPS: одна тревога и восстановление.
