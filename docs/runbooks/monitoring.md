# Наблюдение (блок 8, 2.1-W08a)

Zabbix 7.0 LTS на том же VPS, тревоги в личный Telegram, внешний пульс
Healthchecks.io. Это W08a — наблюдение и тревоги. **Блок 8 целиком этим не
закрыт:** журналы — W08b, внутренняя ITSM — W08c, общая приёмка — после них.

## Состав

| Часть                       | Где                                                                                                                     |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Zabbix server, веб, agent 2 | `infra/docker-compose.yml`, профиль `monitoring` (+ `monitoring-host` на VPS, `monitoring-local` на стенде)             |
| База Zabbix                 | отдельная база `zabbix` и роль `zabbix` (предел 30 соединений) в том же PostgreSQL — попадает в копии W07               |
| Наблюдение за PostgreSQL    | роль `zbx_monitor`: `pg_monitor` и CONNECT, без доступа к данным                                                        |
| Конфигурация                | `node scripts/monitoring.mjs configure` — узел, проверки, пороги, Telegram, повторы, хранение (идемпотентно)            |
| Контейнеры                  | `scripts/monitor-export.mjs` раз в минуту пишет файл; агент читает его, Docker socket ему не даётся                     |
| Пульс                       | `scripts/monitor-pulse.mjs` раз в минуту: отметка только при свежей работе Zabbix                                       |
| Ядро                        | служебный порт: `/live` (не завис), `/ready` (зависимости), `/jobs` (фоновые задачи), `/queues` (очереди, функция M152) |

Наружу не публикуется ничего: веб Zabbix — `127.0.0.1:8090`, приём от агента
— `127.0.0.1:10051`. На VPS веб открывается через ssh-туннель:
`ssh -L 8090:127.0.0.1:8090 root@<VPS>`, затем http://127.0.0.1:8090/.

Пороги — таблица 8.2, собраны в `THRESHOLDS` в `scripts/monitoring.mjs`.

| ------------------ | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Ядро               | `/live`                                                          | не живо; нет данных 3 мин — «неизвестно» (высокая)                                     |
| Ядро               | `/ready` — база, хранилище, Valkey, NATS, фон                    | зависимость fail три проверки подряд (высокая)                                         |

| Zabbix             | очередь проверок                                                 | больше 50 старше 10 минут                                                              |

**Готовность ядра (правило 4.9).** Состояние процесса читается после ожидания
зависимостей: остановка, начавшаяся во время проверки, снимает готовность в том
же ответе. `/ready`: общая готовность — завершён
запуск, основная БД и обязательные счётчики (Valkey, если настроен). При
сигнале остановки готовность снимается первым шагом. Хранилище и NATS —
отдельные строки `functions`: их отказ виден и даёт свою тревогу, но общую
готовность не снимает (функции, 4.11). Фоновые задачи — тоже отдельной
строкой. Ожидание каждой проверки — 2 с (`READINESS_CHECK_TIMEOUT_MS`).
Разметка групп функций по 4.11 этим **не** закрыта.

**Контрольная операция.** `/control`: ядро читает контрольную запись
(`audit.control_objects`, M153) обычным пулом приложения, скачивает
контрольный файл `control/probe-v1` своими учётными данными хранилища и
сверяет размер и SHA-256. Провал (запись не читается, файла нет, содержимое
другое, хранилище не отвечает) — высокая тревога после трёх неудач подряд,
восстановление после двух успехов; в значении «состояние файла» — что именно.
Завести объект: `node scripts/monitoring.mjs control-init`.

**Разрешённое чтение прикладным путём (2.5).** Служебная учётка мониторинга
`monitoring@5espace.invalid` (роль investor, происхождение `monitoring`, M154 —
скрыта из обычного списка админки) раз в минуту (`fifth-monitor-app-probe`)
входит обычным входом через публичный адрес (`MONITOR_PUBLIC_URL`) и читает
закрытый «Контрольный проект наблюдения» и его PDF по выданному разрешению
(profile + materials), сверяя SHA-256. Это ловит поломку входа и проверки
прав при исправной инфраструктуре; `/control` проверяет саму инфраструктуру.
Завести учётку и проект: `node scripts/monitor-probe-init.mjs` (пароль —
`CONTROL_PROBE_PASSWORD`, секрет). Сессия — в `MONITOR_PRIVATE_DIR`, агенту не
видна; вход — только при 401. **Ограничение учётки на сервере** (AuthGuard, M155): для происхождения
`monitoring` разрешены только «кто я», выход и чтение карточки и материала
проекта с тем же происхождением; всё остальное — 403 «Служебная учётка
мониторинга: действие не разрешено», даже при ошибочно выданном разрешении на
обычный проект. Обычные проверки доступа остаются. Проверка —
`scripts/check-monitoring-account.mjs` (9 случаев; со снятым ограничением
изменение профиля и аватара проходят — проверка это ловит).

**Нет данных — не «в порядке».** У каждой основной проверки своя тревога
«Нет данных: …» (три интервала). Ошибка получения — сервис недоступен,
файла нет — превращается шагом «проверка неподдерживаемого значения» в явный
0 или «устарело» (999999 с), а не оставляет прежнее зелёное значение.

**Появится только с журналами W08b:** анализ ошибок по журналам, доля 5xx,
ошибка при ответе 2xx, задержки запросов, ошибки интерфейса, OOM из журнала
ядра Linux.

## Тревоги

- Критическая и высокая — сразу, повтор раз в 30 минут, пока проблему не
  подтвердили в Zabbix («принято в работу»).
- Предупреждение и средняя — повтор раз в 4 часа до подтверждения.
- Информация — только в Zabbix, без сообщения.
- Восстановление — отдельным сообщением. Недоставку Zabbix повторяет до 5 раз.

Условия действий — строгое «И»: в режиме «И/ИЛИ» Zabbix объединяет условия
одного типа через ИЛИ (поймано испытанием: «Информация» уходила в Telegram).

## Пульс

Healthchecks.io, период 60 с, допуск 120 с. Отметка уходит, только если
контрольный элемент `agent.ping` в Zabbix свежий (до 180 с), — это читается
через API, то есть подтверждает и сервер, и базу Zabbix. Иначе — `/fail`:
сервис сообщает сразу. Внешние тревоги приходят от @HealthchecksBot.

| Испытание (локально, 01.11.2026) | Итог                                              |
| -------------------------------- | ------------------------------------------------- |
| ядро остановлено                 | пульс идёт; тревоги о ядре от Zabbix за ~3 мин    |
| сервер Zabbix остановлен         | отказ «контрольная отметка устарела» через ~3 мин |
| роль базы Zabbix без входа       | отказ сразу: «Error connecting to database»       |

## Ресурсы

Пределы контейнеров: сервер 512 МБ / 1 CPU, веб 256 МБ / 0,5, агент 128 МБ /
0,25. Замер на стенде: ~110 МБ памяти всего. Записей ~42 в минуту — около
1,8 млн за 30 дней, база Zabbix порядка 100–150 МБ сверх начальных ~70 МБ.
Почасовые сводки 24 месяца малы. Копии W07 растут на объём базы Zabbix и её
журнала изменений; срок хранения копий не согласован — рост учитывать.

## Включение на VPS (отдельным согласованным действием)

1. Дамп, `npm run deploy` с кодом W08a (миграция M152).
2. `.env`: `MONITOR_ENV=vps`, `ZABBIX_HOST_NAME=5e-vps`,
   `MONITOR_STATE_DIR=/var/lib/fifth-monitor`, пароли `ZABBIX_DB_PASSWORD`,
   `ZABBIX_MONITOR_DB_PASSWORD`, `ZABBIX_ADMIN_PASSWORD` (генерируются),
   позже `HEALTHCHECKS_PING_URL`.
3. `COMPOSE_PROFILES=monitoring,monitoring-host node scripts/infra.mjs up zabbix-db-init zabbix-server-host zabbix-web zabbix-agent2-host`.
   Сервер Zabbix на VPS — в сети узла (`zabbix-server-host`): Telegram с VPS
   доступен только по IPv6, у сетей Docker IPv6 нет. В `.env`
   `ZABBIX_WEB_SERVER_HOST=host.docker.internal`; в ufw —
   `ufw allow proto tcp from 172.16.0.0/12 to any port 10051` (веб-интерфейс к
   серверу), снаружи порт закрыт политикой «входящие запрещены».
4. Служебная учётка и контрольный проект: `node scripts/monitor-probe-init.mjs`,
   `node scripts/monitoring.mjs control-init`.
5. Таймеры: `cp infra/systemd/fifth-monitor-* /etc/systemd/system/`,
   `systemctl daemon-reload`, `systemctl enable --now fifth-monitor-export.timer fifth-monitor-pulse.timer fifth-monitor-app-probe.timer`.
6. `node scripts/monitoring.mjs configure`, затем `status --items` — все
   проверки с данными.
7. Пароль Admin — в KeePassXC Томаса. Пульс: аккаунт Healthchecks.io
   (Томас), адрес пинга — в `.env` и KeePassXC.
8. Проверка доставки на VPS: одна тревога и восстановление.
9. Публичный пульс для внешней проверки (отдельное согласование): в `.env`
   `MONITOR_PULSE_PUBLIC_DIR=/var/lib/fifth-monitor/public`, пересоздать
   контейнер `web` (том `/srv/pulse`), проверить
   `https://5espace.com/_pulse.json` — `{ at, ok }`. Затем в репозитории
   `rebel-diesel/scripts` задать переменную Actions `FIVE_E_PULSE_URL`.

## Внешняя проверка (5e_watch)

Временная мера после инцидента 2026-11-02 (`docs/incidents/2026-11-02-beget-dns.md`):
публичный репозиторий `rebel-diesel/scripts`, каталог `5e_watch`, запуск
GitHub Actions каждые 5 минут. Проверяет DNS через Cloudflare и Google, HTTPS
с ожидаемым кодом (сайт 200 через учётку `watch` на входе, секрет `FIVE_E_GATE_AUTH`, настройка — `infra/host/watch-gate-setup.sh`; files 404; при отказе DNS — по IP с Host и SNI),
сертификаты, срок домена, публичный пульс. Тревоги — в Telegram (тот же бот),
секреты — в GitHub Secrets. Запуск краснеет только при недоставке тревоги.
Ограничения: расписание GitHub задерживается и пропускает запуски; остановку
самого расписания схема не видит.
