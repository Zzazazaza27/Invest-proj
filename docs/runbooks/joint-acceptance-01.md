# Общая приёмка раздела 01 — план

Работы № 3–8 подготовлены локально. Работы № 1 и № 2 приняты. Этот план — порядок
проверок, нужные изменения на серверах, ресурсы и способы возврата. Каждый шаг с сервером
выполняется по слову Томаса. CI, установки, площадка WSL и копия prod до его «да» не
запускаются.

Сводка: [порядок](#порядок), [серверные изменения](#серверные-изменения),
[ресурсы](#ресурсы), [возврат](#возврат), [решения](#решения-тэнк-1211).

## Порядок

### 0. Сборка (ноутбук, затем CI)

1. Локально: `npm run lint:migrations` и чистая временная БД — миграции M177–M181
   (`docs/testing/change-matrix.md`).
2. Отправить накопленные коммиты в `main` одним push. Хук pre-push проверит секреты.
3. **«Да» Томаса** → `gh workflow run ci.yml`. Получается комплект `2.1-b<N>.1`.
4. Отчёт совместимости `compat.yml` для пары b136 → b\<N\>. Запускает Томас. Без подписанного
   отчёта установка на test-1 не идёт.

### 1. test-1 — комплект с работами № 4, № 6–8

### 2. test-1 — получатель вебхука (№ 3)

1. **Подключение на узле — отдельный шаг.** Два DNS-имени, HTTPS на порту 443, например
   `hook-a.test-1.5espace.com` и `hook-b.test-1.5espace.com` → получатель `127.0.0.1:18444`.
   Разные имена — разные узлы назначения (хост:порт), пауза ядра считается по узлу.
   - DNS-записи на адрес узла — Томас.
   - В Caddy — только два временных блока маршрута получателя, после испытания убрать.
     Дополнительные порты не открываются; другие блоки Caddyfile не меняются. Это не выпуск
     всего Caddyfile.

2. Сценарий:

   ```bash
   fifth-test op prod-webhook-receiver test-1 <A> <B> fail
   ```

   Затем `timeout`. Каждый прогон занимает около 3 минут.

3. Подключение снимается тем же шагом, что ставилось.

### 3. Узел — служба места (№ 4), только test-1

Службе нужна M181 в базе каждой цели, а у prod её до выпуска нет. До выпуска prod — явное
ограничение на test-1:

1. `fifth-test op prod-disk-guard-setup on test-1`, затем `status` — в выводе «цели: test-1».
   Цели задаёт drop-in службы. Zabbix в этом режиме не перенастраивается. Если первый отчёт не
   принят, таймер не включается.
2. Вместе с выпуском prod (M181): `prod-disk-guard-setup on` — все среды узла и
   `monitoring.mjs configure` (пороги 70/85 %, тревоги службы, «OpenBao открыт, но отказывает в
   запросах»).

**Сигнал при OOM ядра — сверено 12.11, первое объяснение Мауса было неверным.** После выхода
ядра обёртка завершается сама, контейнер поднимает Docker. В испытании № 4 `RestartCount`
вырос на 1 при `OOMKilled=false`. Выгрузка `monitor-export` такой перезапуск видит: опыт на
ноутбуке — `restarts` растёт при `OOMKilled=false`. Дальше срабатывает тревога «Контейнер
перезапускался» (`change(containers.restarts)>0`, уровень «предупреждение») и действие
«предупреждение — Telegram». На узле остаётся подтвердить фактическую тревогу и сообщение —
при первом перезапуске ядра prod (по журналу Zabbix) или отдельным шагом. Правка наблюдения не
нужна.

### 4. Полное восстановление (№ 5)

**4а. Искусственный комплект — первым.** Локальный стенд узловую часть комплекта не даст: он
на Docker Desktop под Windows, без systemd, юнитов и Caddy, а съём узла работает только на
Linux. Нужен узел-источник:

- **Предложение:** второй дистрибутив WSL `fifth-source`.
  1. Рабочая установка штатным путём из комплекта, собранного локально (`kit.mjs pack`):
     Caddy, юниты, OpenBao, Garage, Zabbix.
  2. Искусственные данные (`seed-demo`) и свой ключ получателя копий, не ключ Томаса.
  3. Снять комплект и выключить источник (`wsl --terminate fifth-source`). Две установки
     одновременно ноутбук не нагружают.
  4. Комплект → `restore-site-wsl` на `fifth-restore`.
  5. Оба дистрибутива удаляются.
- Это отдельная подготовка, около дня. Попутно она проверит установку на чистом Ubuntu.

**4б. Настоящий комплект prod — после зелёного 4а.**

1. Код копий (`backup.mjs`, `lib/host-config.mjs`) — на сервер через `fifth-test sync`. Синхронизация
   меняет инструменты узла. Дополнения Compose prod она не трогает: после работы № 1 они берутся
   из комплекта или закреплённой истории сборки (`compose/overlays`).
2. Внеочередной комплект: `op prod-backup-set`. Первый комплект сохранит все образы узла.
3. `backup.mjs pull` → аварийный комплект OpenBao → свежая выгрузка аудита prod
   (`audit-offsite.mjs pull`).
4. `restore-site-wsl.mjs create/prepare/check/run`, затем `destroy`.
5. Разница версий Caddy площадки и prod пишется в протокол.

### 5. prod накопительно — отдельным решением

После приёмки на test-1 Томас отдельно решает, что из этого переходит на prod. Кандидаты:

- комплект с M177–M181;
- служба места на все среды и настройка Zabbix (шаг 3.2);
- правило lifecycle бакета prod;
- Caddyfile из Git.

## Ресурсы

- **Время.**
  - Сборка CI — около 40 минут.
  - test-1, шаги 1.1–1.5 — 1,5–2 часа.
  - Наблюдение lifecycle — сутки ожидания.
  - № 3 — около 30 минут вместе с подключением.
  - № 4а: подготовка около дня, прогон 1–2 часа. № 4б — 2–3 часа, в основном перенос образов.
- **Место.**
  - Образы узла в каталоге копий — оценить до 4б: `docker system df` на узле (только чтение).
  - На ноутбуке — скачанный комплект prod (данные, образы) и два дистрибутива WSL.
- **Память.** WSL ограничен 4 ГБ. На время № 5 остановить стенд (`npm run stand:down`).
  Возможно, поднять предел до 6 ГБ — решение Томаса.
- **Внимание Томаса.**
  - «Да» на CI и запуск `compat.yml`.
  - DNS-записи двух имён получателя.
  - Согласие на скачивание образа ОС для WSL.
  - Ключ и фраза для открытия комплектов.

## Решения (Тэнк 12.11)

1. CI — после завершения локальной подготовки, одной сборкой для общей приёмки. Этот план сам
   по себе разрешением запускать CI не является.
2. Получатель — два DNS-имени, HTTPS на 443; в Caddy только временные маршруты.
3. Источник искусственного комплекта — второй дистрибутив WSL; после снятия копии он
   выключается, восстановление идёт отдельно.
4. Служба места на prod — вместе с выпуском (M181); до него — явно только test-1.
5. Правку наблюдения за OOM не заказывать: сигнал есть (см. шаг 3), на узле подтвердить его
   доставку.
