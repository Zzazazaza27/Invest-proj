# Раннбук: HestiaCP и почтовый сервер на стенде

Панель управления сервером и почтовый сервер на ВПС `193.233.217.210`
(`unicorn.ptr.network`, Ubuntu 24.04). Установлено 2026-08-25, версия
HestiaCP **1.10.4**.

## Что установлено и почему именно так

Панель нужна ради двух вещей: управление сервером и **почтовый сервер**
(задачи ТЗ №1 и №2). Веб-хостинг Hestia не используется — приложение уже живёт
за Caddy, и менять это ТЗ прямо запрещает. Отсюда состав:

| Компонент                              | Состояние                                        | Причина                                              |
| -------------------------------------- | ------------------------------------------------ | ---------------------------------------------------- |
| Панель `hestia-nginx`                  | 8083, работает                                   | сама панель                                          |
| Exim4                                  | 25, 587, работает                                | отправка и приём почты                               |
| Dovecot + Sieve                        | 993, работает                                    | IMAP, чтение ящиков                                  |
| Системный nginx                        | **отключён** (`systemctl disable --now nginx`)   | занимал 80/443, где работает Caddy с приложением     |
| Apache, MariaDB, PostgreSQL, BIND, FTP | не ставились                                     | не нужны; каждый — лишняя поверхность                |
| ClamAV, SpamAssassin                   | не ставились                                     | съедают 1–2 ГБ ОЗУ; для внутреннего стенда избыточно |
| iptables/fail2ban Hestia               | **не ставились** (`--iptables no --fail2ban no`) | на сервере работает ufw, и его правила терять нельзя |

**Про `--force` и ufw.** Установщик считает `ufw` конфликтующим пакетом, но
удаляет его ТОЛЬКО в интерактивном режиме при ответе «y». С `--force` он
пропускает весь блок конфликтов целиком — ufw остаётся нетронутым. Это
проверено фактом: после установки правила ufw (22, 4300 из docker-сети, 80, 443) на месте.

**Про `--username`.** С `--interactive no`, но без `--username` установщик
уходит в бесконечный цикл «Please use a valid username»: он спрашивает имя
администратора, а stdin закрыт. Обязательно передавать `--username admin`.

**Про `WEB_SYSTEM=no`.** После отключения nginx любая операция Hestia с
доменами пыталась его перезапустить и падала с `Restart of nginx failed`.
Веб-подсистема выведена из управления панелью — почты и панели это не
касается.

## Доступ

| Что                     | Адрес                                                                                          | Примечание                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Панель                  | `https://193.233.217.210:8083`                                                                 | пользователь `admin`, пароль в `/root/.hestia-admin` (права 600) |
| Панель через туннель    | `ssh -i .ssh/SERG -L 8083:127.0.0.1:8083 root@193.233.217.210`, затем `https://127.0.0.1:8083` | не требует открытого порта наружу                                |
| Ящик `info@vgorkakh.ru` | IMAP `193.233.217.210:993` (SSL), SMTP `:587` (STARTTLS)                                       | пароль в `/root/.mail-info-account` (600)                        |

Пароли на сервере в файлах с правами 600 и в репозиторий не попадают. В чат
они не выводились и выводиться не должны.

**Панель по HTTPS с нормальным сертификатом.** Сейчас на 8083 сертификат
самоподписанный. Чтобы отдать её через Caddy (у него уже работает
Let's Encrypt), нужна A-запись `panel.vgorkakh.ru → 193.233.217.210`, после
чего в `/etc/caddy/Caddyfile` добавляется:

```
panel.vgorkakh.ru {
    reverse_proxy https://127.0.0.1:8083 {
        transport http {
            tls_insecure_skip_verify
        }
    }
}
```

`tls_insecure_skip_verify` здесь допустим и только здесь: соединение идёт по
петле к самоподписанному сертификату самой же машины, наружу трафик выходит
уже под сертификатом Caddy. Наружу порт 8083 при этом открывать не нужно.

## Записи DNS, которые нужно опубликовать

Домен обслуживается в панели Timeweb, PTR — в панели Aeza. Ни туда, ни туда
доступа из репозитория нет: записи публикует владелец.

| Запись                    | Значение                                                          | Зачем                                                |
| ------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------- |
| `mail` A                  | `193.233.217.210`                                                 | имя почтового сервера                                |
| `panel` A                 | `193.233.217.210`                                                 | панель по HTTPS через Caddy                          |
| `vgorkakh.ru` MX          | `10 mail.vgorkakh.ru`                                             | **переключает приём почты с Timeweb на этот сервер** |
| `vgorkakh.ru` TXT         | `v=spf1 a mx ip4:193.233.217.210 ~all`                            | заменяет `include:_spf.timeweb.ru`                   |
| `mail._domainkey` TXT     | публичный ключ из `v-list-mail-domain-dkim-dns admin vgorkakh.ru` | подпись писем                                        |
| `_dmarc` TXT              | `v=DMARC1; p=none; rua=mailto:postmaster@vgorkakh.ru`             | политика; начинать с наблюдения                      |
| PTR для `193.233.217.210` | `mail.vgorkakh.ru`                                                | без него почту с этого адреса отвергают              |

**Переключение MX ломает текущую почту домена на Timeweb.** Если на ящики
Timeweb кто-то пишет или ими пользуются, сначала перенести их содержимое, а
уже потом менять MX. Это решение владельца, а не техническая деталь.

Порядок безопасного переключения: сначала `mail` A и PTR → потом SPF и DKIM →
проверить отправку → и только последним шагом MX.

## Проверка

```bash
# состояние домена и записей (публичный резолвер, не системный)
node scripts/probe-mail-readiness.mjs --domain vgorkakh.ru --ip 193.233.217.210 \
  --relay mail.vgorkakh.ru:587 --direct

# исходящие порты с самого сервера
ssh -i .ssh/SERG root@193.233.217.210 'cd /opt/unicorn-launch && \
  node scripts/probe-mail-readiness.mjs --domain vgorkakh.ru --outbound'

# настоящая отправка через свой сервер
MAIL_SMTP_PASSWORD=<пароль ящика> node scripts/probe-mail-delivery.mjs \
  --host 193.233.217.210 --port 587 --user info@vgorkakh.ru --to <внешний адрес>
```

**Порт 25 с этого ВПС открыт** — проверено с сервера 2026-08-25 содержательным
соединением: `220` от `gmail-smtp-in.l.google.com`, `mx.yandex.ru`,
`mx1/mx2.timeweb.ru`, все 8 направлений, с позитивным контролем
`github.com:443`. Прежний вывод от 2026-08-24 («25 закрыт провайдером»)
устарел — провайдер порт открыл.


## Что НЕ трогать

- **Не включать системный nginx** — он займёт 80/443 и уронит приложение.
  Если Hestia включит его обновлением, выключить снова.
- **Не ставить фаервол Hestia** — на сервере ufw, и его правила (4300/tcp из
  `172.16.0.0/12` для nginx-контейнера) при замене потеряются, а без них
  приложение перестанет отвечать.
- **Не создавать веб-домены в панели** — веб обслуживает Caddy.
