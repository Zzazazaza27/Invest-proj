# Совместимые миграции и точка возврата (блок 09, задание 2)

Постановка: `11 MVP/01 Operations and Updates/09 Update and Rollback.md`, 9.2–9.3.
Согласовано Тэнком 09.11.2026 с уточнениями; этот документ — как это устроено в коде.

## Правило: добавить → переключить → убрать

| Шаг         | Что можно                                                                                                       | Чем проверяется                         |
| ----------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| Добавить    | новые таблицы, необязательные колонки, колонки с DEFAULT, индексы, новые функции                                | линтер; прогон совместимости            |
| Переключить | заполнение порциями, перевод кода на новое                                                                      | прогон совместимости, проверки миграции |
| Убрать      | DROP, RENAME, SET NOT NULL, удаление функций — **отдельной миграцией `-- migrate:contract` следующим выпуском** | возврат за неё запрещён установщиком    |

Прежний код обязан работать на новой схеме: при возврате (схема остаётся новой — копию
БД поверх рабочей не восстанавливаем) и при двух ядрах (задание 3).

## Метки в файле миграции

| Метка                                | Значение                                                                                     |
| ------------------------------------ | -------------------------------------------------------------------------------------------- |
| `-- migrate:contract`                | удаляет то, на что опирается прежний код; возврат на сборку без этой миграции запрещён       |
| `-- migrate:no-transaction`          | выполняется вне транзакции (CREATE INDEX CONCURRENTLY); только повторяемые операции          |
| `-- migrate:lock-timeout=30s`        | своё ожидание блокировки (по умолчанию 5s)                                                   |
| `-- migrate:statement-timeout=20min` | свой предел выполнения (по умолчанию 5min); тяжёлой миграции — отдельная оценка длительности |
| `-- migrate:compat-none: <причина>`  | рискованная операция не затрагивает прежний код — объяснение обязательно                     |

## Линтер (`npm run lint:migrations -w database`), правила с M171

- **Ошибка без `migrate:contract`:** RENAME; `SET NOT NULL`; `ADD COLUMN … NOT NULL` без
  DEFAULT; `DROP FUNCTION`; `DROP TYPE|VIEW|SCHEMA` (вместе с прежними DROP TABLE/COLUMN,
  TRUNCATE, сменой типа).
- **Ошибка без проверки:** смена существующей функции (`CREATE OR REPLACE` функции из прежних
  миграций), REVOKE, смена политик RLS, новое значение перечисления, новые CHECK/UNIQUE/FK.
  Нужен файл `database/compat/<миграция>.mjs` либо `-- migrate:compat-none: <причина>`.

Признак contract — запрет. Его отсутствие совместимости не доказывает: её подтверждает прогон.

## Прогон миграций (`database/src/migrate.ts`)

- Ограничения времени на каждую миграцию — и транзакционную (`SET LOCAL`), и
  нетранзакционную (на сеанс, сбрасываются после). Превышение — «Миграция … остановлена:
  ожидание блокировки дольше 5s» или «выполнение дольше 5min»; выпуск не продолжается.
- Непригодный индекс до прогона:
  - **свой** — его строит ожидающая миграция вне транзакции (`CREATE INDEX CONCURRENTLY IF
NOT EXISTS имя`) и он совпадает с ней не только именем, но и таблицей и определением
    (`pg_get_indexdef` против текста миграции): удаляется и строится заново этой же
    миграцией (`IF NOT EXISTS` сам по себе оставил бы его непригодным). Соответствие
    доказывается только для однозначной формы — `[UNIQUE] INDEX имя ON [схема.]таблица
[USING метод] (колонка, …)` с именами без кавычек;
  - **то же имя, но другая таблица или определение, либо форма не однозначна** (WHERE,
    выражения, кавычки, INCLUDE, порядок сортировки, классы операторов) — остановка без
    удаления, в диагностике оба определения. Такой индекс разбирают вручную;
  - **чужой** — остановка с диагностикой, индекс не трогается: выяснить происхождение и
    решить отдельно.
- После миграции вне транзакции её индексы обязаны быть пригодными, иначе она не применена.

Испытание: `node scripts/check-migrate-interrupt.mjs` — своя временная база.

## Прогон совместимости

```bash
node scripts/kit.mjs fetch --build <прежняя> --run <запуск CI>
node scripts/check-migration-compat.mjs --previous <прежняя> --candidate <кандидат>
```

Прежняя — фактически установленная сборка среды. Образы обоих комплектов — по дайджесту,
временная среда `test-77` из образов, рабочие среды не затрагиваются. Фазы:

1. прежний комплект: участник A — вход, контакт, файл, проект;
2. кандидат (миграции + ядро): сессия A жива, чтение записей A; участник B — записи
   кандидата; права (B не видит черновик A);
3. **прежний образ на новой схеме** (то, что даёт возврат): вход A и B, права, чтение
   проекта, зашифрованного контакта и файла обоих, запись прежним ядром; проверки
   `database/compat/<миграция>.mjs` для новых миграций;
4. кандидат снова: чтение записи прежнего ядра; проверки миграций.

Отчёт `<комплекты>/<кандидат>/compat-<прежняя>.json` привязан к хешам обоих комплектов.
Хеши связывают отчёт с образами, но не подтверждают, кто выполнил проверку: доверенное
происхождение отчёта и его доставка на узел — до выпуска (TODO сейфа, Тэнк 09.11).

## Установщик (`scripts/release.mjs install`)

- Одно правило (`scripts/lib/rollback-policy.mjs`) и для отметки, и для самого возврата:
  «проверена» значит ровно «возврат будет разрешён».
- Обычная установка записывает в журнал и результат **точку возврата**: прежняя сборка и
  «проверена» / «НЕ проверена» с причиной. Новая contract-миграция — «НЕ проверена» даже при
  пройденном отчёте.
- `--rollback` при незнакомых целевому комплекту миграциях в базе:
  - есть contract-миграция — отказ: только исправление вперёд (9.3);
  - нет отчёта `ok` этой пары комплектов, покрывающего все незнакомые миграции, — отказ:
    остановить выпуск и решить с Томасом. Автоматический возврат установщика получает тот
    же отказ.
