# Как запускать наборы и читать отчёт

Коротко: две команды перед передачей работы, одна — перед выкатом, и одна
отдельная для разрушительных проверок. Всё остальное — детали, которые
нужны, только когда что-то покраснело.

## Перед тем как отдать работу владельцу

```bash
npm run suite:handoff
```

Семь позиций, около минуты. Это ядро: тесты схемы базы, проверки прав,
тестовых сессий, профиля, переноса содержимого, границ наружу и связанный
сценарий «основатель → эксперт → инвестор».

Сверх этого набора запускается то, что назначила
[матрица изменений](матрица-изменений.md) для затронутой области. Правка
авторизации, работы с базой или общих пакетов задевает все кабинеты сразу —
там проверяются все потребители, а не один экран.

## Перед выкатом или по требованию

```bash
npm run suite:regression
```

Двенадцать позиций, около семи минут: всё из `handoff` плюс браузерные
проходы и проверка живучести соединений с базой. Браузерным проходам нужен
поднятый стенд (`npm run stand:up`) — набор проверяет это сам и честно
пропускает, а не делает вид, что прошло.

## Разрушительные проверки

```bash
npm run suite:isolated
```

Обрывы соединений, остановка брокера, порча данных. Работает на **своём**
ядре, своей базе и своём брокере (`unicorn-nats-test`): общий стенд не
трогается. Запускается отдельно от остальных наборов.

## Как читать отчёт

Отчёт пишется в `out/suites/<набор>-<дата>.md` и **не затирает предыдущий** —
чтобы было видно, был ли прогон нестабильным.

В шапке отчёта:

- **версия кода** — коммит, на котором получен результат;
- **«+ незакоммиченные правки»** — зелено на рабочем дереве, а не на
  коммите. Это другое утверждение, и в приёмку оно годится хуже;
- **стенд** — поднят или нет.

В таблице три исхода, и путать их нельзя:

| Итог        | Что означает                                                                   |
| ----------- | ------------------------------------------------------------------------------ |
| `успех`     | прогон отработал и не нашёл дефектов                                           |
| `ОТКАЗ`     | нашёл дефект или упал сам; полный вывод лежит рядом с отчётом отдельным файлом |
| `пропущено` | **не запускался**. Не считается пройденным ни при каких обстоятельствах        |

Строка «Пропущенное — НЕ считается пройденным» в конце отчёта перечисляет
пропуски с причиной. Если такая строка есть — набор не зелёный, что бы ни
показывал счёт.

## Если покраснело

1. Откройте файл `out/suites/<набор>-<дата>-<ИДЕНТИФИКАТОР>.log` — там весь
   вывод прогона целиком, а не обрезанный хвост.
2. Запустите этот прогон отдельно: его команда есть в
   [реестре](реестр.md).
3. Зелёный повторный запуск **не отменяет** первого отказа. Если прогон
   краснеет через раз — это находка, и о ней пишут, а не перезапускают до
   зелёного.

Частая причина отказа «через раз» — ограничение частоты: наборы идут
подряд, быстрее человека. Клиенты прогонов ждут названное сервером время и
повторяют сами; если всё же 429 — в отчёте это видно по тексту ошибки.

## Что этот зелёный цвет не означает

Наборы проверяют то, что покрыто. Непокрытое перечислено в
[карте пробелов](пробелы.md): доступ к файлам по прямой ссылке, протечки
через поиск, одновременная работа двух человек вне денежного контура и
логика ядра без модульных проверок.
