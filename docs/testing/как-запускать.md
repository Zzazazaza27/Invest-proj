# Как запускать наборы и читать отчёт

Коротко: две команды перед передачей работы, одна — перед выкатом, и одна
отдельная для разрушительных проверок. Всё остальное — детали, которые
нужны, только когда что-то покраснело.

## Кто что запускает

**CI не запускает ни одного набора.** В CI работают задания `push`, `static`,
`secrets-scan`, `sast`, `deps`, `database`, `unit`, `build` — линтер, формат,
типы, сборка, миграции, тесты схемы базы и 36 статических проверок и гейтов.
Это всё, что защищено без участия человека.

Наборы ниже запускает **Маус вручную**. Ночной автоматизации нет — по
решению владельца. Поэтому отчёт о запуске и есть единственное
свидетельство: не запустили — значит, не проверено.

## Сколько проверять — по размеру правки

Правило владельца, и оно важнее привычки «на всякий случай прогоню всё».
Полный набор после каждой мелочи никто долго не терпит: его начинают
пропускать целиком, и тогда он не защищает ничего.

| Что сделано                                                             | Что запускать                                                                                      |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **Небольшая правка** — текст, отступ, одна подпись, одна проверка формы | Ничего из наборов. Посмотреть изменённый экран и, если правка задела разметку, прогон этого экрана |
| **Создание или изменение самой проверки**                               | Эту проверку — обязательно, иначе неизвестно, работает ли она                                      |
| **Большое изменение** — поведение, схема, права, договор                | **Блок затронутой части** и блоки зависимостей: `npm run suite:block block:<имя>`                  |
| **Передача работы владельцу**                                           | `npm run suite:handoff`                                                                            |
| **Полная регрессия**                                                    | `npm run suite:regression` — **только по прямой команде Томаса**, не по своему усмотрению          |

Общий набор НЕ запускается автоматически после каждой правки.

### Функциональные блоки

Блок — это то, что проверяют вместе, когда трогали одну часть продукта.

```bash
npm run suite:block block:доступ
```

| Блок                      | Что покрывает                                   | Позиций |
| ------------------------- | ----------------------------------------------- | ------- |
| `block:доступ`            | Права, роли, видимость и границы доступа        | 18      |
| `block:вход`              | Вход, сессии, восстановление доступа            | 6       |
| `block:заявка`            | Заявка, проект и материалы (кабинет основателя) | 16      |
| `block:инвестор`          | Каталог, избранное, сделки                      | 6       |
| `block:эксперт`           | Назначения и разбор                             | 5       |
| `block:деньги`            | Тарифы, подписки, комиссии, оплата, раунды      | 17      |
| `block:администрирование` | Пользователи, сотрудники, полномочия, админка   | 8       |
| `block:содержимое`        | Подготовленное содержимое, витрина, поддержка   | 10      |
| `block:события`           | Outbox, брокер, вебхуки, интеграции, почта      | 8       |
| `block:надёжность`        | База, соединения, живучесть под сбоями          | 5       |
| `block:граница`           | Договоры, сборка, общие пакеты                  | 6       |
| `block:безопасность`      | Секреты, роли БД, шифрование, выкат             | 11      |
| `block:стенд`             | Порты, развёртывание, консоль                   | 7       |
| `block:разбор-моделью`    | Шлюз языковой модели                            | 4       |
| `block:порядок`           | Сам реестр проверок и учёт техдолга             | 3       |

Состав блоков — суждение о том, что ломается вместе, собранное по назначению
прогонов. Это не доказательство: тело большинства проверок не читалось, и у
каждой записи реестра честно проставлен уровень изучения. Прогон, попавший не
в свой блок, — ошибка группировки; о такой находке говорят, а не молчат.

Один прогон может входить в несколько блоков: граница доступа к файлам нужна
и когда трогали файлы, и когда трогали права. Внутри одного запуска общая
команда выполняется один раз — восемнадцать тестов схемы не гоняются
восемнадцать раз.

## Перед тем как отдать работу владельцу

```bash
npm run suite:handoff
```

Семь позиций, около минуты. Это ядро: тесты схемы базы, проверки прав,
тестовых сессий, профиля, переноса содержимого, границ наружу и связанный
сценарий «основатель → эксперт → инвестор».

Сверх этого набора запускается то, что назначила
[матрица изменений](матрица-изменений.md) для затронутой области. Правка
авторизации, работы с базой или общих пакетов задевает все кабинеты сразу —
там проверяются все потребители, а не один экран.

## Перед выкатом или по требованию

```bash
npm run suite:regression
```

Двенадцать позиций, около семи минут: всё из `handoff` плюс браузерные
проходы и проверка живучести соединений с базой. Браузерным проходам нужен
поднятый стенд (`npm run stand:up`) — набор проверяет это сам и честно
пропускает, а не делает вид, что прошло.

## Разрушительные проверки

```bash
npm run suite:isolated
```

Обрывы соединений, остановка брокера, порча данных. Работает на **своём**
ядре, своей базе и своём брокере (`unicorn-nats-test`): общий стенд не
трогается. Запускается отдельно от остальных наборов.

## Как читать отчёт

Отчёт пишется в `out/suites/<набор>-<дата>.md` и **не затирает предыдущий** —
чтобы было видно, был ли прогон нестабильным.

В шапке отчёта:

- **версия кода** — коммит, на котором получен результат;
- **«+ незакоммиченные правки»** — зелено на рабочем дереве, а не на
  коммите. Это другое утверждение, и в приёмку оно годится хуже;
- **стенд** — поднят или нет.

В таблице три исхода, и путать их нельзя:

| Итог        | Что означает                                                                   |
| ----------- | ------------------------------------------------------------------------------ |
| `успех`     | прогон отработал и не нашёл дефектов                                           |
| `ОТКАЗ`     | нашёл дефект или упал сам; полный вывод лежит рядом с отчётом отдельным файлом |
| `пропущено` | **не запускался**. Не считается пройденным ни при каких обстоятельствах        |

Строка «Пропущенное — НЕ считается пройденным» в конце отчёта перечисляет
пропуски с причиной. Если такая строка есть — набор не зелёный, что бы ни
показывал счёт.

## Если покраснело

1. Откройте файл `out/suites/<набор>-<дата>-<ИДЕНТИФИКАТОР>.log` — там весь
   вывод прогона целиком, а не обрезанный хвост.
2. Запустите этот прогон отдельно: его команда есть в
   [реестре](реестр.md).
3. Зелёный повторный запуск **не отменяет** первого отказа. Если прогон
   краснеет через раз — это находка, и о ней пишут, а не перезапускают до
   зелёного.

Частая причина отказа «через раз» — ограничение частоты: наборы идут
подряд, быстрее человека. Клиенты прогонов ждут названное сервером время и
повторяют сами; если всё же 429 — в отчёте это видно по тексту ошибки.

## Что этот зелёный цвет не означает

Наборы проверяют то, что покрыто. Непокрытое перечислено в
[карте пробелов](пробелы.md): доступ к файлам по прямой ссылке, протечки
через поиск, одновременная работа двух человек вне денежного контура и
логика ядра без модульных проверок.
