# Матрица изменений: что запускать после правки

Этот файл отвечает на один вопрос: **я поправил вот это — что обязан
прогнать перед тем, как отдать работу?**

Он написан руками, а не выведен из реестра: связь «файл → проверка» — это
суждение о том, что может сломаться, и машина его не выведет. Идентификаторы
проверок здесь настоящие, их существование сторожит `npm run check:registry`
(он краснеет на ссылке в никуда), а что делает каждая — в
[реестре](реестр.md).

## Как пользоваться

1. **Сначала решите, большая ли правка.** Мелкая — ничего из наборов не
   нужно, довольно посмотреть изменённый экран. Правила по размеру правки —
   в [инструкции](как-запускать.md).
2. Для большого изменения найдите строку, в которую оно попадает. Попадает в
   несколько — выполняются все.
3. Быстрее всего это делается блоком: `npm run suite:block block:<имя>`.
   Строки ниже говорят, какие блоки и отдельные прогоны относятся к области.
4. Пропущенное не считается пройденным. Если прогон не запускался — так и
   пишите в отчёте, а не «там всё то же самое».

```bash
npm run suite:block block:доступ
```

## Правило широкого следа

Три области ломают не себя, а всех, кто ими пользуется. Здесь **не бывает**
«поправил одно место — проверил один экран»:

| Что задето                                                                                                   | Почему широко                                                             | Что обязательно                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Авторизация, сессия, гвард, CSRF (`apps/core/src/auth/**`) — блоки `доступ`, `вход`                          | Одно правило решает доступ во всех кабинетах сразу                        | `CHK-TESTING-SESSIONS`, `SMK-CORE`, `SMK-ADMIN-ROLES`, `SMK-PROJECT-ACCESS`, `RND-AUTH`, `RND-LAB`, `RND-INVESTOR`, `RND-EXPERT`, `RND-ADMIN`, `RND-PROFILE`, `RND-STAFF-ACCESS`, `SCN-ROUND-REVIEW` |
| Работа с базой: соединения, транзакции, контекст запроса, миграции — блок `надёжность`                       | Отказ проявляется не там, где правка, а в первом же запросе под нагрузкой | `DBT-ALL`, `CHK-DB-RECONNECT`, `npm run suite:isolated`, `SMK-CORE`                                                                                                                                  |
| Общие пакеты `packages/ui`, `packages/cabinet`, `packages/api-client`, `packages/contracts` — блок `граница` | Компонент виден во всех кабинетах; договор ломает и клиента, и сервер     | `CHK-FRONT-BUILDS`, `SMK-API-CLIENT`, и браузерные проходы **каждого** кабинета: `RND-LAB`, `RND-INVESTOR`, `RND-EXPERT`, `RND-ADMIN`, `RND-CONSOLE`, `RND-WEB-PUBLIC`, `RND-PROFILE`                |

Правка в этих трёх областях — повод предупредить владельца до начала работы,
а не после: она задевает больше, чем один экран.

## Чего матрица не обещает

Она перечисляет **существующие** проверки. Область, у которой проверки нет,
здесь не появится от того, что её вписали, — незакрытое собрано в
[карте пробелов](пробелы.md). Все три — высокие или средние, и правка
в их области проверяется руками, с записью в отчёте о том, что именно
смотрели глазами.
