## 2. Участие отдельно от полномочий

**Сейчас.** `lab.founders_projects` с ролями `owner|cofounder` — одновременно и участие, и
права. `lab.is_project_member` не различает владельца и сооснователя. Сооснователь сегодня
может всё, что владелец: править проект, менять видимость и листинг, загружать и удалять
материалы, логотип и обложку, выдавать и снимать персональный доступ, видеть закрытые
материалы и удалённые проекты (`project-media.service.ts:378` прямо разрешает `cofounder`).
Это противоречит П4.

**Станет.**

| Понятие               | Где хранится                                                         | Что даёт                                                                              |
| --------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Создатель             | `lab.projects.creator_id`, неизменяемо (триггер)                     | ничего, кроме факта в истории                                                         |
| Владелец              | `lab.projects.owner_id`, ровно один                                  | полномочия оператора + удаление, передача, назначение операторов                      |
| Оператор бизнес-юнита | `access.unit_assignments`, состояние `active`                        | все полномочия на проект, кроме владельческих; входит в круг «Операторы бизнес-юнита» |
| Роль участия          | `lab.founders_projects` (переименование не делаю — меньше переделки) | только факт; ни одна проверка доступа на неё не смотрит                               |

Владелец всегда имеет активное назначение оператора, пока он владелец (инвариант в БД). При
будущей передаче (S11) назначение прежнего владельца остаётся или снимается — модель это
допускает, сама передача в 3.1 не делается.

`identity.users.primary_role` (`founder|investor`) на доступ к проектам перестаёт влиять:
проверки маршрутов `@Roles('founder')` на действиях с существующим проектом заменяются общей
проверкой. Создание проекта остаётся за прежним условием до пакета «регистрация и подключение
кабинетов» (S01, S06) — там «роль при регистрации» заменится подключением «Проектов».

## 3. Общая проверка доступа

### 3.1 Две функции — два вопроса

Доступ и полномочия отвечают на разные вопросы (_06 «Ссылки, показ и публикация»), поэтому
функции две, обе в БД, в схеме `access`:

- **`access.can_view(object_id, user_id) → boolean`** — может ли пользователь открыть объект.
  Объект существует, не удалён, не заблокирован → среди кругов, которым открыт объект, есть
  круг, куда пользователь входит по действующему основанию → то же для родителя (П11).
- **`access.can_act(unit_id, user_id, action) → boolean`** — может ли пользователь действовать.
  `action` из справочника: `edit` (оператор), `manage_operators`, `delete`, `transfer`
  (владелец). Справочник «действие → кто» — таблица `access.unit_actions`, а не ветки в коде.

Принадлежность к кругу решает **одна** функция `access.in_circle(circle, circle_owner, user)`.
Основание каждого круга — данные: «Все» — без основания; «Операторы бизнес-юнита» — активное
назначение в `access.unit_assignments`; «Интересанты» — запись участника круга проекта
(`access.circle_members`), в MVP наполнится принятым откликом (B2-S30), сейчас пуст. Новый круг —
строка в `access.circles` и одна ветка основания в этой функции.

Для «Посмотреть как…» — **`access.can_view_as(object_id, circles[])`**: та же логика, но
принадлежность к кругам задана списком. Это убирает вторую копию правил на TypeScript
(`packages/contracts/src/domain/visibility.ts`, `project-views.service.ts` viewPreview).

### 3.2 Где применяется

| Путь обращения                                           | Сейчас                                                                 | Станет                                                                            |
| -------------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Строки `lab.projects`, материалов, медиа (RLS)           | `is_project_member`, `project_audience`, `visible_to`                  | политики вызывают только `access.can_view` / `access.can_act`                     |
| API ядра: страница, правка, видимость, материалы         | `assertCanChange`, `assertProjectVisible`, `assertCanEdit` по членству | один помощник ядра `AccessService.require(view                                    | act)`, который зовёт функции БД; своих правил в ядре нет |
| Каталог, поиск по названию, избранное                    | `v_public_catalog` через `can_view_project`                            | тот же каталог через `can_view` страницы                                          |
| Файлы материалов (`/materials/:id/content`, прокси ядра) | RLS-строка, 404                                                        | `can_view` материала и страницы; при отказе — общий 404                           |
| Медиа (логотип, обложка, публичный маршрут)              | RLS по тизеру                                                          | медиа — часть страницы: `can_view` страницы                                       |
| Загрузка, финализация, удаление файлов                   | членство, автор                                                        | `can_act(edit)`; отмена своей загрузки — по-прежнему автор                        |
| «Посмотреть как…»                                        | TS-копия правил                                                        | `can_view_as`                                                                     |
| Фоновые задачи, служебные выгрузки                       | роль `app_integration` читает всё                                      | без изменений: это не доступ пользователя; правила S21 — позже                    |
| Лента, уведомления                                       | нет                                                                    | функции, когда появятся, обязаны ходить через `can_view`; сторож из § 6 это ловит |

**Прямые запросы.** Всё, что открывает данные проекта, закрыто RLS с этими функциями: прямой
SQL от `app_backend` и любой новый маршрут без помощника ядра получат пустой ответ, а не
данные. Попутно закрываются найденные обходы:
`founders_insert WITH CHECK (true)` (любой сеанс мог вписать себя в проект),
`GET …/materials/:id/content` без проверки маршрута, SECURITY DEFINER-счётчики материалов без
проверки проекта.

### 3.3 Один ответ об отказе

Все отказы по объектам доступа — **404 «Страница недоступна»** с одинаковым телом. Сейчас
различаются, и это меняется:

- `@Roles` отвечал 403 раньше поиска объекта;
- 403 администратору на правке медиа;
- 403 в viewPreview;
- `42501 → 403 db-policy`;
- **422 «Пользователь с таким адресом не найден» при выдаче доступа** — раскрывает, есть ли
  адрес на платформе. В приглашении это не повторяем: ответ одинаковый для любого адреса
  (приложение А).

Исключения, которые остаются отдельными ответами:

- **«Полномочия отозваны».** Тому, у кого было назначение на этот проект, а теперь его нет, —
  тот же 404, но с признаком `revoked`. Существование проекта он и так знает, другим признак
  не выдаётся.
- **Сбой проверки** — 503 «временно недоступно» по П16. Это не 404.

### 3.4 Служебный доступ (временно)

Сейчас `app.has_role('admin')` в `project_audience` открывает всё, включая черновики и
удалённые проекты. Служебные права — непройденный B1-S17, поэтому придумывать их сейчас не
буду. Предлагаю **костыль по правилу 18.11**:

- **Что.** Администратор читает проекты для каталога администрирования. Это одна ветка
  `staff_read` в `access.can_view`, а не обход в разных местах.
- **Почему иначе нельзя.** Модели служебных прав ещё нет.
- **Где.** Одна функция.
- **Когда уберём.** После S17: ветка заменится служебным кругом или назначением.

Решение — за Томасом (вопрос 3).

## 4. Изменения схемы

Новые миграции после M181, только вперёд, в порядке expand → перенос → contract
(сосуществование версий ядра — по порядку W09):

1. **Расширение.**
   - Схема `access`:
     - `circles` (код, хозяин-тип, этап);
     - `objects` (id, вид `project_page|material|history`, бизнес-юнит, родитель);
     - `openings` (объект, круг, хозяин круга, кто и когда открыл);
     - `unit_assignments` (бизнес-юнит, пользователь, состояние
       `invited|active|declined|cancelled|withdrawn|revoked`, кто пригласил, временные метки;
       одно активное на пару);
     - `invitations_contact` (адрес приглашённого — зашифрован общим `CryptoService`,
       плюс слепой индекс);
     - `circle_members` (пусто);
     - `unit_actions`.
   - Функции `can_view`, `can_act`, `in_circle`, `can_view_as`.
   - В `lab.projects` — `creator_id`, `owner_id`, оба NOT NULL после переноса.
2. **Перенос данных** (§ 5) и объекты для существующих страниц и материалов.
3. **Сжатие** — после выпуска ядра на новых проверках:
   - RLS переводятся на новые функции;
   - `project_audience`, `can_view_project`, `visible_to` для проектов и `is_project_member`
     удаляются или становятся тонкими обёртками до следующего выпуска;
   - `lab.projects.visibility` и `project_materials.visibility` перестают читаться: колонки
     остаются до отдельного решения, триггер запрещает запись.

Журнал действий — новые глаголы:

- `access.opening.changed` — прежние и новые круги (П14);
- `access.assignment.invited|accepted|declined|cancelled|withdrawn|revoked`.

В событии записываются роль действующего (`owner|operator`) и основание. Сейчас владелец и
сооснователь оба пишутся как `founder`.

## 6. Проверки

1. **Таблица случаев матрицы просмотра — одним файлом данных** (`database/tests/access-cases.*`),
   её читают и тест БД, и проверка API. Измерения:
   - пользователь — гость, вошедший, интересант (подставной участник круга), оператор,
     владелец, отозванный оператор, только сооснователь, приглашённый без ответа,
     администратор;
   - объект — черновик, открытая страница, материал «только операторам», материал на
     закрытой странице, удалённый проект;
   - путь — строка SQL, каталог и поиск, API страницы, байты файла, медиа, «Посмотреть как…».

   Ожидание — «открыто» или «404». Правило меняется — меняется строка таблицы.

2. **Отказы:**
   - одинаковое тело 404 на всех путях (сравнение ответов, включая заголовки и длину);
   - отозванный оператор со старой сессией получает отказ на следующем же запросе;
   - сбой БД при проверке — 503, а не 404 и не 200;
   - прямой `INSERT` в участие или назначение от `app_backend` — отказ;
   - сооснователь без назначения не может править, загружать, менять круги.
3. **Приглашение:**
   - повторное приглашение того же адреса идемпотентно;
   - ответ одинаковый для существующего и несуществующего адреса;
   - нельзя принять отозванное или чужое;
   - владелец не может отказаться от назначения;
   - гонка «принять» / «отозвать» — побеждает одно.
4. **Сторож:** тест БД перечисляет политики RLS на таблицах объектов доступа (`pg_policies`).
   Каждая обязана вызывать `access.*`, прямые условия на `founders_projects` и `visibility` —
   отказ.
5. **Переписать прогоны, которые знают старую модель:**
   - DBT-PROJECT-ACCESS, DBT-ACCESS-PATHS, DBT-PROJECT-VIEWS, DBT-RLS (случаи cofounder);
   - SMK-PROJECT-ACCESS, SMK-LAB (403/404);
   - SMK-PROJECT-MEDIA, CHK-FILE-ACCESS;
   - RND-PROJECT-PAGE, RND-LAB;
   - UNIT-PKG-CONTRACTS-VISIBILITY — удаляется вместе с TS-копией.

## 8. Выпуск и откат

- Три миграции по порядку expand → перенос → contract, как в W09:
  - старое ядро работает на расширенной схеме;
  - сжатие — следующим выпуском, после подтверждения.
- Цепочка сред: локал → test-1 → test-2 → prod (prod — отдельным решением). Перед переносом на
  каждой среде — опись по § 5.
- Откат до сжатия — прежний выпуск, данные доступа старой модели не тронуты. После сжатия —
  только исправлением вперёд.

## Приложение А. Эскиз экранов приглашения

Простой эскиз: тексты и состояния. Вид — из общих компонентов `packages/ui`, отдельной
вёрстки в эскизе нет. Место — карточка «Операторы» на странице управления проектом и список
«Приглашения» в «Проектах». Полный состав кабинета — B2-S23, здесь только минимум.

### А1. Владелец: карточка «Операторы проекта»

```
Операторы проекта
Операторы ведут проект вместе с вами: правят страницу, открывают её кругам,
работают с материалами. Удалить или передать проект можете только вы.

  Анна Смирнова         владелец
  Пётр Иванов           оператор            [Снять назначение]
  ivan@…mail.ru         ждёт ответа         [Отозвать приглашение]

Участники без назначения
  Олег Ким — сооснователь   Участие не даёт прав на проект.   [Пригласить оператором]

[Пригласить оператора]
```

### А2. Владелец: приглашение

```
Пригласить оператора
Почта пользователя  [__________________]
Он увидит приглашение в разделе «Проекты» и сможет принять или отклонить его.
Права появятся только после принятия.
                                         [Отмена] [Пригласить]
```

После нажатия: «Приглашение создано. Если по этому адресу нет пользователя 5Э, он увидит
приглашение после регистрации». Ответ одинаковый для любого адреса.

### А3. Получатель: список «Приглашения» в «Проектах»

```
Приглашения
  «Кофейни у дома» — приглашение стать оператором проекта
  Приглашает: Анна Смирнова · 18.11.2026
  Оператор правит страницу проекта, открывает её кругам и работает с материалами.
  Удалить или передать проект он не может.
                                         [Отклонить] [Принять]
```

### А4. Состояния и тексты

| Состояние                   | Владелец видит                                  | Получатель видит                                                                                                                    |
| --------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Ждёт ответа                 | «ждёт ответа» + «Отозвать приглашение»          | приглашение с «Принять» / «Отклонить»                                                                                               |
| Принято                     | «оператор» + «Снять назначение»                 | «Вы оператор проекта «…»» — проект в списке                                                                                         |
| Отклонено                   | «отклонил приглашение» (можно пригласить снова) | —                                                                                                                                   |
| Отозвано до ответа          | строка исчезает                                 | «Приглашение отозвано» при попытке ответить                                                                                         |
| Снято владельцем            | строка исчезает                                 | «Полномочия отозваны» на следующем действии; проект — по общим кругам                                                               |
| Отказался сам               | «отказался от назначения»                       | подтверждение: «Отказаться от назначения в «…»? Вы потеряете доступ к закрытым сведениям проекта» → «Вы больше не оператор проекта» |
| Владелец пробует отказаться | —                                               | кнопки нет; подсказка «Владелец не может отказаться. Передайте проект или удалите его»                                              |
| Сбой при ответе             | —                                               | «Не удалось сохранить ответ. Попробуйте ещё раз» — состояние не меняется                                                            |
