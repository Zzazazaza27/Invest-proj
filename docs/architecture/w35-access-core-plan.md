## 2. Участие отдельно от полномочий

**Сейчас.**

- `lab.founders_projects` с ролями `owner|cofounder` — одновременно и участие, и права.
- `lab.is_project_member` не различает владельца и сооснователя. Поэтому сооснователь может
  всё, что владелец:
  - править проект;
  - менять видимость и листинг;
  - загружать и удалять материалы, логотип и обложку;
  - выдавать и снимать персональный доступ;
  - видеть закрытые материалы и удалённые проекты.
- `project-media.service.ts:378` прямо разрешает `cofounder`.

Это противоречит П4.

**Станет.**

| Понятие               | Где хранится                                                   | Что даёт                                                                                |
| --------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Создатель             | `lab.projects.creator_id`, неизменяемо (триггер)               | ничего, кроме факта в истории                                                           |
| Владелец              | `lab.projects.owner_id`, ровно один                            | полномочия оператора + публикация, назначение операторов, удаление, передача            |
| Оператор бизнес-юнита | `access.unit_assignments`, состояние `active`                  | работа с проектом, кроме владельческих действий; входит в круг «Операторы бизнес-юнита» |
| Роль участия          | `lab.founders_projects` (не переименовываю — меньше переделки) | только факт; ни одна проверка доступа на неё не смотрит                                 |

Владелец всегда имеет активное назначение оператора, пока он владелец (инвариант в БД).
Передача (S11) в 3.1 не делается; модель её допускает.

`identity.users.primary_role` (`founder|investor`) на доступ к проектам перестаёт влиять.
`@Roles('founder')` на действиях с существующим проектом заменяется общей проверкой. Создание
проекта остаётся за прежним условием до пакета «регистрация и подключение кабинетов» (S01,
S06).

## 3. Общая проверка доступа

### 3.1 Две функции — два вопроса, полномочия — справочником

Доступ и полномочия — разные вопросы (_06 «Ссылки, показ и публикация»). Обе функции в БД, в
схеме `access`.

**`access.can_view(object_id, user_id) → boolean`**

- Объект существует, не удалён, не заблокирован.
- Среди кругов, которым открыт объект, есть круг, куда пользователь входит по действующему
  основанию.
- То же выполняется для родителя (П11).

**`access.can_act(unit_id, user_id, action) → boolean`** — по справочнику
`access.unit_actions` «действие → кто», а не по веткам в коде:

| Действие                                                | Кто                                 | Основание                                                                |
| ------------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------ |
| `edit` — содержимое, материалы, медиа                   | оператор (владелец — тоже оператор) | B1-S06, B1-S09                                                           |
| `publish` — открыть или закрыть страницу внешним кругам | **только владелец**                 | П10; сводная строка 32                                                   |
| `block_circles` — круги блоков                          | оператор                            | B1-S07; **реализация после B2-S26/S27**, в 3.1 только строка справочника |
| `material_circles` — круги материала                    | оператор                            | B1-S07 (то же, что у блока: оператор выбирает внешний круг)              |
| `manage_operators` — пригласить, отозвать, снять        | владелец                            | П5                                                                       |
| `delete`, `transfer`                                    | владелец                            | П2 (`transfer` — после S11)                                              |

**Публикация (`publish`).**

- Это открытие страницы любому кругу, кроме «Операторов бизнес-юнита»: «Опубликовать — открыть
  страницу кругу доступа» (_06).
- Проверка — функция `lab.teaser_complete(project)`, одна для всех путей.
- **Состав тизера ещё не определён** (11 MVP/04 «Тизер проекта — 06.11», B2-S28). Рабочее
  допущение до B2-S28: заполнены название и краткое описание (`title`, `tagline`). Когда
  состав согласуют, меняется только эта функция.
- Закрыть страницу (вернуть в черновик) — тоже `publish`. Снятие публикации по нарушениям —
  B1-S16, не здесь.
- Сейчас открытие требует KYC владельца и проходит проверки листинга. B1-S06 «без
  предварительной проверки 5Э» это снимает: для страницы проекта KYC больше не нужен. Листинг
  и его проверки — B1-S10, не трогаю.

**Принадлежность к кругу** решает одна функция `access.in_circle(circle, circle_owner, user)`.
Основание каждого круга — данные:

- «Все» — без основания;
- «Операторы бизнес-юнита» — активное назначение;
- «Интересанты» — `access.circle_members`. В MVP круг наполнится принятым откликом (B2-S30),
  сейчас он пуст.

Для «Посмотреть как…» — **`access.can_view_as(object_id, circles[])`**. Логика та же, но
принадлежность к кругам задана списком. Это убирает вторую копию правил на TypeScript
(`packages/contracts/src/domain/visibility.ts`, viewPreview).

### 3.2 Где применяется

| Путь обращения                                    | Сейчас                                                                 | Станет                                                        |
| ------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------- |
| Строки `lab.projects`, материалов, медиа (RLS)    | `is_project_member`, `project_audience`, `visible_to`                  | политики вызывают только `access.can_view` / `access.can_act` |
| API ядра: страница, правка, публикация, материалы | `assertCanChange`, `assertProjectVisible`, `assertCanEdit` по членству | один помощник ядра `AccessService.require(view                | act)` → функции БД; своих правил в ядре нет |
| Каталог, поиск по названию, избранное             | `v_public_catalog` через `can_view_project`                            | тот же каталог через `can_view` страницы                      |
| Файлы материалов (прокси ядра `/content`)         | RLS-строка, 404                                                        | `can_view` материала и страницы; при отказе — общий 404       |
| Медиа (логотип, обложка, публичный маршрут)       | RLS по тизеру                                                          | медиа — часть страницы: `can_view` страницы                   |
| Загрузка, финализация, удаление файлов            | членство, автор                                                        | `can_act(edit)`; отмена своей загрузки — по-прежнему автор    |
| «Посмотреть как…»                                 | TS-копия правил                                                        | `can_view_as`                                                 |
| Фоновые задачи, служебные выгрузки                | `app_integration`                                                      | без изменений: это не доступ пользователя; S21 — позже        |
| Лента, уведомления                                | нет                                                                    | обязаны ходить через `can_view`; сторож § 6 это ловит         |

**Прямые запросы.** Всё, что открывает данные проекта, закрыто RLS с этими функциями. Прямой
SQL от `app_backend` и новый маршрут без помощника получат пустой ответ, а не данные.

Попутно закрываются найденные обходы:

- `founders_insert WITH CHECK (true)` — любой сеанс мог вписать себя в проект;
- `GET …/materials/:id/content` без проверки маршрута;
- SECURITY DEFINER-счётчики материалов без проверки проекта.

### 3.3 Один ответ об отказе

Все отказы по объектам доступа — **404 «Страница недоступна»** с одинаковым телом. Сейчас
ответы различаются, и это меняется:

- `@Roles` отвечает 403 раньше поиска объекта;
- правка медиа отвечает администратору 403;
- viewPreview отвечает 403;
- ошибка политики БД `42501` превращается в `403 db-policy`;
- выдача доступа отвечает 422 «адрес не найден» — так раскрывается, есть ли адрес на
  платформе.

Два ответа остаются отдельными:

- **«Полномочия отозваны».** Тому, у кого было назначение на этот проект, а теперь его нет, —
  тот же 404 с признаком `revoked`. Признак получает только он сам.
- **Сбой проверки** — 503 «временно недоступно» (П16).

### 3.4 Служебный каталог — без общей ветки

Глобальной ветки служебного чтения в `can_view` нет. Администратор видит проекты через
`can_view` так же, как любой пользователь: черновики, материалы, файлы и удалённые проекты ему
закрыты до B1-S17. Пропадает и нынешняя возможность загружать в любой проект.

Действующему администрированию нужны два места. Оба переводятся на одну служебную функцию
`access.staff_project_directory(...)`:

- проверяет `app.has_role('admin')`;
- отдаёт **только** перечисленные поля;
- из `can_view` не вызывается и данных страниц не открывает.

| Маршрут                                              | Экран                              | Поля                                                                                  |
| ---------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------- |
| `GET /v1/admin/projects?q=` (`directory.service.ts`) | поиск проекта по названию          | `id`, `title`, `status`, `listing_status`; без удалённых; 25 строк                    |
| `GET /v1/admin/users/:id` (`users.service.ts:165`)   | карточка пользователя, его проекты | `id`, `title`, `listing_status` + роль участия; новое — признак «владелец / оператор» |

Это костыль по правилу 18.11:

- **Почему.** Служебные права (S17) не пройдены, а экраны уже есть.
- **Где.** Одна функция, два маршрута.
- **Когда уберём.** После S17 функция заменится служебным назначением.

## 4. Изменения схемы

Новые миграции после M181, только вперёд. Шаги и момент переключения — § 8.

**Схема `access`:**

- `circles` — код, тип хозяина, этап;
- `objects` — id, вид `project_page|material|history`, бизнес-юнит, родитель;
- `openings` — объект, круг, хозяин круга, кто и когда открыл;
- `unit_assignments` — бизнес-юнит, пользователь, состояние
  `invited|active|declined|cancelled|expired|withdrawn|revoked`, кто пригласил, метки
  времени; одно действующее на пару;
- `circle_members` — пусто;
- `unit_actions` — справочник действий.

**Функции:** `can_view`, `can_act`, `in_circle`, `can_view_as`, `staff_project_directory`,
`lab.teaser_complete`.

**Таблица `lab.projects`:** новые `creator_id`, `owner_id`, оба NOT NULL после переноса.

**Приглашение:**

- адрес не хранится отдельно — приглашение привязывается к аккаунту с подтверждённым адресом;
- уведомление — общий механизм `comms.notifications`, канал «в 5Э» и письмо (§ 9, вопрос 2).

**Журнал действий — новые глаголы:**

- `access.opening.changed` — прежние и новые круги (П14);
- `access.assignment.invited|accepted|declined|cancelled|expired|withdrawn|revoked`.

В событии записываются роль действующего (`owner|operator`) и основание. Сейчас владелец и
сооснователь оба пишутся как `founder`.

## 8. Переключение, откат и выпуск

### 8.1 Три шага

**Шаг 1. Расширение и перенос** (миграция, выпуск N, ядро прежнее).

- Создаются таблицы и функции `access`, переносятся данные.
- Триггеры поддерживают новые таблицы в соответствии со старыми, пока пишет прежнее ядро:
  - новый проект создаёт создателя, владельца, назначение и черновик;
  - смена `visibility` меняет открытия.
- **Действует старая политика.** Новые функции ничего не решают.
- Откат — просто прежнее ядро.

**Шаг 2. Переключение — одна миграция**, тот же выпуск N, перед стартом нового ядра.

Одной транзакцией:

- RLS-политики `lab.projects`, материалов, медиа, каталога, участия переводятся на
  `access.*`;
- старые функции `lab.is_project_member`, `lab.project_audience`, `lab.can_view_project`,
  `lab.visible_materials` переписываются тонкими обёртками над новыми:
  - `is_project_member` = активный оператор;
  - `project_audience` = результат `can_view`.

**С этого момента API (и старого, и нового ядра), прямое чтение и файлы применяют одну
политику.** Отдельного окна, где API уже на новом, а RLS ещё на старом, нет. Файлы и медиа
отдаёт ядро после чтения строки под RLS, поэтому переключаются тем же шагом.

**Шаг 3. Сжатие** — следующим выпуском, после приёмки на средах. Удаляются:

- триггеры совместимости;
- обёртки;
- запись в `visibility`.

Колонки и строки выдач остаются до отдельного решения.

### 8.2 Возврат старого ядра после шага 2

База назад не откатывается: миграции только вперёд. Старое ядро работает на переключённой базе.

**Что работает:**

- Права, изменённые после переключения, **сохраняются и действуют**: они в `access.*`, а RLS
  и обёртки читают оттуда:
  - принятые назначения;
  - снятые операторы;
  - открытия страниц.
- Снятый оператор остаётся снятым.
- Новый оператор в старом ядре правит через `assertCanChange`: обёртка
  `is_project_member` видит его как оператора.

**Что старое ядро делает хуже, но не шире:**

- Медиа: `project-media.service.ts` смотрит на `founders_projects` напрямую. Новый оператор
  получит отказ (раньше 403), сооснователь упрётся в RLS. Шире не становится.
- Публикация: прежняя кнопка режимов пишет `visibility`, триггер переводит запись в
  открытия:
  - `public` → «Все» только при `can_act(publish)` и заполненном тизере, иначе отказ;
  - `selected_investors` → отказ.
- Выдачи и исключения: таблицы закрыты на запись — отказ с понятной ошибкой.
- Приглашений в старом интерфейсе нет. Принятые остаются, неотвеченные ждут.

**Чего нельзя:** вернуть старую политику в БД. Права, выданные после переключения, в старой
модели не выражаются: оператор без строки участия пропал бы. Если это понадобится — только
отдельной миграцией вперёд по решению Томаса.

### 8.3 Приёмка обоих переходов

На локальном стенде на данных прогонов, затем на test-1.

1. **Переключение под старым ядром.** Старое ядро работает → шаг 2 → таблица случаев по SQL и
   по маршрутам старого ядра.
   - Ожидание — новая политика.
   - Расхождения только в перечне § 8.2, и все они в сторону отказа.
   - Разница доступа совпадает с § 5.2: 11 выдач теряют просмотр, остальное без изменений.
2. **Возврат старого ядра после изменений прав.** Новое ядро:
   - пригласить и принять оператора;
   - снять другого оператора;
   - открыть страницу «Все»;
   - вернуть страницу в черновик.

   Затем вернуть старое ядро и прогнать таблицу случаев. Ожидание:
   - принятый работает;
   - снятый не работает;
   - открытия те же;
   - запрещённые старым ядром записи отказаны, а не применены.

3. Prod и test-2: проверка пустоты (§ 5.2) → выпуск по цепочке локал → test-1 → test-2 → prod
   (prod — отдельным решением).
4. Учёт: строка 2.1-W35 во «Временном учёте» карточки релиза 2.1 — до первого коммита кода.

## 9. Вопросы к Томасу

1. **Снятие действующих прав по описи.** На prod и test-2 ожидаются нули. Тогда решать нечего,
   при отклонении — остановка. Для будущих сред и как правило:
   - выдачи на `selected_investors` — просмотр снимается, строки сохраняются;
   - сооснователи — только факт участия, без автоматического назначения;
   - исключения на открытых страницах перестают действовать.

   _Блокирует перенос; при нулях на prod и test-2 — не блокирует._

2. **Приглашение оператора.**
   - Только пользователю с подтверждённым адресом; ответ одинаковый для любого адреса.
   - Получатель узнаёт тремя способами:
     - письмо на подтверждённый адрес — по слову Томаса 18.11, строку в F-001 добавляет Тэнк;
     - всплывающее окно справа внизу, если он на сайте;
     - строка в «Приглашения», которая остаётся, пока не отвечено.
   - Всплывающее окно — по опросу списка уведомлений при открытой странице: постоянного
     канала с сервера сейчас нет, задержка до минуты. Мгновенная доставка — отдельная работа.
   - **Срок ожидания:** предлагаю 14 дней, затем «истекло», владелец может пригласить снова.
     До будущей регистрации приглашение не ждёт: на неподтверждённый или несуществующий
     адрес оно не создаётся.

   _Блокирует экраны, не серверную основу._

3. **Служебный каталог** (§ 3.4): два маршрута с перечисленными полями до B1-S17.
   Администратор теряет просмотр черновиков, материалов, файлов и удалённых проектов. _Блокирует._
4. **Тизер до B2-S28:** рабочее допущение «название и краткое описание». _Не блокирует:
   меняется одна функция._
