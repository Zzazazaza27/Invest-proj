## 1. Коротко

1. Сумма запроса живёт в **четырёх** представлениях: колонка заявки,
   колонка проекта (кеш), `snapshot_jsonb.core.investmentAsk` и вопрос
   `investment_ask` в конфигурации формы; все четыре завязаны на
   `FORM_CORE_FIELDS` (`packages/contracts/src/domain/application-form.ts:112-140`).
   Раунд как отдельная сущность требует одного владельца пересчёта —
   сегодня им является `recomputeProjectProjection`
   (`apps/core/src/lab/applications.service.ts:845-875`), но мимо него сумму
   пишут ещё три пути (§2.3).
2. Видимость проекта сегодня — **один булев признак** `listing_status =
'listed'`, повторённый в шести местах (вью, RLS публичной роли, ветка
   инвестора в `projects_select`, RLS паспорта, оценок, материалов) и в
   горячем SQL каталога (§3.1). Единый предикат нужен раньше режимов, иначе
   режимы разъедутся так же.
3. **Инвесторской проекции нет.** `GET /v1/projects/:id` отдаёт инвестору
   полную строку проекта; единственная серверная проекция —
   `buildApplicationPreview`, недоступная инвестору по RLS (§3.2).
4. Роль `investor` **самоназначается при регистрации** без проверки
   (`apps/core/src/identity/identity.service.ts:157-195`); подтверждение
   личности (`kyc.has_valid_kyc(user,'identity')`) и квалификация
   (`kyc_verifications.kind='accredited'`) в схеме есть, второе нигде не
   читается (§4).
5. Подписка инвестора (`investor_membership`, 100 000 ₽) **до сих пор
   запирает** материалы и скоринг на уровне RLS, а активировать её нельзя
   (платежи выключены). Это противоречит решению владельца от 2026-09-14
   «инвестору лимита нет» и новому «базовый Investor View бесплатно» (§5.4).
6. Акционные тарифы 0 ₽ (план 0.2 §2.9.7, «коммит 2.7») **не реализованы**:
   коммит `94946f5` менял только документ. Отменяются без отката кода (§5.2).
7. Прямого доступа к файлам мимо API **нет**: presigned-ссылок на чтение не
   существует, MinIO слушает только loopback, анонимный доступ к бакету
   выключен. Но доступ инвестора к материалам грубый («подписка + листинг =
   все материалы всех проектов»), а `evidence` не проверяется на
   принадлежность проекту (§6).
8. Для хроники есть outbox с relay внутри ядра и очередь уведомлений, но
   **воркера доставки уведомлений нет**: строки `comms.notifications`
   остаются `queued`, письма идут мимо очереди (§7).
9. Легаси, которое пора убирать, распадается на четыре группы: безопасно
   сейчас; после этапа 4.5/8; противоречит курсу и требует решения
   владельца; устаревшая документация (§8).
10. Вехи 5.6 и 5.7 можно сделать expand-only без переписывания M071–M080
    и без потери старых снимков (§9).

**Предложение по форме (главный файл §5 п.2).** Вопросы раунда остаются в
версионируемой конфигурации, чтобы администратор правил их тексты и
состояния той же таблицей, но раздел получает системный признак
`scope: 'round'` (новое поле раздела в документе конфигурации; для старых
версий отсутствие = `'profile'`). Мастер показывает такой раздел только
при открытом или создаваемом раунде; ответы раздела пишутся в раунд, а не
в `answers_jsonb` заявки. Это системная зависимость кодом, не редактор
условий (главный файл §5 п.5). Альтернатива — вынести поля раунда из
конфигурации в системный блок с текстами в `content.texts` — теряет
админскую матрицу стадий для этих вопросов; не рекомендую.

### 2.5. Модель раунда — предложение (expand-only, M081+)

`lab.funding_rounds`: `id`, `project_id`, `application_version_id NULL FK
lab.project_versions` (поданная версия профиля, на которой открыт раунд;
NULL допустим только в `draft`), `status CHECK IN ('draft','open','paused',
'closed','cancelled')`, `funding_scope`, `funding_scope_note`,
`target NUMERIC(14,2)`, `currency CHAR(3)`, `investor_mode CHECK IN
('single','multiple','either')`, `ticket_min`, `ticket_max`, `committed
NUMERIC(14,2) DEFAULT 0` (со слов основателя; источник статуса — колонка
`committed_source CHECK IN ('self_reported')` с заделом под будущие
значения), `answers_jsonb` (ответы вопросов раунда по ключам конфигурации:
`round_type`, `ask_rationale`, `use_of_funds`, …), `schema_version`,
`max_published_target` (для учёта лимита, см. §5.3), `created_by`,
`created_at`, `opened_at`, `paused_at`, `closed_at`, `cancelled_at`,
`close_reason`. CHECK: `status='open' → target > 0 AND funding_scope IS
NOT NULL AND application_version_id IS NOT NULL`. Частичный уникальный
индекс `WHERE status = 'open'` по `project_id` — «не более одного открытого
раунда на проект» (главный файл §3.2; подтверждается). RLS: как у заявок
(члены проекта, admin, organizer) + чтение инвестором через предикат §3.4.

Связь с версией: **предложение** — смена связанной версии у открытого
раунда запрещена; чтобы взять новую версию, раунд ставится на паузу и
переоткрывается новой записью с `superseded_by`/`supersedes` (аудит явный,
история цельная). Простой альтернативный вариант «UPDATE
application_version_id с глаголом аудита» — дешевле, но история изменения
основания живёт только в журнале. Решение — §10 п.4.

Аудит: глаголы `lab.funding_round.{created,updated,opened,paused,resumed,
closed,cancelled}`, регистрация миграцией (реестр fail-closed,
`M001_audit_core.sql:10-22`). `opened/closed/cancelled` — через
`audit.record` в outbox (хроника U3 позже подпишется на них).

**Совместимость (кеш).** `investment_applications.investment_ask` и
`funding_scope` остаются колонками до вывода кабинета v1 и Integration
API, но получают одного владельца: пересчёт из открытого раунда в той же
функции `recomputeProjectProjection`; прямые записи из мастера v2
прекращаются. `lab.projects.investment_ask` (NOT NULL) при отсутствии
раунда сохраняет последнее значение (как сегодня при отсутствии открытых
заявок) и **не показывается** пользователю как запрос: каталог и Investor
View берут сумму только из открытого раунда, иначе «Сейчас не привлекает
инвестиции» (главный файл §6.2). CHECK `applications_submitted_has_ask` и
`…_has_scope` (M071/M078) снимаются миграцией (`DROP CONSTRAINT` — это
contract-операция для линтера, помечается `-- migrate:contract`; данные не
теряются).

## 3. Видимость и доступ

### 3.1. Сегодня — один булев признак в шести местах

Эффективная видимость = `listing_status='listed' AND deleted_at IS NULL`:

- вью `lab.v_public_catalog` (`M004_lab.sql:83-87`, единственное определение,
  `security_invoker`), колонки-allowlist `id, taxonomy_id, title, tagline,
stage, geo_country, investment_ask, ask_currency, listed_at`;
- RLS публичной роли `projects_public_teaser` (`M004:255-256`);
- ветка инвестора в `projects_select` (`M004:240-245`) + `has_active_investor_membership`;
- RLS паспорта `passports_read` (`M006_scoring.sql:177-183`), оценок
  (`M006:205-207`), IRS (`M006:213+`);
- RLS материалов `materials_select_investor` (`M065:25-31`), парсов (`M065:33-40`);
- горячий SQL каталога (`catalog.service.ts:73`); избранное
  (`favorites.service.ts:143-151`).

Вторая публичная проекция, которая **не согласована с первой**: рейтинг
сезона `GET /v1/seasons/:id/rating` (`seasons.controller.ts:44-56`) строится
на `mv_season_rating` (`M007_experts_seasons.sql:158-171`) по `projects.status`
и отдаёт `title` + IRS **без проверки `listing_status`** — утечка названия
и оценки неопубликованного проекта. Из UI маршрут не вызывается (§8).

### 3.2. Инвесторской проекции нет

`GET /v1/projects/:id` (`projects.controller.ts:47-51`) отдаёт полную
строку `PROJECT_COLUMNS` (`projects.service.ts:978-988`: description,
status, listing_status, required_plan_id, season_id, current_version_id,
current_application_id, irs) любому, кого пропустит RLS. Материалы —
полный список, паспорт — целиком. Инвесторский кабинет
(`apps/investor/src/pages/ProjectDetailsPage.tsx:119-151`) делает три
вызова и сам решает, что показать.

Единственная серверная проекция — `buildApplicationPreview`
(`packages/contracts/src/domain/application-views.ts:144-201`): применяет
`hidden`, условие `funding_scope_note`, пропускает пустое, `platform`/`private`
→ `withheld`. **`public` и `investors` сегодня неразличимы** — аудитория
жёстко `'investors'` (`:195`). Маршрут `GET /applications/:id/preview`
(`applications.controller.ts:66-77`) доступен только по RLS
`applications_select` (`M071:243-246`) — основателю, admin, organizer,
рецензенту; инвестор его вызвать не может.

Политика видимости у вопроса уже есть: `FormVisibilitySchema =
public | investors | platform | private` (`application-form.ts:49-50`),
хранится в `config_jsonb` версии. В v1 все пять системных вопросов —
`public` (`:600-643`); фактические значения по 91 вопросу: `public` у
`funding_scope`, `funding_scope_note`, `investment_ask`, `round_type`;
`investors` у остальных вопросов раунда. Полную сверку по всем разделам
нужно сделать в 5.7 (главный файл §7.2) — проверяемый критерий: новый
вопрос без явной политики получает `investors`, не `public`
(сегодня схема требует поле, умолчания нет — это правильно).

### 3.4. Минимальная модель — предложение

1. `lab.projects.visibility TEXT NOT NULL DEFAULT 'private' CHECK IN
('private','public','registered_investors','selected_investors')`
   (expand; существующие `listed` проекты переводятся в `public` одной
   миграцией данных — это единственное место, где старое «опубликован»
   трактуется как явное решение владельца проекта; предлагаю так, потому
   что листинг сегодня нажимался вручную после KYC). `listing_status`
   остаётся как совместимый признак «профиль показан» (см. §3.5) до
   вывода v1.
2. `lab.project_access_grants (id, project_id, grantee_user_id NULL,
grantee_entity_id NULL, level CHECK IN ('investor','extended'),
granted_by, granted_at, revoked_at, reason)` — задел под
   `selected_investors` и Extended Access; в 5.7 создаётся, UI — 5.8.
3. `lab.project_access_exclusions (project_id, excluded_user_id NULL,
excluded_entity_id NULL, created_by, created_at, revoked_at)` — запрет
   имеет приоритет над разрешением.
4. Один предикат в БД `lab.can_view_project(p_project UUID, p_user UUID,
p_level TEXT) RETURNS BOOLEAN` (STABLE, `SET search_path`), учитывающий по
   порядку: член проекта/admin/organizer → true; исключение → false;
   режим `private` → false; уровень `public` → режим `public`; уровень
   `investor` → роль investor и (`public` или `registered_investors`) или
   действующий grant при `selected_investors`; уровень `extended` → grant
   `extended` и подтверждённая личность (`kyc.has_valid_kyc(user,'identity')`).
   Все шесть мест из §3.1 переводятся на вызов предиката (RLS проекта,
   паспорта, оценок, материалов; вью каталога получает `WHERE
lab.can_view_project(id, NULL, 'public')`, что при `security_invoker`
   и публичной роли эквивалентно `visibility='public'`). Подписка инвестора
   из предиката **исключается** (§5.4, решение владельца).
5. Проекции на сервере: `application-views.ts` получает параметр
   `audience: 'public' | 'investor'`; Public View = поля проекта из
   allowlist каталога + ответы снимка с `visibility='public'` + статус
   привлечения; Investor View = `+ investors` + разрешённая проекция
   открытого раунда (`target, currency, committed, remaining, ticket range,
status`). Маршруты: `GET /v1/catalog/:id` отдаёт Public View (сегодня —
   тизер), новый `GET /v1/projects/:id/investor-view` (или замена тела
   `GET /v1/projects/:id` для роли investor — решение §10 п.7),
   `GET /applications/:id/preview?audience=public|investor` для владельца.
   Один модуль — один результат: предпросмотр обязан вызывать ту же функцию.
6. `selected_investors` **не показывается в UI**, пока нет способа выдать
   grant (главный файл §7.5) — режим в CHECK есть, переключатель в
   кабинете отсутствует до 5.8.

### 5.3. Новое правило — предложение

Новая версионируемая политика раундов (расширение `ApplicationPolicySchema`
или отдельная `lab.round_policies` — предпочитаю **отдельную** таблицу того
же образца, чтобы политика заявок осталась про число заявок):

```json
{
  "freeCumulativeTarget": "5000000.00",
  "paidBarrierEnabled": false,
  "maxOpenRoundsPerProject": 1,
  "maxPublishedRoundsFree": null,
  "maxProjectsPerAccount": null,
  "cancelledRoundsCount": "admin_decision",
  "baseCurrency": "RUB",
  "fxRule": "rub_only"
}
```

Формула: `used(project) = Σ max_published_target` по раундам проекта со
статусом когда-либо `open` (в том числе `paused`, `closed`), кроме тех, что
исключены административным решением с аудитом; черновики не считаются;
уменьшение `target` после публикации `max_published_target` не уменьшает;
удаления нет по конструкции (нет DELETE). Платная зона: `used + new_target
≥ freeCumulativeTarget` (ровно 5 млн — платно). При `paidBarrierEnabled =
false` правило только считается и показывается; при `true` открытие или
увеличение раунда требует активной подписки владельца на тариф, который
покрывает `used + new_target`.

**Единица счёта — проект**, не заявка и не версия (§10 п.2): у проекта до
трёх заявок по политике; счёт по заявке дал бы новый бесплатный лимит на
каждую.

Ступени `t1…t5` не совпадают с порогом 5 млн: t1 покрывает до 1 млн, t2 —
до 10 млн. **Предложение:** резолвер для платной зоны берёт ступень по
`used + new_target` (первая покрывающая), тарифная сетка при этом не
меняется миграцией; переоценка ступеней — продуктовое решение владельца,
делается в админке версиями тарифов. `resolve_founder_plan` остаётся (её
вызывают 16 мест), но перестаёт быть условием чего-либо в v2.

Валюта: `rub_only` — раунды только в RUB до поддержки пересчёта (сегодня
`CHECK (ask_currency='RUB')` в пяти таблицах, 0.1 §5).

### 5.4. Подписка инвестора — противоречие, решение владельца

RLS `projects_select` (`M004:242-245`), паспорта/оценок (`M006:177-183,
205-207, 213+`), материалов (`M065:25-40`) требуют
`has_active_investor_membership`. Решение 2026-09-14 «инвестору лимита нет»
(план 0.2 §0а п.1) трактовало подписку как «даёт доступ либо нет»; главный
файл §7.1 требует базовый Investor View **бесплатно**. Активировать
подписку сегодня нельзя (платежи выключены), то есть в продукте ни один
инвестор не видит ни карточки, ни материалов, ни паспорта — только тизер.
**Предложение:** в 5.7 предикат §3.4 не учитывает подписку; RLS
переписываются на предикат; `investor_membership` и `has_active_investor_membership`
остаются в схеме как инфраструктура для будущих платных возможностей
(главный файл §7.1), но нигде не гейтят. Это правится только миграцией.

## 10. Спорные решения — нужны от владельца

1. **Потолок 5 млн против порога 5 млн.** Политика заявок v1 ограничивает
   сумму заявки 5 млн (`M071:171-176`); новое правило делает 5 млн порогом
   платной зоны. Предложение: `maxAskPerApplication` в политике раундов
   становится `maxTargetPerRound = null` (без потолка), лимит выражается
   `freeCumulativeTarget`.
2. **Единица совокупного лимита — проект**, не заявка (§5.3).
3. **`registered` или `verified` для базового Investor View.** Главный файл
   — `registered`; спецификация видимости — `verified`. Предложение:
   `registered` (иначе Investor View не увидит никто: KYC инвестора сегодня
   никто не проходит).
4. **Смена версии профиля у открытого раунда**: запрет + переоткрытие (§2.5)
   или UPDATE с аудитом.
5. **Перевод существующих `listed` проектов в `public`** одной миграцией —
   или все в `private` с ручным включением (пустой каталог на стенде).
6. **Вопросы раунда остаются в конфигурации формы** с признаком раздела
   `scope: 'round'` (§2.4) — или выносятся в системный блок.
7. **Investor View — новый маршрут** или подмена тела `GET /projects/:id`
   для инвестора (совместимость кабинета инвестора против чистоты API).
8. **Судьба контуров группы В**: сезоны и золотые билеты, экспертиза,
   Integration API/Capital, медиаконтур и согласия, Keycloak/OIDC. Без
   решения они остаются как есть и не мешают 5.6–5.7, но каждый удерживает
   код и тесты.
9. **Материалы с уровнем видимости** в 5.7 (умолчание `investor`) — или
   отложить до Extended Access.
10. **Порядок U1 (хроника) относительно этапа 6** — после проверки
    владельцем.
