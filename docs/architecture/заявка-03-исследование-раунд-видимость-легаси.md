7. Публичный рейтинг сезона отдаёт названия и IRS неопубликованных проектов

### 2.5. Модель раунда — предложение (expand-only, M081+)

`lab.funding_rounds`:

- `id`, `project_id NOT NULL FK lab.projects`;
- `application_version_id UUID NULL`, **составной FK**
  `(project_id, application_version_id) REFERENCES lab.project_versions (project_id, id)`
  — версия обязана принадлежать тому же проекту (замечание §2 ответа);
- `schema_version INTEGER NOT NULL` — версия конфигурации формы, по которой
  заполнялись вопросы раунда; **независима** от `application_version_id`:
  публикация новой конфигурации открытый раунд не меняет, раунд читает
  форму своей версии (как заявка, `applications.service.ts:918-939`);
- `status CHECK IN ('draft','open','paused','closed','cancelled')`;
- `funding_scope`, `funding_scope_note`, `target NUMERIC(14,2)`, `currency CHAR(3)`;
- `investor_mode CHECK IN ('single','multiple','either')`, `ticket_min`, `ticket_max`;
- `committed NUMERIC(14,2) NOT NULL DEFAULT 0`, `committed_source CHECK IN
('self_reported')` (задел под будущие источники; предварительный интерес
  инвесторов в эту колонку не попадает);
- `answers_jsonb` (ответы вопросов раунда по ключам конфигурации),
  `evidence_jsonb`;
- `accounted_target NUMERIC(14,2) NOT NULL DEFAULT 0` — учтённый вклад в
  совокупный лимит (исторический максимум опубликованного `target`, §5.4);
- `accounting_excluded_at`, `accounting_excluded_by`, `accounting_excluded_reason`
  — административное исключение из учёта с аудитом;
- `market_code` — рынок, зафиксированный при открытии (копия
  `projects.market_code`, §5.3);
- `created_by`, `created_at`, `opened_at`, `paused_at`, `closed_at`,
  `cancelled_at`, `close_reason CHECK IN ('completed','partially_funded',
'not_funded','withdrawn') NULL`; «закрыт» ≠ «деньги получены» — результат
  описывается `close_reason`, подтверждённого поступления средств в 5.6 нет.

CHECK: `status IN ('open','paused') → target > 0 AND funding_scope IS NOT
NULL AND application_version_id IS NOT NULL AND currency IS NOT NULL`.
**Одна незавершённая кампания на проект**: частичный уникальный индекс по
`project_id WHERE status IN ('open','paused')` (замечание §2: пауза не
освобождает место). Черновиков раунда — не более одного на проект (ещё
один частичный индекс `WHERE status='draft'`), чтобы «Открыть раунд»
всегда продолжал начатое.

Переходы: `draft→open`, `open→paused`, `paused→open`, `open|paused→closed`,
`draft|open|paused→cancelled`; `closed` и `cancelled` терминальны. Повтор
запроса «открыть» на уже открытом раунде идемпотентен (без расхода лимита).

**Смена основания (версии профиля) — тем же раундом.** Таблица
`lab.funding_round_basis_history (id, round_id, from_version_id NULL,
to_version_id, changed_by, changed_at, reason)`; действие `PUT
/rounds/:id/basis {applicationVersionId, reason}` допустимо в `draft`,
`open`, `paused`; пишет историю и меняет FK; учёт лимита и `target` не
трогаются; если владелец хочет паузу на время правки — возобновляется тот
же раунд. Новая запись раунда создаётся только когда основатель начинает
другой сбор. Вариант «пауза → новая запись с `supersedes`» из редакции 1
**снят** (двойной учёт, ломаная история).

Принадлежность: `evidence_jsonb` раунда и заявки проверяется по
`project_materials.project_id` при сохранении (сегодня не проверяется —
`applications.service.ts:210-213`; исправление 5.6.0); у grant и exclusion
ровно один получатель (CHECK `num_nonnulls(user_id, entity_id) = 1`).

Аудит: глаголы `lab.funding_round.{created,updated,opened,paused,resumed,
closed,cancelled,basis_changed,accounting_excluded}` регистрируются
миграцией (реестр fail-closed, `M001_audit_core.sql:10-22`);
`opened/paused/resumed/closed/cancelled` — через `audit.record` в outbox с
`nextAggregateVersion` (хроника U3 подпишется позже).

**Совместимость (кеш, один владелец).** `investment_applications.investment_ask`
и `funding_scope` остаются колонками; `lab.projects.investment_ask`
(NOT NULL) остаётся. Их единственный писатель в v2 —
`recomputeProjectProjection`, который берёт значения из **открытого или
приостановленного** раунда проекта; при отсутствии раунда колонки проекта
сохраняют последнее значение и **не показываются как запрос** (каталог,
Investor View, Integration API — §2.7). CHECK
`applications_submitted_has_ask` и `…_has_scope` снимаются миграцией с
пометкой `-- migrate:contract` (данные не теряются).

### 2.6. Готовность — два независимых показателя в обоих сценариях

- **Полнота профиля** считается всегда и только по вопросам разделов
  `scope='profile'`; раздел раунда в проценте профиля **не участвует ни
  при каких условиях** (снято двойное толкование редакции 1). В
  `computeCompleteness` (`application-readiness.ts:146-226`) применимое
  множество фильтруется по `scope`; для схем без признака раздел с ключом
  `funding` считается раундом (совместимость v1, §2.7).
- **Готовность раунда** — отдельный объект в ответе раунда:
  `{ canOpen, missing: [...], percent }` по вопросам раздела раунда для
  стадии заявки-основания; `canOpen` требует `target`, `funding_scope`
  (и заметку при `direction`), обязательные вопросы раунда, версию-основание.
- Подача профиля: `checkSubmission` перестаёт требовать сумму и предмет
  финансирования; `CORE_KEYS` (`applications.service.ts:904-910`) сокращаются
  до `stage`, `business_type`.
- Investment Score, уровень проверки и состояние раунда остаются отдельными
  показателями; в одно число не сводятся.

### 3.4. Минимальная модель — предложение

1. `lab.projects.visibility TEXT NOT NULL DEFAULT 'private' CHECK IN
('private','public','registered_investors','selected_investors')`.
   Миграция данных: `listed` → `public` **только в смысле тизера** (§3.5):
   ответы анкеты не раскрываются, пока владелец проекта не подтвердит
   Public View предпросмотром. `blocked_at`, `blocked_reason` —
   административная блокировка (нет сегодня; комплаенс блокирует только
   листинг через паспорт, `projects.service.ts:807-821`).
2. `lab.project_access_grants (id, project_id, grantee_user_id NULL,
grantee_entity_id NULL, level CHECK IN ('investor','extended'),
granted_by, granted_at, revoked_at, reason)`, CHECK
   `num_nonnulls(grantee_user_id, grantee_entity_id) = 1`.
3. `lab.project_access_exclusions (id, project_id, excluded_user_id NULL,
excluded_entity_id NULL, created_by, created_at, revoked_at)`, тот же
   CHECK; запрет имеет приоритет.
4. `lab.can_view_project(p_project UUID, p_user UUID, p_level TEXT)`
   (STABLE, `SET search_path`, `p_level ∈ public|investor|extended`), по
   порядку:
   1. проект `deleted_at IS NOT NULL` или `blocked_at IS NOT NULL` → внешним
      `false` (команда и admin видят; §4 ответа);
   2. член команды или `admin` → `true`; назначенный рецензент → `true`
      для `investor`;
   3. действующее исключение для пользователя или его организации → `false`;
   4. `visibility='private'` → `false`;
   5. `p_level='public'` → `visibility='public'`;
   6. `p_level='investor'` → `app.has_role('investor')` **явно** и
      (`visibility IN ('public','registered_investors')` или действующий
      grant `investor|extended` при `selected_investors`);
   7. `p_level='extended'` → п.6 и `kyc.has_valid_kyc(p_user,'identity')` и
      действующий grant `extended`.
      Подписка инвестора в предикате не участвует (согласовано). Шесть мест
      §3.1 переводятся на предикат; вью каталога — `WHERE
lab.can_view_project(id, NULL, 'public')`.
5. Исключения надёжны только в закрытых режимах: в `public` человек выйдет
   из аккаунта и увидит Public View. В матрице и в интерфейсе это сказано
   явно («скрыть от конкретного пользователя» действует для входа под его
   учётной записью; для надёжного ограничения — закрытый режим).
6. `selected_investors` не показывается в UI, пока нет способа выдать
   grant (5.8).

Три понятия разделяются и хранятся отдельно:

| Понятие            | Где                                                 | На что влияет                                            |
| ------------------ | --------------------------------------------------- | -------------------------------------------------------- |
| Язык интерфейса    | `identity.users.locale`, `content.languages`        | переводы, формат чисел и дат, подписи                    |
| Рынок обслуживания | `lab.projects.market_code` → `lab.markets`          | применимая версия политики, разрешённые валюты, тарифы   |
| Валюта раунда      | `funding_rounds.currency` ⊂ разрешённых валют рынка | денежная единица; учёт ведётся в базовой валюте политики |

Смена языка не меняет рынок; смена валюты не обнуляет учёт и не назначает
порог; IP, язык браузера и символ валюты рынок не определяют.

**Таблицы (M081, expand):**

- `lab.markets (code TEXT PK, is_active BOOLEAN, sort_order INT, created_at)`
  — сид: `ru` активен. Названия, описания и подсказки — в `content.text_entries`
  с новым `namespace='market'` (расширение CHECK M079 — expand: `ALTER …
DROP CONSTRAINT … ADD CONSTRAINT` с прежними и новым значением), поля
  `name`, `description_md`, `hint_md`; правятся на экране «Словарь и ЧАВО»
  той же механикой версий.
- `lab.market_policies (id, market_code FK, version INT, config_jsonb,
is_active, valid_from, created_by, created_at, reason)`, один активный на
  рынок (частичный UNIQUE), история версий. `config_jsonb`
  (`MarketPolicySchema`, числа — строки с фиксированной точностью, коды
  валют ISO 4217):

```json
{
  "baseCurrency": "RUB",
  "allowedRoundCurrencies": ["RUB"],
  "freeCumulativeTarget": "5000000.00",
  "paidBarrierEnabled": true,
  "limits": {
    "maxApplicationsPerProject": 3,
    "maxUnfinishedRoundsPerProject": 1,
    "maxPublishedRoundsFree": null,
    "maxTargetPerRound": null
  },
  "paidPlans": [{ "code": "founder_t2", "minVersion": 1 }],
  "cancelledRounds": "admin_decision",
  "fx": { "mode": "none" }
}
```

Значения в примере — фикстура стартового российского рынка, **не правило в
коде**: сид версии 1 берёт их из миграции данных, дальше — админка.
Пороги других рынков задаёт владелец; пересчётом из RUB они не
выводятся. `null` у любого лимита = ограничение выключено.

- **Глобальные ограничения аккаунта** (`maxProjectsPerAccount`,
  `maxApplicationsPerAccount`) живут **не в рынке**, а в существующей
  политике заявок `lab.application_policies` (`M071:151-167`), чтобы
  переключение рынка их не обходило; `maxApplicationsPerProject` из неё
  переезжает в рынок (или остаётся глобальным — решение §11 п.5).
- `lab.projects.market_code TEXT NULL FK lab.markets` и
  `lab.projects.market_policy_version INT NULL` (версия, применённая к
  последнему учтённому действию, для показа «ваши условия»).

**Первоначальный выбор рынка — предложение минимального правила.** При
создании проекта: если активный рынок ровно один — проставляется он; если
несколько — обязательный выбор в форме создания проекта с описанием
условий из `content.texts`; из гражданства, IP и языка не выводится.
Существующие проекты миграцией получают `ru`.

**Смена рынка после первой публикации раунда** — контролируемый перенос:
действие `PUT /projects/:id/market {marketCode, reason}` под advisory-локом
проекта; `accounted_target` раундов **сохраняется в базовой валюте
прежнего рынка вместе с кодом валюты** (`accounted_currency`), новый
порог сравнивается только с учётом в той же валюте; при несовпадении
валют перенос **недоступен** до появления `fx.mode` с зафиксированным
источником курса и датой (пересчёт истории плавающим курсом запрещён).
История переносов — `lab.project_market_history`.

**Публикация новой версии политики** показывает администратору, кого
затронет: число проектов рынка, число незавершённых раундов, число
проектов, у которых `used ≥ новый порог` (они не получают долга задним
числом: исторические публикации не переписываются; для следующего
действия применяется версия момента, и мастер показывает новые условия
до подтверждения).

**Тексты и числа.** Интерфейс подставляет значения в переводимые шаблоны
(`S.limits.free('{amount}')`, `content.texts` для админских подсказок);
строк «5 млн» в коде нет; форматирование — `formatMoney(amount, currency,
locale)` из `@unicorn/ui`; расчёт — в минорных единицах (`BigInt`) как
сегодня в `checkSubmission` (`applications.service.ts:776-779, 834-836`).

**Первый выпуск**: один рынок `ru`, только RUB, `fx.mode='none'`; экран
«Рынки и условия» в админке рядом с «Настройки заявки» (§10.2); добавление
рынка — строка и версия политики, без изменения схемы.

### 5.4. Формула лимита, атомарность, сценарии

Определения (все — в базовой валюте политики рынка проекта):

- `used(project)` = Σ `accounted_target` по раундам проекта, кроме
  исключённых административно (`accounting_excluded_at IS NULL`);
- `old_accounted` = текущий `accounted_target` изменяемого раунда (0 для
  нового);
- `new_accounted` = `max(old_accounted, new_target)` — исторический максимум
  опубликованного `target`; черновики (`status='draft'`) не учитываются
  до первой публикации;
- `projected_used = used − old_accounted + new_accounted`.

Тариф требуется перед действием (открытие раунда, увеличение `target`
незавершённого раунда), если `policy.paidBarrierEnabled` и
`projected_used ≥ policy.freeCumulativeTarget`. При требовании тарифа
проверяется активная подписка владельца проекта на план из
`policy.paidPlans`, покрывающий `projected_used` (резолв по `ask_limit`
действующей версии плана; `resolve_founder_plan` для этого **не**
используется, чтобы не смешивать со старым триггером).

Атомарность: проверка, изменение раунда и запись нового `accounted_target`
— в одной транзакции под `pg_advisory_xact_lock('project-write:<id>')`
(как создание заявки, `applications.service.ts:93`); повторный запрос с тем
же `Idempotency-Key` не создаёт расхода (ключи идемпотентности уже есть у
POST-маршрутов ядра).

Подписка истекла или отменена: чтение истории, черновики, пауза,
возобновление без изменения суммы, закрытие и отмена раунда **не
блокируются**; блокируются только открытие нового и увеличение `target`.
**Отдельное продуктовое предложение** (не наследуется от старого
триггера): уже открытый платный раунд при истечении подписки остаётся
открытым и видимым до закрытия основателем; в Investor View помечается
без изменений; владелец платформы может отдельной настройкой политики
`onSubscriptionLapse: 'keep_open' | 'pause'` выбрать автопаузу.

Сценарии-тесты (порог — фикстура политики, не реализация; две тестовые
политики: A — `RUB`, порог `5000000.00`; B — `USD`, порог `250000.00`,
обе помечены в фикстурах как «не коммерческие условия»):

| #   | Действие                                                       | Ожидание                                                              |
| --- | -------------------------------------------------------------- | --------------------------------------------------------------------- |
| 1   | открыть первый раунд 3 млн                                     | `used = 3 млн`, тариф не нужен                                        |
| 2   | увеличить тот же раунд до 4 млн                                | `used = 4 млн` (не 7)                                                 |
| 3   | уменьшить до 2 млн                                             | `used` остаётся 4 млн                                                 |
| 4   | закрыть первый, открыть следующий 1 млн                        | `projected_used = 5 млн` — ровно порог, тариф нужен                   |
| 5   | пауза и возобновление без изменения суммы                      | расхода нет                                                           |
| 6   | повтор запроса открытия (тот же `Idempotency-Key`)             | один расход, один раунд                                               |
| 7   | два параллельных открытия по одному проекту                    | второе ждёт лок и получает отказ «уже есть незавершённый раунд»       |
| 8   | смена версии-основания открытого раунда                        | `used` не меняется; запись в `basis_history`                          |
| 9   | админ исключил ошибочный раунд из учёта                        | `used` уменьшается на его `accounted_target`; аудит с основанием      |
| 10  | новая версия политики с порогом ниже `used`                    | долга нет; следующее открытие требует тариф; черновики не блокируются |
| 11  | политика B: раунд `USD 200 000`, затем увеличение до `260 000` | второе действие требует тариф; валюта учёта `USD`                     |
| 12  | раунд в валюте вне `allowedRoundCurrencies`                    | недоступно с понятной ошибкой, до появления `fx`                      |
| 13  | новая заявка того же проекта                                   | `used` не обнуляется (единица — Project ID)                           |
| 14  | второй проект того же пользователя                             | свой `used`; число проектов — глобальная политика аккаунта            |
| 15  | `paidBarrierEnabled=false` в опубликованной политике           | лимит только считается и показывается                                 |

## 11. Спорные решения — нужны от владельца

1. **Потолок суммы одного раунда**: по умолчанию выключен
   (`maxTargetPerRound: null`) — прежний потолок 5 млн на заявку
   становится порогом платной зоны.
2. **Перевод существующих `listed` проектов в `public` как тизер** (ответы
   анкеты — только после «Опубликовать публичный вид») — или все в
   `private` с ручным включением.
3. **Внутренний доступ**: `organizer` только для функций сезона без
   содержимого анкеты; рецензент — назначенные проекты.
4. **Правило первоначального выбора рынка**: единственный активный рынок
   проставляется автоматически, при нескольких — обязательный выбор.
5. **Где `maxApplicationsPerProject`**: в политике рынка или остаётся
   глобальным в политике заявок.
6. **Истечение подписки при открытом платном раунде**: `keep_open` по
   умолчанию, `pause` как настройка.
7. **Несколько `paused` раундов** — не допускаются (одна незавершённая
   кампания). Подтвердить.
8. **Судьба контуров группы В** (сезоны, экспертиза, Integration API,
   медиаконтур, OIDC) — отдельные решения, 5.6–5.7 не блокируют.
9. **Порядок U1 (хроника) относительно этапа 6** — после проверки
   владельцем.
10. **Сумма раунда в Public View** — по умолчанию скрыта
    (`public_round_visible=false`), включается владельцем проекта.
