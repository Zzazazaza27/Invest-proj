## 1. Ядро: `identity.users`

Живая схема стенда (19 колонок, M002 + M035 + M081/M083):

| Колонка                                   | Тип         | Смысл                                                               |
| ----------------------------------------- | ----------- | ------------------------------------------------------------------- |
| `id`                                      | uuid        | UUIDv7                                                              |
| `email_ciphertext`, `phone_ciphertext`    | bytea       | контакты **зашифрованы** (envelope, KEK-домен `passport_sensitive`) |
| `contact_wrapped_dek`                     | bytea       | обёрнутый ключ данных к этим двум полям                             |
| `email_hmac`, `phone_hmac`                | bytea       | слепой индекс: поиск по точному значению без расшифровки            |
| `password_hash`                           | text        | Argon2id; NULL при внешнем IdP                                      |
| `display_name`                            | text        | отображаемое имя, задаётся при регистрации                          |
| `primary_role`                            | text        | основная роль из 7 (`founder…showrunner`)                           |
| `status`                                  | text        | `pending_consents` / `active` / `suspended` / `deleted`             |
| `locale`, `currency_pref`, `home_contour` | text        | предпочтения                                                        |
| `mfa_enabled`                             | boolean     | второй фактор (сейчас всегда false)                                 |
| `service_country`                         | text        | страна обслуживания (этап 5.6)                                      |
| `sessions_valid_from`                     | timestamptz | **рубеж действительности сессий** (M035)                            |
| `created_at`, `updated_at`, `deleted_at`  | timestamptz | мягкое удаление уже предусмотрено схемой                            |

Чего в таблице **нет**: аватара, юридического имени, отчества, даты рождения,
адреса. Личность подтверждается не профилем, а KYC (§4).

## 2. Что заполняется когда

- **При регистрации** (`POST /v1/auth/register`): email или телефон, пароль
  (≥ 12 символов), `displayName` (2–120), роль из `founder`/`investor`,
  локаль, акцепты четырёх документов. Всё остальное — умолчания схемы.
- **Позже**: `service_country` (этап 5.6), `status` (активация по акцептам),
  роли (админом), `sessions_valid_from` (при смене прав/пароля).
- **Никогда через интерфейс**: `display_name` после регистрации, контакты,
  пароль (только по ссылке «забыли пароль»). Методов нет ни в одном кабинете —
  проверено по контроллерам `identity`, `verification`.

## 3. Контакты: как устроена защита

Три уровня, и все три придётся уважать в карточке администратора:

1. **Шифрование.** Значение лежит зашифрованным; расшифровка — только через
   `CryptoService.openField('passport_sensitive', dek, ciphertext, поле)`.
2. **Слепой индекс.** Поиск по точному email/телефону возможен (`blindIndex`),
   поиск по части адреса — нет: это означало бы расшифровку всей таблицы.
   Текущий `DirectoryService.findUsers` ищет **только по `display_name`**
   через `ILIKE`, и комментарий там честно называет причину.
3. **Маска наружу.** `GET /v1/auth/me` отдаёт `emailMasked`/`phoneMasked`
   даже владельцу: полный контакт не покидает сервер без нужды
   (`identity.service.ts`, `maskEmail`/`maskPhone`).

Отсюда решение для карточки: **по умолчанию маска**, полное значение —
отдельным действием под отдельным полномочием и с записью в журнал.

## 4. Роли, полномочия, назначения, KYC — четыре РАЗНЫХ слоя

Их нельзя валить в один экран «права»:

| Слой                                                  | Где живёт                                                                    | Кто меняет                                                         |
| ----------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **Роль** (`admin`, `expert`, …)                       | `identity.user_roles`                                                        | админ, не себе, последнего админа не снять (M024 + `RolesService`) |
| **Функциональное полномочие** («фиксировать возврат») | `identity.staff_capabilities` (каталог) + `identity.staff_capability_grants` | админ; запрет самовыдачи стоит триггером в БД (M097)               |
| **Область работы** (с какими объектами)               | `experts.expert_assignments` (M007/M021/M099)                                | админ                                                              |
| **Подтверждение личности**                            | `kyc.kyc_verifications`, `kyc.kyb_verifications`, `kyc.business_entities`    | процесс KYC, не администратор                                      |

Каталог полномочий типизирован: код вида `finance.tranche_return.record`,
раздел, вид действия (`view`/`create`/`update`/`confirm`/`financial_adjust`/
`discuss`), признак `is_implemented` — полномочие существует, только если
проверка на него есть в коде. Это готовое место для полномочия «видеть
контактные данные».

KYC-процесс **реализован частично**: таблицы, статусы
(`pending`/`in_review`/`approved`/`rejected`/`verification_pending`), причина
отказа, ссылка на зашифрованный документ, `pep_status`, `sanctions_status`,
`risk_level`. Пользователь видит свой статус (`VerificationCard` в
`@fifth/cabinet`). Отдельного процесса подачи с возвратом на исправление
нет — выдумывать его в этой задаче нельзя.

## 5. Сессии и блокировка — механизм уже есть

- `status = 'suspended'` **уже проверяется при входе**
  (`identity.service.ts:352`): заблокированный не войдёт.
- `sessions_valid_from` (M035) — рубеж: токен, выпущенный раньше отметки,
  отклоняется guard'ом. Сдвигается при выдаче/снятии роли и сбросе пароля.
- `TokenRevocationService` (M038) — точечный отзыв одного токена (выход).

Значит блокировка **не требует нового механизма**: смена статуса + сдвиг
рубежа закрывают и будущие входы, и уже выданные сессии. Конкурирующий статус
заводить нельзя — он был бы вторым местом правды.

## 6. Связанные с человеком объекты

`lab.founders_projects` (проекты основателя), `billing.subscriptions`,
`comms.support_tickets`, `experts.expert_assignments` (назначения эксперта),
`kyc.business_entities.owner_user_id` (юрлица), `kyc.kyc_verifications`,
`identity.staff_capability_grants`, `identity.consents` (акцепты).

В карточку идут те, что нужны администратору для работы: проекты, подписка,
обращения, назначения, юрлица, KYC. Выгрузкой всех таблиц карточка не
становится.

## 7. Журнал

`audit.events` + `audit.event_type_registry`: **fail-closed** — событие с
незарегистрированным `verb` или недопустимой ролью актора не пишется, а падает.
Любое новое административное действие требует строки в реестре, то есть
миграции. Записи связаны hash-chain'ом.

## 9. Что выносится в интерфейс, а что нет

**Список:** имя + аватар, маска email, маска телефона, роли, состояние
аккаунта, статус KYC, дата регистрации.

**Карточка:** то же плюс идентификатор, страна обслуживания, локаль, основная
роль, даты, рубеж сессий, полномочия, назначения, связанные объекты, история
административных действий по этому человеку.

**Не выносится никогда:** `password_hash`, `contact_wrapped_dek`, `*_hmac`,
`evidence_wrapped_dek`, содержимое документов KYC, ключи и токены. Полные
контакты — только под полномочием и с записью в журнал.
