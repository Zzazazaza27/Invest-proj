## Что есть сейчас (по коду)

- Журнал `audit.events`: `actor_id`, `actor_role`, `context_jsonb`, `trace_id`;
  всё входит в hash-цепочку. Запись — только `audit.app_emit_event`; роль
  сверяется с реестром глагола (`actor_roles_allowed`).
- 71 вызов `emit/record/recordDuringView` в 22 сервисах. Роль автора каждый
  выбирает сам: `roles.includes('admin') ? 'admin' : 'founder'`, `roles[0]`,
  константа. У человека с двумя ролями роль в журнале зависит от сервиса, а не
  от того, какая проверка пропустила действие.
- До входа: `identity.user.registered` и `identity.login.failed` пишут
  `actor_id` = учётная запись, `actor_role = 'system'`. Это неверно в обе
  стороны: делал не владелец учётной записи и не система.
- Сервисные учётные записи (вебхуки) пишутся как `system` с id в контексте.
- Фоновые задачи не несут инициатора: сверка загрузок пишет `system`, а
  автора кладёт в `onBehalfOf` по своему соглашению.

## Поле `context_jsonb.actor` (версия 1)

Новый столбец не вводится: формула hash-цепочки и сверка `verify_event_chain`
не меняются, старые записи не переписываются. Ключ `actor` в контексте
зарезервирован: если его прислал вызывающий код, запись отклоняется.

| Поле | Тип | Откуда | Смысл |
| --- | --- | --- | --- |
| `v` | 1 | сервер | версия формы |
| `kind` | `person` · `service_account` · `anonymous` · `system` | сервер | кто действовал |
| `userId` | uuid · null | токен (не тело, не заголовок) | человек; для сотрудника — он сам, не «админка» |
| `serviceAccountId` | uuid · null | токен сервисной учётной записи | только для `service_account` |
| `role` | строка | из `basis` | равна столбцу `actor_role` |
| `basis` | массив | фактически пройденные проверки | см. ниже; роль сама основанием не считается |
| `onBehalfOf` | uuid · null | контекст доступа (M129) | чей кабинет — тестовая сессия или просмотр |
| `testSessionId` | uuid · null | контекст доступа | |
| `viewMode` | bool | контекст доступа | просмотр без изменений |
| `operationId` | uuid | сервер | одна операция пользователя; переживает повторы и фон |
| `requestId` | строка · null | trace запроса | конкретный HTTP-запрос (= `trace_id`) |
| `job` | `{name, runId, attempt}` · null | исполнитель фона | прогон и попытка — отдельно от операции |
| `initiator` | `{kind, userId?, serviceAccountId?}` · null | сохранённое происхождение | кто начал операцию, если действует фон |
| `originUnknown` | true · отсутствует | — | старая запись очереди без происхождения: не выдумываем |

**`basis`** — элементы вида:
`{check:'route-role', role}` — пропустил страж маршрута по этой роли;
`{check:'member', object}` — проверка участника проекта в сервисе;
`{check:'self'}` — действие над собственной учётной записью;
`{check:'token-purpose', purpose}` — одноразовая ссылка (сброс, подтверждение);
`{check:'service-scope', scope}` — право сервисной учётной записи;
`{check:'job', name}` — плановая работа системы;
`{check:'public'}` — открытое действие до входа.
Контекст прав не даёт: он записывает то, что уже проверено, и ни одну проверку
объекта, полномочия или RLS не заменяет.

**`role`** выводится из основания, а не из списка ролей: `route-role` → эта
роль; `member` → `founder`; `self` → `user`; `public`/`token-purpose` до
входа → `anonymous`; `service-scope` → `service`; `job` → `system`. Два
основания с разной ролью — отказ записи, а не выбор «старшей».

**Человек с двумя ролями.** Роли маршрута перечислены от меньших прав к большим
(`'founder', 'admin'`); страж отмечает первую, которой человек владеет. Сервис,
проверивший объект, уточняет основание (`settleBasis`): над проектом — условие
политики «участник ИЛИ администратор», участник проверяется первым
(`lab/acting-role.ts`). Администратор, сам состоящий в команде проекта,
действует как участник; над чужим проектом — как администратор. Автор при этом
всегда один — человек.

**Пустое основание.** Если ни одна проверка не отмечена (маршрут без ролей,
внутренний системный контекст), роль берётся из вызова, а `basis` пишется
пустым — честно «не отмечено», а не выдуманная проверка. Если основание есть и
роль вызова с ним не совпадает — отказ.

## Согласованность со столбцами

Миграция M171 (forward-only) заменяет тело `audit.app_emit_event`: если в
контексте есть `actor`, то `actor.userId` = `p_actor_id`, `actor.role` =
`p_actor_role`, `kind=person` ⇔ `p_actor_id` задан, `operationId` обязателен.
Расхождение — исключение, транзакция откатывается вместе с изменением. Записи
без `actor` (прежнее ядро при возврате и двух слотах, старые записи) функция
принимает как раньше; цепочка и формула хеша не меняются. Реестр глаголов роли
только добавляет: `anonymous` — глаголам до входа, `user` — действиям над
собой, `service` — сервисным учётным записям, `admin` — `lab.project.created`,
`lab.material.added`, `lab.listing.published` (их мог сделать администратор,
а журнал прежде писал `founder`).

## Как контекст попадает в запись

- Страж запроса собирает контекст: `userId` из токена, `operationId` — новый
  uuidv7, `basis` — пройденная роль маршрута. Страж интеграции — сервисная
  учётная запись и пройденный скоуп.
- `Database.transaction`/`readOnly`/`asServiceRole` связывают контекст с
  соединением на время транзакции и снимают связь в `finally` (соединения в
  пуле общие). `emit` берёт автора только оттуда; вызов без связанного
  контекста — отказ. Так подключены все 71 вызов.
- Аргументы `actorId`/`actorRole` у `emit` остались, но сверяются с
  контекстом: расхождение — отказ (ошибка кода, ловится тестами).
- Событие и изменение — одна транзакция. **Исправлено попутно:** смена пароля
  по ссылке и подтверждение почты писали журнал отдельной транзакцией после
  изменения и глотали сбой записи (пароль сменён, записи нет). Теперь — в той же
  транзакции (роли `app_auth` выдано право на функцию журнала — M171, и на схему
  `audit` — M172: без него смена пароля отвечала 500, поймал набор блока «вход»).
- Прежде пропускавшиеся записи пишутся: отзыв своего токена и устройства
  молча не писались, если у человека не было «подходящей» роли.

## Смысловые вопросы Тэнку

1. **Полномочия сотрудников сейчас не проверяются.** Каталог и выдача есть,
   но действие пропускает роль `admin` на маршруте. Пишу честно основание
   `route-role: admin`, а не выдуманное полномочие. Проверки по полномочиям —
   отдельным заданием: это изменение прав, а не журнала.
2. **Роль `user` для действий над собой.** Прежде роль бралась «первая из
   списка» (у человека founder+investor — случайно). Ввёл `user` с основанием
   `self`; реестр глаголов дополнен. Прежние записи остаются как есть.
3. **Загрузка, завершённая после отзыва прав.** Сверка завершает начатую
   загрузку, не проверяя, может ли автор ещё менять проект. Предлагаю при
   завершении проверять текущее право автора и отклонять материал, если права
   нет. Это изменение поведения — не сделано, жду решения.
