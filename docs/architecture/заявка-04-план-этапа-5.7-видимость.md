## 1. Коротко

Сегодня раскрытие держится на трёх несвязанных вещах: один булев признак
`listing_status='listed'` в шести местах RLS, подписка инвестора как гейт
доступа, и «строже из двух» для полей раунда (M086) без какого-либо
разрешения владельца. Ответы анкеты инвестору вообще не отдаются серверной
проекцией: кабинет инвестора читает полную строку проекта, материалы и
паспорт тремя вызовами и сам решает, что показать.

5.7 вводит **одну модель** из четырёх слоёв, проверяемых по порядку:

1. **Режим проекта** (решение владельца, кому в принципе виден проект):
   `private | public | registered_investors | selected_investors`.
2. **Предикат доступа** `lab.project_audience(project, user, permission)` —
   отвечает, **с какой аудиторией** зритель видит конкретный объект
   (`teaser | profile | round | materials | passport | extended`), или
   `NULL` — доступа нет. Аноним в режиме `public` получает аудиторию
   `public` для профиля и раунда — так Public View собирается через тот же
   предикат, без обхода. Для выбранных получателей — по набору разрешений
   в grant, не по сравнению названий уровней.
3. **Эффективная видимость поля** = **строже** из административной политики
   (активная конфигурация) и **версии условий, на которую согласился
   владелец**. Согласие привязано к конкретному неизменяемому снимку
   (для ответов) и к раунду (для полей раунда). Ограничение администратора
   действует сразу; расширение — только после явного действия владельца с
   предпросмотром разницы.
4. **Поле показывается**, если `visible_to(эффективная видимость, аудитория
из п.2)`. Разрешение любого вида не поднимает аудиторию выше
   `investors`: поля `platform` и `private` наружу не попадают никогда.

**Права на данные отделены от коммерческого допуска.** Проверка «инвестор
допущен» — одна функция `lab.investor_gate(user)` = роль `investor` **и**
(барьер подписки выключен настройкой **или** действующее членство). Барьер
— флаг `billing.investor_access_requires_subscription`; миграция ставит его
**включённым** (сегодняшнее поведение), переключение — решение владельца
(§6). Настройка оплаты никогда не обходит режим проекта, исключения и
разрешения владельца: она проверяется после них.

Материалы — отметка владельца у каждого материала (`private | investors`);
административная политика материалов в 5.7 не строится (TODO, §5).

Порядок работ обязателен и при выкате: **структуры и проекции → перевод
кабинетов → закрытие старых путей и RLS**; исполнение порядка — §7.

## 3. Модель

### 3.1. Режим проекта — `lab.projects.visibility`

`TEXT NOT NULL DEFAULT 'private' CHECK IN ('private','public',
'registered_investors','selected_investors')`, плюс `visibility_changed_at`,
`blocked_at`, `blocked_reason` (административная блокировка; внешним —
ничего, команда и админ видят).

- Устанавливает владелец действием «Кто может видеть проект» с теми же
  проверками, что листинг сегодня: KYC владельца и комплаенс паспорта;
  пересчёт тарифа и барьер подписки основателя — нет (`заявка-03` §3.7).
- `listing_status` — **следствие**: `listed` для режимов шире `private`,
  `not_listed` для `private` (кеш для v1, триггера тарифа и Integration
  API). Открытие, пауза, закрытие раунда режим не меняют.
- Перенос данных: `listed` → `public` **только как безопасный тизер**
  (§3.5); остальные — `private`. Для текущих тестовых данных допустим
  согласованный сброс (`reset-test-db.mjs`, §0г.6) — перенос ради них не
  усложняется.
- `selected_investors` в интерфейсе 5.7 не показывается (нет способа выдать
  grant — 5.8), но предикат его уже понимает.

### 3.2. Разрешения получателей и исключения

```
lab.project_access_grants (
  id, project_id, grantee_user_id NULL, grantee_entity_id NULL,
  permissions TEXT[] NOT NULL
    CHECK (permissions <@ ARRAY['profile','round','materials','passport','extended']
           AND cardinality(permissions) > 0),
  granted_by, granted_at, revoked_at, reason,
  CHECK (num_nonnulls(grantee_user_id, grantee_entity_id) = 1))
lab.project_access_exclusions (
  id, project_id, excluded_user_id NULL, excluded_entity_id NULL,
  created_by, created_at, revoked_at, тот же CHECK)
```

Grant — **набор независимых разрешений**, не уровень. Получатель с
`{materials}` видит тизер и разрешённые материалы, но ответы анкеты и раунд
для него закрыты; с `{round}` — тизер и проекцию раунда, без ответов.
`extended` — одно из разрешений, требующее ещё и KYC получателя; выдачи
расширенных данных в 5.7 нет. Исключение имеет приоритет над любым grant и
режимом; в режиме `public` оно надёжно только для входа под учётной записью
(в интерфейсе это сказано явно).

### 3.3. Предикат — `lab.project_audience(p_project, p_user, p_permission)`

`STABLE`, `SECURITY DEFINER`, `SET search_path`; возвращает аудиторию
(`private` — полный доступ команды и админа; `platform`; `investors`;
`public`) или `NULL`. `lab.can_view_project(...)` = `project_audience(...)
IS NOT NULL` — для RLS и вью. Порядок проверок:

1. проект удалён или заблокирован → внешним `NULL` (команда, админ — п.2);
2. член команды или `admin` → `private`; назначенный рецензент →
   `platform` для всех разрешений, кроме `extended`;
3. `organizer` — прав не даёт: сезонный контур отложен целиком (решение
   владельца 2026-09-18, M088; `app.has_role('organizer')` — `false`, пока
   флаг `seasons.enabled` выключен); прежний п. 3 ред. 2 (тизер проекта
   сезона) снят вместе с §3.6;
4. действующее исключение для пользователя или его организации → `NULL`;
5. `visibility='private'` → `NULL`;
6. `public`: `teaser | profile | round` → `investors`, если
   `lab.investor_gate(p_user)`, иначе `public` (аноним и любой вошедший без
   допуска); `materials | passport` → `investors` при `investor_gate`,
   иначе `NULL` (публичных материалов и паспорта в 5.7 нет);
7. `registered_investors`: любое разрешение → `investors` при
   `investor_gate`, иначе `NULL`;
8. `selected_investors`: `teaser` → `investors` при любом действующем
   grant; иное разрешение → `investors`, если оно есть в `permissions`
   grant; `investor_gate` здесь **не требуется** — выбранный получатель
   допущен владельцем лично;
9. `extended`: только п.8 с `'extended'` в grant **и**
   `kyc.has_valid_kyc(p_user,'identity')`; аудитория всё равно `investors`
   (уровня раскрытия полей выше `investors` наружу нет).

Сборка любого представления: аудитория из предиката → поля по
`visible_to(эффективная видимость, аудитория)`. Тест на п.6: в режиме
`public` анониму доступен ответ с эффективной `public`, соседний ответ
`investors` — нет, ответ `platform` — никому, кроме команды.

Паритет с TypeScript: `projectAudience()` в
`packages/contracts/src/domain/visibility.ts` для интерфейсов; тест
паритета по матрице (как `visible_to`).

### 3.4. Разрешение владельца и версия условий

Согласие — не «последняя поданная заявка», а **конкретный снимок и версия
условий, которые владелец видел**:

| Что           | Где                                                                                                                           | Когда ставится                                                                                                                                                                                                                              | Когда обновляется                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Ответы анкеты | `lab.projects.disclosed_version_id` (FK на `project_versions (project_id, id)`), `disclosure_form_version`, `disclosed_at/by` | при **подаче** версии профиля: экран подачи показывает предпросмотр по обеим аудиториям и сообщает «внешнее представление переключится на эту версию»; тело `submit` несёт `activeFormVersion`, сервер отказывает при смене активной версии | «Применить новые условия раскрытия» → `disclosure_form_version` = активная (после предпросмотра разницы) |
| Поля раунда   | `lab.funding_rounds.disclosure_version` (есть, M086)                                                                          | при **открытии** = активная версия; тело `open` несёт `confirmDisclosureVersion`, сервер отказывает при несовпадении                                                                                                                        | тем же действием «Применить…» — для существующего раунда, **без нового раунда**                          |
| Материалы     | `lab.project_materials.visibility`                                                                                            | все существующие → `private` (миграция ничего не раскрывает)                                                                                                                                                                                | владелец, переключатель «Показывать инвесторам» у материала                                              |

Правила:

- Public View и Investor View читают **только** `disclosed_version_id` —
  неизменяемый снимок; черновики и другие анкеты проекта наружу не попадают.
  Новая подача (любой анкеты проекта) переключает `disclosed_version_id` на
  поданный снимок — это сказано на экране подачи до кнопки. Отдельной копии
  публичного вида нет.
- `disclosure_form_version` при подаче = `schema_version` поданного снимка
  (конфигурация, по которой владелец видел подписи «кому видно»). Вопрос
  сопоставляется по ключу; ключ, отсутствующий в версии условий → `private`.
- **Эффективная видимость** `lab.effective_visibility(key, form_version)` =
  `stricter(активная конфигурация, form_version)`; `NULL` → `private`. Для
  ответов — `disclosure_form_version` проекта, для полей раунда —
  `disclosure_version` раунда (сегодняшняя `round_field_visibility`).
- Администратор ужесточил → сразу на всё. Смягчил → ничего не
  расширяется; в кабинете видна разница «станет видно дополнительно: …»
  до нажатия «Применить». Владелец не может раскрыть шире политики.
- Защита от изменений между предпросмотром и действием — у **всех трёх**
  действий (`submit`, `open`, `apply`): версия, которую видел владелец,
  идёт в теле запроса; расхождение с активной → 409 с просьбой посмотреть
  предпросмотр заново.

Пример. Версия 36: `problem_statement = investors`. Владелец подал профиль
(снимок S1, условия 36). Администратор публикует 37 с `public` → анониму
по-прежнему ничего (строже = investors); в кабинете: «после применения
версии 37 анониму станут видны: Проблема». Владелец применяет → public.
Администратор публикует 38 с `investors` → сразу investors, у всех.

### 3.5. Составы представлений

Все представления собираются одним модулем (`application-views.ts` +
проекции БД) из аудитории предиката по каждому разрешению. Блок включается
по **своему** разрешению; отсутствующий блок — `null`, поля считаются в
`withheld`.

**Public View** (`GET /catalog/:id`; предикат `teaser` с аудиторией
`public`): тизер (`id, title, tagline, taxonomy, stage, geoCountry,
listedAt`; без суммы из кеша — сумма только из раунда, как с 5.6.4),
`round` — проекция раунда по аудитории `round`, `sections` — ответы снимка
`disclosed_version_id` с эффективной видимостью, прошедшей `visible_to(…,
'public')`, `materials: null`, `withheld`.

**Investor View** (`GET /projects/:id/investor-view`; требуется только
`teaser`): тизер + `description, geoRegion` (по `profile`) + `sections` по
аудитории `profile` + `round` по аудитории `round` (нет права →
`undisclosed`) + `materials` с отметкой `investors` по праву `materials` +
`passport` **явным составом** по праву `passport`: `version, disclosureTier,
irs, axes` в границах `disclosure_tier` + `withheld`. Байты материала — тот
же маршрут `…/materials/:id/content` под RLS на предикат `materials` и
отметку. Получатель grant `{materials}` получает тизер и материалы, всё
остальное — `null`.

**Предпросмотр владельца** (`GET /projects/:id/view-preview?audience=`):
то же тело для выбранной аудитории плюс `audienceSummary` («кто это
увидит» по режиму: никто / зарегистрированные инвесторы (с учётом барьера)
/ все) и `pending` — поля, которые станут видны после применения активной
версии (профиль и незавершённый раунд отдельно). Конфликт «ответ виден,
подтверждение закрыто» — у вопроса с `evidence` из `private`-материала.

**Экран подачи** — тот же предпросмотр с `activeFormVersion` и текстом об
обновлении внешнего представления.

**Предпросмотр перед открытием раунда** (`GET /rounds/:id/open-preview`):
проекция раунда по активной версии для обеих аудиторий + `audienceSummary`

- предупреждение при режиме `private` («раунд никто не увидит»).

### 3.8. Коммерческий допуск инвестора — настройка, не миграция

`lab.investor_gate(p_user)` = `app.has_role('investor')` для `p_user` **и**
(`NOT lab.investor_access_requires_subscription()` **или**
`lab.has_active_investor_membership(p_user)`). Флаг
`billing.investor_access_requires_subscription` в `audit.feature_flags`,
меняется в админке без рестарта; M087 заводит его **включённым** — ровно
сегодняшнее поведение. Все новые проекции и RLS зовут только
`investor_gate`; `viewer_audience()` переводится на неё же. Выключение
флага — решение владельца о составе бесплатного доступа (§6), не часть
этапа безопасности. Права на данные (режим, согласие, grant, отметки
материалов) проверяются **до** флага, поэтому оплата их не обходит.

## 7. Выкат — как порядок исполняется на самом деле

`deploy.mjs` применяет **все** ожидающие миграции одной командой и только
потом перезапускает ядро; отдельного «до M087» у раннера нет. Поэтому
порядок обеспечивается **двумя релизами**, а не флагами раннера:

1. **Релиз 5.7-а** = коммиты 5.7.1–5.7.4 (в репозитории есть только M087).
   `npm run deploy`: миграция M087 → рестарт. M087 только добавляет;
   старое ядро над M087 работает как прежде (окно между миграцией и
   рестартом безопасно).
2. **Релиз 5.7-б** = 5.7.5–5.7.6 (M090). `npm run deploy`: M090 → рестарт.
   M090 **ужесточает**: в окне до рестарта и при откате кода старое ядро
   получает от БД пустые выборки для инвестора (ошибки в
   кабинетах), но не строки. Откат кода допустим, откат M090 — нет, пока
   стенд живёт с новым ядром; откат обоих — только вместе и до включения
   флага барьера в выключенное положение.
3. Стенд сейчас на `9d63281` (до этапов 1–5). Если выкатывать всё одним
   разом, оба релиза сливаются в один прогон: все миграции, затем новое
   ядро; окно «старое ядро над M090» — секунды между `db:migrate` и
   рестартом, с тем же исходом (пусто, не утечка). Сброс тестовой базы
   стенда до выката — по §0г.6, тогда переноса данных нет вовсе.
4. После миграций: скрипты переводов конфигурации из runbook 5.6; новых
   скриптов 5.7 не добавляет. Проверка после: `smoke-lab`,
   `smoke-favorites`, `smoke-integration` против стенда; флаг барьера —
   в положении, выбранном в §6.
