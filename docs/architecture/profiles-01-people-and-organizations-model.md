## 1. Постановка (кратко)

1. Состав личного профиля фиксирован в коде; из админки настраиваются только
   вопросы заявки и раунда.
2. Администратор в карточке человека видит профиль в той же структуре, что
   человек у себя; служебные данные и действия — отдельно. Один
   React-компонент на обе страницы не обязателен.
3. Дополнительные сведения о человеке — настраиваемые анкеты по ролям.
   Системные данные (вход, контакты, роли, страна, проверки) — не поля анкеты.
4. Организация — не набор полей в личном профиле. Один человек — несколько
   организаций, одна организация — несколько представителей.
5. Различать, кто действует: человек лично или организация через
   представителя — минимум для подачи проекта и интереса инвестора; для сделок
   критично. Полный процесс проверки юрлиц и кабинет акселератора — не сейчас.

## 2. Что есть в коде (2026-09-25, последняя миграция M145)

- **Человек** — `identity.users`: вход, контакты зашифрованы, имя, основная
  роль, статус, страна обслуживания, язык. Ролей несколько
  (`identity.user_roles`). KYC — `kyc.kyc_verifications`.
- **Личный профиль** — один экран `packages/cabinet/src/ProfilePage.tsx` во
  всех кабинетах; изменяются имя, аватар, пароль. Контракт
  `packages/contracts/src/domain/profile.ts`.
- **Профиль инвестора** — таблица `identity.investor_profiles` (о себе,
  направления, чек, `entity_id`) есть в M002 и в контракте, но **ни ядро, ни
  интерфейс её не читают и не пишут**. Заготовка, не функционал.
- **Основатель** — отдельного профиля нет, только `lab.founders_projects`.
  **Эксперт** — `experts.experts` (о себе, теги, загрузка).
- **Проект** — колонки владельца нет; `founders_projects(user_id, owner|
cofounder)`, ровно один owner — человек. Добавить сооснователя через API
  нельзя.
- **Заявка / раунд** — привязаны к проекту; `created_by` — автор. Форма
  юрлица, юрисдикция, владение — только ответы анкеты (`legal_entity` и др. в
  `application-form.v1.ts`).
- **Интерес инвестора** — сущности нет. Есть избранное
  (`lab.project_favorites`) и заготовка сделок `investments.*`.
- **Юрлица** — `kyc.business_entities` (ИНН/ОГРН, KYB) + `kyc.entity_members`
  (signatory / beneficial_owner / representative); карточка
  `BusinessEntitiesCard` в кабинетах основателя и инвестора («лично или от
  компании»).
- **Прежнее решение владельца (2026-09-19):** командную систему не строим;
  приглашения, выход, роли в организации отложены; флаг
  `access.entity_grants.enabled` выключен (TODO «Организации и участники»).
  Этап 9 это решение пересматривает — нужно явное слово владельца.

### Где человек и организация смешаны или проект привязан только к человеку

1. Проект принадлежит человеку (`founders_projects.user_id`); компания
   основателя — ответ анкеты, с юрлицами не связана.
2. Эмитент в сделке определяется по владельцу проекта, а не по подписанту
   юрлица (`apps/core/src/investments/investments.service.ts:290-306`); RLS
   (M005:335) проверяет подписанта — код и БД расходятся.
3. Выпуск предложения проверяет владение проектом и KYB юрлица, но не
   членство вызывающего в этом юрлице (`investments.service.ts:459-475`).
4. Инвестор в договоре — только человек (`investment_agreements.investor_id`).
5. Юрлицо записано на одного человека (`business_entities.owner_user_id`);
   карточка админки ищет юрлица по нему, а не по составу.
6. Участника добавляют в юрлицо по id без его согласия
   (`kyc.service.ts` `addMember`); ИНН уникален — второй представитель сам
   ту же компанию не заведёт.
7. Подписка инвестора и покупка пакета раунда — только на человека; плательщик
   «юрлицо» возможен только в счёте.

## 3. Предлагаемая модель (черновик)

- **Человек** — вход, системные данные, личная анкета по ролям. Сведения
  личного профиля принадлежат только человеку.
- **Организация** — новая сущность: компания, фонд, акселератор, клуб; тип,
  название, страна, сайт, описание. Реквизиты юрлица и KYB
  (`business_entities`) к ней **прикрепляются**, не заменяют её.
  Существующие юрлица переносятся в организации с реквизитами.
- **Членство** человек ↔ организация: роль (управляющий / представитель),
  статус с историей (приглашён → действует → вышел / исключён) и **уровень
  полномочия**: «заявлено» или «подтверждено» (администратор по документу,
  либо автоматически для подписанта проверенного юрлица). Вступление — только
  через приглашение с согласием приглашённого.
- **Правообладатель проекта** — человек или организация. Команда проекта
  (`founders_projects`) по-прежнему решает, кто редактирует. Членство в
  организации не даёт автоматического доступа к её проектам.
- **«От чьего имени»** — у значимого действия: кто нажал (человек), от чьего
  имени (человек или организация) и уровень полномочия на момент действия. На
  запуске — подача заявки, открытие раунда, интерес; позже — сделки (подпись
  только подтверждённым представителем).
- **Админка:** карточка человека — профиль в структуре кабинета, блок
  «Организации» (роль, полномочие, «Подтвердить» с основанием), служебные
  блоки; карточка организации — профиль, реквизиты и проверка, состав,
  проекты, действия от её имени.

### Сквозной пример

1. Анна регистрируется основателем, заполняет системные данные и анкету
   основателя.
2. Заводит «ООО Альфа» — управляющая, полномочие «заявлено»; по желанию
   прикрепляет ИНН (KYB как сейчас).
3. Создаёт проект, правообладатель — «ООО Альфа» (в выборе только
   организации, где она действующий член).
4. Подаёт заявку: подала Анна от имени ООО Альфа, полномочие «заявлено».
5. Приглашает Бориса; он принимает, становится представителем; в команду
   проекта добавлен явно; после доверенности администратор подтверждает
   полномочие.
6. Инвестор Ирина проявляет интерес лично — основатель видит «Ирина».
7. Ирина — подтверждённый представитель «Фонда Бета»; второй интерес — от
   фонда: «Фонд Бета (представитель — Ирина)». Подписка и доступ на запуске
   личные.

### Для запуска / позже

- **Для запуска:** организация; членство с приглашением и историей; два
  уровня полномочия; ручное подтверждение администратором; правообладатель
  проекта; «от чьего имени» в заявке, раунде, интересе; карточки человека и
  организации в админке; перенос юрлиц; настраиваемые личные анкеты по ролям.
- **Позже:** проверка полномочий по реестру; кабинет организации и
  акселератора (идея 001 — модель её не закрывает); доступ по членству
  (`entity_grants`); оплата и подписка от организации; передача проекта;
  публичная страница организации; настраиваемая анкета организации по типу;
  правила подписи в сделках.

## 4. Настраиваемые анкеты профиля

**Граница.**

- Системное (в коде): вход, контакты, имя, аватар, роли, статус, страна,
  язык, согласия, проверки, членство в организациях.
- Системные ключи в анкете: то, по чему платформа считает, фильтрует или
  раздаёт права (направления и чек инвестора, экспертиза). Тексты и порядок
  меняются, удаление и смена типа — нет (приём `coreField` анкеты заявки).
- Через админку: описательные поля — тип, обязательность, видимость (я и
  администрация / участники / публично), порядок, тексты по языкам.

**Изменение анкеты при заполненных профилях.** Правила эволюции заявки:
опубликованный ключ не удаляется, а архивируется; тип не меняется; новый смысл
— новый ключ. Архивные ответы хранятся, видны администратору. Новое
обязательное поле не блокирует аккаунт — профиль «неполный», обязательность
проверяется в точке действия. Сужение видимости — сразу; **расширение** для
уже заполненных ответов — только после согласия человека (как раскрытие в
5.7).

**Сравнение с вопросами заявки.** Повторно: типы вопросов, тексты по языкам,
варианты, ограничения; черновик → публикация → активная версия, откат;
`checkAgainstPublished`, `buildAnswersSchema`, `QuestionField`, приёмы
`QuestionsPage`. Отличается: нет стадий (флаг «обязательно / желательно»);
профиль живой — нет подачи, снимков и закрепления версии; анкет несколько (по
роли, позже по типу организации); нет материалов и весов готовности; другие
аудитории. Технически — общее ядро (типы, тексты, проверка ответа) и отдельная
таблица версий анкет профиля с ключом анкеты.

## 5. Спорные решения — за владельцем

1. Возвращаем ли направление «Организации» (отмена решения 2026-09-19 в
   объёме: приглашение, выход, исключение; без доступа по членству)?
2. Организация отдельно от юрлица с прикреплёнными реквизитами — или
   расширение `business_entities`?
3. Доступ к проектам организации — явно через команду проекта или всем
   членам?
4. Какие действия на запуске требуют подтверждённого полномочия (предложение:
   никакие, статус виден везде; блокировка — со сделками)?
5. Интерес инвестора — строить минимальную сущность в этапе 9 или только
   заложить «от чьего имени»?
6. Одна личная анкета с разделами по ролям — или отдельная на кабинет?
7. `investor_profiles` не оживлять, поля — системными ключами анкеты
   инвестора?
