# Блок 09, задание 3 — два ядра при выпуске

Постановка: `11 MVP/01 Operations and Updates/09 Update and Rollback.md`, 9.1, 9.3, 9.5.
План согласован Тэнком 09.11.2026 с уточнениями 1–7 ниже; документ фиксирует их до кода.
VPS не меняется до отдельного разрешения Томаса; рабочая выкладка — по его действующему
порядку.

## Устройство

- **Слоты** `core-a` (порт 4300) и `core-b` (4310) из образа комплекта. Активный слот —
  в **файле маршрута** на узле; файл подключается в nginx `fifth-web` и только читается
  обоими слотами.
- **Порядок переключения** (установщик, под блокировкой выпуска):
  1. кандидат в свободном слоте — без фона; проверки прямо в его порт с узла;
  2. пауза фона старого слота (уточнение 2);
  3. файл маршрута → `nginx -t` → `nginx -s reload`;
  4. подтверждение запросом через nginx (уточнение 4);
  5. старт фона кандидата;
  6. наблюдение; затем завершение старого слота (уточнение 1).
- **Переходный выпуск web** (разово, отдельно, с коротким перерывом и своим возвратом):
  адрес ядра в nginx — из файла маршрута, а не из окружения при старте контейнера.
- **Перечень обращений к `fifth-core` по имени** (копии, Zabbix, диагностика, скрипты
  выпуска) переводится на «активный слот» — первым шагом реализации.

## Уточнения Тэнка (09.11) и как они выполняются

### 1. Старое ядро — до доказанного завершения, а не на 10 минут

Окно наблюдения — минимум. Перед остановкой старого слота установщик проверяет:

- **старые обработчики nginx его больше не используют:** в контейнере web нет процессов
  `worker process is shutting down`;
- **активных запросов нет:** ядро считает начатые и завершённые HTTP-запросы и отдаёт
  счётчик на внутреннем порту (`GET /state`).

Ждёт до предела (предварительно 5 мин после окна). Превышен — **явный порядок**: в журнал
выпуска пишется число незавершённых запросов и их маршруты (без тел), затем SIGTERM со
штатным сроком 30 с; оборванные запросы клиент выясняет как «результат неизвестен» по ключу
повтора (2.6). Разрыв не скрывается: он виден в журнале и в отчёте выпуска.

### 2. Пауза фона — обратимая

Нынешний `stop()` прерывает контроллер навсегда — это остановка процесса, паузой он не
становится. Добавляется отдельное состояние:

| Состояние  | Новые проходы                   | Идущие проходы            |
| ---------- | ------------------------------- | ------------------------- |
| `running`  | захватываются                   | идут                      |
| `pausing`  | не захватываются, таймеры сняты | ждутся до предела паузы   |
| `paused`   | нет                             | нет                       |
| `stopping` | нет (навсегда)                  | ждутся до срока остановки |

- Пауза: свой контроллер **эпохи** (не контроллер остановки процесса). Ждём идущие проходы
  до предела (предварительно 30 с); не дождались — прерываем сигналом эпохи: advisory-
  блокировки освобождаются в `finally`, незавершённая работа остаётся в прикладных записях и
  подхватывается после истечения аренды — тем экземпляром, у которого фон работает.
- Продолжение: новая эпоха, задачи планируются заново; стартовые уборки (`runAtStart`)
  повторяются только у задач, для которых это безопасно (помечены).
- Команды — `POST /background/pause`, `POST /background/resume`, `GET /background` на
  внутреннем порту (уточнение 5).

### 3. Владелец фона переживает перезапуск

Владелец фона определяется **файлом маршрута**, а не памятью процесса. Слот в режиме
выпуска (`BACKGROUND_START=route`) при старте читает файл: свой слот активен — фон
запускается, иначе остаётся на паузе. Порядок шагов переключения гарантирует, что файл
меняется только между паузой старого и стартом нового.

Испытание: перезапуск **обоих** слотов во время наблюдения и перезапуск неактивного слота —
неактивный остаётся без фона, активный восстанавливает работу. Advisory-блокировки
двойного прохода не допускают, но **повторные последствия** проверяются отдельно: письма,
события outbox и вебхуки при перезапусках уходят по одному разу (счётчики в БД и почтовом
каталоге).

### 4. Переключение подтверждается запросом

Ядро отдаёт сборку в заголовке ответа (`X-Fifth-Build`). После reload установщик делает
серию запросов **через nginx** и требует ответ кандидата в каждом. Не подтвердилось —
прежний файл маршрута, reload, подтверждение прежней сборкой, фон старого слота
возобновляется. Журнал хранит содержимое файла маршрута до и после: после обрыва
фактическое состояние восстанавливается сверкой файла, ответа через nginx и состояния фона
в каждом слоте.

### 5. Кандидат и команды закрыты извне

- Порты слотов слушают только адрес, доступный nginx (шлюз Docker / петля), и закрыты
  фильтром узла снаружи; прямой порт кандидата не обходит пароль Caddy. Фактические
  `CORE_BIND_HOST` и правила фильтра prod проверяются на узле до выкладки.
- Внутренний порт — только петля. Команды изменения состояния — `POST` с токеном из файла
  секрета, который есть только у установщика; без токена — отказ и запись в журнал.

### 6. Ресурсы — предварительно

Предел пилота 768 МБ потребление prod не доказывает. До выкладки собираются фактические
данные с узла: ограничения и расход рабочего ядра, пик при запуске кандидата, суммарные пулы
БД обоих слотов (`DATABASE_POOL_MAX` + служебные) против `max_connections`, место под
образы и статику по сборкам. Предварительная проверка установщика останавливает выпуск при
нехватке; test-2 автоматически не останавливается.

### 7. Формы и сессии — по текущему механизму

- Вход — подписанная cookie (общий ключ среды) и рубеж отзыва в БД
  (`sessions_valid_from`). Оба ядра принимают одну cookie; кэш рубежа в каждом процессе —
  до 5 с (`CACHE_TTL_MS`), как и сейчас в одном ядре. Полноценного реестра сессий в БД нет и
  не предполагается. CSRF — двойная отправка, работает на обоих ядрах.
- Уведомление «Доступна новая версия» страницу не перезагружает. Сохранение полей после
  нажатия «Обновить» не обещается, пока не реализовано и не проверено.

## Испытания (локально, временная среда из образов)

Поток запросов, загрузка файла, длинный запрос и занятый фон во время переключения;
отказ кандидата до переключения; отказ после переключения с возвратом; обрыв команды на
каждом этапе; нехватка ресурсов в предварительной проверке; **перезапуск неактивного
слота; перезапуск обоих слотов в окне наблюдения; отказ reload после паузы старого фона —
прежняя работа восстанавливается.**

## Решения по ходу реализации

- **Разрешение фона** — файл `BACKGROUND_GRANT_PATH` (не `_FILE`: так загрузчик окружения
  читает секреты из файлов). Пишет только установщик. Токен команд —
  `BACKGROUND_CONTROL_TOKEN` (можно штатно через `BACKGROUND_CONTROL_TOKEN_FILE`).
- **Наблюдение.** Zabbix опрашивает служебный порт ядра по постоянному адресу
  `127.0.0.1:4400`. Служебные порты слотов — 4401 (`core-a`) и 4411 (`core-b`); постоянный
  4400 обслуживает nginx по тому же файлу маршрута. Перенастраивать Zabbix при каждом
  переключении не нужно.
- **Скрипты узла.** Действующие обращаются к контейнеру по имени `fifth-core`:
  `prod-control`, `prod-db-reach`, `prod-startup-times`, `prod-env-activity`, `prod-preflight`,
  `release.mjs`, `network-audit`. Они переходят на общую функцию «активный слот» (по файлу
  маршрута; без режима слотов — `fifth-core`). Разовые сценарии прошлых переходов
  (`prod-production`, `prod-vault`, `prod-signing`, `prod-retire-secrets` и др.) не меняются.
