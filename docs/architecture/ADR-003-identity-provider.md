# ADR-003 — Внешний проверенный IdP, а не самописный OIDC

- **Статус:** принято
- **Дата:** 2026-08-10
- **Основание:** `docs/architecture/Architect_Launch.md` §2.5, §7; `docs/architecture/Database_Launch.md` §2

## Контекст

Спецификация прямо требует: issuer `https://id.unicorn.vc` реализуется
**проверенным self-hosted IdP**, а не собственной реализацией протокола. В
`fifth_element` не должно быть таблиц сессий, refresh-токенов, WebAuthn-ключей,
MFA-факторов, кодов восстановления, ключей подписи и OAuth-клиентов — они живут
в отдельной БД IdP.

## Решение

- **IdP:** Keycloak 26 (self-hosted, разворачивается в РФ-контуре, отдельная БД
  `keycloak`). Реализует: пароль + Argon2id, TOTP/WebAuthn/passkeys, step-up
  через `acr_values`, брокеринг соц-входа (Google, VK, Apple, Telegram, phone).
- **Core** — OIDC Relying Party и resource server: валидирует JWT по JWKS
  issuer'а, кеширует ключи (`OIDC_JWKS_CACHE_TTL_SECONDS`), проверяет `iss`,
  `aud`, `exp`, `nbf`, алгоритм из allowlist (RS256/ES256; `none` и HS*
  отвергаются), `acr` для step-up операций.
- **Доменный профиль** пользователя — `identity.users`; связь с IdP —
  `identity.auth_identities(provider, provider_uid)`, где `provider_uid` —
  неизменяемый `sub` IdP. Секреты IdP в `fifth_element` не дублируются.

### Локальный адаптер для dev/CI

Поднимать Keycloak в каждом юнит-тесте — неоправданно. Введён `AUTH_MODE=local`:
core сам подписывает короткоживущие токены ключом `LOCAL_AUTH_SIGNING_KEY`.

**Fail-closed:** при `NODE_ENV=production` и `AUTH_MODE!=oidc` приложение
**отказывается стартовать** с явной ошибкой. Это не флаг «на всякий случай», а
проверка в схеме конфигурации, покрытая тестом. Ключ короче 64 символов также
роняет старт.

## Step-up MFA

Обязателен (`docs/architecture/Architect_Launch.md` §7) на: выбор проекта инвестором, принятие
инвестиционного предложения, подписание договора, смену платёжных реквизитов.
Реализуется требованием `acr` уровня `mfa` в токене; отсутствие → `403` с
`WWW-Authenticate: Bearer error="insufficient_user_authentication"`.

## Последствия

- Плюс: сессии, MFA и криптография аутентификации — ответственность зрелого
  продукта, а не наша.
- Минус: локальный контур зависит от дополнительного контейнера; в CI
  используется `AUTH_MODE=local`, поэтому реальный OIDC-поток проверяется
  только в E2E-профиле `idp` и на staging. Это ограничение зафиксировано в
  отчётах и не помечается зелёным без фактического прогона.
