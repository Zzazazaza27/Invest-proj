# ADR-002 — Полностью заменяемый фронтенд (Vite SPA вместо Next.js BFF)

- **Статус:** принято
- **Дата:** 2026-08-10
- **Основание:** прямое требование владельца продукта — «frontend должен быть
  абсолютно отдельным и полностью или по частям заменяемым»; `Architect_Launch.md` §3

## Контекст

`Architect.md` §5 предлагал Next.js 15 с BFF-модулем на каждый фронт. BFF даёт
серверный рендеринг и прячет токен в серверной сессии, но одновременно **вшивает
фронтенд в серверный рантайм**: заменить портал означает переписать его BFF,
маршруты и деплой. Владелец поставил заменяемость выше SSR.

## Решение

Пять независимых SPA (Vite + React + TypeScript strict), каждый со своим
`package.json`, своей сборкой и своим статическим деплоем:

| Приложение        | Порт dev | Назначение                                                     |
| ----------------- | -------- | -------------------------------------------------------------- |
| `apps/web-public` | 5173     | Лендинг, тизерный каталог, тарифы и вознаграждение ОИП открыто |
| `apps/lab`        | 5174     | Кабинет основателя (ЛПИ)                                       |
| `apps/investor`   | 5175     | Кабинет инвестора                                              |
| `apps/expert`     | 5176     | Кабинет эксперта                                               |
| `apps/admin`      | 5177     | Admin-lite (allowlist/VPN)                                     |

**Единственный шов между фронтом и бэком — HTTP `/v1` и пакет
`@unicorn/api-client`, типы которого выводятся из `@unicorn/contracts`.**
Ни одного другого канала не существует:

- фронтенд не импортирует ни строки из `apps/core` и `database` — это
  запрещено правилом ESLint `no-restricted-imports` и SAST-правилом
  `unicorn-frontend-must-not-touch-db` (ошибка сборки, а не замечание ревью);
- бэкенд не рендерит HTML, не отдаёт шаблоны и не знает про React;
- фронтенд не содержит бизнес-инвариантов: любая проверка, влияющая на деньги,
  доступ или регуляторику, продублирована на сервере и является там источником
  правды. UI-проверка контролем не считается.

Компенсация утраченного BFF:

| Что давал BFF                 | Чем заменено                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------- |
| Токен вне JS                  | `__Host-` httpOnly + `Secure` + `SameSite=Strict` cookie, выдаваемая core                |
| Защита от CSRF                | Double-submit CSRF-токен + проверка `Origin`/`Sec-Fetch-Site` на сервере                 |
| Скрытие внутренних эндпоинтов | Строгий CORS-allowlist, отдельные скоупы, RLS на уровне строк                            |
| SSR/SEO                       | Пререндер публичных страниц на этапе сборки (`web-public`), `sitemap.xml`, микроразметка |

## Как заменить фронтенд (полностью или по частям)

1. Удалить каталог `apps/<portal>` — бэкенд и остальные порталы продолжают
   собираться и работать (проверяется в CI: `npm run build`).
2. Новый фронт на любом стеке (Next.js, Nuxt, Svelte, нативный мобильный)
   подключается к тому же `/v1`. Контракт запросов и ответов уже описан
   zod-схемами в `packages/contracts` и отдаётся как OpenAPI 3.1 по
   `GET /v1/openapi.json`.
3. Добавить Origin нового фронта в `CORS_ALLOWED_ORIGINS`. Больше в бэкенде
   менять нечего.

Возврат к Next.js остаётся открытым и стоит ровно одной замены каталога —
именно ради этого выбран данный вариант.

## Последствия

- **Минус:** публичный каталог рендерится клиентом; для SEO используется
  пререндер и серверная отдача метаданных. Это слабее ISR Next.js.
- **Минус:** access-токен живёт в httpOnly-cookie, поэтому мобильное приложение
  использует отдельный поток OAuth PKCE с Bearer-токеном — два режима
  аутентификации вместо одного.
- **Плюс:** нулевая связанность. Портал можно выбросить и переписать за спринт.
