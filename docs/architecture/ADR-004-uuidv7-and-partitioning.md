# ADR-004 — UUIDv7 в приложении и обслуживание партиций `audit.events`

- **Статус:** принято
- **Дата:** 2026-08-10
- **Основание:** `docs/architecture/Database_Launch.md` §1 «Общие правила DDL», §12

## Контекст

Спецификация требует PK типа UUIDv7 («генерация в приложении **или**
`pg_uuidv7`-расширение») и месячное партиционирование `audit.events` через
`pg_partman` 5.x.

## Решение

### UUIDv7

1. **Основной путь — генерация в приложении.** `packages/contracts` экспортирует
   `uuidv7()` (RFC 9562: 48 бит времени в мс, 12 бит счётчика внутри
   миллисекунды для монотонности, 62 бита из `crypto.randomBytes`). Все вставки
   из core передают id явно.
2. **Дублирующая SQL-функция** `public.uuid_generate_v7()` на `pgcrypto` — для
   сидов, миграций и серверных доменных функций (`confirm_first_tranche`,
   `app_emit_event`), где id рождается внутри транзакции БД.

Расширение `pg_uuidv7` не используется: оно требует сборки из исходников и
тащит в production-образ компилятор. Функциональной разницы нет — формат тот же,
локальность индексов та же.

### Партиционирование

`pg_partman` 5.5.0 **установлен** в образе (`infra/postgres/Dockerfile`) и
используется, если доступен. Миграция `M001` содержит DO-блок:

- есть `pg_partman` → `partman.create_parent(... p_interval := '1 month')` +
  запись в `partman.part_config`;
- нет → создаётся идемпотентная функция `audit.ensure_event_partitions(months_ahead)`,
  которая делает ровно то же самое нативными `CREATE TABLE ... PARTITION OF`.

Оба пути дают одинаковую физическую раскладку, поэтому переключение между ними
не требует миграции данных. Наличие партиции на текущий и следующий месяц —
инвариант, проверяемый тестом.

## Последствия

- Плюс: образ БД без toolchain, воспроизводимая сборка, нет зависимости от
  доступности стороннего репозитория при пересборке.
- Минус: две реализации обслуживания партиций вместо одной. Митигируется тестом,
  который проверяет результат, а не путь.
