## 2. Что строим: три продукта, два контура, одно ядро

| | Unicorn Lab | Unicorn Capital | Реалити-шоу |
|---|---|---|---|
| Контур | Закрытый | Закрытый | Публичный (opt-in шлюз) |
| Роль | Находит, оценивает (IRS), выращивает проекты | Верифицированные инвесторы, листинги, окна, **аукционы**, сделки | Воронка внимания, бренд, спонсорство |
| Данные | Полные, конфиденциальные | Полные, конфиденциальные | Только явно разрешённая обезличенная проекция |

Непреложные принципы (док 00 §2): дефицит вместо каталога (инвесторы : листинги ≥ 5:1); двусторонний отбор; конфиденциальность как продукт; «AI ускоряет, человек решает»; честный FOMO только из append-only журнала событий; место в рейтинге не продаётся; радикальная прозрачность правил и цен при непрозрачности чужих данных.

**Граница доверия — главный архитектурный инвариант:** между закрытым и публичным контурами — односторонний шлюз (Media Gateway с физически отдельной БД-проекцией). Публикация невозможна без активного opt-in согласия команды проекта; отзыв согласия удаляет проекцию ≤ 15 минут.

## 3. Архитектурные принципы

1. **Модульный монолит + событийное ядро** (ADR-001). Команда ≤ 12 инженеров; транзакционная целостность сделок и аукционов важнее автономии сервисов. Границы модулей — явные интерфейсы + линтер зависимостей (Nx/dependency-cruiser). Вынос модуля в сервис — только по триггерам (нагрузка, команда, регуляторика), не по моде.
2. **Двухслойные данные:** Closed Truth (PostgreSQL, закрытый контур) / Public Projection (отдельный кластер `pubDb`). RLS как основной механизм авторизации на уровне строк + явные проверки в сервисном слое (defense in depth).
3. **Append-only журнал событий — контракт честности.** Все сигналы дефицита, FOMO-счётчики, история аукционных торгов — только реальные события из журнала с хеш-цепочкой (SHA-256 `prev_hash`/`row_hash`). Подделка события = компрометация цепочки, детектируется сверкой.
4. **Transactional Outbox:** доменная запись и событие — в одной транзакции БД; релей в NATS JetStream; консьюмеры идемпотентны (дедуп по `event_id`).
5. **Идемпотентность всех денежных и торговых мутаций:** `Idempotency-Key` обязателен для ставок, интересов, allocation, платежей.
6. **«AI ускоряет, человек решает»:** все AI-оценки — рекомендательные; финальные решения (отбор, листинг, allocation, победитель аукциона при споре) фиксирует человек, решение подписывается и попадает в журнал.
7. **Fail-closed для всего, что касается доверия:** watermark-сервис недоступен → документ не показывается; юрисдикционный роутинг LLM не подтверждён → hard fail; согласие на публикацию не найдено → не публикуется.
8. **Конфигурация вместо кода:** сезоны, тарифы, параметры аукционов, правила воронки — записи в БД, меняемые админкой, а не релизы.
9. **Контуры юрисдикций — физически раздельные кластеры БД** (РФ → СНГ → Hub), не `region_id` в одной базе (152-ФЗ).
10. **Expand/contract миграции, feature flags, trunk-based development.**

## 7. Домен «Аукцион» (новый, отсутствует в Rules_arc)

### 7.1. Место в продукте

Аукцион — **опциональный режим конкурентного ценообразования внутри Capital**, включаемый администраторами точечно, для выбранных админами листингов (проектов, допущенных к инвестициям). Не заменяет стандартный поток «окно → интересы → allocation», а является альтернативной веткой статуса `investor_competition`: админ решает, идёт ли раунд по ручному allocation или через аукцион.

### 7.2. Жизненный цикл

```
listing (round_status = due_diligence / investor_competition)
   │  админ: «включить аукцион» (параметры: формат, даты, мин.ставка, шаг, резервная цена)
   ▼
auction: draft ──► pending_approval ──► scheduled ──► active ──► closing ──► completed
                      ▲ 4-eyes: второй       │              │  │              │
                      │ админ подтверждает   │              │  │              ├─► failed (резерв не достигнут)
                      │                      │              │  └─► cancelled (только 4-eyes + reason)
                      │                      │              └─ anti-snipe продление (extended)
                      │                      ▼
                      │                ставки инвесторов (KYC✓ + грант на листинг)
                      ▼
              Отказ → draft (причина в журнале)

completed ──► winner → allocation/deal_documents (UNICORN Terms) ──► round_closing
```

Инварианты:
- **1 активный аукцион на листинг** (частичный уникальный индекс).
- Включение, отмена, ручное вмешательство — **четырёхглазый принцип** (инициатор ≠ подтверждающий, оба в журнале, SoD на уровне БД).
- Участник аукциона: инвестор с `kyc_verifications.status='approved'`, активным tier и активным `access_grants` на листинг уровня ≥ `full`. Проверка — RLS + сервисный слой (defense in depth).
- Все переходы и ставки — события append-only журнала: `auction.enabled`, `auction.started`, `auction.bid_placed`, `auction.outbid`, `auction.extended`, `auction.completed`, `auction.cancelled`. Публичные сигналы («идут торги, N ставок») — только из этих событий (честный FOMO).
- Деньги в аукционе не двигаются: ставка — обязательство, не платёж. Опциональный депозит (эскроу через `billing`) — этап 2, после юрзаключения.

### 7.3. Форматы (конфигурация на аукцион, не код)

| Формат | Описание | Когда |
|---|---|---|
| `english_open` | Открытый повышающий: видны текущий максимум и число ставок, не видны ставившие (анонимные метки) | Основной; честный FOMO из журнала |
| `sealed_first_price` | Закрытые ставки до дедлайна; вскрытие — детерминированной джобой; побеждает максимум | Максимальная конфиденциальность, нет гонки в последнюю секунду |
| `dutch` | Цена снижается по расписанию от стартовой; первый акцепт забирает | Быстрое закрытие при низкой активности |

### 7.4. Критические механики

- **Гонка ставок:** размещение ставки — одна транзакция: `SELECT … FOR UPDATE` строки аукциона → проверка статуса/дедлайна/минимума (`max(current_bid) + min_increment`) → INSERT ставки → обновление агрегата аукциона (`current_bid`, `bids_count`, optimistic `version`) → outbox-событие. Нарушение — 409 `BID_TOO_LOW` / `AUCTION_NOT_ACTIVE`. Плюс `Idempotency-Key` (повтор = тот же ответ, не вторая ставка) и частичный UQ в БД.
- **Антиснайпинг:** ставка в последние `anti_snipe_window_sec` (напр. 120 с) продлевает `ends_at` на `extension_sec` (напр. 300 с), максимум `max_extensions` продлений — всё в той же транзакции; продление — событие `auction.extended`, видимое всем участникам через SSE/push.
- **Sealed-ставки:** сумма шифруется per-record DEK (envelope encryption, домен `auction_sealed`); KMS-unwrap недоступен до `closing`-джобы (политика KMS + время в политике ключа); вскрытие — детерминированно, логируется.
- **Резервная цена:** хранится зашифрованной, не отдаётся API до завершения; если `current_bid < reserve_price` → `failed`, основатель и комитет решают дальнейший шаг (новое окно / allocation / снятие).
- **Реалтайм:** SSE-канал аукциона (обновления ставок/таймера) + push при outbid; деградация до поллинга. Стаггер push-рассылок микро-батчами (анти-thundering-herd при открытии и за 10 минут до закрытия).
- **Rate-limit:** класс `money` (10/мин) на размещение ставок + прогрессивная задержка при серии отклонённых ставок (анти-флуд/анти-разведка шага).
- **Антифрод:** запрет ставок от связанных лиц основателя (проверка по KYB-бенефициарам и `founders_projects`); аномалия «ставка-отбивка» (bid shielding) — детект по паттерну «высокая ставка → отзыв в последнюю минуту»; отзыв ставок запрещён в `english_open` после перебития чужой ставкой (настройка `retraction_policy`).
- **Аудит:** полная история ставок append-only, видна админам и (после завершения) основателю; участникам в процессе — только агрегаты (текущий максимум, число ставок, своя ставка).

## 8. KYC / KYB

### 8.1. Потоки

**KYC (физлицо — основатель, инвестор, эксперт):**
1. Документ + liveness через KYC-провайдера (Sumsub/Veriff-класс, webhook с HMAC-подписью).
2. Пакет доказательств шифруется **до** загрузки в S3 (AES-256-GCM, per-object ключ, KEK-домен `kyc_documents`).
3. Проверка по санкционным спискам и спискам Росфинмониторинга (AML, 115-ФЗ — при приёме членских взносов).
4. `status: pending → approved | rejected`; повторная подача — новая строка (история 1:N сохраняется).
5. Биометрия (этап 2): отдельное письменное согласие `pdn_biometric` (ст. 11 152-ФЗ), отдельное шифрованное хранилище, доступ только verification-сервису.

**KYB (юрлицо — инвестор-фонд, корпорация, основатель-юрлицо):**
1. `business_entities`: ИНН/ОГРН (или аналог СНГ), юрисдикция, реквизиты.
2. Автопроверка по ЕГРЮЛ/ЕГРИП через СМЭВ (асинхронно; недоступность реестра не блокирует заявку — `verification_pending`).
3. Бенефициарные владельцы (≥25%): каждый проходит KYC.
4. Проверка дисквалификации, санкций, статуса (действующее/ликвидировано).
5. Ре-верификация: ежегодно и при апгрейде tier (Trusted → Black → Founding).

**Гейт доверия:** автогранта нет — перед первым доступом к DealRoom/аукционам **ручная проверка комплаенс-офицером** (очередь в `apps/admin`). `verification_status` меняется только сервером, никогда от клиента.

### 8.2. Связка с правами

| Действие | Требование |
|---|---|
| Подать заявку в Lab | регистрация + согласия (оферта, ПДн) |
| Видеть teaser-листинги | KYC approved (инвестор) |
| Data Room, фиксация интереса | KYC approved + tier ≥ Member + грант + NDA-акцепт + MFA |
| **Ставка в аукционе** | KYC approved + tier + грант ≥ full + step-up MFA на первую ставку сессии |
| KYB-инвестор | KYB approved + KYC всех бенефициаров + подтверждение полномочий подписанта |

## 9. Уведомления: 5 каналов, fallback-цепочки

### 9.1. Каналы и приоритет

| Канал | Назначение | Провайдер |
|---|---|---|
| `push` | Мобильные приложения (iOS/Android) и PWA (Web Push) — мгновенные события: outbid, открытие окна, новое сообщение | FCM (Android + Web Push), APNs (iOS) — напрямую или через FCM-клиент iOS |
| `telegram` | Основной канал РФ/СНГ: сервисные уведомления, дайджесты, deep-link авторизация | Telegram Bot API |
| `email` | Транзакционные (подтверждения, документы, инвойсы), дайджесты, fallback | РФ-провайдер транзакционной почты |
| `sms` | Только критичное: OTP-fallback восстановления, security-алерты (смена реквизитов, вход с нового устройства), аукцион выигран/проигран | SMS-провайдер РФ (SMSC-класс) — дорого, поэтому узкий список шаблонов |
| `inapp` | Центр уведомлений в порталах + SSE-реалтайм | Собственный |

### 9.2. Архитектура доставки

- Событие домена → `notifications` (queued) через outbox → BullMQ-воркеры на канал → провайдер → статус `sent|failed` + retry с exponential backoff → **fallback-цепочка** по шаблону (напр., `auction.outbid`: push → telegram → email; `security.credentials_changed`: sms + email одновременно).
- `user_devices`: push-токены устройств (platform ios/android/web_pwa, app_version, last_seen); протухший токен (APNs/FCM `Unregistered`) — автоотзыв.
- `notification_templates` (code, channel, locale, version) — версионированные, рендер на сервере; `notification_preferences` — per user × channel × topic, тихие часы, маркетинговые рассылки — отдельное отзываемое согласие (`marketing_communications`).
- Стаггер рассылок (открытие окна, старт аукциона) микро-батчами; rate-limit на пользователя; дедуп по `dedup_key` (не отправить outbid дважды при ретрае события).

## 10. PWA + iOS + Android (отклонение от Rules_arc: мобайл — обязателен)

Rules_arc осознанно откладывал нативный мобайл; требование заказчика отменяет это решение. Стратегия — **три поверхности из одного TS-ядра**:

1. **PWA (все порталы, с MVP):** installable manifest, service worker (Workbox) с offline-shell и кэшем статики; критичные экраны требуют сети (DealRoom, аукцион — by design, fail-closed); Web Push через FCM; адаптив mobile-first, CWV-бюджеты под 4G, WCAG 2.2 AA. Это закрывает «приложение» без сторов с первого дня.
2. **iOS/Android (Expo / React Native, фаза Capital):** одна кодовая база `apps/mobile`; повторное использование `packages/contracts` (zod), `api-client`, `i18n`, дизайн-токенов. Нативные push (APNs/FCM), биометрия (FaceID/TouchID как локальный фактор поверх WebAuthn), безопасное хранилище токенов (Keychain/Keystore — никогда AsyncStorage). Навигация Expo Router; OTA-обновления (EAS Update) для не-критичных правок; релизы через EAS Build/Submit.
3. **Аутентификация на мобильных:** тот же OIDC-поток через BFF; refresh-token rotation с device binding; «выйти со всех устройств» — мгновенный revocation через Redis.

Покрытие функций: MVP-мобайл = каталог, уведомления, сообщения, интересы, участие в аукционах (ставки подтверждаются step-up). DealRoom-просмотр документов на мобильных — только через secure viewer (watermark в битмапе), массовый экспорт заблокирован на мобильной платформе.

## 11. Безопасность (сводка; детали — STRIDE в Rules_arc §8, здесь — обязательный минимум проекта)

**AuthN:** пароли Argon2id (≥12, проверка по утечкам k-anonymity); **WebAuthn/passkeys — основной второй фактор**, SMS-OTP только fallback восстановления; MFA обязателен для Capital/экспертов/админов, для основателей — с момента листинга; access JWT EdDSA/Ed25519 TTL 15 мин (в памяти, не localStorage); refresh 30 дней с ротацией и детектом reuse (отзыв цепочки); админка: access 5 мин + VPN/allowlist; **step-up MFA** на смену реквизитов, allocation, первую ставку аукциона, массовый экспорт; cooling-off 24 ч на выплаты после смены реквизитов.

**AuthZ:** deny by default; RBAC (7 ролей) + ABAC поверх **Postgres RLS** (session-переменные `app.current_user_id`/`app.current_roles`, SET LOCAL на транзакцию, совместимо с PgBouncer); инвестор не имеет политики на `projects` вообще — только через VIEW допущенных листингов; SoD и **четырёхглазый принцип** на фиксированном списке: allocation, включение/отмена аукциона, платёжные реквизиты, массовый экспорт, удаление проекта/аккаунта, смена весов IRS; JIT-доступ админов (тикет → одобрение вторым лицом → TTL ~2 ч → автоотзыв → журнал).

**Данные:** envelope encryption AES-256-GCM (KMS master → KEK per домен → per-record DEK); домены: `kyc_documents`, `capital_financial`, `passport_sensitive`, `auction_sealed`, `search_index` (blind index HMAC-SHA256 для email/ИНН); HSM-backed root обязателен до запуска Capital; TDE для остального; PITR RPO ≤ 5 мин, бэкапы в WORM, квартальные учения восстановления.

**Периметр и API:** WAF/анти-DDoS РФ-провайдера; NetworkPolicy default-deny; rate-limit классы read/write/search/money; вебхуки — HMAC-SHA256 + timestamp ≤5 мин + nonce; загрузки — magic bytes, антивирус, изоляция парсинга; SSRF-allowlist для AI-воркеров (блок 169.254.169.254); CORS строго по доменам порталов; security-заголовки, CSP.

**Цепочка поставки и гейты CI:** merge-blocking — lint/typecheck, тесты, SAST (Semgrep/CodeQL), SCA с транзитивами, gitleaks, IaC-скан (tfsec/checkov), линтер миграций expand/contract, CODEOWNERS ≥2 для identity/dataroom/auctions/infra; deploy-blocking — интеграционные тесты, Trivy, E2E (Playwright), DAST (ZAP, обязателен перед Capital), eval-прогон Langfuse при смене промптов, cosign-подпись + admission; canary/blue-green с авто-rollback.

**Гейты go/no-go:** A (Lab): РКН/УЗ ИСПДн, RLS с тестами на обход, изоляция AI-контекста, восстановление из бэкапа, пентест периметра. B (Capital, включает аукцион): юрзаключение 259-ФЗ (**блокирующее**), MFA/passkeys принудительно, HSM, пентест ASVS L3, нагрузочный тест окна/аукциона/allocation (гонки не воспроизводятся), fail-closed watermark, SIEM-детекты, KYC/AML согласованы. C (Шоу): односторонность шлюза проверена атакой, двухслойное согласие, счётчики только из событий, «путь без камер» работает.

**Юридика:** 152-ФЗ (ПДн в РФ-контуре, версионированные согласия, каскад отзыва ≤15 мин в публичный контур), 259-ФЗ (граница «интро vs организация сделки» — до юрзаключения фичи фиксации условий, включая финализацию аукциона, работают в режиме «намерение»), 115-ФЗ (AML-скрининг при взносах), 149-ФЗ (рекомендательные технологии), дисклеймеры «платформа — не инвестсоветник», открытые правила и цены на сайте.

## 14. Открытые вопросы (блокирующие помечены)

1. **[BLOCKING, юрист, до Capital]** Граница «интро vs организация сделки» по 259-ФЗ — влияет на финализацию аукциона и allocation.
2. **[Юрист + Product]** Правовой статус аукционной ставки (обязательство/оферта) и нужен ли депозит-эскроу.
3. **[Юрист]** Статус субъекта 115-ФЗ на этапе 1; перечень допустимых LLM по юрисдикционным классам.
4. **[SRE, до Capital]** REPEATABLE READ для платежей и ставок — нагрузочный тест.
5. **[Product]** Норматив нагрузки эксперта при 3000+ заявок; лимиты аукционов в сезон (рекомендация: ≤ 3 одновременно активных, чтобы не размывать дефицит).
6. **[Мобайл]** Решение по push-провайдеру iOS (прямой APNs vs FCM) и стор-стратегия (RU Store / App Store / Google Play ограничения).
