# UNICORN LAUNCH — обзор

## Что это

Первый сервис экосистемы UNICORN: инвестиционная платформа российского
**оператора инвестиционной платформы (ОИП)**. Строится как самостоятельный,
независимо деплоящийся продукт, но каждый внешний шов заранее спроектирован под
подключение [[Unicorn Capital]] и [[Медиаконтур Шоу]].

## Три продукта экосистемы

|        | Unicorn Lab (Launch)                         | Unicorn Capital                             | Реалити-шоу                                   |
| ------ | -------------------------------------------- | ------------------------------------------- | --------------------------------------------- |
| Контур | Закрытый                                     | Закрытый                                    | Публичный (opt-in шлюз)                       |
| Роль   | Находит, оценивает (IRS), выращивает проекты | Инвесторы, листинги, окна, аукционы, сделки | Воронка внимания, бренд                       |
| Данные | Полные, конфиденциальные                     | Полные, конфиденциальные                    | Только явно разрешённая обезличенная проекция |

**Главный архитектурный инвариант:** между закрытым и публичным контурами —
односторонний шлюз. Публикация невозможна без активного opt-in согласия команды
проекта; отзыв согласия действует НЕМЕДЛЕННО — согласие проверяется на
каждый запрос (integration.service.ts), а не сверяется фоновым процессом.
Прежняя формулировка «≤ 15 минут» занижала фактическую гарантию: по ней
готовились бы регуляторные ответы (INFO аудита №2).

## Как выглядит вход для пользователя (с Ф49)

Единая точка входа: витрина, кабинеты и API на одном адресе, без номеров
портов. `/` — витрина с кнопками «Войти» и «Регистрация», `/login/` — вход,
дальше `/lab/`, `/investor/`, `/expert/`, `/admin/` по роли.

Роль при входе НЕ выбирается: кабинет определяется ролями из `/v1/auth/me`.
Самостоятельно выдаются только `founder` и `investor` — эксперта назначает
платформа, иначе рецензент выдал бы себе роль сам.

Витрина остаётся анонимной по построению: форма входа живёт в отдельном
приложении `apps/auth`, а не на публичной странице.

Служебная консоль API (`apps/console`) — только локально. Её код лежит в
репозитории, но публикация выключена тремя независимыми слоями, и неизвестное
значение `APP_ENV` трактуется как боевое.

## Ключевые бизнес-инварианты (не подлежат продуктовому пересмотру)

1. **Два денежных контура не смешиваются.** Инвестиционный principal —
   `investments.*` и номинальный счёт. Выручка платформы — `billing.*`.
   Principal никогда не попадает в `billing.payments`. → [[ADR-005]]
2. **Вознаграждение ОИП: 10% инвестор / 5% ЛПИ от ПОЛНОЙ суммы договора.**
   Начисляется ровно один раз. Триггер составной и неделимый: обе подписи +
   подтверждённый банковским событием первый транш. Последующие транши нового
   начисления не создают и старое не уменьшают.
3. **Акцепт тарифов и условий вознаграждения — блокирующий** для активации
   аккаунта обеих ролей. Не UI-галочка, а сервисный инвариант.
4. **Рейтинг и IRS не продаются.** Публичные счётчики — только из append-only
   журнала с hash-chain.
5. **Fail-closed везде, где речь о доверии.** Нет согласия → не публикуем.
   Юрисдикционный роутинг LLM не подтверждён → hard fail.

## Регуляторная рамка

Инвестиционный контур включается **только после** гейта A: включение юрлица в
реестр ОИП Банка России + согласование Правил платформы + договор с банком по
номинальному счёту + пентест + проверенное восстановление из бэкапа.
До этого — feature flags выключены.

## Технологические решения

- Модульный монолит NestJS + событийное ядро (NATS JetStream + transactional
  outbox) → [[ADR-001]]
- **Фронтенд полностью заменяем**, единственный шов — HTTP `/v1` → [[ADR-002]]
- Проверенный IdP (Keycloak), а не самописный OIDC → [[ADR-003]]
- PostgreSQL 16: 12 доменных схем, 65 таблиц, RLS ENABLE+FORCE везде (число
  сверено прогоном в Ф46; схема content появилась в M048 и до Ф46 не входила
  ни в манифест теста покрытия, ни в эту заметку)

## Локальный стенд (2026-08-11)

Развернуть контур целиком: `node scripts/dev-stand.mjs`, проверить —
`node scripts/check-stand.mjs` (браузер, 23 проверки). Учётные записи по ролям:
`stand-investor`, `stand-founder`, `stand-expert`, `stand-admin`,
`stand-organizer`; пароль общий, из `DEV_TEST_USER_PASSWORD`. Короткое имя
дополняется доменом во ВСЕХ кабинетах.

Смысл разделения: одна учётка со всеми ролями (`ssurgut`) удобна, но на ней не
видно главного свойства платформы — что роли видят разное. Разные учётные
записи показывают именно это.

## Внешние аудиты (2026-08-11)

По проекту прошли два независимых внешних аудита — кибербезопасности и кода.
**20 находок закрыто с доказательствами**, каждая — прогоном, а не рассуждением;
восемь прогонов стали постоянными гейтами (`probe-*`, `check-*`).

Три находки были критическими и все три подтвердились фактом:
подпись сервисных токенов ключом, который в production мог быть пустым;
обход ограничения частоты подделкой cookie (45 попыток входа — 0 отказов);
права PUBLIC на функциях SECURITY DEFINER, включая подтверждение денежного
транша.

**Вердикт аудита «не допускать в production» остаётся в силе** — не из-за
закрытых находок, а из-за нереализованных OIDC-потока и KMS-провайдера. Это
внешние системы, а не код репозитория.

Ответ с таблицей «находка → доказательство»:
`docs/audits/2026-08-11-внешний-аудит-ответ.md`.
