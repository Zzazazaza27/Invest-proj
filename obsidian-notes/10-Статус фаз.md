1. **`INSERT ... RETURNING` падал на RLS.** Возврат строки требует прав на

   ничего не значило. Восстановлен из git; при полном прогоне обнаружились
   13 находок, все устранены.
3. **`parseOrThrow` не отвергал неизвестные поля** вопреки собственному
   комментарию: zod по умолчанию их отбрасывает. Клиент мог прислать
   `requiredPlanId` и не получить отказа — тариф резолвит сервер.
4. **Публичный поиск раскрыл бы описание проекта.** Существующий `search_tsv`
   включает `description`, доступный только по подписке. Заведён отдельный
   вектор по полям тизера; проверено тестом: слово из описания публичным
   поиском не находится.
5. **Фикстуры тестов обходили новые барьеры** — `approveKyc`/`createEntity`
   вставляли «одобрено» без проверяющего. 16 тестов упали сразу после миграции,
   что и было позитивным контролем: триггер работает.
6. **Тесты идут против отдельной БД `unicorn_test`** — миграцию нужно
   применять дважды. Прогон без этого был бы зелёным по неверной причине.
7. **semgrep на Windows падает на кириллице в правилах** без `PYTHONUTF8=1`.
8. **GitHub Actions использовались по подвижным тегам** — закреплены по SHA.

**Не проверялось (честно)**

- `gitleaks` локально не установлен — секрет-скан только в CI.
- Разбор загруженных материалов (`parse_status='queued'`): AI-воркеры — Ф7.

## Ф5 — Биллинг и админский кабинет ✅ 2026-08-10

Подписки, управление тарифами и `apps/admin` — первый фронтенд платформы.
**43 живые проверки бэкенда + проверка кабинета в реальном браузере** (Playwright).

| Гейт                         | Результат                           |
| ---------------------------- | ----------------------------------- |
| Живой прогон `smoke-billing` | **43 проверки, 0 провалено**        |
| Живые прогоны Ф3/Ф4          | 44 + 90 проверок, 0 провалено       |
| Все тесты репозитория        | **187 passed** (было 172)           |
| Тесты БД                     | 84 passed (+7 на M015–M017)         |
| SAST semgrep                 | 513 правил на 143 файлах, 0 находок |
| npm audit / линт / формат    | 0 / exit 0 / чисто                  |
| Сетевая безопасность         | 8 проверок, 0 находок               |

**Главное продуктовое решение.** Цена не редактируется — цена **объявляется**:
администратор публикует новую версию тарифа с датой вступления в силу («с 1-го
числа следующего месяца»), прежняя закрывается ровно этим моментом. Объявление
видно на публичной витрине заранее и может быть отменено до вступления в силу.
Переписать действующую версию нельзя ни через API, ни напрямую в БД (M015/M016).

**Находки фазы — все из прогона**

1. **Денежный лимит 10/мин, распространённый на админские пути, сделал кабинет
   неработоспособным**: 22 провала подряд с 429. Классы разведены — денежный
   только для мутаций, административный отдельный (60/мин).
2. **Ключ ограничения частоты фактически считался по IP**: `keyGenerator`
   читает `request.auth`, которого на этом этапе ещё нет. За одним NAT
   пользователи выбирали лимит друг за друга. Теперь ключ — пара «адрес +
   владелец сессии из cookie», причём cookie используется только как ключ
   ведра, не как подтверждение личности.
3. **Разбор токена в ключе брал не ту часть**: локальный токен — `payload.mac`,
   а не JWT из трёх частей. Все анонимные запросы делили одно ведро.
4. **В браузере вход не работал вовсе**: cookie с префиксом `__Host-` без
   `Secure` браузер молча отбрасывает, а в dev сервер работает по http.
   Скрипты на `fetch` этого не видят — правила префиксов применяет браузер.
   Дефолты имён исправлены, конфигурация теперь падает на такой комбинации.
5. **Схема не допускает «цена назначена, но не утверждена»** — CHECK требует
   обе подписи сразу. Двухшаговое согласование вынесено в отдельную таблицу
   `billing.custom_price_proposals` (M017), утверждение переносит цену в
   подписку одной транзакцией.
6. **Админка ходила на `127.0.0.1`, будучи открытой на `localhost`** — для
   браузера это разные сайты, cookie не отправлялась. Базовый URL теперь
   привязан к текущему хосту.
7. Регрессия от собственной правки: константа использовалась до объявления
   (TDZ) — белый экран. Поймано в браузере, не вычиткой.
8. Широкая таблица распирала страницу: grid-колонка не сжимается без
   `min-width: 0`.

**Не проверялось (честно)**

- Инвойсы и платежи не реализованы: `billing.invoices` требует PDF в хранилище.
- Автопродление и просрочка подписок не работают — нет провайдера.
- Управление контентом витрины в кабинете отсутствует: самой витрины на API ещё нет (Ф10).
- Кабинет проверен в одном браузере (Chromium) и одном разрешении; мобильная
  вёрстка и доступность не тестировались.

## Ф6 — Регулируемые инвестиции ✅ 2026-08-10

Модуль `apps/core/src/investments`: инвестиционные предложения, договоры,
подписи сторон, подтверждение первого транша. Плюс M018 (глаголы событий) и
M019 (область действия ключа идемпотентности).

Контур **выключен фичефлагом** `investments.enabled` и остаётся выключенным
после прогона: маршруты отвечают `503 feature_disabled`. Это состояние
продукта до включения оператора в реестр ОИП, а не незавершённая работа.

**Доказательства:** 191 тест (было 187) + 34 живые проверки регулируемого
контура; регрессия остальных прогонов зелёная (44 + 90 + 43). Гейт: lint 0,
typecheck 0, semgrep 450 правил / 0 находок, npm audit 0, сетевой гейт 8/8,
gitleaks — no leaks, линтер миграций 20 файлов / 0.

**Находки фазы — все из прогона**

1. **Главная: `SET LOCAL ROLE app_investments` не работал и не должен был.**
   `app_backend_user` намеренно не состоит в сервисных группах
   (`bootstrap-roles.ts`), поэтому переключение падало с
   `42501 permission denied to set role`. Первая реализация пыталась пересечь
   ту самую границу, ради которой роли разделены. Решение — отдельное
   подключение под `app_investments_user` (ADR-006), инвариант закреплён тестом
   «логин-роль приложения не состоит в сервисных группах».
2. **`42501` в этом контуре означает две разные вещи**: отказ политики БД и
   бизнес-правило («issuer KYB is not valid» поднимается триггером с тем же
   кодом). Различает их только текст, поэтому KYC/KYB разбираются до общей
   ветки — иначе непройденная проверка юрлица выглядит как поломка прав.
3. **Ключ идемпотентности договора был уникален глобально**: посторонний, заняв
   ключ первым, ронял чужую сделку конфликтом. M019 — уникальность в паре с
   `investor_id`.
4. **Подтверждение транша шло по общему лимиту частоты** (120/мин), хотя
   создаёт начисление вознаграждения. Отнесено к денежному классу (10/мин).
5. **Прерванный прогон оставлял контур включённым**: восстановление флагов было
   последней строкой скрипта. Теперь — `finally`, плюс громкое предупреждение,
   если флаги застали включёнными от прошлого раза. Именно это и произошло:
   первый запуск проверял «контур закрыт» на включённом контуре.
6. **`.semgrep/guardian.yml` во второй раз оказался пустым файлом** (та же
   грабля, что в Ф4). Восстановлен из git до прогона SAST.
7. **Пароль тестовой учётки лежал в коде** — найден SAST'ом
   (`node_password`). Переехал в `DEV_TEST_USER_PASSWORD` в `.env`.
8. **semgrep по умолчанию сканирует только файлы под git** — новый модуль,
   пока он в untracked, в отчёт не попадает, и «0 находок» означает «0 в старом
   коде».

**Не проверялось (честно)**

- Приём предложения и подпись договора через API: оба маршрута требуют step-up
  MFA, локальный адаптер его не выдаёт. Проверен отказ; дальше — фикстурой в БД.
- Автоматическая сверка с выпиской номинального счёта: банк и формат statement
  не утверждены (открытый вопрос №3). Транш заносит оператор.
- Два счёта на сделку не выставляются: `billing.invoices` требует PDF, а
  генератора PDF нет.

## Ф8 — Экспертиза, сезонный рейтинг, уведомления ✅ 2026-08-11

Три модуля core поверх схем M007/M008, которые лежали без прикладного слоя с Ф1:
`experts` (назначения, рецензии, конфликты, консенсус), расширение `seasons`

Плюс две миграции: M020 (verb'ы, обёртка пересчёта рейтинга, шаблоны) и M021

**Три правила, задающие конструкцию экспертизы**

1. Конфликт интересов сильнее назначения — блокирует триггер в БД, а не проверка

2. Рецензия принадлежит эксперту: только своё назначение, только после принятия,
   только один раз.
3. Решение принимает человек. Расхождение считает сервер, но при разбросе выше
   3 баллов из 10 вердикт без третьего рецензента не принимается вовсе.

**Доказательства:** 223 теста (16+35+81+91) + 49 живых проверок. Гейт: lint 0,
typecheck 0, prettier чисто, линтер миграций 0/0, semgrep 11 своих правил и 1330
OWASP — 0 находок, npm audit 0, pip-audit чисто, граница фронт↔бэк 10/10,
сетевой гейт 13/13, rate-limit на новом публичном маршруте — 429 на 119-м

**Находки фазы — обе из живого прогона, ни одной из вычитки**

1. **`ON CONFLICT DO NOTHING` несовместим с постановкой уведомления ЧУЖОМУ
   пользователю при RLS** (см. [[20-Находки и грабли#Г-017]]). Дало HTTP 500 на

   SAVEPOINT.
2. **Назначенный рецензент не видел проект, который рецензирует**: политика
   `projects_select` из M004 эксперта не перечисляет. Экспертиза была
   неработоспособна целиком. Исправлено отдельной permissive-политикой: доступ
   по факту назначения, а не по роли — отказался от рецензии, доступ закрылся.
3. **Событие консенсуса писалось на агрегат `project`** с версией = числу
   рецензий. У проекта своя нумерация версий в `lab`, совпадение тройки
   (агрегат, версия, тип) молча погасило бы одно из двух событий в outbox из-за
   `ON CONFLICT DO NOTHING`. Агрегатом стало само решение.
4. **`.semgrep/guardian.yml` обнулился в третий раз** — прогон SAST был бы
   зелёным на пустом наборе правил. Восстановлен из git ДО прогона.

**Решения фазы**

- Фильтрация по предпочтениям пользователя выполняется НЕ ядром, а контуром
  доставки: чужие предпочтения роли приложения не видны, и это правильно.
  Статус `skipped_by_preference` делает решение «не слать» наблюдаемым.
- Пересчёт рейтинга — явная команда организатора, а не побочный эффект чтения:
  иначе публичная страница рейтинга стала бы способом нагрузить БД чужим
  запросом.
- Полезная нагрузка уведомления проверяется на ПДн и секреты грубым барьером по
  именам ключей: она уходит сторонним провайдерам push и SMS.

**Не проверялось (честно)**

- Доставка уведомлений: контур `app_notifications` появится в своей фазе.
- Фильтрация по предпочтениям — по той же причине.
- `gitleaks` локально не установлен: секрет-скан только в CI.
- Пересчёт рейтинга на синтетическом объёме сезона.

## Ф9 — Integration API и события ✅ 2026-08-11

Дверь для внешних систем и выход событий наружу. Три подфазы, три стоп-коммита:
Ф9a (сервисные клиенты и проекции), Ф9b (публикация в NATS и вебхуки),
Ф9c (управление ролями и описание API).

**Границу держит роль БД, а не аккуратность кода**

Весь интеграционный модуль работает под `app_integration`. У неё нет доступа ни
к схеме `identity`, ни к денежным таблицам биллинга, ни к очереди уведомлений —
проверено семью негативными RLS-тестами и позитивным контролем, что роль вообще
работает. Даже ошибка в SQL этого модуля не вынесет наружу персональные данные:
прав просто нет.

**Доказательства:** 279 тестов (16+35+126+102) + 105 живых проверок фазы
(integration 50, events 30, roles 25). Гейт: lint 0, typecheck 0, prettier
чисто, линтер миграций 0/0, semgrep 11 своих правил и 1330 OWASP — 0 находок,
npm audit 0, сетевой гейт 13/13. Регрессия прежних фаз: core 44/44, lab 90/90,
billing 43/43, investments 34/34, experts 49/49, ai 40/40.

**Находки фазы — все из живого прогона**

1. **SECURITY DEFINER не отменяет USAGE на схему.** Обёртка факта согласия,
   положенная в `identity`, не вызывалась интеграционной ролью вовсе:
   `permission denied for schema identity`. Функция переехала в схему
   `integration` — так роль не получает видимость схемы с ПДн в принципе.
2. **Глобальный AuthGuard съедал сервисный токен.** Он пытался разобрать его
   как токен IdP и отвечал 401 раньше, чем до запроса доходил профильный guard.
   Введена явная схема маршрута `@ServiceAuth()`: это не «публичный», а
   «проверяет другой guard».
3. **`dev-core.mjs` врал об успешном старте** (см. [[20-Находки и грабли#Г-020]]).
   25 «падений» подряд объяснялись тем, что прогон шёл против старой сборки.
4. **`smoke-lab` зависел от глобального состояния сезонов**: сезон в статусе
   `review`, оставленный прогоном Ф8, делал 7 проверок красными не по вине кода.
5. **Правило SAST сработало на `listed.clientSecret === undefined`.** Формально
   ложная находка, но правило право по букве: проверка переписана на отсутствие
   ключа (`!('clientSecret' in listed)`) — так честнее и по смыслу.

**Решения фазы**

- Паспорт наружу отдаётся, только если опубликованный уровень раскрытия НЕ ВЫШЕ
  запрошенного. Урезать содержимое на лету сервер не умеет и не делает вид.
- Момент выпуска проекта проставляет триггер, а не сервис: точка отсчёта
  синхронизации внешних систем не зависит от пути кода.
- Учётные данные NATS вынесены из URL: пароль внутри адреса попадает в логи
  подключения и в тексты ошибок как есть.
- Секрет подписи вебхука шифруется напрямую ключом своего KEK-домена: схема
  таблицы держит один шифртекст, а ротация нескольких строк дешевле, чем
  размазывать формат по колонкам.
- Агрегаты вознаграждения в `/deals` не вошли осознанно: они лежат в таблицах
  роли `app_billing`, и расширять права интеграции ради них означало бы сломать
  ровно ту границу, ради которой роли разделены.

**Не проверялось (честно)**

- Реальная интеграция с Capital: события забирает собственный тестовый
  потребитель, а не внешняя система.
- mTLS: заголовок от терминирующего прокси, самого прокси в dev нет. В
  production пустое имя заголовка не проходит валидацию конфигурации.
- `gitleaks` локально не установлен: секрет-скан только в CI.
- Описание API содержит типы, но не перечень маршрутов — неполнота объявлена
  в самом документе.

## Ф10a — Дизайн-система и живая витрина ✅ 2026-08-11

Первая подфаза фронтендов. `packages/ui` (токены + примитивы) и публичная
витрина, переписанная с макета на реальные данные.

**Что было и что стало**

Витрина была статическим макетом на JSX с захардкоженными «проектами»
(NeuroMind AI, CourseAI, DesignHub…) и ценами, которых нет в системе. Это ровно
тот случай, который запрещён правилами: сгенерированное выдавалось за
подтверждённое. Теперь она ходит в API и показывает то, что платформа реально
отдаёт анониму: тизеры каталога, тарифы с объявленными изменениями цен,
обязательное раскрытие условий вознаграждения и метроном сезона.

**Находки — обе из реального рендера, ни одной из вычитки**

1. **`api-client` расходился с сервером в трёх методах.** `taxonomy`,
   `currentSeason` и `rating` ждали голые данные, а сервер отдаёт конверт
   (`{items}`, `{season}`). Методы падали при каждом вызове — и это никем не
   замечалось два года условного времени, потому что фронтенда, который их
   вызывает, не существовало. Пакет, созданный ровно для того, чтобы ловить
   расхождение с контрактом, сам расходился с ним. Закрыто прогоном
   `smoke-api-client.mjs`: каждый публичный метод вызывается против живого API.
2. **CORS-allowlist знал только `localhost`,** а vite поднимает витрину на
   `127.0.0.1`. Для браузера это разные сайты — витрина не получала ни одного
   ответа. В dev в списке теперь оба имени.

Отдельно: скриншот показал «Сейчас активного сезона нет» при открытом сезоне —
мой же `.catch(() => null)` превратил ошибку схемы в «данных нет». Убрано:
недоступный сервер и отсутствие сезона — разные ответы.

**Доказательства:** 279 тестов + 13 проверок в реальном браузере (обычная
загрузка, мобильная ширина 390px, оборванная сеть) + 9 проверок клиента против
живого API. Гейты: lint 0, typecheck 0 (6 воркспейсов), prettier чисто,
semgrep 11 своих правил и 1330 OWASP — 0 находок, npm audit 0 (playwright
закреплён), граница фронт↔бэк 10/10, сетевой гейт 13/13.

**Решения**

- Состояния экрана вынесены в примитивы (`LoadingState`, `EmptyState`,
  `ErrorState`, `OfflineBanner`): пустой экран без объяснения читается как
  поломка, а ошибка без действия восстановления оставляет в тупике.
- Тема следует системной настройке, фокус видимый, цель нажатия 44px,
  `prefers-reduced-motion` уважается — это проверяется рендером, а не обещанием.
- Цена `null` показывается как «Индивидуально», а не «0 ₽»: второе —
  дезинформация о стоимости.

**Не проверялось (честно)**

- Кабинеты основателя, инвестора и эксперта не написаны — Ф10b–d.
- Админский кабинет на новые примитивы не переведён.
- Скринридером интерфейс не тестировался: проверены только машинные признаки
  доступности (подписи, один h1, skip-link, отсутствие горизонтальной прокрутки).

## Ф10b — Кабинет основателя ✅ 2026-08-11

`apps/lab` на 5175: вход, список своих проектов, подача заявки, карточка
проекта с действиями (подать в сезон, запустить анализ, опубликовать/снять
листинг), инвестиционный паспорт и карта готовности.

**Находка фазы — снова расхождение клиента с сервером**

`GET /v1/projects` отдаёт `{items: ProjectSummary[]}` без пагинации, а
`api-client` ждал страницу полных карточек (`pageResponseSchema(ProjectFull)`).
Метод падал на разборе ответа — кабинет показывал «Ответ сервера не
соответствует контракту API» вместо списка. Это ТРЕТЬЕ такое расхождение за две

представлению о контракте, а не по фактическому поведению сервера.

Прав оказался сервер: список своих проектов у одного основателя — единицы
записей, курсор здесь усложнение без пользы. Клиент приведён к нему.

Вход настоящей учётной записью, отказ при неверном пароле, пустое состояние со
словами вместо пустоты, создание заявки, открытие карточки, отказ публикации

- Ни одна кнопка не «предсказывает» ответ сервера: условия публикации листинга

- Ошибки полей формы показываются у самих полей — сервер отдаёт их списком.
- 401/403/404 в консоли браузера исключены из проверки «ошибок нет»: сценарий
  намеренно вызывает доменные отказы, и считать их дефектом интерфейса значит
  запрещать приложению корректно их обрабатывать.

**Не проверялось (честно)**

- Загрузка материалов и ссылка на продукт: экранов нет, маршруты сервера есть.
- Роадмап в интерфейс не выведен.
- Полный путь «подача → анализ → листинг» не пройден до конца: нужен KYC и
  активная подписка, которых у тестовой учётной записи нет.
