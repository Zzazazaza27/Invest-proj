# UNICORN LAUNCH

Инвестиционная платформа российского **оператора инвестиционной платформы (ОИП)**.
Основатели (ЛПИ) размещают проекты и инвестиционные предложения, получают
AI-анализ и развитие; верифицированные инвесторы по подписке смотрят полные
карточки и заключают договоры инвестирования средствами платформы. Движение
инвестиционных средств учитывается через номинальный счёт ОИП.

Источники правды: [`Architect_Launch.md`](./Architect_Launch.md) (архитектура),
[`Database_Launch.md`](./Database_Launch.md) (схема БД),
[`RULES.md`](./RULES.md) (метод работы), [`Architect.md`](./Architect.md) и
[`Database.md`](./Database.md) (целевая экосистема — швы под Unicorn Capital и
медиаконтур Шоу).

> **Статус реализации: все фазы Ф0–Ф11 завершены.** Работает ядро API:
> регистрация с блокирующим акцептом условий, вход, публичные тарифы,
> верификация участников и юрлиц (KYC/KYB), проекты и версии заявок, подписанная
> загрузка материалов, публикация листингов и публичный каталог с поиском,
> подписки, **административный кабинет** (`apps/admin`) с управлением тарифами,
> персональными ценами и функциями платформы, а также **регулируемое ядро ОИП**
> (предложения, договоры, транши, начисление вознаграждения) — реализованное и
> проверенное, но выключенное фичефлагом до гейта A, **AI-контур**: шлюз с
> юрисдикционным роутингом, разбор заявки, скоринг по 9 осям, IRS, карта
> готовности и роадмап, и **экспертный контур**: назначения рецензентов,
> рецензии по рубрике, конфликты интересов, консенсус с человеком в решении,
> сезонный рейтинг с золотыми билетами и очередь уведомлений. С Ф9 работает
> **интеграционный контур**: Integration API для внешних систем под
> собственной ролью БД, публикация событий в NATS JetStream через
> transactional outbox, вебхуки с подписью и защитой от SSRF, управление
> ролями через API и машиночитаемое описание типов. С Ф10 работают **пять
> фронтендов**: публичная витрина и кабинеты основателя, инвестора, эксперта и
> администратора — все на общей дизайн-системе, все проверены в реальном
> браузере.
> 358 тестов плюс **более 600 живых проверок** против запущенных сервисов, из
> них 91 — в реальном браузере (витрина и четыре кабинета) и 90 — зонды
> безопасности, воспроизводящие конкретные атаки (обход ограничения частоты,
> DNS rebinding, подстановка чужого CSRF-токена, отзыв прав, предъявление
> скопированного токена после выхода, работа по токену приостановленной
> интеграции, бессрочная блокировка адреса залипшим счётчиком, удвоение
> разрешённой частоты вторым экземпляром, брошенный объект в хранилище).
> Все двенадцать фаз плана закрыты; проект остаётся в состоянии «до гейта A» —
> инвестиционный контур выключен фичефлагом до включения оператора в реестр
> Банка России, и это состояние продукта, а не незавершённая работа.
> По проекту прошли два независимых внешних аудита (безопасность и код):
> 20 находок закрыто с доказательствами, ответ — в
> [`docs/audits/2026-08-11-внешний-аудит-ответ.md`](./docs/audits/2026-08-11-внешний-аудит-ответ.md).
> Вердикт «не допускать в production» остаётся в силе: OIDC-поток и KMS-провайдер
> не реализованы, и это требует внешних систем, а не кода в этом репозитории.
> Что уже проверено прогоном инструмента, а что ещё нет — в
> [`TODO.md`](./TODO.md) и [`docs/audits/`](./docs/audits/). Ничего не
> помечается готовым без вывода команды из текущей сессии.

## Главный принцип структуры: фронтенд заменяем

Фронтенд **полностью отделён** от бэкенда и заменяем целиком или по частям.
Единственный шов — HTTP `/v1` и пакет `@unicorn/api-client`, типы которого
выведены из `@unicorn/contracts`. Подробности и инструкция по замене —
[ADR-002](./docs/architecture/ADR-002-replaceable-frontend.md) и
[`docs/frontend-replacement-guide.md`](./docs/frontend-replacement-guide.md).

Граница не на словах: импорт бэкенда во фронтенд роняет `npm run lint` и SAST,
а не всплывает в ревью.

```
Фронтенды (5 независимых SPA)  ──HTTP /v1──►  apps/core (NestJS)  ──►  PostgreSQL 16
      │                                             │                   NATS JetStream
      └── зависят только от:                        └── не знает про React,
          @unicorn/contracts                            не рендерит HTML
          @unicorn/api-client
          @unicorn/ui
```

## Быстрый старт

Требуется: Node.js ≥ 22, Docker, Git.

```bash
cp .env.example .env          # заполнить CHANGE_ME
npm install
npm run infra:up              # PostgreSQL 16 + Redis + NATS JetStream + MinIO (+ бакет)
npm run db:migrate            # миграции M000–M043
npm run db:seed               # сезон, таксономия, тарифы, fee schedule, шаблоны
npm run bootstrap:roles -w database   # логин-роли БД из переменных окружения
```

Тестовая база мигрируется отдельно — интеграционные тесты работают против неё:

```bash
NODE_ENV=test npm run db:migrate
```

Между живыми прогонами нужна пауза в минуту: ведро класса auth считается по
адресу (подделка cookie не должна давать новый лимит), поэтому все локальные
прогоны делят одно окно. `security-audit-full.mjs` выдерживает паузы сам.
Счётчик теперь общий (Redis), поэтому перезапуск ядра окно НЕ обнуляет —
сбросить вёдра локально можно только руками:
`docker exec unicorn-redis redis-cli -a "$REDIS_PASSWORD" FLUSHDB`.

Запуск ядра и живая проверка:

AI-шлюз — отдельный процесс на Python; окружение ставится один раз:

```bash
python -m venv apps/ai-gateway/.venv
apps/ai-gateway/.venv/Scripts/python -m pip install -r apps/ai-gateway/requirements-dev.txt
```

Прогоны обращаются к `/v1/auth/register`, у которого лимит 30 запросов в минуту.
Запущенные подряд, они упираются в 429 — это работающая защита, а не сбой:
между прогонами нужна минута.

Регулируемый контур ходит в базу под **своей** логин-ролью
(`DATABASE_URL_APP_INVESTMENTS`): роль приложения не состоит в группе
`app_investments` и переключиться в неё не может — см.
[ADR-006](./docs/architecture/ADR-006-service-role-connections.md).

Административный кабинет:

```bash
node scripts/dev-make-admin.mjs you@example.com --create   # первый администратор
npm run build -w apps/admin && npm run preview -w apps/admin   # http://localhost:5174
```

Открывать кабинет нужно по тому же имени хоста, на котором доступен API
(`localhost` ↔ `localhost`): для браузера `localhost` и `127.0.0.1` — разные
сайты, и сессионная cookie на «чужой» адрес не отправляется.

Поднять IdP (Keycloak) отдельно, когда нужен реальный OIDC-поток:

```bash
docker compose -f infra/docker-compose.yml --profile idp up -d keycloak
```

| Сервис         | Адрес                                                         |
| -------------- | ------------------------------------------------------------- |

Все порты биндятся на `127.0.0.1` — контейнеры не выставлены в сеть.

## Локальный стенд

Полный контур на одной машине с учётными записями по ролям — чтобы пройти
платформу глазами каждого участника, а не одной учёткой со всеми правами.

```bash
# 1. Инфраструктура и данные
npm run infra:up && npm run db:migrate && npm run db:seed

# 2. Сервисы
npm run build -w apps/core && node scripts/dev-core.mjs --detached   # API на 4300
node scripts/dev-ai-gateway.mjs --detached                            # AI-шлюз на 8100
npm run dev -w apps/web-public   # витрина 5173
npm run dev -w apps/admin        # админка 5174
npm run dev -w apps/lab          # кабинет основателя 5175
npm run dev -w apps/investor     # кабинет инвестора 5176
npm run dev -w apps/expert       # кабинет эксперта 5177

# 3. Учётные записи и демонстрационные данные (идемпотентно)
node scripts/dev-stand.mjs

# 4. Проверка, что стенд действительно работает (браузер, 23 проверки)
node scripts/check-stand.mjs
```

Учётные записи стенда (пароль общий, берётся из `DEV_TEST_USER_PASSWORD` в
`.env`; в поле входа достаточно короткого имени — домен подставляется):

| Логин             | Роль           | Кабинет                |
| ----------------- | -------------- | ---------------------- |
| `stand-investor`  | инвестор       | http://127.0.0.1:5176/ |
| `stand-founder`   | основатель     | http://127.0.0.1:5175/ |
| `stand-expert`    | эксперт        | http://127.0.0.1:5177/ |
| `stand-admin`     | администратор  | http://127.0.0.1:5174/ |
| `stand-organizer` | организатор    | http://127.0.0.1:5174/ |
| `ssurgut`         | все роли сразу | любой кабинет          |

Что уже подготовлено: сезон с открытым приёмом заявок и квотами воронки,
опубликованный проект основателя с материалами и версией заявки, активная
подписка инвестора, назначение эксперта на рецензию, одобренная верификация
основателя и инвестора.

Стенд разворачивается только вне production: скрипт отказывается работать при
`NODE_ENV=production`, а учётные записи удаляются перед выходом в прод
(см. `TODO.md`).

## Гейты качества

Ни одна фаза не считается завершённой без прогона. Команды:

```bash
npm run lint                        # ESLint + граница «фронт ↔ бэк»
npm run typecheck                   # TypeScript strict
npm run test                        # юнит + интеграционные + негативные RLS
npm run lint:migrations -w database # expand/contract, RLS, search_path, деньги-float
npm run gate:deps                   # npm audit --audit-level=high
npm run gate:secrets                # gitleaks — вся история коммитов (ожидание: 0)
node scripts/security-audit-full.mjs # ВСЕ гейты подряд на одной сборке (~25 мин)
npm run gate:boundary               # граница фронт↔бэк работает (позитивный контроль)
npm run gate:ai                     # тесты AI-шлюза + pip-audit
npm run gate:net                    # сетевая безопасность (RULES.md §3.2)
npm run gate                        # всё перечисленное подряд
```

Сетевой гейт (`scripts/network-audit.mjs`) проверяет **фактическое состояние**:
реальные привязки портов контейнеров, реальные заголовки ответа API, реальное
поведение CORS с чужим Origin. Ссылка на конфиг доказательством не считается.
Порядок прогона и разбор находок — [`docs/runbooks/security-gates.md`](./docs/runbooks/security-gates.md).

SAST (semgrep с правилами `.semgrep/guardian.yml` + OWASP) и секрет-скан
прогоняются в CI на каждый push и PR: [`.github/workflows/ci.yml`](./.github/workflows/ci.yml).
Там же с этой фазы прогоняются постоянные гейты прав — границы сервисных ролей
БД и права PUBLIC на функциях SECURITY DEFINER — и статическая часть сетевого
гейта. До этого они запускались руками, то есть не запускались на каждом
изменении: расширить права сервисной роли можно было незаметно для CI.
Локальный прогон semgrep на Windows требует `PYTHONUTF8=1` — иначе он падает на
кириллице внутри правил, и «нет вывода» легко принять за «нет находок».

### Граф проекта

Граф кода перестраивается после каждой фазы командой `/graphify` и лежит в
`graphify-out/` (в репозиторий не коммитится — это производный артефакт).
Последний прогон: 3330 узлов, 5982 связи, 322 сообщества. Связи извлекаются
структурно (AST); семантический слой по документам пересобирается отдельно.

Извлечение выполняется ПОСЛЕДОВАТЕЛЬНО: параллельный обход возвращал ноль узлов
для 174 файлов, и граф терял треть содержимого. Поймала это встроенная защита
graphify, отказавшись перезаписывать граф меньшим.

## Что уже отвечает по HTTP

Всё под `/v1`. Маршрут без пометки «публичный» требует сессии: guard включён
глобально, анонимный доступ открывается только явным декоратором.

| Метод и путь                                    | Доступ               | Назначение                                                |
| ----------------------------------------------- | -------------------- | --------------------------------------------------------- |
| `GET /health`                                   | публичный            | Живость сервиса и БД                                      |
| `GET /pricing`                                  | публичный            | Тарифы и условия вознаграждения ОИП                       |
| `GET /taxonomy`                                 | публичный            | Справочник направлений                                    |
| `GET /catalog`                                  | публичный            | Каталог тизеров: поиск, фильтры, keyset-курсор            |
| `GET /catalog/:id`                              | публичный            | Тизер листинга                                            |
| `GET /seasons/current`                          | публичный            | Метроном сезона                                           |
| `POST /auth/register` · `/login`                | публичный            | Регистрация с блокирующим акцептом, вход                  |
| `GET /auth/me` · `POST /auth/consents`          | сессия               | Профиль, ре-акцепт условий                                |

Поверх классовых вёдер работает **потолок по адресу**. Ключ ведра для
аутентифицированных классов включает подсказку сессии из cookie, а она читается
до проверки подписи: подставив произвольный `sub`, клиент получал новое ведро на
каждый запрос. Полностью закрыть это ключом по адресу нельзя — денежный лимит
10/мин, общий на адрес, наказывал бы нескольких реальных пользователей за одним
NAT. Потолок считает все запросы с адреса в одно ведро с высоким порогом и
останавливает именно шторм: проверено прогоном — 600 запросов с разными
поддельными cookie проходили, 601-й получил 429.

Ограничение частоты считается в общем счётчике (Redis), а не в памяти
процесса. Разница не косметическая: при счётчиках в памяти два экземпляра ядра
считают свои запросы независимо, то есть фактически разрешённая частота
умножается на их число, а перезапуск обнуляет её целиком. Проверено прогоном на
двух экземплярах: лимит, исчерпанный на первом, действует на втором, и
перезапуск счётчик не обнуляет; без общего счётчика второй экземпляр отвечал
401 вместо 429 — то есть давал вторую порцию попыток. Недоступный счётчик
означает отказ, а не снятие защиты: `skipOnError: false` выбран сознательно —
уронить счётчик и получить неограниченный перебор паролей не должно быть
дешевле, чем уронить платформу.

Токен разбирается строго. Идентификатор пользователя обязан быть UUID — он
уходит в `app.current_user_id`, на котором построены все политики RLS, и
произвольная строка превращалась там в ошибку приведения типа уже внутри
запроса. Роли из токена проходят через allowlist: неизвестное имя роли
отбрасывается, иначе значение claim'а становилось бы частью выражения любой
будущей политики `app.has_role(...)`. Признак второго фактора тоже allowlist —
`pwd` или `mfa`, прочее приравнивается к его отсутствию.

Поверхность для разведки сведена к минимуму. Заголовки `x-ratelimit-*` наружу
не выдаются: они сообщают точный порог и остаток по каждому классу операций, то
есть позволяют подобрать темп перебора, оставаясь под лимитом. На отказе
остаётся `retry-after` — сколько ждать, клиент узнаёт тогда, когда это ему
действительно нужно. Машиночитаемое описание API в production отдаётся только
по сессии и отвечает 404, а не 403: 403 подтвердил бы, что документ существует.
Вне production оно открыто — там оно нужно разработке и живым прогонам.

Журнал событий выгружается в холодное хранилище отдельной процедурой
(`scripts/archive-events.mjs`), а не задачей ядра: выгрузка требует доступа ко
всему журналу, и такого права у приложения нет. Процедура только **копирует** —
удалять события она не умеет вовсе, потому что срок хранения журнала оператора
определяется законом, а не удобством эксплуатации. Перед выгрузкой сверяется
hash-chain, после — объект читается обратно и его отпечаток сверяется с
записанным в реестр `audit.event_archives`. Если объект прошлой выгрузки исчез
из хранилища, следующий прогон восстановит его из журнала и потребует
совпадения отпечатка байт в байт: расхождение означало бы, что append-only
журнал изменился, и прогон падает вместо перезаписи.

Материалы проекта убираются за собой. Билет на загрузку выдаётся вместе со
строкой материала, но загрузка может не состояться: с M037 такой материал
наружу не выдаётся, а с M039 — ещё и не остаётся навсегда. Плановое
обслуживание убирает брошенные билеты старше суток вместе с объектом в
хранилище; порядок — сначала объект, потом строка, потому что при обратном
падение между шагами оставляет объект, который уже нечем найти. Уборку
выполняет отдельная роль БД `app_maintenance`, которая не видит ни проектов, ни
пользователей, ни подтверждённых материалов: это ограничено политиками, а не
аккуратностью кода.

Выход и отзыв сессий устроены двумя разными механизмами, потому что отвечают
на разные вопросы. **Рубеж сессий** (`identity.users.sessions_valid_from`)
обесценивает ВСЕ токены пользователя разом — им закрываются изменение прав и
компрометация аккаунта: снятая роль перестаёт действовать сразу, а не по
истечении токена. **Реестр отозванных токенов** (`identity.revoked_tokens`)
закрывает одну конкретную сессию по идентификатору `jti`: выход на одном
устройстве не роняет остальные, а скопированное значение cookie перестаёт
работать в момент выхода, а не через час. Удаления cookie для этого
недостаточно — оно действует только на клиента. Проверка идёт снимком реестра с
окном в пять секунд: на своём экземпляре отзыв мгновенный, на остальных — не
позже окна; величина названа числом, а не спрятана в «примерно сразу». Записи
об истёкших токенах убирает плановое обслуживание, и права на удаление есть
только у сервисной роли уборки.

Публикация листинга требует одновременно: действующего KYC владельца, тарифа,
соответствующего текущему `investment_ask`, и активной подписки этого тарифа.
Тариф резолвит **сервер** — клиент не может ни выбрать его, ни удержать после
роста запроса инвестиций.

### Изменение тарифов

Цена действующего тарифа **не редактируется** — публикуется новая версия с
датой вступления в силу («с 1-го числа следующего месяца»). Прежняя версия
закрывается ровно этим моментом и остаётся в истории; подписки, оформленные
раньше, продолжают действовать по своей цене. Объявление видно на публичной
витрине (`announcedPlans` в `GET /v1/pricing`) и может быть отменено или
изменено, пока не вступило в силу. Переписать уже действующую версию нельзя ни
через API, ни напрямую в базе — это запрещено триггером (ADR-005).

Экспертиза устроена так, что оценку невозможно получить в обход процедуры:
рецензию пишет только назначенный эксперт и только по принятому назначению;
заявленный и неразрешённый конфликт интересов блокирует назначение на уровне
БД; финальное решение по проекту фиксирует человек своим идентификатором из
сессии, а при расхождении оценок рецензентов выше 3 баллов из 10 решение без
третьего рецензента не принимается вовсе. Доступ рецензента к проекту даётся
фактом назначения, а не ролью: отказался от рецензии — доступ закрылся.

Уведомления ядро только ставит в очередь — в одной транзакции с доменным
фактом. Отправляет их отдельный контур под своей ролью БД; он же решает, не
слать ли из-за настроек пользователя, и помечает это статусом
`skipped_by_preference`. Уведомления о безопасности и платежах отключить
нельзя ни через API, ни напрямую в базе. Персональные данные в очередь не
попадают: полезная нагрузка проходит через сторонних провайдеров push и SMS.

Integration API — единственная дверь для внешних систем (Unicorn Capital,
медиаконтур Шоу): прямого доступа к чужой БД не предусмотрено ни в каком виде.
Он работает под собственной ролью БД `app_integration`, у которой нет доступа
ни к схеме `identity`, ни к денежным таблицам биллинга, ни к очереди
уведомлений — поэтому даже ошибка в SQL этого модуля не вынесет наружу
персональные данные. Права выражены скоупами, а не ролями; маршрут без явно
объявленного скоупа guard отклоняет. Токен клиента живёт 15 минут: сервисный
клиент нельзя «разлогинить», и короткий срок — единственная работающая защита
от утёкшего токена. Обезличенная проекция для медиаконтура проверяет согласие
на КАЖДЫЙ запрос: отзыв убирает её немедленно, тем же токеном.

События уходят наружу через transactional outbox: доменная операция пишет факт
и событие одной транзакцией, а публикатор отправляет его в NATS JetStream и
помечает опубликованным **только после подтверждения брокером**. Повтор после
сбоя не создаёт второго сообщения — дедупликация по `msgID` на стороне стрима.
Подписчики получают доставку с подписью `t=<unixtime>,v1=<hmac>`: метка времени
входит в подписываемую строку, поэтому перехваченную доставку нельзя переиграть
позже. Адрес вебхука проходит три независимых барьера — схему запроса, CHECK в
БД и проверку резолва **перед каждой** доставкой: имя, безопасное при
регистрации, может начать указывать во внутреннюю сеть (DNS rebinding).

Файлы материалов идут в объектное хранилище **напрямую** по подписанной форме
(POST policy SigV4): условия подписи фиксируют точный ключ, Content-Type и
диапазон размера, поэтому лимит обеспечивает хранилище, а не доверие к клиенту.

### Вознаграждение ОИП за сделку

Инвестор — **10%**, ЛПИ — **5%** от **полной суммы подписанного договора**.

первый транш подтверждён банковским событием номинального счёта. Последующие
транши нового начисления не создают и уже возникшее обязательство не уменьшают.
Инвариант и его технические гарантии —
[ADR-005](./docs/architecture/ADR-005-two-money-contours.md).

**блокирующий для активации аккаунта** обеих ролей.

## AI-контур

Оценку считает **не языковая модель**, а воспроизводимая эвристика
`v0.1-heuristic` внутри российского контура. Это baseline: будущая LLM обязана
показать улучшение относительно него, иначе подключать её незачем. Ответ
API честно помечен `isLlm: false` — выдавать одно за другое нельзя.

Что удерживает контур:

- **юрисдикционный роутинг с hard fail**: класс данных `pdn` или
  `commercial_secret` провайдеру вне РФ не отдаётся никогда — 403 и запись в
  журнал, а не выбор другого провайдера;
- **недоверенный текст заявки — только данные**: он не попадает в инструкции и
  не может изменить ни провайдера, ни класс данных; попытка фиксируется;
- **у шлюза нет доступа ни к БД, ни к хранилищу, ни к сессиям** — он получает
  задачу и возвращает результат;
- **прогон всегда оставляет след** в `audit.agent_runs`: и успешный, и упавший;
- **история паспортов не переписывается** — новая версия помечает предыдущую
  устаревшей, поэтому оценки моделей есть с чем сравнивать.

Содержимое дек и внешних ссылок не разбирается: парсера нет, а ходить по
пользовательской ссылке сервером — это SSRF. В анализ попадают текст заявки и
факт наличия материала. Подробности — [ADR-007](./docs/architecture/ADR-007-ai-contour.md).

## Регуляторная рамка

Инвестиционный контур включается **только после** включения российского
юридического лица в реестр ОИП Банка России и согласования Правил
инвестиционной платформы (гейт A, `Architect_Launch.md` §9). До этого момента
соответствующая функциональность закрыта feature flag'ами. Способы
инвестирования (`instrument_type`) — серверный allowlist, а не свободный
параметр клиента.

Контур **реализован и проверен живым прогоном**, но флаг `investments.enabled`
выключен: маршруты отвечают `503 feature_disabled`. Это состояние продукта, а не
незавершённая работа. Каждый способ инвестирования включается отдельным флагом
(`investments.instrument.*`), и все они тоже выключены.

Что удерживает контур помимо флага:

- первый транш подтверждается только банковским событием номинального счёта —
  клиентским запросом это невозможно ни при какой роли;
- начисление вознаграждения создаёт команда БД `billing.confirm_first_tranche` в
  одной транзакции с переходом договора в силу, `UNIQUE(agreement_id)` исключает
  повторное начисление, повторная доставка того же события возвращает прежний
  результат;
- принятие предложения и подписание договора требуют подтверждения вторым
  фактором (`step_up_required`);
- предложение размещает только владелец проекта и только от юрлица с
  действующим KYB; публикует его комплаенс, а не ЛПИ;
- ключ идемпотентности принадлежит инвестору: чужой ключ не блокирует сделку и
  не работает как оракул существования договора.
