## Главный принцип структуры: фронтенд заменяем

Фронтенд **полностью отделён** от бэкенда и заменяем целиком или по частям.
Единственный шов — HTTP `/v1` и пакет `@fifth/api-client`, типы которого
выведены из `@fifth/contracts`. Подробности и инструкция по замене —
[ADR-002](./docs/architecture/ADR-002-replaceable-frontend.md) и
[`docs/frontend-replacement-guide.md`](./docs/frontend-replacement-guide.md).

Граница не на словах: импорт бэкенда во фронтенд роняет `npm run lint` и SAST,
а не всплывает в ревью.

```
Фронтенды (6 независимых SPA)  ──HTTP /v1──►  apps/core (NestJS)  ──►  PostgreSQL 16
      │                                             │                   NATS JetStream
      └── зависят только от:                        └── не знает про React,
          @fifth/contracts                            не рендерит HTML
          @fifth/api-client
          @fifth/ui
```

## Быстрый старт

Требуется: Node.js ≥ 22, Docker, Git.

```bash
cp .env.example .env          # заполнить CHANGE_ME
npm install
npm run infra:up              # PostgreSQL 16 + Redis + NATS JetStream + MinIO (+ бакет)
npm run infra:mail-up         # локальный почтовый приёмник mailpit (нужен только прогону почты)
npm run db:migrate            # миграции M000–M150
# Справочники (таксономия, шаблоны документов и уведомлений) заводят
# миграции, а не отдельная команда: они применяются тем же db:migrate и
# потому не могут разойтись со схемой.
npm run bootstrap:roles -w database   # логин-роли БД из переменных окружения
```

Тестовая база мигрируется отдельно — интеграционные тесты работают против неё:

```bash
NODE_ENV=test npm run db:migrate
```

Между живыми прогонами нужна пауза в минуту: ведро класса auth считается по
адресу (подделка cookie не должна давать новый лимит), поэтому все локальные
прогоны делят одно окно. `security-audit-full.mjs` выдерживает паузы сам.
Счётчик теперь общий (Valkey), поэтому перезапуск ядра окно НЕ обнуляет —
сбросить вёдра локально можно только руками:
`docker exec unicorn-valkey valkey-cli -a "$REDIS_PASSWORD" FLUSHDB`.

Прогоны обращаются к `/v1/auth/register`, у которого лимит 30 запросов в минуту.
Запущенные подряд, они упираются в 429 — это работающая защита, а не сбой:
между прогонами нужна минута.

Административный кабинет:

```bash
node scripts/dev-make-admin.mjs you@example.com --create   # первый администратор
npm run build -w apps/admin && npm run preview -w apps/admin   # http://localhost:5174
```

Открывать кабинет нужно по тому же имени хоста, на котором доступен API
(`localhost` ↔ `localhost`): для браузера `localhost` и `127.0.0.1` — разные
сайты, и сессионная cookie на «чужой» адрес не отправляется.

Поднять IdP (Keycloak) отдельно, когда нужен реальный OIDC-поток:

```bash
docker compose -f infra/docker-compose.yml --profile idp up -d keycloak
```

### Порты локального контура

| Сервис         | Адрес                                                              |
| -------------- | ------------------------------------------------------------------ |
| Core API       | http://localhost:4300/v1                                           |
| PostgreSQL     | 127.0.0.1:5433 (`fifth_element`, `fifth_element_test`, `keycloak`) |
| Redis          | 127.0.0.1:6380 (общий счётчик ограничения частоты)                 |
| NATS JetStream | 127.0.0.1:4222 (мониторинг 8222)                                   |
| MinIO          | http://localhost:9000 (консоль 9001)                               |
| Keycloak       | http://localhost:8081 (профиль `idp`)                              |
| Mailpit        | http://localhost:8025 (профиль `idp`/`full`)                       |

Все порты биндятся на `127.0.0.1` — контейнеры не выставлены в сеть.

### Единая точка входа

Пользователь не видит номеров портов: витрина, кабинеты и API раздаются с
одного адреса обратным прокси (nginx, профиль `web` в compose).

```bash
npm run build            # собрать все фронтенды: прокси раздаёт dist, а не dev-серверы
npm run web:up           # поднять единую точку входа
npm run web:down         # остановить
```

| Адрес                        | Что                                     |
| ---------------------------- | --------------------------------------- |
| `http://127.0.0.1/`          | витрина, кнопки «Войти» и «Регистрация» |
| `http://127.0.0.1/login/`    | вход и регистрация (`apps/auth`)        |
| `http://127.0.0.1/lab/`      | кабинет основателя                      |
| `http://127.0.0.1/investor/` | кабинет инвестора                       |
| `http://127.0.0.1/admin/`    | админка                                 |
| `http://127.0.0.1/v1/…`      | API ядра                                |
| `http://127.0.0.1/console/`  | служебная консоль — **только локально** |

Единый origin — не только косметика: список разрешённых origin в CORS
перестаёт быть нужен, становится возможна cookie с префиксом `__Host-`, а
CSRF-схема упрощается до одного сайта.

#### Служебная консоль не уезжает в боевой контур

Код консоли лежит в репозитории и попадёт на сервер вместе с ним — это
неизбежно. Не должна попасть **публикация**, и она выключена тремя
независимыми способами; достаточно любого одного:

| Что выключено | Где                                                                                                                                         |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| сборка        | `npm run build` не собирает консоль — для неё отдельная команда `npm run build:console`                                                     |
| маршрут       | `location /console/` объявлен только в `infra/nginx/local/console.conf`, который подключается шаблоном `include /etc/nginx/local/*.conf`    |
| монтирование  | каталог подключает лишь `infra/docker-compose.local.yml`, а его добавляет `scripts/infra.mjs` — только когда `APP_ENV`/`NODE_ENV` не боевые |

Неизвестное значение переменной считается боевым: забытая настройка не должна
открывать наружу то, что открывать не собирались.

```bash
npm run gate:console-private   # три защиты плюс фактический ответ /console/
```

Проверено фактом: при `APP_ENV=production` адрес `/console/` отдаёт витрину, а
не консоль. Гейт проверен на падение — с возвращённой в `build` консолью даёт
exit 1.

Локально консоль открыта и по единому адресу (`http://127.0.0.1/console/`), и
напрямую (`http://127.0.0.1:5178/console/`).

Кабинеты собираются с `base` равным своему подпути (`/lab/`, `/investor/`, …).
Поэтому при прямом запуске dev-сервером они открываются тоже по подпути:
`http://127.0.0.1:5275/lab/`, а не в корне — по корню страница ответит 200 и
останется пустой, потому что бандл придёт 404.

### Вход и роли

Регистрации в кабинетах нет и не будет: вход один на всех — `apps/auth`.
После входа приложение читает `/v1/auth/me` и отправляет человека в кабинет по
его роли; у кого ролей несколько — показывает выбор.

Самостоятельно выдаются **только две роли**: `founder` и `investor`
(`SelfServiceRoleSchema`). Роль администратора назначает платформа. Роли
`organizer`, `showrunner` и `expert` удалены в 2.1-W05: из старого токена они
отсекаются ядром и в базе прав не дают.

Версии обязательных документов приложение получает с сервера
(`GET /v1/auth/consents/templates`), а не зашивает: акцепт с недействующей
версией сервер отвергает.

### Порты задаются в одном месте

Числа портов живут в `.env` (`POSTGRES_PORT`, `REDIS_PORT`, `LAB_PORT`, …), а
`docker-compose.yml`, конфиги Vite и скрипты проверки читают их оттуда через
`scripts/lib/ports.mjs`. Значения в `.env.example` — исходные порты проекта;
заняты на машине или стенд переезжает на другой хост — правится один файл.

Порт БД и Redis записан в `.env` дважды: отдельной переменной и внутри
`DATABASE_URL_*` / `REDIS_URL`. Расхождение между ними не сообщает о себе, а
выглядит как «база не отвечает», поэтому его ловит гейт:

```bash
npm run gate:ports      # порты в .env согласованы между собой и с CORS
```

`npm run infra:up` передаёт корневой `.env` в compose явно (`--env-file`):
без этого compose читает только `infra/.env` и молча поднимает контейнеры на
fallback-значениях — с дефолтными паролями и портами.

## Комплект демонстрационных данных

Восстанавливаемое наполнение: шесть учётных записей (администратор,
основатели, инвесторы), пять проектов с материалами и файлами, сценарии
избранного и поддержки.
Исходные данные лежат файлами в `fixtures/demo/`, скрипт только переносит их в
систему — поэтому наполнение восстанавливается после любой переустановки.

```bash
npm run demo:load      # загрузить (идемпотентно: повтор не плодит дубликатов)
npm run demo:status    # что сейчас загружено
npm run demo:clean     # удалить ТОЛЬКО данные комплекта, включая файлы
```

Идентификаторы выводятся из фиксированного пространства имён (UUIDv5): отсюда
и воспроизводимость, и идемпотентность, и точность уборки — `clean` удаляет
строки по этим же идентификаторам, а не «всё похожее на тестовое». В
production скрипт не работает: он отказывается при `NODE_ENV=production` и не
вызывается ни из миграций, ни из сборки.

Подробности и порядок восстановления после чистой установки —
`fixtures/demo/README.md`. Проверки: `node scripts/smoke-demo.mjs` и
`node scripts/render-check-demo.mjs`.

## Локальный стенд

Полный контур на одной машине с учётными записями по ролям — чтобы пройти
платформу глазами каждого участника, а не одной учёткой со всеми правами.

```bash
# 1. Инфраструктура и данные
npm run infra:up && npm run db:migrate

# 2. Сервисы
npm run build -w apps/core && node scripts/dev-core.mjs --detached   # API на 4300
npm run dev -w apps/web-public   # витрина 5173
npm run dev -w apps/admin        # админка 5174
npm run dev -w apps/lab          # кабинет основателя 5175
npm run dev -w apps/investor     # кабинет инвестора 5176
npm run dev -w apps/console      # консоль API 5178 (служебная, в production не публикуется)

# 3. Демонстрационный комплект: учётные записи по ролям и проекты
node scripts/seed-demo.mjs load

# 4. Проверка, что стенд действительно работает
npm run stand:status
```

Учётные записи — демонстрационный комплект `demo-*` и обстановка приёмки
`priem-*`, логины и пароли в `.local/приёмка.md` (вне Git). В поле входа
достаточно короткого имени — домен подставляется.

Прогоны общими учётками основателя и инвестора не пользуются: заводят себе
своих через учёт запуска (`scripts/lib/probe-run.mjs`) и убирают за собой.
Общая только `demo-admin` — роль администратора регистрацией не получить.
Прежние учётки `stand-*` и скрипты вокруг них (`dev-stand`, `check-stand`,
`check-stand-logins`, `dev-reset-stand-passwords`, `seed-local-scenarios`)

### Консоль API (`apps/console`)

Служебный фронтенд для разработки и ручного тестирования: все операции `/v1`
одним списком, форма на каждую, сырой ответ рядом. В production не публикуется
и продуктовыми кабинетами не используется.

Зачем она нужна отдельно от кабинетов:

- покрывает то, чему в кабинетах места нет вовсе — `integration/token`,
  вебхуки, служебные учётные записи, ротация секретов;
- показывает фактический ответ каждой ручки: коды отказов, форму данных,
  сообщения валидации — по ней пишутся кабинеты;
- сквозной сценарий проходится в одном окне со сменой роли, а не прыжками
  между приложениями.

Идентификаторы созданных объектов запоминаются в **блокноте прогона** и сами
подставляются в поля с тем же именем: `projectId` из ответа «Создать проект»
попадёт в «Приложить материал» и «Опубликовать листинг».
Блокнот живёт в `sessionStorage` — перезагрузка страницы посреди сценария его
не теряет, но следующий прогон в новой вкладке начинается с чистого.

```bash
npm run dev -w apps/console           # http://127.0.0.1:5178/
node scripts/render-check-console.mjs # 13 проверок в реальном браузере
```

Что подготовлено демонстрационным комплектом: опубликованные проекты
основателей с материалами, избранное инвестора и обращения в поддержку.

Стенд разворачивается только вне production: скрипт отказывается работать при
`NODE_ENV=production`, а учётные записи удаляются перед выходом в прод
(см. `TODO.md`).

## Стенд на ВПС: панель и почта

Внутренний стенд развёрнут на `193.233.217.210` (`vgorkakh.ru`). С 2026-08-25
там же **HestiaCP 1.10.4** и собственный почтовый сервер.

| Что               | Адрес                       | Примечание                                       |
| ----------------- | --------------------------- | ------------------------------------------------ |
| Приложение        | `https://vgorkakh.ru`       | Caddy (80/443) → nginx в контейнере → ядро       |
| Панель управления | `https://panel.vgorkakh.ru` | Caddy проксирует на 8083; сам порт наружу закрыт |
| Почта             | `mail.vgorkakh.ru`          | приём на 25, отправка клиентом на 587, IMAP 993  |

Доступы лежат **только на сервере**: `/root/.hestia-admin` и
`/root/.mail-info-account`, права 600. В репозиторий они не попадают; локальная
копия `hestia.md` — под `.gitignore`.

Что важно знать, прежде чем трогать стенд:

- **Системный nginx там отключён намеренно** — 80/443 держит Caddy с
  приложением. Включённый nginx уронит сайт.
- **Firewall Hestia не ставится** — на сервере ufw, и в нём правило
  `4300/tcp` из `172.16.0.0/12`, без которого nginx-контейнер не достаёт ядро.
- **`header_up Host {host}` в блоке панели обязателен** — без него панель
  считает любой вход подделкой запроса (`Potential CSRF use detected`).

Проверка домена одной командой (публичный резолвер, а не системный):

```bash
node scripts/probe-mail-readiness.mjs --domain vgorkakh.ru --ip 193.233.217.210   --relay mail.vgorkakh.ru:25 --dkim-selector mail --direct
```

Полная процедура, DNS-записи и порядок восстановления — `docs/runbooks/hestiacp.md`.

### Секреты и транскрипты агентских сессий

Entire (`.entire/`) сохраняет транскрипт сессии в git-ссылку
`entire/checkpoints/v1` этого же репозитория. В транскрипт попадает вывод
команд, то есть рано или поздно — значения из `.env`. Так 2026-08-12 в git
попал ключевой материал KEK; объекты вычищены, редакция настроена и проверена
замером.

Защита состоит из трёх частей:

| Что                                  | Где                                                           | Закрывает                                                                                                                     |
| ------------------------------------ | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Правила на имена и формы             | `.entire/redactors/project-secrets.yaml` (коммитится)         | `ИМЯ=значение` для `KEK_*`, `*_PASSWORD`, `*_SECRET`, `*_TOKEN`, `*_SIGNING_KEY`, DSN; голый ключевой материал от 43 символов |
| Точные значения из `.env`            | `.entire/redactors/local/env-values.yaml` (**не коммитится**) | секрет, процитированный в свободном тексте — короткий и без имени рядом                                                       |
| Сверка объектов репозитория с `.env` | `npm run probe:secret-leak`                                   | доказательство отсутствия утечки                                                                                              |

```bash
npm run secrets:redactors    # пересобрать локальный пак — ОБЯЗАТЕЛЬНО после ротации секретов
npm run gate:redactors       # пак не отстал от .env (ожидание: 0)
npm run probe:secret-leak    # проверить, что значений из .env нет в объектах git
```

`gate:redactors` закрывает главный способ вернуть утечку: сменить секрет и
забыть пересобрать пак. Тогда пак редактирует прежние значения, а новые уходят
в транскрипт открытыми — и `probe:secret-leak` поймает это только после того,
как утечка уже произошла. В общий `npm run gate` не включён: требует `.env`,
которого в CI нет.

Замер на стенде 2026-08-12 (`docs/audits/2026-08-12-F25-checkpoint-secret-redaction.md`):
без паков в git-объекты утекли 2 значения из 8, с паками — 0 из 8.

**`gitleaks` этот класс утечки не ловит.** На том же прогоне, где значение
`POSTGRES_PASSWORD` фактически лежало в объектах, `gitleaks detect` вернул 0:
сигнатурный сканер ищет узнаваемые формы и связку «ключевое слово рядом со
значением», а секрет, упомянутый в тексте ответа агента, под них не подходит.
Поэтому `gate:secrets` доказательством отсутствия утечки ключевого материала
не является — им является `probe:secret-leak`.

После ротации секретов локальный пак обязан быть пересобран: иначе он
редактирует прежние значения, а новые уходят в транскрипт открытыми.

### Секреты стенда: у каждой службы — своё значение

До Ф26 одно значение обслуживало шесть служб (postgres, Redis, NATS, MinIO,
Keycloak, S3), а другое — три вебхука; в хранилище приложение ходило под
root-учёткой MinIO. Теперь у каждой службы и каждого вебхука своё случайное
значение, а в MinIO заведена отдельная учётка `unicorn_app` с политикой
только на свой бакет (создаёт `minio-init` идемпотентно). Гейт
`npm run gate:secret-reuse` следит, чтобы схема не вернулась: он проверяет
`.env` локально, а в CI — плейсхолдеры `.env.example` и fallback-значения
`docker-compose` (они тоже различимы по службам намеренно).

Переиспользованные значения на живом стенде разносятся одной командой:

```bash
npm run rotate:stand-secrets        # генерирует, пишет .env, ALTER ROLE, пересоздаёт контейнеры
node scripts/dev-seed-test-user.mjs # обновить пароль тестовой учётки
```

Новые значения не печатаются и не проходят через argv: в `.env` они попадают
записью файла, в postgres — через stdin, а пак редакции Entire пересобирается
до того, как значение может оказаться в каком-либо транскрипте.

### Ротация ключей шифрования (KEK)

Схема шифрования конвертная: значение шифруется одноразовым DEK, а KEK шифрует
только сам DEK. **Смена KEK не перешифровывает данные** — переобёртывается
только DEK. Данные теряет лишь слепая подстановка нового значения в `.env` без
переобёртки: старые `wrapped_dek` перестанут открываться.

```bash
npm run rotate:kek -- --domain passport_sensitive                     # осмотр, без записи
npm run rotate:kek -- --domain passport_sensitive --generate --test   # ротация с откатом
npm run rotate:kek -- --domain passport_sensitive --generate --apply --write-env
```

Карта «домен → таблица» внутри `rotate-kek.mjs` ведётся вручную, поэтому её
честность держит гейт `npm run gate:kek`: он сверяет тип `KekDomain`, фактические
вызовы `seal*` в core, карту ротации и колонки `*_wrapped_dek` в миграциях, а при
доступной БД проверяет, что зарезервированные схемой колонки (домены
`kyc_documents`, `nominal_account_evidence`, `billing_documents` — объявлены «на
вырост», кодом не используются) действительно пусты. Как только код начнёт писать
в такую колонку, гейт упадёт и потребует внести её в карту ротации.

`--write-env` — предпочтительный способ: скрипт сам подставляет новое значение
в `.env`. Иначе ключ придётся передать через argv (виден в списке процессов)
или прочитать с экрана — и он осядет в транскрипте сессии, то есть повторит
путь утечки. `.env` пишется до фиксации транзакции: при сбое откатываются оба,
иначе возможен разъезд «новые обёртки в базе, старый ключ в файле».

После ротации: `npm run secrets:redactors` → перезапустить ядро (пока оно
работает, в памяти остаётся прежний ключ).

Ротация 2026-08-12: `KEK_KYC_DOCUMENTS`, `KEK_NOMINAL_ACCOUNT_EVIDENCE`
(значения заменены, данными не пользуются) и `KEK_PASSPORT_SENSITIVE`
(переобёрнуто 1403 из 1403 строк, данные проверены расшифровкой).

Не все домены переобёртываются. `webhook_secrets` шифруется KEK напрямую
(нужна перешифровка строк), `search_index` служит ключом HMAC для blind index
(смена инвалидирует `email_hmac`/`phone_hmac`/`inn_hmac`, их надо пересчитать
из открытых значений). Скрипт для этих доменов отказывается и называет причину.

SAST (semgrep с правилами `.semgrep/guardian.yml` + OWASP) и секрет-скан
прогоняются в CI на каждый push и PR: [`.github/workflows/ci.yml`](./.github/workflows/ci.yml).
Там же с этой фазы прогоняются постоянные гейты прав — границы сервисных ролей
БД и права PUBLIC на функциях SECURITY DEFINER — и статическая часть сетевого
гейта. До этого они запускались руками, то есть не запускались на каждом
изменении: расширить права сервисной роли можно было незаметно для CI.
Локальный прогон semgrep на Windows требует `PYTHONUTF8=1` — иначе он падает на
кириллице внутри правил, и «нет вывода» легко принять за «нет находок».

Поверх классовых вёдер работает **потолок по адресу**. Ключ ведра для
аутентифицированных классов включает подсказку сессии из cookie, а она читается
до проверки подписи: подставив произвольный `sub`, клиент получал новое ведро на
каждый запрос. Полностью закрыть это ключом по адресу нельзя — денежный лимит
10/мин, общий на адрес, наказывал бы нескольких реальных пользователей за одним
NAT. Потолок считает все запросы с адреса в одно ведро с высоким порогом и
останавливает именно шторм: проверено прогоном — 600 запросов с разными
поддельными cookie проходили, 601-й получил 429.

Ограничение частоты считается в общем счётчике (Redis), а не в памяти
процесса. Разница не косметическая: при счётчиках в памяти два экземпляра ядра
считают свои запросы независимо, то есть фактически разрешённая частота
умножается на их число, а перезапуск обнуляет её целиком. Проверено прогоном на
двух экземплярах: лимит, исчерпанный на первом, действует на втором, и
перезапуск счётчик не обнуляет; без общего счётчика второй экземпляр отвечал
401 вместо 429 — то есть давал вторую порцию попыток. Недоступный счётчик
означает отказ, а не снятие защиты: `skipOnError: false` выбран сознательно —
уронить счётчик и получить неограниченный перебор паролей не должно быть
дешевле, чем уронить платформу.

С Ф40 класс маршрута определяется по **нормализованному** пути: раньше
классификатор сравнивал сырой `request.url`, а Fastify маршрутизирует по
декодированному — `POST /v1/%61uth/login` доходил до входа, но считался в
общем классе (120/мин вместо 30). Проверено фактом: при лимите 5 закодированный
путь получает 429 на шестой попытке, ровно как обычный. Поверх лимитов по
адресу работает счётчик неудачных входов **на аккаунт** (ключ — отпечаток
контакта, не сам контакт): распределённый перебор с ботнета не обходит его
сменой адреса, а после порога вход отклоняется до argon2 — измерено, ответ
ускоряется с ~50 мс до ~6 мс, то есть перебор перестаёт стоить нам
хеширования. Успешный вход счётчик обнуляет. Каждая неудача попадает в журнал
событием `identity.login.failed`. При `AUTH_MODE≠local` маршруты входа и
регистрации отвечают 404 сразу: раньше они отрабатывали целиком и падали 500
на последнем шаге, бесплатно нагружая процессор.

Токен разбирается строго. Идентификатор пользователя обязан быть UUID — он
уходит в `app.current_user_id`, на котором построены все политики RLS, и
произвольная строка превращалась там в ошибку приведения типа уже внутри
запроса. Роли из токена проходят через allowlist: неизвестное имя роли
отбрасывается, иначе значение claim'а становилось бы частью выражения любой
будущей политики `app.has_role(...)`. Признак второго фактора тоже allowlist —
`pwd` или `mfa`, прочее приравнивается к его отсутствию.

Поверхность для разведки сведена к минимуму. Заголовки `x-ratelimit-*` наружу
не выдаются: они сообщают точный порог и остаток по каждому классу операций, то
есть позволяют подобрать темп перебора, оставаясь под лимитом. На отказе
остаётся `retry-after` — сколько ждать, клиент узнаёт тогда, когда это ему
действительно нужно. Машиночитаемое описание API в production отдаётся только
по сессии и отвечает 404, а не 403: 403 подтвердил бы, что документ существует.
Вне production оно открыто — там оно нужно разработке и живым прогонам.

Журнал событий выгружается в холодное хранилище отдельной процедурой
(`scripts/archive-events.mjs`), а не задачей ядра: выгрузка требует доступа ко
всему журналу, и такого права у приложения нет. Процедура только **копирует** —
удалять события она не умеет вовсе, потому что срок хранения журнала оператора
определяется законом, а не удобством эксплуатации. Перед выгрузкой сверяется
hash-chain **диапазонным verifier'ом** (M053): проверяется ровно диапазон
текущей выгрузки с верхней границей, а связь первого нового события с
последним заархивированным сверяется по row_hash предшественника — разрыв на
стыке архивов больше не проходит незамеченным. После — объект читается
обратно и его отпечаток сверяется с записанным в реестр
`audit.event_archives`. Если объект прошлой выгрузки исчез
из хранилища, следующий прогон восстановит его из журнала и потребует
совпадения отпечатка байт в байт: расхождение означало бы, что append-only
журнал изменился, и прогон падает вместо перезаписи.

С Ф31 выгрузка работает с минимальными правами (остаток SEC-10): в БД — групповая роль
`app_archive` (M052) и логин `app_archive_user` из bootstrap-roles (журнал
только чтение, чужих схем не видит), в
хранилище — учётка `unicorn_archive` (пишет и читает только `archive/*`,
права удаления НЕТ — политика `unicorn-archive-append`, создаёт `minio-init`).
С Ф34 у роли нет и прямого INSERT в реестр: единственный путь записи —
`audit.append_event_archive()` (M053), которая держит непрерывность диапазонов
(`period_start` = текущий `max(period_end)`), запрещает границу в будущем и
сверяет заявленные count/first/last с фактическим журналом — украденные креды
архива больше не позволяют отравить реестр «будущей» записью, из-за которой
последующие выгрузки молча пропускали бы события. События собираются во
временный файл партиями — в памяти живёт партия, а не весь диапазон. Границы
роли держит гейт `check-service-roles` (42 проверки).

С Ф35 загрузка материалов держится на общей матрице «тип → MIME → размер»
(`MATERIAL_UPLOAD_RULES` в контрактах): API отвергает `video/mp4`, заявленный
как презентация, ещё на разборе DTO, а подсказка в кабинете основателя читает
лимит из той же константы и не может разойтись с сервером. Подтверждение
загрузки читает объект из хранилища потоком: `content_hash` — настоящий
`sha256:<hex>` по фактическим байтам (ETag хранилища криптографическим
отпечатком не является), а первые байты сверяются с сигнатурой формата —
HTML, заявленный как PDF, получает 409 и подтверждённым материалом не
становится (проверено зондом: 17 проверок, включая подделку формата).

Материалы проекта убираются за собой. Билет на загрузку выдаётся вместе со
строкой материала, но загрузка может не состояться: с M037 такой материал
наружу не выдаётся, а с M039 — ещё и не остаётся навсегда. Плановое
обслуживание убирает брошенные билеты старше суток вместе с объектом в
хранилище; порядок — сначала объект, потом строка, потому что при обратном
падение между шагами оставляет объект, который уже нечем найти. Уборку
выполняет отдельная роль БД `app_maintenance`, которая не видит ни проектов, ни
пользователей, ни подтверждённых материалов: это ограничено политиками, а не
аккуратностью кода.

Выход и отзыв сессий устроены двумя разными механизмами, потому что отвечают
на разные вопросы. **Рубеж сессий** (`identity.users.sessions_valid_from`)
обесценивает ВСЕ токены пользователя разом — им закрываются изменение прав и
компрометация аккаунта: снятая роль перестаёт действовать сразу, а не по
истечении токена. **Реестр отозванных токенов** (`identity.revoked_tokens`)
закрывает одну конкретную сессию по идентификатору `jti`: выход на одном
устройстве не роняет остальные, а скопированное значение cookie перестаёт
работать в момент выхода, а не через час. Удаления cookie для этого
недостаточно — оно действует только на клиента. Проверка идёт снимком реестра с
окном в пять секунд: на своём экземпляре отзыв мгновенный, на остальных — не
позже окна; величина названа числом, а не спрятана в «примерно сразу». Записи
об истёкших токенах убирает плановое обслуживание, и права на удаление есть
только у сервисной роли уборки.

Публикация листинга требует действующего KYC владельца; режим видимости
проекта решает, кому листинг виден. Тарифа и подписки для публикации нет с
2.1-W05.

## AI-контур

> **Требует новой проработки.** AI-шлюз, скоринг и паспорт удалены в 2.1-W05
> (M150). Ниже — прежняя архитектура как основание, а не работающая система.

Оценку считает **не языковая модель**, а воспроизводимая эвристика
`v0.1-heuristic` внутри российского контура. Это baseline: будущая LLM обязана
показать улучшение относительно него, иначе подключать её незачем. Ответ
API честно помечен `isLlm: false` — выдавать одно за другое нельзя.

Что удерживает контур:

- **юрисдикционный роутинг с hard fail**: класс данных из `restricted_classes`
  провайдеру вне `allowed_jurisdictions` не отдаётся никогда — 403 и запись в
  журнал, а не выбор другого провайдера. По решению владельца от 2026-08-26
  зарубежные модели (OpenAI, Claude, Kimi, Qwen, DeepSeek) в работе не ограничены:
  `allowed_jurisdictions` = RU, US, CN (ADR-008 §7); механизм сохранён;
- **недоверенный текст заявки — только данные**: он не попадает в инструкции и
  не может изменить ни провайдера, ни класс данных; попытка фиксируется;
- **у шлюза нет доступа ни к БД, ни к хранилищу, ни к сессиям** — он получает
  задачу и возвращает результат;
- **прогон всегда оставляет след** в `audit.agent_runs`: и успешный, и упавший —
  публикация обёрнута целиком, ошибка на любом шаге закрывает прогон
  терминальным `failed`, а не оставляет его «выполняющимся» навсегда;
- **вход зафиксирован снапшотом**: текст заявки и список подтверждённых
  материалов сохраняются рядом с прогоном вместе с отпечатком sha256; если
  проект изменился, пока шлюз считал, результат отбрасывается с 409 — паспорт
  не публикуется по устаревшей заявке;
- **учитываются только подтверждённые материалы** — незавершённый билет
  загрузки не считается «материал есть»;
- **ответ шлюза читается с потоковым пределом в байтах** и разбирается схемой
  не слабее публичного контракта: полный набор осей без дублей, непустые
  источники у каждой оценки, интервал уверенности накрывает значение;
- **история паспортов не переписывается** — новая версия помечает предыдущую
  устаревшей, поэтому оценки моделей есть с чем сравнивать.

Содержимое дек и внешних ссылок не разбирается: парсера нет, а ходить по
пользовательской ссылке сервером — это SSRF. В анализ попадают текст заявки и
факт наличия материала. Подробности — [ADR-007](./docs/architecture/ADR-007-ai-contour.md).

## Регуляторная рамка

> Инвестиционный процесс удалён в 2.1-W05; рамка ниже относится к будущей
> проработке сделок, а не к текущей платформе.

Инвестиционный контур включается **только после** включения российского
юридического лица в реестр ОИП Банка России и согласования Правил
инвестиционной платформы (гейт A, `docs/architecture/Architect_Launch.md` §9). До этого момента
соответствующая функциональность закрыта feature flag'ами. Способы
инвестирования (`instrument_type`) — серверный allowlist, а не свободный
параметр клиента.

Контур **реализован и проверен живым прогоном**, но флаг `investments.enabled`
выключен: маршруты отвечают `503 feature_disabled`. Это состояние продукта, а не
незавершённая работа. Каждый способ инвестирования включается отдельным флагом
(`investments.instrument.*`), и все они тоже выключены.

Что удерживает контур помимо флага:

- первый транш подтверждается только банковским событием номинального счёта —
  клиентским запросом это невозможно ни при какой роли;
- начисление вознаграждения создаёт команда БД `billing.confirm_first_tranche` в
  одной транзакции с переходом договора в силу, `UNIQUE(agreement_id)` исключает
  повторное начисление, повторная доставка того же события возвращает прежний
  результат;
- принятие предложения и подписание договора требуют подтверждения вторым
  фактором (`step_up_required`);
- предложение размещает только владелец проекта и только от юрлица с
  действующим KYB; публикует его комплаенс, а не ЛПИ;
- ключ идемпотентности принадлежит инвестору: чужой ключ не блокирует сделку и
  не работает как оракул существования договора.

## Лицензия и доступ

Приватный репозиторий. Персональные данные обрабатываются в российском контуре
(152-ФЗ): БД, S3 и AI-контур размещаются в РФ, юрисдикционный роутинг LLM
проверяется политикой с hard fail при нарушении. Передача текстов заявок
зарубежным LLM-провайдерам открыта решением владельца (ADR-008 §7).
